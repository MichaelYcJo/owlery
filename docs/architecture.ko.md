# 구조: 앱, 데몬, 에이전트 어댑터, AgenticSeal 프로세스

*[English](./architecture.md) · 한국어*

## 결론

- **바탕은 작업함, AgenticSeal 프로세스, 인장의 뒷면이고, 터미널은 그 위에서 불러 씁니다.** 데몬은 사용자의 Claude Code를 헤드리스 모드(`claude -p`, 입출력 `stream-json`)로 띄워 AgenticSeal 프로세스의 역할 세션을 뒤에서 돌리고, 그 결과를 작업함과 인장의 뒷면에 보여 줍니다. 첫 버전에서 사람이 일을 시키는 세션은 에이전트의 CLI를 터미널에 그대로 띄운 것이라, 어느 CLI든 붙습니다. 그 상태는 훅과 git으로 읽습니다. 데스크톱에는 채팅 화면이 없습니다. 같은 터미널 세션을 채팅 모양으로 보여 주는 것은 휴대폰이고, CLI의 훅과 세션 기록을 읽습니다([휴대폰: 터미널 세션을 채팅 모양으로](#휴대폰-터미널-세션을-채팅-모양으로)).
- **Owlery는 로그인을 제공하지 않습니다.** 인증은 사용자의 CLI가 갖습니다. Claude Code에서는 사용자가 `/login`으로 구독 로그인이나 API 키를 고르고, Owlery는 그 CLI를 띄울 뿐입니다([Claude 어댑터의 인증](#claude-어댑터의-인증)).
- **Owlery는 자체 데스크톱 앱입니다.** 다른 앱 위의 플러그인으로 두지 않습니다. 사용자의 Claude Code를 데몬이 직접 띄우고 역할 세션은 사용자 환경에서 떼어 띄우므로, 세션과 터미널을 다른 앱에 맡길 까닭이 없습니다. 작업함, AgenticSeal 프로세스, 장부가 한 제품 안에서 같은 기록을 읽습니다.
- **화면은 Electron으로 만들고, 일은 데몬이 합니다.** 화면은 데몬에 WebSocket으로만 붙는 얇은 껍데기입니다. 나중에 다른 화면 프레임워크로 바꿀 길을 남겨 두려는 것입니다.
- **AgenticSeal 프로세스의 순서는 데몬의 코드가 실행하고, 판단만 orchestrator 에이전트에게 남깁니다.**
- **AgenticSeal은 참고하는 원본이고, Owlery는 그것을 넓힌 제품입니다.** AgenticSeal에 기대어 돌지 않습니다. 원칙, 불변식, 역할, 기록 형식을 AgenticSeal에서 가져와 Owlery의 것으로 고쳐 갖고, 역할의 에이전트 정의와 스킬은 Owlery가 앱에 함께 넣어 역할 세션의 기본값으로 씁니다([AgenticSeal에서 가져오는 것](#agenticseal에서-가져오는-것)).
- **가볍게 두는 것이 목표이고, 그것은 프레임워크가 아니라 앱의 범위와 구조에서 나옵니다.** 가벼움은 상대적인 것입니다. 채팅 화면, 터미널, IDE 수준의 편집기, 브라우저, 팀 관리, 클라우드를 함께 얹는 제품보다 Owlery가 얹는 것이 적다는 뜻입니다. 창은 하나만 쓰고, 터미널은 보이는 것만 그리고, 일하지 않는 Claude 프로세스는 끝냅니다.

## 전체 구성

```
┌──────────────────────────┐
│ 화면 (Electron 렌더러)    │  작업함, 인장의 뒷면, diff, 사용자 세션의 터미널 칸
│ 휴대폰 앱 (v0.2)          │  작업함, 질문 묶음, 인장, 터미널 세션마다 채팅 모양
└────────────┬─────────────┘
             │ WebSocket (둘이 같은 프로토콜)
┌────────────┴─────────────┐
│ 데몬 (앱보다 오래 삶)     │  순서 실행, 터미널 출력 보관, 비용 기록
│  ├─ 사용자 세션 (node-pty) │  터미널에 띄운 에이전트 CLI(무엇이든). 그 훅과 세션 기록으로 읽음
│  ├─ AgenticSeal 프로세스 │  순서, 기록, 불변식은 데몬의 코드
│  │   └─ 역할 실행본       │  첫 버전: 사용자의 Claude Code(claude -p) + 앱에 든 Owlery 역할 묶음
│  └─ git, gh              │  브랜치를 지켜보다 인장 뒤에 들어온 커밋을 잡음
└──────────────────────────┘
```

- **데몬은 앱이 재시작하거나 업데이트되는 동안에도 살아 있습니다.** 리뷰 회차가 길어져도 작업이 끊기지 않게 하려는 것입니다.
- **에이전트 상태는 이벤트로 판정하고, 터미널 화면 출력에서 추측하지 않습니다.** 역할 세션은 구조화된 출력의 이벤트로 알려 줍니다. 터미널로 연 사용자 세션은 Claude Code처럼 그 CLI의 훅으로 알려 줍니다. 훅을 확인하지 않은 CLI라면 작업함에는 브랜치가 바뀌었는지만 보여 줍니다. 사람에게 결정을 띄울 때 잘못 띄우는 일이 없어야 하기 때문입니다.
- **권한 요청은 정식 이벤트로 다룹니다.** framer, crafter, proofer, sealer는 데몬이 직접 띄우므로, 그중 하나가 끝나거나 권한을 요청하면 데몬이 먼저 알고 orchestrator 에이전트나 사람에게 넘깁니다. 에이전트가 자기 아래에 자식 에이전트를 띄우면 그 부모와 자식 관계도 함께 다룹니다. 사용자 세션의 권한 요청은 그 터미널에서 답하거나, CLI의 권한 요청 훅을 거쳐 휴대폰에서 답합니다([휴대폰: 터미널 세션을 채팅 모양으로](#휴대폰-터미널-세션을-채팅-모양으로)).
- **훅으로 상태를 알리는 CLI가 창을 연 지 10초가 지나도록 이벤트를 하나도 보내지 않으면, 사람을 기다리는 것으로 보여 줍니다.** CLI는 세션을 시작하기 전에 먼저 물어볼 것을 묻고, 묻는 동안에는 이벤트를 보내지 않습니다. 2026-11-19에 Claude Code 2.1.327을 띄워 보니, 폴더를 신뢰하는지 묻는 동안에는 훅 이벤트를 하나도 보내지 않았습니다. 이 질문은 사람이 Claude Code에서 신뢰한 적 없는 저장소의 첫 워크트리에서 나옵니다. 묻지 않는 곳에서는 2초 안에 세션 시작을 알렸습니다. 데몬은 이벤트가 오지 않았다는 사실로 판정하고 창에 찍히는 글자로는 판정하지 않으며, 세션의 첫 이벤트가 오면 그 상태로 바꿉니다.
check: apps/desktop/test/daemon.test.ts
- **데몬은 에이전트가 일하는 동안 Mac이 쉬다가 잠들지 않게 합니다.** Mac이 잠들면 에이전트가 모두 멈추고, 기다리기 시작한 에이전트의 알림은 사람이 Mac을 깨울 때까지 오지 않습니다. 데몬은 세션마다 상태를 알고 앱이 닫혀 있는 동안에도 살아 있으므로, 잠들지 않게 하는 일은 데몬이 맡습니다. 데몬은 자식 프로세스 하나로 이 일을 합니다. 자기 프로세스 ID를 넘긴 `caffeinate -i -w`입니다. 그래서 데몬이 어떻게 끝나든 데몬이 끝나면 Mac은 다시 잠들 수 있습니다. 화면은 꺼질 수 있고, 덮개를 닫으면 Mac은 전과 같이 잠듭니다. 사람은 "While an agent works", "Always", "Never" 가운데 하나를 고르고, 처음 값은 "While an agent works"입니다. "While an agent works"는 프로세스가 살아 있는 칸이나 헤드리스 세션 가운데 하나라도 일하는 동안 유지됩니다. "Always"는 데몬이 도는 동안 유지되고, 할 일이 없어진 데몬이 스스로 끝나는 것을 막지 않습니다. 이 선택은 데몬의 상태입니다. 데몬의 실행 디렉터리에 저장되고 모든 클라이언트에 전달되므로, 창과 나중에 붙을 휴대폰이 같은 값을 보여 줍니다.
check: apps/desktop/test/keep-awake.test.ts apps/desktop/test/daemon.test.ts
- **사람은 앱 메뉴에서 데몬을 멈추고, 앱은 자기 실행 폴더의 데몬만 멈춥니다.** 보통의 종료는 데몬과 세션을 그대로 둡니다. "Restart Daemon…"과 "Quit Owlery Completely…"는 실행 중인 세션을 먼저 이름으로 보여 주고, 사람이 확인하면 앱이 데몬을 끝냅니다. 앱은 실행 폴더의 `daemon.json`이 가리키는 프로세스에 신호를 보내며, 그 파일의 주소에서 그 파일의 토큰으로 데몬이 응답한 뒤에만 보냅니다. 앞의 항목은 이어서 지금 실행 중인 빌드의 데몬을 띄우고, 뒤의 항목은 데몬을 띄우지 않고 앱을 끝냅니다. 신호를 쓰는 까닭은 어느 빌드의 데몬이든 신호를 받으면 끝나지만, 프로토콜에 새로 넣은 메시지는 이전 빌드의 데몬이 알지 못하기 때문입니다. 데몬은 자기가 실행하는 스크립트의 SHA-256 값을 `daemon.json`에 적습니다. 그 값이 앱이 띄울 스크립트의 값과 다르면 상태 줄이 데몬이 다른 빌드의 것이라고 알리고 "Restart Daemon…"을 가리킵니다.
check: apps/desktop/test/daemon-client.test.ts apps/desktop/test/daemon-restart.test.ts

## 에이전트 어댑터

데몬이 에이전트를 구조화된 방식으로 다룰 때는 회사마다의 연결부(어댑터) 하나만 거칩니다. 첫 버전의 실제 어댑터는 Claude 어댑터 하나이고, AgenticSeal 프로세스의 역할 세션을 돌립니다. 터미널로 연 사용자 세션에는 어댑터가 필요 없습니다. 데몬은 그 CLI를 터미널에 띄우기만 하기 때문입니다. 어댑터는 역할 세션에만 있습니다. 다른 회사의 모델이 역할을 맡을 때(v0.3) Codex app-server와 ACP가 같은 자리에 붙습니다.

| 방향 | 어댑터가 데몬에 맞춰 주는 것 |
|---|---|
| 데몬에서 에이전트로 | 문장 보내기, 중간에 끼어들기와 멈추기, 슬래시 명령, 권한 요청에 대한 답 |
| 에이전트에서 데몬으로 | 메시지, 도구 호출, 고친 파일, 권한 요청, 상태(일하는 중, 입력 대기, 끝남), 모델별 토큰과 비용, 사용 한도 |
| 어댑터가 밝히는 것 | 지원하는 기능 목록. 예: 슬래시 명령을 받는가, `!` 출력을 에이전트에게 보내는 것이 그 CLI의 습관인가 |

### Claude 어댑터의 인증

Claude 어댑터는 사용자가 설치하고 로그인한 `claude` CLI를 데몬이 띄우는 길 하나로만 붙습니다. Agent SDK는 쓰지 않습니다. Agent SDK 문서는 미리 승인받지 않은 제3자 제품이 claude.ai 로그인이나 구독의 사용 한도를 제공하는 것을 허용하지 않기 때문입니다(Agent SDK overview, 2026-11-18에 읽음). 사용자의 CLI를 띄우면 인증은 처음부터 사용자의 것입니다.

| 무엇 | 어떻게 |
|---|---|
| 인증 | 사용자가 Claude Code에서 `/login`으로 고릅니다. 구독 로그인이면 사용자의 구독 한도를, API 키면 사용자의 API 과금을 씁니다. Owlery는 로그인 화면도, 키 저장도 갖지 않습니다 |
| 역할 세션 | 헤드리스 모드(`claude -p --input-format stream-json --output-format stream-json`)로 역할 세션을 띄워, 메시지, 도구 호출, 권한 요청, 결과를 이벤트로 받습니다 |
| 원래 화면 | 사용자가 들여다보고 싶으면 역할 세션을 터미널로 엽니다(`claude --resume <세션 ID>`). 이때 상태는 훅으로 판정합니다 |
| 역할 묶음 | 앱에 든 Owlery의 에이전트 정의와 스킬을 데몬이 역할 세션에만 싣습니다(`--plugin-dir`). 사용자의 Claude Code에 설치하지 않으므로, 앱의 버전과 묶음의 버전이 언제나 같습니다. 아래 「세션마다 싣는 것」 |

Anthropic이 공개한 문서 가운데 이 일과 관계있는 것은 둘이고, 어느 쪽도 다른 제품이 사용자가 로그인해 둔 CLI를 헤드리스 모드로 띄우는 일을 다루지 않습니다. 지원 문서 "Use the Claude Agent SDK with your Claude plan"은 `claude -p`와 제3자 앱의 사용량이 여전히 사용자의 구독 한도에서 나간다고 적습니다. Agent SDK overview에는 이 절 첫머리에 적은 claude.ai 로그인에 관한 규칙이 있습니다. 둘 다 2026-11-18에 읽었습니다. Owlery는 Anthropic에 문의를 보내지 않습니다. 헤드리스 역할 세션은 이 두 문서를 놓고 판단하고, 둘 가운데 하나가 바뀌면 다시 판단합니다. 역할 세션은 어댑터로만 띄우므로, 훅으로 읽는 대화형 터미널로 옮기는 비용은 작게 유지됩니다.

### 사용량 읽기

앱은 사용자의 구독 한도를 얼마나 썼는지와 언제 다시 채워지는지를 보여 주고, 데몬은 AgenticSeal 프로세스를 시작하기 전에 같은 값을 봅니다. 한 번의 실행이 작업 하나에 단계를 네다섯 번 띄울 수 있으므로, 5시간 한도가 거의 찬 상태에서 시작하면 중간에 멈춥니다. 그럴 때 데몬은 실행을 미루거나 사람에게 알립니다.

Claude Code가 이 값을 직접 넘겨주는 길은 둘입니다. 둘 다 Claude Code 2.1.327 실행 파일에서 찾았고(2026-11-18), 아직 실제로 돌려 보지는 않았습니다.

| 세션 | 값이 오는 곳 | 들어오는 것 |
|---|---|---|
| 터미널로 연 사용자 세션 | Claude Code가 상태줄 명령에 넘기는 JSON의 `rate_limits` | `five_hour`, `seven_day` 각각의 `used_percentage`. 구독자에게만, 첫 API 응답 뒤에 들어옵니다 |
| 역할 세션 | 헤드리스 출력 스트림의 `rate_limit_event` | 이벤트마다의 한도 정보. 필드는 아직 확인하지 않았습니다 |

- **사용자의 상태줄은 그대로 둡니다.** 데몬은 작은 상태줄 명령을 끼워 넣습니다. 그 명령은 받은 JSON을 데몬에 넘기고, 사용자가 원래 쓰던 상태줄 명령을 불러 그 출력을 그대로 보여 줍니다.
- **값은 마지막 호출 기준입니다.** 아무것도 돌지 않을 때는 마지막으로 받은 값과 다시 채워지는 시각을 보여 줍니다.

다른 길도 있고, 구현할 때 이 경우를 함께 고려해야 합니다. 앱이 Claude Code의 자격 증명 파일이나 키체인에서 사용자의 로그인 토큰을 읽고, 그 토큰으로 공개되지 않은 사용량 주소를 부르는 길입니다. 언제든 지금 값을 받을 수 있지만, 첫 버전에서는 쓰지 않습니다. 까닭은 셋입니다.

- 공개되지 않은 주소라 응답 모양이 예고 없이 바뀔 수 있습니다.
- 요청이 Claude Code인 것처럼 보여야 합니다. 막히면 피해는 사용자의 계정이 받습니다.
- 인증은 사용자의 CLI가 갖는다는 이 문서의 규칙과 어긋납니다.

나중에 더할지는 「결정을 남겨 둔 것」에 있습니다. Codex가 비슷한 값을 넘겨주는지는 확인하지 않았습니다.

### 세션마다 싣는 것

| 세션 | Owlery 역할 묶음 | 규칙이 들어오는 길 |
|---|---|---|
| 데몬이 띄우는 역할 세션(framer, crafter, proofer, sealer) | `--plugin-dir`로 앱 안의 묶음을 싣고, 역할은 `--agent`로 고릅니다 | 데몬이 그 역할과 단계의 규칙(core, 에이전트 계약, 역할의 규칙)을 시스템 프롬프트에 붙여 넣습니다(`--append-system-prompt-file`). 사람이 보는 세션을 위한 훅(세션 시작에 규칙 출력, 턴 끝에 인장 그리기)은 묶음에 넣지 않습니다. 인장 그리기는 데몬이 기록을 읽어 화면에 그리는 일로 합니다 |
| 터미널로 연 사용자의 작업 세션 | 싣지 않습니다. 사용자의 CLI(Claude Code, Codex, 그 밖의 것) 그대로입니다 | 해당 없음. AgenticSeal 프로세스는 사용자 세션과 따로 돕니다(아래 규칙 4) |

규칙을 에이전트 정의의 `skills:` 목록에 맡기지 않습니다. `--agent`로 띄운 세션에서는 그 목록의 스킬이 미리 실리지 않고, 모델이 Skill 도구로 스스로 부를 때만 읽힙니다(2026-11-17 시험, 사용자 환경을 뗀 세션 3번 모두 규칙을 읽지 않음). 시스템 프롬프트에 붙인 규칙은 2번 모두 지켜졌습니다.

#### 역할 세션은 사용자 환경에서 떼어 띄웁니다

역할 세션은 사용자의 Claude Code로 돌므로, 그대로 띄우면 사용자가 설치한 플러그인, 훅, 스킬, MCP 서버, 전역 `CLAUDE.md`, 자동 메모리, 권한 모드가 함께 들어옵니다. 판정이 사용자 환경에 따라 달라지면 안 되므로, 데몬은 역할 세션을 아래와 같이 띄웁니다. 모두 2026-11-17 Claude Code 2.1.326에서 구독 로그인(`claude.ai`)으로 시험했습니다.

| 들어오는 것 | 떼는 방법 | 시험 결과 |
|---|---|---|
| 사용자 설정과 저장소 설정의 훅, 켜 둔 플러그인, 권한 규칙, 사용자 스킬, MCP 서버, 전역 `CLAUDE.md` | `--setting-sources ""` | 사용자 훅 9건이 0건이 되고, 켜 둔 플러그인과 사용자 스킬, MCP 서버가 빠지고, 전역 `CLAUDE.md`의 규칙(한국어로 답하기)이 사라짐 |
| 그 밖의 훅 | `--settings '{"disableAllHooks": true}'` | 훅 0건 |
| 그 밖의 MCP 설정 | `--strict-mcp-config` | MCP 서버 0개 |
| 자동 메모리 | `--settings '{"autoMemoryEnabled": false}'` | 끄지 않으면 저장소에 맞는 메모리 색인이 들어옴. 끄면 메모리 경로가 없음 |
| 환경 변수로 들어오는 플러그인과 설정(예: `CLAUDE_CODE_PLUGIN_DIRS`) | 데몬이 환경 변수를 비우고 필요한 것만 넘김(`HOME`, `USER`, `PATH`, `LANG`, `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD`) | 환경 변수로 들어오던 플러그인이 빠지고, 구독 로그인은 그대로 됨 |
| 권한 모드 | `--permission-mode`를 데몬이 정함 | 사용자 설정을 떼면 `default`가 됨. 역할마다 데몬이 정해 넘겨야 함 |

- **`--bare`는 쓰지 않습니다.** `--bare`에서는 Claude Code가 OAuth와 키체인을 읽지 않아 구독 로그인으로 돌 수 없습니다(`claude --help`).
- **떼지 못하는 것은 Claude Code에 내장된 플러그인(`cc-plugin-*`, `builtin`)뿐입니다.** 사용자가 고를 수 없는 Claude Code의 일부이므로 받아들입니다.
- **저장소의 `CLAUDE.md`는 읽고, 저장소의 설정은 읽지 않습니다.** `CLAUDE.md`는 그 저장소의 규칙이라 판정에 필요합니다. 그래서 설정 출처는 비운 채 저장소를 `--add-dir`로 넘기고, 환경 변수 `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1`로 그 디렉터리의 `CLAUDE.md`를 읽게 합니다(2026-11-17 시험: `CLAUDE.md`의 규칙이 지켜지고, 저장소 설정이 켠 플러그인은 실리지 않음). `--setting-sources project`로 읽으면 저장소의 `.claude/settings.json`도 함께 들어와, 그 설정이 켠 플러그인과 권한 규칙까지 역할 세션에 실립니다(같은 날 시험: 저장소 설정이 켠 AgenticSeal 플러그인이 실림).

### 이식할 수 있게 지키는 규칙

이식할 수 있는 상태를 지키는 규칙은 넷입니다.

1. **화면은 어느 회사의 에이전트인지 모릅니다.** 데몬과 화면 사이의 프로토콜에는 어댑터가 맞춰 준 형태만 지나가고, 회사마다의 필드는 지나가지 않습니다. 모바일 화면도 같은 프로토콜을 씁니다.
2. **회사마다 다른 기능은 기능 목록으로 다룹니다.** 화면은 기능 목록을 보고 단추를 보이거나 숨깁니다. 이름으로 회사를 가려 분기하지 않습니다.
3. **처음부터 어댑터를 둘 둡니다.** 실제 Claude 어댑터와, 테스트에서 쓰는 가짜 어댑터입니다. 어댑터가 하나뿐이면 연결부의 모양이 Claude에 맞춰 굳어도 알아채기 어렵습니다.
4. **AgenticSeal 프로세스는 사용자 세션과 따로 돕니다.** 사용자 세션이 어느 회사의 에이전트든 인장은 같은 AgenticSeal 프로세스가 찍습니다. 체인의 역할을 맡는 에이전트도 같은 어댑터를 거쳐 띄우므로, 판정자를 다른 모델로 바꿀 때 체인의 코드는 바뀌지 않습니다.

## AgenticSeal에서 가져오는 것

AgenticSeal은 Owlery가 참고하는 원본이고, Owlery는 그것을 넓힌 제품입니다. Owlery는 AgenticSeal 플러그인을 싣거나 그 버전에 기대어 돌지 않습니다. AgenticSeal의 각 부분을 Owlery의 것으로 가져와 제품에 맞는 자리에 둡니다. AgenticSeal은 MIT 라이선스이므로, 가져온 파일에는 그 저작권 고지를 남깁니다.

**Owlery가 AgenticSeal에서 가져온 것은 가져온 날부터 Owlery의 것이고, Owlery는 AgenticSeal의 릴리스를 따라가지 않습니다.** AgenticSeal은 Owlery가 출발한 자리입니다. Owlery는 역할 묶음과 PR 검사의 스크립트를 비롯한 사본을 자기 데몬에 맞게 고치고, 어떤 테스트도 사본을 AgenticSeal의 바이트에 묶지 않습니다. AgenticSeal에서 뒤에 나온 생각은 다른 생각과 똑같이 Owlery의 이슈로 들어옵니다. 가져온 파일을 둔 폴더마다 AgenticSeal의 라이선스 전문과, 그 파일이 어디서 출발했는지 밝히는 고지를 둡니다.
check: apps/desktop/test/role-bundle.test.ts apps/desktop/test/pr-check.test.ts

| AgenticSeal에 있는 것 | Owlery에서 맡는 자리 |
|---|---|
| 가치와 원칙: 판단이 필요한 곳에만 판단을 쓰고 나머지는 스크립트가 답한다, 각 에이전트는 자기 대상을 독립적으로 판정한다, 사람에게 물을 것은 첫 편집 전에 한 번에 묻는다 | 제품의 원칙으로 그대로 가져옵니다 |
| 네 불변식: 빌드 없는 리뷰 없음, 어떤 회차도 읽지 않은 수정 없음, HEAD에서 전체 검사 없이 인장 없음, 인장 없이 PR 없음 | 제품이 지킵니다. 데몬의 코드와 PR의 검사가 맡고, 어느 에이전트가 만든 작업에도 똑같이 적용합니다 |
| 역할: framer, crafter, proofer, sealer | 역할의 정의(무엇을 읽고, 무엇을 판정하고, 무엇을 남기는가)는 제품이 갖습니다. 실행본은 런타임마다 둡니다. 첫 버전의 Claude 런타임은 AgenticSeal의 에이전트 정의와 스킬에서 시작한 Owlery 역할 묶음을 앱에 함께 넣어 기본값으로 쓰고, 다른 런타임에는 같은 역할 정의를 그 런타임의 형식으로 옮깁니다 |
| 기록 형식: 설계 파일, 회차 기록, `guarantee.md`의 `seal` 블록, `routing.md` | 제품의 기록 형식입니다. 첫 버전은 AgenticSeal 형식과 같고, 여러 에이전트를 받으면서 필요한 칸(만든 쪽, 판정한 모델과 규칙 버전)을 더합니다 |
| 순서를 적은 문서(orchestration) | 데몬의 코드가 실행합니다. 판단만 orchestrator에게 남깁니다 |
| `seal` 명령의 스크립트: `chain_check`, `seal pr-body`, `seal pr-wait`, `seal stamp`, `seal cost` | 같은 일을 Owlery의 데몬과 PR의 검사가 합니다. PR의 검사는 AgenticSeal의 코드를 가져오고, 거기서부터 Owlery가 고칩니다. `chain_check`가 싣는 스크립트는 AgenticSeal 0.38.4에서 출발해 `pr-check/`에 있고, 연결한 저장소의 워크플로가 Owlery의 저장소에서 그것을 받아 옵니다. 지금 다시 짠 검사는 데몬이 기록을 하나도 쓰기 전에 사슬의 모든 기록을 판정해야 합니다. 데몬은 Python을 실행하지 않습니다. 사람의 Mac에 Python이 있다고 기대할 수 없기 때문입니다. 데몬은 자기 코드로 기록을 읽고 쓰며, 나머지 명령이 하던 일은 그 일을 만드는 이슈가 방법을 정합니다 |
| Claude Code에만 있는 장치: 세션 시작 훅이 core를 출력하는 일, Stop 훅이 인장을 그리는 일, 권한과 worktree 훅 | 가져오지 않습니다. 앱과 데몬이 같은 일을 직접 합니다([세션마다 싣는 것](#세션마다-싣는-것)) |
| 질문 묶음(`frame/questions.md`) | 앱의 질문 화면이 됩니다 |

### 플러그인이 아니라서 달라지는 것

AgenticSeal은 Claude Code 플러그인이라 쓸 수 있는 수단이 정해져 있습니다. 에이전트가 읽는 마크다운, 훅 두 개(세션 시작에 core를 출력하는 것, 세션이 멈출 때 인장을 그리는 것), 그리고 `seal` 명령입니다. 그래서 여러 장치가 "에이전트에게 글로 시키고, 지켰는지를 나중에 검사로 확인하는" 모양입니다. Owlery는 데몬, 화면, 저장소를 가진 제품이므로 같은 목적을 구조로 이룹니다. 아래 표는 그 옮김입니다.

| 목적 | 플러그인에서 하는 법 | Owlery에서 하는 법 |
|---|---|---|
| 각 당사자가 자기 대상만 판정 | 에이전트 정의에 proofer와 sealer는 코드를 고치지 않는다고 적고, 회차 기록을 검사로 확인 | 역할마다 도구 권한을 데몬이 정합니다. proofer와 sealer는 소스를 고치는 도구를 받지 못합니다(`--tools`, `--allowedTools`, `--disallowedTools`). 그 밖의 권한 요청은 데몬이 받아 답합니다(`--permission-prompts host`, `--permission-prompt-tool`) |
| 규칙을 에이전트에게 전함 | 세션 시작 훅이 core 전체를 출력하고, 에이전트 정의의 `skills:` 목록이 core와 에이전트 계약을 실음 | 데몬이 역할과 단계마다 규칙을 시스템 프롬프트에 붙여 넣습니다([세션마다 싣는 것](#세션마다-싣는-것)). 첫 버전은 core와 에이전트 계약 전체를 넣고, 필요한 부분만 넣는 것은 시작 토큰을 잰 뒤에 정합니다(「만들기 전에 잴 것」). 바이트마다 토큰이 들기 때문입니다 |
| 순서 지키기 | orchestrator가 순서를 적은 문서를 읽고 따름 | 데몬의 코드가 순서를 실행합니다 |
| CI 결과 기다리기 | orchestrator가 `seal pr-wait`를 부르고 종료 코드를 읽음 | 데몬이 기다리고, 끝나면 화면과 알림으로 알립니다. 에이전트는 기다리는 동안 떠 있지 않습니다 |
| 비용 재기 | 끝난 뒤 `seal cost`가 대화 기록 파일을 읽어 계산하고, 이슈에 댓글로 남김 | 데몬이 헤드리스 모드의 결과 이벤트(`total_cost_usd`와 모델별 토큰)를 단계마다 바로 기록합니다. 장부는 데몬이 갖고, 예산 상한도 걸 수 있습니다(`--max-budget-usd`). 구독 로그인이면 이 비용은 실제 청구액이 아니라 API 가격으로 환산한 값이고, 장부에도 그렇게 표시합니다 |
| 사람에게 묻기 | `frame/questions.md`에 적고 세션이 묻기 | 앱의 질문 화면. 선택지와 기본값이 있는 입력 양식이라, 모바일 화면을 붙이면 휴대폰에도 띄울 수 있습니다 |
| 인장 보여 주기 | 세션이 멈출 때 훅이 터미널에 그림 | 작업함, 인장 뒷면, PR, 알림에서 같은 기록을 읽어 그립니다 |
| 기록을 다른 기기로 옮기기 | `seal export`, `seal import`로 zip을 주고받고, `seal mode`로 저장소에 커밋할지(shared) 로컬에만 둘지(local)를 고름 | 기록은 저장소에 커밋되므로 git으로 옮겨집니다([기록은 저장소에 커밋합니다](#기록은-저장소에-커밋합니다)). 기록을 옮기는 명령은 두지 않습니다. 기기 사이에 옮길 것은 데몬의 상태(진행 상태, 비용 장부, 질문과 답)뿐이고, 나중에 기기 사이 동기화로 옮깁니다 |
| 여러 작업을 함께 돌리기 | 세션 하나가 작업을 차례로, 또는 사람이 세션을 여럿 엶 | 데몬이 작업 여럿의 순서와 동시 실행 수를 정하고, 같은 릴리스의 작업끼리 겹치는 곳을 framer에게 넘깁니다 |

이 표가 뜻하는 것은 둘입니다.

- **글로 시키던 규칙 가운데 상당수가 구조가 됩니다.** 구조로 막은 것은 에이전트가 어길 수 없으므로, 그 규칙을 에이전트에게 읽히는 비용도 줄어듭니다. 그래도 판단이 필요한 규칙(무엇이 같은 뜻인가, 이 설계가 맞는가)은 여전히 글로 에이전트에게 갑니다.
- **PR의 검사는 그대로 남깁니다.** 데몬이 구조로 막더라도, PR을 받는 저장소 쪽에서 인장이 HEAD에 있는지 확인하는 검사는 Owlery 밖에서도 돌아야 합니다. 앱을 쓰지 않는 동료가 PR을 볼 때도 같은 판정이 나와야 하기 때문입니다.

### 상태는 세 곳에 둡니다

| 어디 | 무엇 | 왜 |
|---|---|---|
| 사용자의 저장소 | 인장 기록과 그 근거(설계, 회차 기록, 전체 검사 결과)를 포함한 작업 기록 전체 | PR의 검사와 앱을 쓰지 않는 사람이 읽어야 하고, 커밋에 묶여야 하기 때문입니다 |
| 데몬 | 진행 상태, 세션 이벤트와 출력, 비용 장부, 질문과 답, 일정 | 자주 바뀌고, 저장소에 커밋할 이유가 없기 때문입니다 |
| 에이전트에게 주는 것 | 그 역할, 그 단계에 필요한 규칙과 앞 단계의 파일 | 에이전트는 매번 새로 뜨고, 읽는 바이트마다 토큰이 들기 때문입니다 |

**데몬은 저장소를 간직하고, 작업은 모두 저장소 하나에 속합니다.** 저장소는 작업과 따로 더하고 뺍니다. 저장소는 이름, 아이콘, 새 작업이 시작하는 브랜치, 그룹, 그리고 자기 작업을 갖습니다. 창은 작업의 폴더를 보고 저장소를 지어내지 않습니다. 사람이 저장소나 작업에 정해 둔 것은 보관까지 모두 데몬의 상태이고, 사람의 저장소에는 적지 않습니다.

### 기록은 저장소에 커밋합니다

Owlery의 작업 기록은 언제나 사용자의 저장소에 커밋합니다. 커밋하지 않고 로컬에만 두는 모드는 없습니다.

- **커밋되지 않은 기록으로는 인장이 성립하지 않습니다.** PR의 검사가 읽을 기록이 없고, 다른 기기나 다시 받은 클론에서는 기록이 비어 있습니다. "판정의 근거가 커밋에 묶여 따라온다"는 약속을 지킬 수 없습니다.
- **기록 위치가 하나이므로 옮기는 장치도 없습니다.** 기록은 git으로 따라가므로, 기록을 내보내고 들여오는 명령이나 위치를 바꾸는 명령을 두지 않습니다. 기기 사이에 옮길 것은 데몬의 상태뿐입니다.
- **저장소를 처음 연결할 때 기록 자리와 PR의 검사를 함께 만듭니다.** 사람에게 기록 위치를 묻지 않습니다.

그래서 작업 기록을 트리에 둘 수 없는 저장소(회사 규칙으로 막힌 저장소, 남의 프로젝트에 기여하는 저장소)는 Owlery의 대상이 아닙니다.

### AgenticSeal과의 호환

AgenticSeal 플러그인 사용자는 지금처럼 Claude Code에서 그대로 씁니다. Owlery의 기록 형식은 AgenticSeal의 형식에서 출발했고, Owlery의 것입니다. 호환은 Owlery에 쓸모가 있는 곳에서만 지킵니다. Owlery가 자기 PR에 인장을 찍기 전까지는([마일스톤](roadmap.ko.md#마일스톤) 2행) 이 저장소의 기록을 플러그인의 검사와 Owlery의 검사가 함께 읽습니다. `decisions.md`는 AgenticSeal이 읽지 않는 파일이고, AgenticSeal의 검사는 이 파일이 있을 때와 없을 때 같은 답을 냅니다(2026-11-22 실험, 0.38.2와 0.38.4).

## 순서는 코드가, 판단은 orchestrator가

Claude Code 세션의 orchestrator는 지금 두 가지를 함께 합니다. 하나는 정해진 순서를 돌리는 일이고, 다른 하나는 판단입니다. 순서를 코드로 옮기면, orchestrator가 매번 읽고 손으로 따라 하던 절차문이 필요 없어집니다. AgenticSeal 0.38.0이 CI 결과를 기다리는 363단어짜리 절차를 `seal pr-wait` 명령으로 바꾼 것이 같은 방향의 앞선 예입니다.

| 데몬의 코드가 실행하는 순서 | orchestrator 에이전트에게 남는 판단 |
|---|---|
| frame → craft → 리뷰 회차 → 전체 검사(gate) → seal → `seal pr-body` → PR → `seal pr-wait` | 작업마다 어느 경로로 갈지(routing) |
| | 리뷰 지적을 설계로 되돌릴지(fold) |
| | 회차가 수렴하고 있는지 |
| | 사람에게 물을 것을 한 번에 묶기 |

에이전트가 앱을 다루는 법을 배우는 별도 스킬은 만들지 않습니다. 앱이 순서를 맡으므로 그런 스킬이 할 일이 없습니다.

## Claude Code를 띄우는 옵션

Claude Code 2.1.326의 `claude --help`에서 확인한 것입니다(2026-11-17).

| 옵션 | 쓰는 자리 |
|---|---|
| `-p`, `--input-format stream-json`, `--output-format stream-json` | 역할 세션. 데몬이 문장을 보내고 이벤트를 받습니다 |
| `--plugin-dir <path>` | 앱 안의 Owlery 역할 묶음을 그 세션에만 싣습니다 |
| `--agent <agent>` | 역할 세션을 그 역할의 에이전트 정의로 띄웁니다 |
| `--append-system-prompt-file <file>` | 그 역할과 단계의 규칙을 시스템 프롬프트에 붙입니다 |
| `--setting-sources`, `--settings`, `--strict-mcp-config`, `--permission-mode`, `--add-dir` | 역할 세션을 사용자 환경에서 뗍니다([역할 세션은 사용자 환경에서 떼어 띄웁니다](#역할-세션은-사용자-환경에서-떼어-띄웁니다)) |
| `--tools`, `--allowedTools`, `--disallowedTools` | 역할마다 쓸 수 있는 도구를 정합니다 |
| `--permission-prompts host`, `--permission-prompt-tool` | 권한 요청을 데몬이 받아 사람이나 규칙으로 답합니다 |
| `--mcp-config` | 데몬이 띄운 MCP 서버로 에이전트에게 앱의 도구를 줍니다. 예: 승인 줄 갱신, 비용 기록 |
| `--json-schema` | 역할의 출력을 정해진 형식으로 받습니다 |
| `--max-budget-usd` | 단계마다 예산 상한을 겁니다 |
| `--resume <세션 ID>`, `--session-id <uuid>` | 멈춘 세션을 이어 실행하고, 데몬이 세션 ID를 미리 정합니다. resume의 시간과 토큰은 아직 재지 않았습니다 |
| `-c`, `--continue` | 사용자가 pane의 폴더에서 가장 최근 대화를 이어서 시작하는 Claude Code pane. 작업 항목의 pane에서는 그 폴더가 worktree입니다. 다른 Claude Code pane과 같이 Owlery의 hook 설정으로 띄웁니다. Claude Code 2.1.329의 `claude --help`에서 확인했습니다(2026-11-20). 세션을 ID로 이어 실행하기 전까지(로드맵의 마일스톤 4, [roadmap.ko.md](roadmap.ko.md#마일스톤)) 대화로 돌아가는 길입니다 |

이 옵션들은 사용자가 설치한 Claude Code의 버전에 따라 달라질 수 있습니다. 데몬은 시작할 때 CLI 버전을 읽고, 지원하는 최소 버전보다 낮으면 업데이트를 안내합니다.

### AgenticSeal의 변경을 가져오는 법

Owlery는 AgenticSeal의 릴리스를 가져오지 않습니다([AgenticSeal에서 가져오는 것](#agenticseal에서-가져오는-것)). Owlery 역할 묶음은 앱과 함께 릴리스되므로, 앱이 실행하는 순서와 묶음이 어긋나지 않습니다. 묶음이나 PR 검사의 스크립트를 고치는 일은 Owlery의 작업이고, 그때 테스트를 함께 돌립니다.

## 라이선스와 다른 프로젝트의 코드

Owlery는 Apache License 2.0으로 냅니다.

- **Apache-2.0을 고른 까닭.** 오픈소스 메인테이너와 회사가 가장 쉽게 받아들이고, 특허 사용 허락이 들어 있습니다. Apache-2.0 프로젝트에서 가져오는 코드와 조건이 같아 고지를 관리하기도 단순합니다. 카피레프트 라이선스(GPL)는 다른 제품이 우리 코드를 복사하지 못하게 막아 줍니다. 하지만 여기서는 그 보호가 약합니다. AgenticSeal 프로세스가 나온 AgenticSeal이 이미 MIT이고, 발상은 어떤 라이선스로도 막을 수 없기 때문입니다. 대신 비용은 분명합니다. 많은 회사가 GPL 코드에 기여하거나 가져다 쓰는 것을 막고, 플러그인을 만드는 사람은 자기 플러그인이 어떤 라이선스를 따라야 하는지 판단하기 어렵고, GPL은 나중에 휴대폰 앱이 거쳐야 할 iOS App Store 약관과 충돌합니다. Apache-2.0에서 카피레프트로 바꾸는 것은 나중에도 할 수 있습니다. 반대로 바꾸려면 외부 기여자 모두의 동의가 필요합니다.
- **MIT나 Apache-2.0 프로젝트의 코드는 가져와 고쳐 씁니다.** MIT 코드는 저작권 고지와 라이선스 문구를 함께 둡니다. Apache-2.0 코드는 LICENSE와 NOTICE를 함께 가져오고, 고친 파일마다 고쳤다는 표시를 남깁니다. 그런 프로젝트 안에서도 라이선스가 따로 붙은 파일은 하나씩 확인합니다.
- **GPL이나 AGPL 프로젝트의 코드는 가져오지 않습니다.** 코드를 가져오면 앱 전체가 같은 라이선스를 따라야 하므로, 발상만 씁니다.
- **다른 제품의 이름과 로고는 쓰지 않습니다.** 라이선스와 별개인 상표 문제입니다.
- **이름과 엠블럼은 Apache 라이선스의 대상이 아닙니다.** Owlery와 AgenticSeal이라는 이름, 올빼미 엠블럼, 저장소에 있는 그 그림은 권리를 보유하며, 무엇이 적용되는지는 저장소 최상위의 `TRADEMARKS.md`가 밝힙니다.
- **라이선스를 바꿀 여지를 남깁니다.** 외부 기여를 받기 시작할 때 기여자 동의서(CLA)를 두어, 이후 버전의 라이선스를 바꿀 수 있게 합니다. 꼭 요구할지는 「결정을 남겨 둔 것」에 있습니다.

## 만드는 순서

v0.1의 마일스톤, 그 순서, 그 순서의 근거는 [roadmap.ko.md](roadmap.ko.md#마일스톤)에 있습니다. v0.1은 이 문서가 첫 버전이라고 부르는 것입니다. 이 절에는 첫 마일스톤의 모양에 대한 규칙과 v0.1 다음에 만드는 것을 둡니다.

- **껍데기는 화면만이 아니라 끝에서 끝까지 이어진 뼈대입니다.** 창, 데몬, 세션이 첫 마일스톤부터 이어져 있어야, 그 위에 AgenticSeal 프로세스를 만들 때 구조를 다시 짜지 않습니다. 가짜 어댑터를 첫 마일스톤부터 두는 것도 같은 까닭입니다([이식할 수 있게 지키는 규칙](#이식할-수-있게-지키는-규칙)).
- **v0.1 다음에는 다른 에이전트가 만든 브랜치의 "인장 받기", 휴대폰 앱(터미널 세션마다 채팅 모양), 역할 세션을 위한 Codex 어댑터 등이 옵니다.** [결정을 남겨 둔 것](#결정을-남겨-둔-것)의 행을 하나씩 정하면서 더합니다.
- **다른 에이전트가 만든 브랜치의 "인장 받기"는 v0.1 다음에 받습니다.** 그런 브랜치를 기록에 어떻게 적을지가 정해져야 하기 때문입니다([product.ko.md](product.ko.md)의 결정을 남겨 둔 것, 바깥에서 만든 브랜치의 기록). 사용자의 Claude Code 세션이 만든 브랜치는 구현한 쪽을 `crafter`나 `the session`으로 적는 지금 기록 형식으로 적을 수 있으므로, 그 "인장 받기"는 v0.1에 받습니다.

## 플랫폼과 그 순서

첫 버전은 macOS 데스크톱 앱 하나입니다. 다른 플랫폼은 아래 순서로 더합니다.

| 순서 | 플랫폼 | 내는 방법 | 넘어가는 조건 |
|---|---|---|---|
| 1 | macOS 데스크톱 | 서명과 공증을 거치고, GitHub Releases로 업데이트 | |
| 2 | 안드로이드 | Play 스토어 밖에서, 서명한 APK를 GitHub Releases로 | 데스크톱 앱이 안정되면 |
| 3 | Play 스토어의 안드로이드 | Play 스토어 등록 | 사람들이 모이기 시작하면 |
| 4 | 아이폰 | App Store | Play 스토어 등록 다음 |
| 5 | 윈도우 | 오픈소스 프로젝트에 무료로 서명해 주는 SignPath Foundation으로 서명 | 아이폰 앱 다음 |

- **안드로이드가 아이폰보다 앞서는 까닭은 만드는 사람이 매일 쓸 수 있어서입니다.** 휴대폰 앱은 만드는 사람이 들고 다니는 기기에서 가장 빨리 다듬어집니다.
- **안드로이드는 Play 스토어 밖에서 시작합니다.** 첫 사용자인 오픈소스 메인테이너는 APK를 직접 설치하는 데 익숙합니다. Google 개발자 계정은 처음 한 번 25달러입니다.
- **안드로이드를 내기 전에 알아 둘 것.** 그 단계를 시작할 때 정하고, 지금 정하지는 않습니다.
  - **Google의 개발자 인증.** Google은 Play 스토어 밖에서 설치하는 앱도 인증된 개발자의 것이어야 하게 바꾸고 있습니다. 2026-09-30에 네 나라에서 시작했고 2027년부터 전 세계로 넓힙니다. 인증받지 않은 앱도 설치는 되지만, 개발자 모드를 켜고 재부팅하고 24시간을 기다려야 합니다. 인증은 Play 스토어 등록과 별개이고 같은 25달러입니다. 그래서 이 규칙이 우리 사용자가 있는 나라에 닿으면, Play 스토어에 올리기 전이라도 인증을 받습니다.
  - **패키지 이름과 서명 키는 첫 출시부터 고정합니다.** 나중에 사용자가 다시 설치하지 않고 Play 스토어로 옮기려면 둘이 같아야 합니다. 서명 키를 잃으면 기존 사용자에게 업데이트를 보낼 수 없으므로 백업해 둡니다.
  - **푸시는 처음에는 Google 서비스에 기대지 않습니다.** Firebase Cloud Messaging(FCM)을 쓰면 그 키를 쥔 우리 서버가 필요하고, F-Droid에 올릴 수 없습니다. 앱이 데몬과 이어져 있을 때는 그 연결로 알림을 받습니다. 끊겨 있을 때는 UnifiedPush가 사용자가 고른 푸시 앱(ntfy 등)으로 알림을 전합니다. FCM은 Play 스토어에 등록할 때 붙입니다.
  - **업데이트.** 앱이 GitHub Releases의 새 버전을 사용자에게 알려 줍니다. 소스에서 직접 빌드하고 몇 주씩 심사하는 F-Droid는 앱이 안정된 뒤에 올립니다.
- **리눅스**는 Electron이라 빌드하는 비용이 작습니다. macOS와 함께 커뮤니티 빌드로 낼지는 「결정을 남겨 둔 것」에 있습니다.

## 밖에서 붙기: 휴대폰과 다른 컴퓨터

첫 버전에는 모바일 앱이 없고, 휴대폰은 안드로이드가 먼저입니다([플랫폼과 그 순서](#플랫폼과-그-순서)). 그래도 휴대폰이나 다른 컴퓨터가 데몬에 닿는 방식은 지금 정해 둡니다. 데몬의 프로토콜 모양이 여기에 달려 있기 때문입니다.

- **먼저 직접 잇고, 안 될 때만 중계합니다.** 휴대폰과 데몬이 각각 밖으로 연결을 열어, 바깥에서 자기가 어떤 주소로 보이는지 알아냅니다. 그다음 둘이 같은 순간에 서로에게 보내면, 양쪽 공유기는 상대가 보낸 패킷을 답장으로 보고 들여보냅니다(홀 펀칭). 같은 와이파이가 아니어도, 다른 네트워크끼리 됩니다. 이렇게 이어지면 데이터는 어떤 서버도 지나지 않습니다. 상대마다 바깥 포트를 바꿔 붙이는 공유기나 UDP를 막는 네트워크처럼 직접 잇기에 실패할 때만 중계를 거칩니다.
- **iroh를 먼저 고려합니다.** iroh는 주소 대신 기기의 공개 키로 기기끼리 잇는 Rust 라이브러리입니다. 직접 연결을 먼저 시도하고, 안 되면 스스로 중계로 넘어갑니다. 데몬에서 쓸 공식 Node 패키지가 있습니다(`@number0/iroh`, Node 20.3 이상). 페어링은 데몬의 공개 키를 담은 QR 코드 하나가 되고, QUIC 연결이라 휴대폰이 와이파이와 LTE 사이를 옮겨도 이어집니다. React Native 휴대폰 앱에서 쓸 수 있는지는 확인하지 않았습니다. 쓸 수 없으면 WebRTC 데이터 채널이 그 자리를 맡습니다. Electron에 들어 있고, 중계(TURN)는 GB 단위로 빌려 씁니다.
- **모든 연결은 종단 간 암호화합니다.** 중계는 읽을 수 없는 바이트만 넘깁니다.
- **운영비는 작게 유지됩니다.** 직접 잇기에 실패한 연결만 중계를 씁니다. 중계는 iroh의 공개 중계나 우리가 띄운 것을 쓰고, 그 코드를 공개해 사용자가 직접 띄울 수도 있게 합니다. Tailscale이나 SSH로 잇는 길도 계속 지원하고, 이 길은 누구에게도 비용이 들지 않습니다.
- **푸시 알림에는 우리 서버가 필요합니다.** 휴대폰에 알림을 보내려면 Apple(APNs)과 Google(FCM)의 발송 키가 있어야 하는데, 이 키는 앱에 넣을 수 없습니다. 작은 푸시 서버가 이 키를 갖습니다.

## 휴대폰: 터미널 세션을 채팅 모양으로

휴대폰은 책상의 터미널에서 도는 세션을 채팅 모양으로 보여 줍니다. 원본은 터미널이고, 휴대폰은 같은 세션을 보는 두 번째 방법입니다. 휴대폰은 사람이 돌리는 모든 에이전트 CLI에 대해 이렇게 하고, 연결은 위의 길로만 오가며 어느 에이전트 회사의 서버도 거치지 않습니다. 휴대폰을 붙일 수 있게 지금부터 두 가지를 지킵니다. 데몬의 WebSocket 프로토콜을 데스크톱 화면에만 맞추지 않고, 화면 쪽에 상태를 두지 않습니다. 테마처럼 한 화면의 겉모습을 정하는 값은 여기서 말하는 상태가 아니며, 그 화면이 스스로 간직합니다.

Claude Code에서는 채팅의 각 부분이 아래에서 옵니다. 2026-11-18에 Owlery가 띄운 대화형 Claude Code 2.1.327 세션에서 훅을 하나씩 실제로 돌렸습니다. 훅 설정은 `--settings`로 넘겼고, 이 설정은 사용자와 프로젝트의 설정에 더해질 뿐 어느 쪽도 바꾸지 않습니다. 모든 이벤트에 `session_id`, `transcript_path`, `cwd`가 들어 있고, `SessionStart`를 뺀 모든 이벤트에 `permission_mode`가 들어 있습니다.

| 채팅의 부분 | 오는 곳 |
|---|---|
| 사람이 보낸 말 | `UserPromptSubmit` 훅 |
| 도구 호출과 그 결과 | `PreToolUse`, `PostToolUse`, `PostToolUseFailure` 훅 |
| 권한 요청 | `PermissionRequest` 훅. `tool_name`, `tool_input`, `permission_suggestions`가 오고 `tool_use_id`는 오지 않습니다. 훅이 휴대폰의 답을 기다렸다가 허용이나 거절을 돌려줍니다 |
| 한 턴의 마지막 답 | `Stop` 훅 입력의 `last_assistant_message` |
| 도구 호출 사이에 에이전트가 쓴 글 | Claude Code가 디스크에 남기는 세션 기록(`~/.claude/projects/<프로젝트>/<세션 ID>.jsonl`)에만 있습니다. 형식이 공개되지 않았으므로 보조로만 읽습니다. 데몬이 해석하지 못하면 휴대폰은 훅 이벤트만 보여 줍니다 |

- **휴대폰은 터미널 화면을 읽지 않습니다.** 작업함과 같은 규칙입니다. 상태와 내용은 이벤트와 파일에서 가져오고, 화면 출력에서 추측하지 않습니다.
- **휴대폰의 입력은 CLI가 입력을 기다릴 때만 터미널에 넣습니다.** 멈추기는 언제든 그 CLI의 중단 키로 넣습니다.
- **훅은 Owlery가 띄우는 세션에만 넣습니다.** 사용자의 설정 파일은 고치지 않습니다.
- **Codex CLI의 상태, 권한 요청, 대화가 어디서 오는지는 확인하지 않았습니다.** Codex 세션의 줄을 작업함에 들이는 마일스톤 4에서 확인하므로([마일스톤](roadmap.ko.md#마일스톤)), 휴대폰 앱을 만들기 전에 확인하게 됩니다.

에이전트 CLI 가운데에는 Claude Code의 Remote Control처럼 자체 원격 기능을 가진 것이 있습니다. Owlery는 그런 기능을 쓰지 않고, 켜지도 않습니다. 사용자가 어떤 세션에서 그 기능을 켜면 같은 권한 요청이 두 곳에 뜰 수 있습니다. 그때 어떻게 할지는 「결정을 남겨 둔 것」에 있습니다.

## 메모리 설계

**Owlery는 메모리를 될 수 있는 대로 적게 쓰고, 아무도 쓰지 않는 기능은 메모리를 쓰지 않습니다.** 기능이 쥐는 것은 그 기능을 열 때 만들고 닫을 때 놓습니다. 메모리는 열어 둔 작업 수가 아니라 지금 일하는 단계 수에 따라 늘게 합니다.

**장면마다 드는 메모리는 재서 공개하고, 기준 장면의 수치는 기능의 상한이 아닙니다.** 장면은 다시 잴 수 있게 적어 둔 앱의 한 상태입니다. 장면마다 잰 날짜, 커밋, 재는 방법을 함께 공개하고, 비교할 만한 제품에서 같은 장면을 잰 값을 나란히 둡니다. 첫 기준 장면은 터미널 넷이 보이는 앱 자체이고, 약 500 MB였습니다. 2026-11-19에 에이전트가 띄운 앱에서 491.1~503.4 MB를 쟀습니다(`apps/desktop/measurements/memory.md`). 비교할 제품에서 같은 장면을 잰 값은 아직 없습니다. 어떤 기능이 더해져 장면의 수치가 올라가도, 그 까닭으로 기능을 물리지 않습니다.

**기능을 먼저 만들고, 측정이 비용을 보여 주는 곳에서 효율을 높입니다.** 기능은 보통의 주의를 기울여, 쓰지 않는 동안 아무것도 쥐지 않게 만듭니다. 그다음 그 기능의 비용을 잽니다. 효율을 높이는 일은 측정이 비용을 보여 준 곳에서 합니다. 이슈 #9가 숨은 칸마다 창 안에 터미널 화면이 남아 있는 것을 찾아내 없앤 것이 그 예입니다. 기능을 만들기 전에 빠듯한 수치를 정해 두고 설계를 거기에 맞추지 않습니다. 기준 장면은 기능이 들어올 때마다 `apps/desktop`에서 `pnpm run measure:memory`로 다시 잽니다. 그래서 수치가 바뀌면 그것이 드러나고, 그에 맞춰 리팩터링을 일정에 넣습니다. 이 측정을 돌리는 검사는 없습니다. 테스트가 `test/memory.test.ts`를 돌려도 `OWLERY_MEASURE_MEMORY=1`이 없으면 아무것도 재지 않습니다.

**Owlery가 지키는 상한은 사람의 컴퓨터에서 읽어 정한 기본값이고, 사람이 그 값을 보고 바꿉니다.** 동시에 도는 에이전트 수와 worktree 수, 그리고 작업 하나의 화면이 한 번에 보이는 칸 수가 그 상한입니다. 상한마다 그 컴퓨터의 메모리, 코어, 남은 디스크에서 제안값을 내고, 다른 컴퓨터에서 잰 장면의 수치에서 내지 않습니다. 이 상한은 이슈 #32가 마일스톤 3에서 만듭니다([마일스톤](roadmap.ko.md#마일스톤)). 그때까지 에이전트와 worktree에는 상한이 없고, 화면의 칸은 넷까지입니다(아래).

아래 네 규칙은 앱이 도는 동안 적게 쥐게 하는 방법입니다.

| 규칙 | 까닭 |
|---|---|
| 터미널 화면과 WebGL 연결은 보이는 칸 수만큼만 만들어 돌려 씁니다. 숨은 터미널의 출력은 데몬이 갖습니다 | 숨긴 WebGL 캔버스도 화면 크기만 한 그림 버퍼를 계속 들고 있어서, 터미널마다 캔버스를 두면 GPU 프로세스 하나가 1 GB를 넘을 수 있습니다(2026-11-17 측정). 화면 객체를 새로 만드는 비용(약 160~190 ms)은 돌려 쓰면 대부분 피할 것 같습니다 |
| 화면에는 기록 1,000줄만 둡니다. 그 위는 데몬과 디스크 로그에서 필요할 때 가져옵니다 | 같은 창에 터미널 하나를 더할 때 기록 1,000줄이면 약 14 MB, 5,000줄이면 약 20 MB가 늘었습니다 |
| 창은 하나만 씁니다. 내장 브라우저는 두지 않습니다 | 창을 하나 더할 때마다 약 130 MB가 늘었습니다 |
| AgenticSeal 프로세스에서 끝난 단계의 Claude 프로세스는 끝냅니다. 이어서 말을 걸 때는 resume을 씁니다. 사용자가 터미널에서 띄운 세션은 사용자가 닫습니다 | Claude 프로세스 하나가 345~679 MB를 씁니다 |

GPU 터미널 한도는 Chromium 기본값인 16을 그대로 씁니다. 한 화면에 17칸 이상은 둘 수 없다는 뜻입니다. 렌더러의 메모리 상한도 올리지 않습니다.

작업 하나의 화면은 지금 칸을 한 번에 넷까지만 보입니다. 넷은 기준 장면을 잰 칸 수이고, 이슈 #32가 컴퓨터에서 읽어 정하는 기본값으로 바꿀 때까지 코드에 고정되어 있습니다(`apps/desktop/src/renderer/view.ts`의 `STAGE_PANES`). 메모리가 더 많은 컴퓨터에서는 그 기본값이 넷보다 커집니다. 그 작업의 나머지 칸은 탭으로 남고, 화면에 없는 칸은 창 안에 터미널 화면을 두지 않습니다. 데몬은 칸마다 출력의 마지막 256K 글자를 갖고 있고, 칸이 다시 화면에 나올 때마다 창은 그 출력을 다시 받아 칸을 그립니다. 데몬이 오래된 출력을 버릴 때는, 남기는 앞쪽 4,096글자 안에 줄바꿈이 있으면 남긴 출력이 줄의 처음에서 시작하게 자릅니다. 그래야 다시 그릴 때 이스케이프 시퀀스 한가운데서 시작하지 않습니다. 줄바꿈이 그보다 뒤에 있으면 글자 수로 센 자리에서 자르므로, 전체 화면 프로그램처럼 줄바꿈 없이 길게 찍는 프로그램도 그 출력을 잃지 않습니다.

## 화면 프레임워크: Electron

화면은 Electron으로 만듭니다. 시스템 웹뷰를 쓰는 프레임워크가 메모리를 조금 덜 썼지만(같은 시나리오 8개에서 최대 약 10%, 2026-11-17 측정) 그 차이로 고를 정도는 아니었고, 아래 네 가지로 정했습니다.

- **세 OS에서 같은 화면:** Chromium을 함께 넣으므로 macOS, Windows, Linux에서 같은 엔진으로 그립니다.
- **macOS 한글 입력:** 터미널 부품(xterm.js)에서 알려진 입력 문제가 없습니다. 2026-11-18에 사람이 Owlery 터미널 창에 두벌식으로 한글을 셸과 Claude Code 안에서 쳤고, 셸은 친 그대로 UTF-8로 받았습니다.
- **Linux:** Wayland, Nvidia, WebGL에서 열린 문제가 적습니다.
- **업데이트:** 바뀐 부분만 받는 차분 업데이트를 씁니다. 대신 앱이 큽니다(.app 253 MB).

macOS에서도 Electron을 씁니다(2026-11-18 결정). macOS만 시스템 웹뷰로 옮기는 안은 두 기준으로 따졌습니다. 한글 입력은 Electron 창에서 됩니다(위). 앱이 얼마나 가벼워지는가는, 잰 차이가 최대 약 10%라 결정할 만큼 크지 않습니다.

**창은 Owlery 자신의 화면만 보이고, 두 번째 창은 열리지 않습니다.** 메인 프로세스는 창이 자기 화면을 다시 읽는 것 말고는 어디로도 이동하지 못하게 막고, 새 창도 모두 막습니다. 그래서 칸에 찍힌 글자는 창을 바꾸거나 Owlery 안에 웹 페이지를 열지 못합니다. 사람이 창에 끌어다 놓은 파일도 창을 바꾸지 못합니다. 창은 끌어 놓기로 이동하지 않습니다. 칸에 찍힌 링크는 Command 키를 누른 채 클릭하면 시스템 브라우저에서 열리고, 주소가 `http`나 `https`일 때만 열립니다. 칸에 찍힌 경로는 메인 프로세스가 그 자리에서 파일이나 폴더를 찾았을 때만 링크가 됩니다. Command 키를 누른 채 클릭하면, 다른 작업의 worktree는 그 작업의 화면을 앞으로 가져오고, 그 밖의 경로는 Finder에서 보여 줍니다. 파일은 들어 있는 폴더에서 선택된 채로 보이고 앱으로 열리지 않습니다. 폴더는 열리지만, 이름의 첫 글자 뒤에 점이 있고 체크아웃이 아닌 폴더는 파일처럼 선택된 채로 보입니다. `OWLERY_BACKGROUND=1`로 띄운 앱은 시스템 브라우저와 Finder에서 아무것도 열지 않고, 시스템의 클립보드 대신 자기 클립보드를 읽고 씁니다.
check: apps/desktop/test/terminal-basics.test.ts apps/desktop/test/navigation.test.ts apps/desktop/test/links.test.ts apps/desktop/test/paths.test.ts apps/desktop/test/clipboard.test.ts

**macOS에서는 창을 닫으면 창이 숨겨지고, 앱은 화면을 그대로 둡니다.** 알림은 창의 화면이 띄우므로, 창을 닫아 둔 동안 세션이 기다리기 시작해도 알림이 옵니다. 알림이나 Dock 아이콘을 클릭하면 창이 다시 보이고, 종료를 고르면 앱이 끝납니다. `OWLERY_BACKGROUND=1`로 띄운 앱은 전과 같이 창을 닫고 함께 끝납니다. 숨긴 창을 다시 불러올 Dock 아이콘이 없기 때문입니다.
check: apps/desktop/test/background.test.ts

## 만들기 전에 잴 것

- **직접 연결 비율:** 국내 LTE와 5G, 회사 와이파이, 카페 와이파이에서 휴대폰이 중계 없이 데몬에 닿는 비율을 iroh와 WebRTC 각각 잽니다([밖에서 붙기](#밖에서-붙기-휴대폰과-다른-컴퓨터)).
- **화면을 돌려 쓸 때의 전환 지연:** 기록 1,000줄과 5,000줄, 200열 기준으로, macOS, Windows, Linux 각각 잽니다.
- **보이는 터미널 하나가 쓰는 GPU 메모리:** 우리 칸 크기에서 WebGL과 DOM 각각, Retina와 4K 각각 잽니다.
- **데몬의 CPU:** 에이전트 10개가 동시에 출력할 때 터미널 출력을 해석하는 비용을 잽니다.
- **ACP의 범위:** 어떤 에이전트가 ACP로 붙고, 권한 요청, 슬래시 명령, 중간에 끼어들기 가운데 무엇을 지원하는지 확인합니다. 지원하지 않는 기능은 터미널로 열기로 메웁니다.
- **resume의 시간과 토큰:** 멈춘 지 5분 이내와 이후로 나눠 잽니다.
- **권한 요청 훅이 휴대폰의 답을 얼마나 기다릴 수 있는가:** 훅의 시간 제한과, 그 시간이 다 됐을 때 CLI가 무엇을 하는지를 Claude Code와 Codex 각각 확인합니다([휴대폰: 터미널 세션을 채팅 모양으로](#휴대폰-터미널-세션을-채팅-모양으로)).
- **구독 로그인에서 비용 칸이 뜻하는 것:** 헤드리스 결과 이벤트에 `total_cost_usd`, `usage`, `modelUsage`가 구독 로그인에서도 들어 있는 것은 확인했습니다(2026-11-17). 구독은 토큰마다 청구되지 않으므로 이 값은 API 가격으로 환산한 값으로 보입니다. 장부에 어떻게 표시할지 정하기 전에, 같은 작업의 값을 API 키 로그인과 견줘 확인합니다.
- **사용량 값:** 구독 로그인으로 세션을 돌려 상태줄 JSON의 `rate_limits`와 `rate_limit_event`의 필드를 확인합니다. Codex에 비슷한 값이 있는지도 봅니다([사용량 읽기](#사용량-읽기)).
- **AgenticSeal의 단계별 비용:** `seal payload`와 `seal cost`로 잽니다.
- **구조로 옮긴 규칙만큼 줄어드는 시작 토큰:** 2026-11-17 `seal payload`로 잰 에이전트마다의 시작 묶음(에이전트 정의, core, 에이전트 계약, CLAUDE.md)은 framer 약 12,000, crafter, proofer, sealer 각 약 10,500 토큰입니다(3.2바이트당 1토큰으로 어림). 작업 하나에 proofer가 여러 회차 뜨므로 이 묶음을 여러 번 냅니다. 문장마다 "판단이 필요한가, 데몬이나 권한이나 출력 형식(`--json-schema`)으로 강제할 수 있는가"로 가르고, 강제한 문장을 뺀 뒤의 묶음을 다시 잽니다. 같은 묶음은 프롬프트 캐시로 싸게 읽히므로, 절감은 바이트 비율보다 작을 것 같습니다.
- **에이전트가 사람의 컴퓨터에서 앱을 띄울 때는 `OWLERY_BACKGROUND=1`을 주고, 사람이 띄울 때만 드러나는 것은 사람이 잽니다.** 이 값 없이 띄우면 창이 시스템의 포커스를 가져가서, 사람이 치던 키가 에이전트의 칸으로 들어가고 사람이 조합하던 한글이 끊깁니다. 이 값을 주면 창은 포커스를 가져가지 않고 Dock 아이콘 없이 열리며, 마우스를 받지 않습니다. 그래서 사람의 포인터가 창 위를 지나도 창 안에는 아무것도 닿지 않고, 사람의 클릭은 그 아래 창으로 갑니다. 그렇게 띄운 앱에는 Dock 아이콘, 메뉴 막대, 시스템의 포커스, 시스템의 포인터가 없습니다. 그래서 사람이 친 한글 줄, 앞에 둔 창의 메모리, 창 위를 지나는 포인터처럼 그 넷 가운데 하나에 기대는 값은 사람이 돌려서 잽니다([마일스톤](roadmap.ko.md#마일스톤), `apps/desktop/measurements/memory.md`).
