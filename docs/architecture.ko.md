# 구조: 앱, 데몬, 에이전트 어댑터, AgenticSeal 프로세스

*[English](./architecture.md) · 한국어*

## 결론

- **바탕은 작업함, AgenticSeal 프로세스, 인장의 뒷면이고, 터미널은 그 위에서 불러 씁니다.** 데몬은 사용자의 Claude Code를 헤드리스 모드(`claude -p`, 입출력 `stream-json`)로 띄워 AgenticSeal 프로세스의 역할 세션을 뒤에서 돌리고, 그 결과를 작업함과 인장의 뒷면에 보여 줍니다. 첫 버전에서 사람이 일을 시키는 세션은 터미널에 띄운 에이전트의 CLI라, 어느 CLI든 붙습니다. owl 체인은 Owlery 자신의 체인이고, owl 체인을 쓰는 저장소의 Claude Code 칸은 그 세션에 Owlery의 역할 묶음도 싣습니다. 그 세션은 자기가 만든 브랜치를 리뷰 회차, 전체 검사, sealer까지 가져갑니다([세션마다 싣는 것](#세션마다-싣는-것)). 그 밖의 칸은 모두 CLI 그대로입니다. 칸의 상태는 훅과 git으로 읽습니다. 데스크톱에는 채팅 화면이 없습니다. 같은 터미널 세션을 채팅 모양으로 보여 주는 것은 휴대폰이고, CLI의 훅과 세션 기록을 읽습니다([휴대폰: 터미널 세션을 채팅 모양으로](#휴대폰-터미널-세션을-채팅-모양으로)).
- **Owlery는 로그인을 제공하지 않고, 사람은 로그인을 여러 개 둘 수 있습니다.** 인증은 사용자의 CLI가 갖습니다. Claude Code에서는 사용자가 `/login`으로 구독 로그인이나 API 키를 고르고, Owlery는 그 CLI를 띄울 뿐입니다. 로그인이 둘 이상인 사람은 로그인마다 계정을 하나씩 두고, 계정마다 CLI의 로그인 명령으로 로그인하며, 저장소나 작업이나 세션 하나에 계정을 묶습니다([Claude 어댑터의 인증](#claude-어댑터의-인증)).
- **Owlery는 자체 데스크톱 앱입니다.** 다른 앱 위의 플러그인으로 두지 않습니다. 사용자의 Claude Code를 데몬이 직접 띄우고 역할 세션은 사용자 환경에서 떼어 띄우므로, 세션과 터미널을 다른 앱에 맡길 까닭이 없습니다. 작업함, AgenticSeal 프로세스, 장부가 한 제품 안에서 같은 기록을 읽습니다.
- **화면은 Electron으로 만들고, 일은 데몬이 합니다.** 화면은 데몬에 WebSocket으로만 붙는 얇은 껍데기입니다. 나중에 다른 화면 프레임워크로 바꿀 길을 남겨 두려는 것입니다.
- **AgenticSeal 프로세스의 순서는 데몬의 체인에서도 칸의 체인에서도 Owlery의 코드가 실행하고, 판단만 에이전트에게 남깁니다.**
- **AgenticSeal은 참고하는 원본이고, Owlery는 그것을 넓힌 제품입니다.** AgenticSeal에 기대어 돌지 않습니다. 원칙, 불변식, 역할, 기록 형식을 AgenticSeal에서 가져와 Owlery의 것으로 고쳐 갖고, 역할의 에이전트 정의와 스킬은 Owlery가 앱에 함께 넣어 역할 세션의 기본값으로 씁니다([AgenticSeal에서 가져오는 것](#agenticseal에서-가져오는-것)).
- **가볍게 두는 것이 목표이고, 그것은 프레임워크가 아니라 앱의 범위와 구조에서 나옵니다.** 가벼움은 상대적인 것입니다. 채팅 화면, 터미널, IDE 수준의 편집기, 브라우저, 팀 관리, 클라우드를 함께 얹는 제품보다 Owlery가 얹는 것이 적다는 뜻입니다. 창은 하나만 쓰고, 터미널은 보이는 것만 그리고, 일하지 않는 Claude 프로세스는 끝냅니다.

## 전체 구성

```
┌──────────────────────────┐
│ 화면 (Electron 렌더러)    │  작업함, 인장의 뒷면, diff, 사용자 세션의 터미널 칸
│ 휴대폰 앱 (나중에)        │  작업함, 질문 묶음, 인장, 터미널 세션마다 채팅 모양
└────────────┬─────────────┘
             │ WebSocket (둘이 같은 프로토콜)
┌────────────┴─────────────┐
│ 데몬 (앱보다 오래 삶)     │  순서 실행, 터미널 출력 보관, 비용 기록
│  ├─ 사용자 세션 (node-pty) │  터미널에 띄운 에이전트 CLI(무엇이든). 그 훅과 세션 기록으로 읽음
│  │   └─ 칸의 owl 체인     │  owl 체인을 쓰는 저장소의 Claude Code 칸: 역할 묶음, 그리고 Owlery의 코드인 체인 명령
│  ├─ AgenticSeal 프로세스 │  순서, 기록, 불변식은 Owlery의 코드. 데몬의 체인과 체인 명령이 함께 씀
│  │   └─ 역할 실행본       │  첫 버전: 사용자의 Claude Code(claude -p) + 앱에 든 Owlery 역할 묶음
│  └─ git, gh              │  브랜치를 지켜보다 인장 뒤에 들어온 커밋을 잡음
└──────────────────────────┘
```

- **데몬은 앱이 재시작하거나 업데이트되는 동안에도 살아 있습니다.** 리뷰 회차가 길어져도 작업이 끊기지 않게 하려는 것입니다. 세션을 끝내는 것과 세션을 되살리는 것은 [세션이 견디는 것](#세션이-견디는-것)에 적습니다.
- **에이전트 상태는 이벤트로 판정하고, 터미널 화면 출력에서 추측하지 않습니다.** 역할 세션은 구조화된 출력의 이벤트로 알려 줍니다. 터미널로 연 사용자 세션은 Claude Code처럼 그 CLI의 훅으로 알려 주고, 사람이 중단한 턴처럼 훅이 아무것도 알리지 않는 곳에서는 CLI가 쓰는 세션 로그로 알려 줍니다. 훅을 확인하지 않은 CLI라면 작업함에는 브랜치가 바뀌었는지만 보여 줍니다. 사람에게 결정을 띄울 때 잘못 띄우는 일이 없어야 하기 때문입니다.
- **권한 요청은 정식 이벤트로 다룹니다.** framer, crafter, proofer, sealer는 데몬이 직접 띄우므로, 그중 하나가 끝나거나 권한을 요청하면 데몬이 먼저 알고 orchestrator 에이전트나 사람에게 넘깁니다. 에이전트가 자기 아래에 자식 에이전트를 띄우면 그 부모와 자식 관계도 함께 다룹니다. 사용자 세션의 권한 요청은 그 터미널에서 답하거나, CLI의 권한 요청 훅을 거쳐 휴대폰에서 답합니다([휴대폰: 터미널 세션을 채팅 모양으로](#휴대폰-터미널-세션을-채팅-모양으로)).
- **훅으로 상태를 알리는 CLI가 창을 연 지 10초가 지나도록 이벤트를 하나도 보내지 않으면, 사람을 기다리는 것으로 보여 줍니다.** CLI는 세션을 시작하기 전에 먼저 물어볼 것을 묻고, 묻는 동안에는 이벤트를 보내지 않습니다. 2026-11-19에 Claude Code 2.1.327을 띄워 보니, 폴더를 신뢰하는지 묻는 동안에는 훅 이벤트를 하나도 보내지 않았습니다. 이 질문은 사람이 Claude Code에서 신뢰한 적 없는 저장소의 첫 워크트리에서 나옵니다. 묻지 않는 곳에서는 2초 안에 세션 시작을 알렸습니다. 데몬은 이벤트가 오지 않았다는 사실로 판정하고 창에 찍히는 글자로는 판정하지 않으며, 세션의 첫 이벤트가 오면 그 상태로 바꿉니다.
check: apps/desktop/test/daemon.test.ts
- **데몬은 에이전트가 일하는 동안 Mac이 쉬다가 잠들지 않게 합니다.** Mac이 잠들면 에이전트가 모두 멈추고, 기다리기 시작한 에이전트의 알림은 사람이 Mac을 깨울 때까지 오지 않습니다. 데몬은 세션마다 상태를 알고 앱이 닫혀 있는 동안에도 살아 있으므로, 잠들지 않게 하는 일은 데몬이 맡습니다. 데몬은 자식 프로세스 하나로 이 일을 합니다. 자기 프로세스 ID를 넘긴 `caffeinate -i -w`입니다. 그래서 데몬이 어떻게 끝나든 데몬이 끝나면 Mac은 다시 잠들 수 있습니다. 무거운 명령이 돌지 않는 동안에는 화면이 꺼질 수 있고, 덮개를 닫으면 Mac은 전과 같이 잠듭니다. 무거운 명령이 도는 동안에는 데몬이 화면도 켜 두고, 명령이 시작할 때 꺼진 화면을 켭니다. 화면에 그려지는 것을 기다리는 테스트는 꺼진 화면에서 실패하기 때문입니다. "Never"에서는 둘 다 하지 않습니다. 사람은 "While an agent works", "Always", "Never" 가운데 하나를 고르고, 처음 값은 "While an agent works"입니다. "While an agent works"는 프로세스가 살아 있는 칸이나 헤드리스 세션 가운데 하나라도 일하는 동안 유지됩니다. "Always"는 데몬이 도는 동안 유지되고, 할 일이 없어진 데몬이 스스로 끝나는 것을 막지 않습니다. 이 선택은 데몬의 상태입니다. 데몬의 실행 디렉터리에 저장되고 모든 클라이언트에 전달되므로, 창과 나중에 붙을 휴대폰이 같은 값을 보여 줍니다.
check: apps/desktop/test/keep-awake.test.ts apps/desktop/test/daemon.test.ts
- **사람은 앱 메뉴에서 데몬을 멈추고, 앱이 스스로 바꾸는 것은 아무것도 돌리지 않는 다른 빌드의 데몬뿐이며, 앱은 자기 실행 폴더의 데몬만 멈춥니다.** 보통의 종료는 데몬과 세션을 그대로 둡니다. "Restart Daemon…"과 "Quit Owlery Completely…"는 실행 중인 세션을, 그리고 그와 따로 컴퓨터를 기다리는 세션을 먼저 이름으로 보여 주고, 사람이 확인하면 앱이 데몬을 끝냅니다. 앱은 실행 폴더의 `daemon.json`이 가리키는 프로세스에 신호를 보내며, 그 파일의 주소에서 그 파일의 토큰으로 데몬이 응답한 뒤에만 보냅니다. 앞의 항목은 이어서 지금 실행 중인 빌드의 데몬을 띄우고, 뒤의 항목은 데몬을 띄우지 않고 앱을 끝냅니다. 신호를 쓰는 까닭은 어느 빌드의 데몬이든 신호를 받으면 끝나지만, 프로토콜에 새로 넣은 메시지는 이전 빌드의 데몬이 알지 못하기 때문입니다. 데몬은 자기가 실행하는 스크립트의 SHA-256 값을 `daemon.json`에 적습니다. 그 값이 앱이 띄울 스크립트의 값과 다르고 데몬이 아무것도 돌리지 않으면, 창이 페이지를 읽을 때 묻지 않고 데몬을 바꿉니다([세션이 견디는 것](#세션이-견디는-것)). 값이 다르고 데몬이 무언가를 돌리고 있으면 상태 줄이 데몬이 다른 빌드의 것이라고 알리고 "Restart Daemon…"을 가리킵니다.
check: apps/desktop/test/daemon-client.test.ts apps/desktop/test/daemon-restart.test.ts apps/desktop/test/view.test.ts
- **에이전트가 사람에게 질문하는 세션은 사람을 기다리는 것으로 보여 주고, 질문과 에이전트가 내놓은 선택지를 그 질문을 알리는 이벤트에서 읽어 함께 보여 줍니다.** 에이전트는 자기 이벤트로 질문합니다. Claude Code는 질문 도구를 호출하는 이벤트로 묻고, 그 이벤트에 질문과 선택지가 하나씩 들어 있습니다. 데몬은 거기서 읽어 중립적인 값으로 보내고, 칸에 찍힌 글자에서는 하나도 읽지 않습니다. 질문을 알리는 이벤트는 사람이 답하기 전에 오므로, CLI가 그 뒤에 어떤 이벤트를 보내든 세션은 그 이벤트부터 사람을 기다립니다.
check: apps/desktop/test/agent-events.test.ts apps/desktop/test/daemon.test.ts
- **사람이 중단한 턴은 그 세션을 사람을 기다리는 상태로 두고, 데몬은 이를 세션 로그에서 읽습니다.** Claude Code는 사람이 턴을 중단할 때 훅 이벤트를 보내지 않습니다. `Stop` 훅은 실행되지 않고, 칸은 대신 무엇을 할지 묻습니다. Claude Code는 중단을 세션 로그에 사람의 항목으로 쓰고, 그 글은 `[Request interrupted by user]`이거나 `[Request interrupted by user for tool use]`입니다. 기록 `apps/desktop/test/fixtures/claude-interrupted-turn.json`에 두 중단이 모두 들어 있고, 기록한 Claude Code의 버전과 날짜도 그 파일에 적혀 있습니다. 훅 이벤트마다 로그 파일의 경로가 들어 있고, 데몬은 칸이 일하는 동안에만 그 파일을 지켜보며, 덧붙은 줄을 읽고 하나도 간직하지 않습니다. 그 뒤 세션은 사람을 기다리고, 중단된 도구 호출의 끝이 나중에 도착해도 일하는 상태로 돌아가지 않습니다. 하위 에이전트의 항목과, 사람이 보낸 메시지가 턴을 끊어서 쓰인 항목은 이런 중단이 아닙니다. 로그의 형식은 공개된 것이 아니므로, 데몬이 읽지 못하는 줄은 아무것도 바꾸지 않고 훅 이벤트만으로 판정합니다.
check: apps/desktop/test/daemon.test.ts apps/desktop/test/agent-events.test.ts apps/desktop/test/agent-state.test.ts apps/desktop/test/session-log.test.ts

- **API 오류로 끝난 턴은 그 세션을 사람을 기다리는 상태로 둡니다.** Claude Code는 이런 턴에서 `Stop` 대신 `StopFailure` 훅을 실행하고, API 오류로 끝난 서브에이전트의 턴에서도 실행하며, 그때 입력에 서브에이전트의 `agent_id`가 들어 있습니다. 데몬은 세션 자신의 것만 읽고, 훅의 입력은 오류의 종류를 `error`에, 칸에 보이는 오류의 글을 `last_assistant_message`에 담습니다. 데몬은 이 이벤트를 실패한 턴으로 읽습니다. 세션은 사람을 기다리고, 작업함은 오류의 글을 보여 줍니다. 에이전트가 시킨 일을 끝내지 못했으므로 세션을 끝났다고 하지 않습니다. `apps/desktop/test/fixtures/claude-stop-failure.json`에 Claude Code의 훅 문서가 적은 대로의 이벤트가 들어 있고, 문서를 읽은 날짜와 입력 선언을 함께 읽은 Claude Code의 버전도 그 파일에 적혀 있습니다.
check: apps/desktop/test/agent-state.test.ts apps/desktop/test/agent-events.test.ts apps/desktop/test/hooks.test.ts apps/desktop/test/daemon.test.ts

- **끝난 칸의 프로세스도, 시작에 실패한 칸도 데몬에 의사 터미널을 하나도 열어 두지 않습니다.** macOS는 기기 전체에 의사 터미널을 기본 511개까지 줍니다(`kern.tty.ptmx_max`). 데몬은 사람이 열고 닫는 모든 칸보다 오래 삽니다. node-pty 1.1.0은 macOS에서 칸을 시작할 때마다 여분의 의사 터미널을 하나 열고, 그것도 칸의 slave도 데몬에서 닫지 않아서, 데몬은 시작한 칸마다 디스크립터를 두 개씩 쥐고 있었습니다. 사용자의 프로세스 한도에 걸릴 때처럼 master를 연 뒤에 spawn이 실패하면, 어느 프로세스도 쥐지 않은 그 master도 열어 둔 채였습니다. 저장소는 그 버전을 패치합니다(`patches/`). node-pty의 이후 소스가 닫는 방식과 같습니다.
check: apps/desktop/test/pty.test.ts

## 세션이 견디는 것

**세션의 프로세스는 그것을 띄운 데몬이 사는 동안 살고, 세션의 대화는 둘보다 오래 남습니다.** 데몬은 칸마다 가상 터미널을, 역할 세션마다 파이프를 쥡니다. 그래서 창을 닫거나 앱을 끝내도 아무것도 끝나지 않고, 데몬이 끝나면 데몬이 띄운 프로세스 가운데 터미널이 끊기는 신호에 끝나는 것은 모두 끝납니다. Claude Code 칸이 그 신호에 끝나는지는 아직 돌려 보지 않았고, 이슈 #61 작업의 첫 실제 세션이 답합니다. 역할 세션은 터미널이 없고 자기 프로세스 그룹을 따로 이끕니다. 데몬이 멈출 때는 신호를 보내고 끝나기를 기다리지만, 데몬이 죽을 때 역할 세션이 끝나는지는 돌려 보지 않았습니다. Owlery는 그 프로세스를 데몬보다 오래 살려 두지 않습니다. 프로세스 밑의 데몬을 살려 두고, 프로세스가 사라진 곳에서는 대화를 되살립니다. 아래 표는 그 밑의 두 규칙을 만든 뒤에 일마다 어떻게 되는지를 적은 것이고, 규칙마다 그것을 만드는 이슈를 밝힙니다.

| 일어나는 일 | 칸의 프로세스 | 역할 세션 | 작업을 되살리는 것 |
|---|---|---|---|
| 창을 닫거나 앱을 끝냄 | 삽니다 | 삽니다 | 필요 없습니다 |
| 앱을 업데이트함 | 이전 빌드가 띄운 데몬 안에서 삽니다 | 살고, 그 실행도 이어집니다 | 필요 없습니다. 데몬은 아무것도 돌리지 않게 된 뒤에, 또는 사람이 시킬 때 바꿉니다 |
| 사람이 "Restart Daemon…"을 고름 | 대화 상자가 이름을 보여 준 뒤에 끝납니다 | 대화 상자가 이름을 보여 준 뒤에 끝납니다 | Claude Code 칸은 사람이 시키면 대화를 이어 가고, 실행은 끊긴 단계를 다시 시작합니다 |
| 데몬이 죽거나 Mac이 다시 시작됨 | 끝납니다 | Mac과 함께 끝납니다. 데몬이 죽은 뒤에는 돌려 보지 않았습니다 | 위와 같습니다 |

**앱을 업데이트해도 세션은 끝나지 않습니다. 이전 빌드가 띄운 데몬은 계속 돌고, 아무것도 돌리지 않게 된 뒤에나 사람이 시킬 때에만 바꿉니다.** 새 빌드의 창은 그 데몬에 붙고, 상태 줄은 데몬이 다른 빌드의 것이라고 알립니다([전체 구성](#전체-구성)). 살아 있는 칸도, 일하거나 컴퓨터를 기다리는 역할 세션도, 돌고 있는 체인도 없는 데몬은 창이 다음에 페이지를 읽을 때 묻지 않고 바꿉니다. 앱은 이것을 데몬이 hello에 답하며 보내는 목록에서 읽습니다. 0.0.2와 그 뒤 빌드의 데몬은 모두 그 목록을 보내고, 앱은 목록을 읽을 수 없는 데몬을 그대로 둡니다. 앱은 실행되는 동안 한 빌드의 데몬을 한 번만 바꿉니다. 그 빌드의 데몬을 다시 만나면 그 빌드의 다른 앱이 같은 실행 폴더에서 돌고 있는 것이므로, 앱은 데몬을 그대로 두고 상태 줄은 데몬이 다른 빌드의 것이라고 알립니다. 그때 함께 사라지는 것은 데몬이 스스로 끝날 때 놓는 것과 같습니다. 프로세스가 끝난 칸의 출력과 끝난 역할 세션의 목록입니다. 셋 중 하나라도 쥔 데몬은 사람이 "Restart Daemon…"을 고를 때까지 그대로 두고, 그 대화 상자는 무엇이 돌고 있는지 이름으로 보여 줍니다. 그보다 먼저 바꾸면 에이전트가 턴 도중에 끊기고, 끊긴 턴은 사람이 알아채고 다시 시켜야 하는 일이 됩니다. 데몬을 바꾸기 전까지 새 빌드는 이전 데몬이 할 수 있는 것만 보여 줍니다. 창은 데몬이 보내지 않는 필드를 꺼진 기능으로 읽습니다. 데몬은 종류를 알지 못하는 요청에 알지 못한다는 거절로 답하고, 창은 그 자리에 "Restart Daemon…"을 가리키는 문장을 보입니다. 그 답이 생기기 전 빌드의 데몬은 그런 요청에 답하지 않습니다. 그런 데몬에 붙은 창은 10초가 지나도 답이 없는 요청을, 작업 항목을 만드는 요청을 빼고, "Restart Daemon…"을 가리키는 문장과 함께 끝냅니다. 그대로 둔 데몬은 자기 빌드의 스크립트와 node-pty의 네이티브 파일, 역할 묶음을 계속 읽으므로, 업데이트는 그 파일을 그대로 두어야 합니다. 이슈 #78의 `.dmg`는 앱의 파일을 폴더로 담고([플랫폼과 그 순서](#플랫폼과-그-순서)), 업데이트 자체를 만드는 이슈 #266이 그대로 둔 데몬의 파일을 지킵니다. 데몬은 멈출 때마다 로그에 한 줄을 씁니다. 왜 멈췄는지, 살아 있던 칸이 몇이고 일하던 에이전트가 몇인지를 적습니다. 자기 코드의 오류로 끝나는 데몬은 끝나기 전에 그 줄을 쓰고, 강제로 종료되었거나 Mac의 전원이 끊긴 데몬은 아무것도 쓰지 못합니다. 어느 쪽이든 `daemon.json`이 남으므로, 그다음에 뜨는 데몬이 앞의 데몬이 멈추지 않고 끝났다고 씁니다. 줄마다 데몬의 프로세스 ID와 시각이 있고, 줄에는 개수만 있으며 프롬프트도 경로도 제목도 없습니다.
check: apps/desktop/test/daemon-client.test.ts apps/desktop/test/daemon-restart.test.ts apps/desktop/test/daemon.test.ts apps/desktop/test/view.test.ts

**대화는 프로세스가 어떻게 끝났든 세션 ID로 되살립니다.** 데몬은 칸마다 기록을 실행 폴더에 둡니다. 그 칸의 작업, 종류, 폴더, 사람이 그 탭에 준 이름과 색, 그리고 에이전트의 훅 이벤트에 실려 오는 세션 ID입니다. 그 기록이 생기기 전까지 칸의 이름과 색은 데몬의 세션에 있고, 칸이 있는 동안만 있습니다. ID는 가장 나중 것을 둡니다. 사람이 Claude Code의 `/resume`처럼 칸을 다른 대화로 옮길 수 있기 때문입니다. 데몬이 다시 시작했거나 죽었거나 Mac이 다시 시작된 뒤에는 그 작업의 화면이 칸을 다시 내놓고, 사람이 시키면 데몬이 에이전트의 CLI를 그 대화에서 시작합니다. Claude Code에서는 `claude --resume <세션 ID>`입니다. 프로세스는 새것이므로 하던 턴은 끊기고, 칸이 그렇게 알립니다. 이어 가기 전에 데몬은 그 대화를 아직 돌리는 프로세스가 없는지 확인합니다. 터미널이 끊기는 신호를 무시하는 프로세스는 데몬보다 오래 살고(2026-11-22에 에이전트 대신 세운 프로세스로 실험), 한 대화를 두 프로세스에서 열지 않기 때문입니다. ID는 데몬 안에만 둡니다. 프로토콜에는 그 종류의 칸이 이어 갈 수 있다는 것만 싣습니다([이식할 수 있게 지키는 규칙](#이식할-수-있게-지키는-규칙)). 셸 칸에는 대화가 없고, 그 프로세스는 되살리지 않습니다. 데몬이 끝나면서 끊긴 AgenticSeal 프로세스의 실행은 커밋된 기록에서 끊긴 단계를 다시 시작합니다. 그러기 전에 데몬은 끊긴 단계의 프로세스가 그 워크트리에서 더는 돌지 않는지 확인하고, 아직 돌면 끝내거나 기다립니다. 데몬이 죽을 때 역할 세션이 끝나는지는 돌려 보지 않았고, 한 워크트리에 에이전트 둘을 두지 않기 때문입니다. 칸 쪽은 이슈 #61이 마일스톤 4에서, 실행 쪽은 이슈 #55가 마일스톤 3에서 만듭니다. 그때까지 Claude Code 칸은 `--continue`로 그 폴더의 가장 최근 대화로 돌아갑니다([Claude Code를 띄우는 옵션](#claude-code를-띄우는-옵션)).

**터미널을 데몬과 따로 쥐는 것은 두지 않습니다.** 아래 방법은 저마다 데몬이 다시 시작해도 일하던 에이전트를 살려 두는데, 위의 두 규칙은 그 재시작을 사람의 선택으로 남깁니다. 방법마다 빌드가 바뀔 때 데몬과 맞춰 가야 하는 것이 하나씩 더 생깁니다. 2026-11-22에 따져 본 결과이고, 이 결정은 [결정을 남겨 둔 것](#결정을-남겨-둔-것)의 한 줄입니다.

| 방법 | 두 규칙이 지키지 못하는 것 가운데 지키는 것 | 드는 것 | 결정 |
|---|---|---|---|
| 터미널을 쥐는 프로세스를 따로 두고, 새 데몬이 그것을 넘겨받음 | 데몬이 다시 시작하거나 죽어도 일하던 에이전트 | 칸이 하나라도 열려 있는 동안 도는 프로세스입니다. 가상 터미널 둘만 쥔 프로세스가 macOS `phys_footprint`로 13.0 MB였습니다(2026-11-22 실험). 데몬과 그 프로세스 사이에 버전을 따로 갖는 둘째 프로토콜이 생깁니다. 역할 세션은 터미널이 아니라서 데몬에 남습니다 | 만들지 않습니다 |
| 터미널의 디스크립터를 다음 데몬에 넘김 | 사람이 고른 재시작에서 일하던 에이전트. 데몬이 죽을 때는 지키지 못합니다 | 쓰지 않는 동안에는 프로세스가 없습니다. 두 빌드가 함께 아는 넘겨주기, 데몬이 바뀌어도 이어지는 칸 ID, 그리고 node-pty가 열지 않은 디스크립터의 크기 바꾸기가 필요하고, 마지막 것은 node-pty 1.1.0이 공개하지 않습니다. 대신 세운 칸은 그것을 쥐던 프로세스가 끝난 뒤에도 살았고, 그 프로세스에게서 칸의 디스크립터를 물려받은 프로세스가 칸을 읽고 칸의 크기를 바꿨으며, 칸은 새 크기를 받았습니다(2026-11-22 실험). 멈추는 데몬이 띄우지 않은 데몬에 넘기는 것은 돌려 보지 않았습니다 | 만들지 않습니다. 먼저 따져 볼 방법입니다 |
| 프로토콜 버전마다 데몬을 하나씩 둠 | 업데이트를 넘는 세션. 그대로 둔 데몬이 이미 지킵니다 | 세대마다 데몬 하나가 통째로 들고, 실행 폴더가 하나만 갖는 상태를 세대마다 나눠야 합니다 | 쓰지 않습니다 |
| 칸마다 tmux나 zellij를 밑에 둠 | 따로 둔 프로세스와 같습니다 | macOS에 들어 있지 않은 프로그램이 필요합니다. 에이전트와 칸 사이에 터미널이 하나 더 끼어 칸의 스크롤백을 가져가고, Shift+Enter와 알림에 따로 설정이 필요합니다 | 쓰지 않습니다. 사람은 셸 칸 안에서 tmux를 돌릴 수 있습니다 |
| Claude Code의 자체 백그라운드 세션(`claude --bg`, `claude attach`) | 데몬이 다시 시작하거나 죽어도 Claude Code 세션. 2.1.330의 `claude --help`를 읽고 그렇게 될 것으로 보았을 뿐 돌려 보지 않았습니다 | Claude Code에서만 됩니다. Owlery의 훅 설정이 그 세션에 닿는지 모르고, 그 세션은 사람의 백그라운드 에이전트 목록에 들어갑니다 | 만들지 않습니다. 돌려 보지 않았습니다 |

## 에이전트 어댑터

데몬이 에이전트를 구조화된 방식으로 다룰 때는 회사마다의 연결부(어댑터) 하나만 거칩니다. 첫 버전의 실제 어댑터는 Claude 어댑터 하나이고, AgenticSeal 프로세스의 역할 세션을 돌립니다. 터미널로 연 사용자 세션에는 어댑터가 필요 없습니다. 데몬은 그 CLI를 터미널에 띄우기만 하기 때문입니다. 어댑터는 역할 세션에만 있습니다. 다른 회사의 모델이 역할을 맡을 때(휴대폰 앱 다음) Codex app-server와 ACP가 같은 자리에 붙습니다.

| 방향 | 어댑터가 데몬에 맞춰 주는 것 |
|---|---|
| 데몬에서 에이전트로 | 문장 보내기, 중간에 끼어들기와 멈추기, 슬래시 명령, 권한 요청에 대한 답 |
| 에이전트에서 데몬으로 | 메시지, 도구 호출, 고친 파일, 권한 요청, 상태(일하는 중, 입력 대기, 끝남), 모델별 토큰과 비용, 사용 한도 |
| 어댑터가 밝히는 것 | 지원하는 기능 목록. 예: 슬래시 명령을 받는가, `!` 출력을 에이전트에게 보내는 것이 그 CLI의 습관인가 |

**역할 세션의 명령은 운영체제의 샌드박스 안에서 돌고, 샌드박스는 그 명령에 역할의 자리를 내주고 실행이 밝힌 곳에 쓰는 것을 거절합니다.** Claude 어댑터는 실행이 이미 넘기는 `--settings` 값에서 Claude Code 자신의 샌드박스를 켜고, macOS에서 그 샌드박스는 Claude Code가 쓴 프로필로 명령마다 `sandbox-exec` 아래에서 돌립니다. crafter의 명령은 작업의 워크트리와 저장소의 git 폴더에 쓰되, 그 폴더의 `hooks`와 `config`에는 쓰지 못합니다. 그래서 커밋은 되고, 명령은 그 둘을 거쳐서는 훅을 심지 못합니다. proofer와 sealer의 명령은 그 세션이 시작할 때 데몬이 새로 만들어 주는 작업 폴더, 실행 폴더의 `scratch/<세션 id>-<여섯 글자>/`를 받고, 워크트리와 저장소의 git 폴더에는 쓰지 못합니다. 그래서 명령은 자기가 판정하는 저장소의 브랜치를 옮기지 못합니다. 세션 id만으로 작업 폴더의 이름을 짓지 않는 것은, id가 데몬마다 1부터 다시 세어지고 앞선 데몬의 세션이 제 폴더에 아직 쓰고 있을 수 있기 때문입니다. 프롬프트가 그 폴더를 밝히고, 세션의 파일 도구가 그 폴더를 읽으며, 세션의 프로세스가 끝나면 데몬이 그 폴더를 지웁니다. orchestrator의 명령은 자리를 받지 못하고 같은 두 폴더에 쓰지 못하며, 어느 역할의 명령도 역할 묶음의 폴더에는 쓰지 못합니다. 데몬은 어느 역할을 시작할 때든 git에 저장소의 폴더를 묻고, git이 워크트리의 저장소를 대지 못하면 그 역할의 세션은 뜨지 않습니다. 명령은 샌드박스 밖에서 돌겠다고 청할 수 없고(`allowUnsandboxedCommands: false`), 샌드박스가 뜨지 못하는 세션은 뜨지 않으며(`failIfUnavailable: true`), 샌드박스 안의 명령도 요청으로 데몬에 오므로 허락이 전처럼 답합니다(`autoAllowBashIfSandboxed: false`). 샌드박스 안의 명령은 루프백 말고는 어느 호스트에도 닿지 못합니다(도메인 없는 `strictAllowlist: true`, 그리고 `allowLocalBinding: true`). 데몬 자신도 루프백에서 듣고 있고, 데몬의 포트와 토큰을 대는 클라이언트는 창이 하듯 샌드박스 밖에서 데몬에게 일을 시킬 수 있습니다. 그 둘은 실행 폴더의 `daemon.json`에 있으므로, 어느 역할의 명령도 실행 폴더 안의 파일은 읽지 못합니다(`filesystem.denyRead`). 실행은 그 안에 있는 proofer와 sealer의 자기 세션 작업 폴더와, 세션의 설정 폴더 아래 `shell-snapshots`를 다시 읽게 해 줍니다(`filesystem.allowRead`, `denyRead`보다 앞섭니다). Claude Code는 사람의 셸 설정을 찍어 둔 스냅샷을 그 폴더에 두고 명령마다 그 스냅샷에서 시작하며, 스냅샷을 읽지 못해도 오류를 알리지 않습니다. 사람이 계정을 더할 때 Owlery가 만드는 설정 폴더는 실행 폴더 안에 있으므로, 이 항목이 없으면 그런 계정의 세션은 사람의 별칭과 함수 없이 명령을 돌립니다. 사람이 넘겨준 폴더는 원래 있던 곳에 그대로 있습니다. 그 설정 폴더의 나머지는 `.claude.json`을 포함해 여전히 읽지 못합니다. macOS에서 CLI는 계정의 로그인을 키체인에 두며, 거절된 읽기는 키체인을 막지 않습니다. 샌드박스 안의 명령은 Claude Code 2.1.332와 2.1.329에서 키체인 서비스에 닿았고(2026-11-27), 거기서 로그인을 읽는지는 돌려 보지 않았습니다. 이 항목이 있을 때 명령이 스냅샷에서 시작하는 것은, 스냅샷을 폴더 안에 직접 가진 설정 폴더로 확인했습니다(2026-11-27, Claude Code 2.1.332와 2.1.329, 대역 모델을 상대로 한 `pnpm run role:refusal`). Claude Code는 파일 도구가 세션의 폴더 밖을 읽기 전에 데몬에 묻고, 데몬은 역할의 규칙에 따라 그 호출을 거절합니다. `pnpm run role:refusal`, `role:refusal:sealer`, `role:refusal:crafter`가 실행 폴더를 대상으로 이를 시도합니다. 파일의 경로로 읽기, 명령이 만든 링크를 거쳐 읽기, 검색, 목록 보기입니다. 명령은 사람의 다른 파일을 여전히 읽을 수 있고, 루프백에서 듣는 다른 서비스에도 모두 닿습니다. 데몬이 막는 곳은 모두 프로필의 거절 항목이고, 거절 항목은 Claude Code가 기본으로 명령에 쓰게 하는 곳보다 앞섭니다. 실행이 허락으로도 거절로도 밝히지 않은 곳에는, 그 기본이 허락하면 명령이 씁니다. 2026-11-27 Claude Code 2.1.332에서 잰 결과, 기본은 Claude Code 자신의 임시 폴더 `/tmp/claude-<사용자 id>`를 허락했습니다. 사람의 다른 Claude Code 세션도 임시 파일을 거기에 두며, 이 폴더는 어느 역할의 명령에도 쓸 수 있는 채로 남습니다. 기본은 세션의 폴더와, 연결된 워크트리가 속한 저장소의 git 폴더도 허락했으므로, 실행은 그 둘에 쓰지 않는 역할에게 그 둘을 거절합니다. `/tmp` 자체와 사람의 홈 폴더 아래, 워크트리들의 윗폴더는 거절되었습니다. 같은 측정에서 명령은 터미널 장치를 열지 못했고 Unix 소켓을 묶지 못했으며, 실행은 그 둘을 허락하지 않습니다. 그래서 그것이 필요한 테스트는 역할 세션 안에서 실패하고, 데몬이 역할 세션 밖에서 돌리는 전체 검사에서 돕니다. 샌드박스를 켠 세션의 Claude Code는 워크트리에 빈 폴더 `.claude/.cc-writes/`도 남기는데, `git status`에는 보이지 않습니다. 이 폴더는 Claude Code 자신의 것이고 설정 파일이 아니며, Owlery는 지우지 않습니다. 샌드박스는 역할 세션이 명령을 돌리는 동안에만 그 명령을 묶습니다. 그 뒤에 데몬이 돌리는 것은 데몬 자신의 프로세스이고 샌드박스 밖에 있습니다. 데몬이 워크트리에서 하는 커밋은 저장소의 훅을 돌리고, 전체 검사는 저장소의 명령을 돌리는데, 둘 다 crafter의 명령이 쓴 파일을 대상으로 합니다. 명령을 읽어서 답하는 데몬은 짐작할 수밖에 없고, 시스템이 거절한 쓰기는 일어나지 않습니다.

### Claude 어댑터의 인증

Claude 어댑터는 사용자가 설치하고 로그인한 `claude` CLI를 데몬이 띄우는 길 하나로만 붙습니다. Agent SDK는 쓰지 않습니다. Agent SDK 문서는 미리 승인받지 않은 제3자 제품이 claude.ai 로그인이나 구독의 사용 한도를 제공하는 것을 허용하지 않기 때문입니다(Agent SDK overview, 2026-11-18에 읽음). 사용자의 CLI를 띄우면 인증은 처음부터 사용자의 것입니다.

| 무엇 | 어떻게 |
|---|---|
| 인증 | 사용자가 Claude Code에서 `/login`으로 고릅니다. 구독 로그인이면 사용자의 구독 한도를, API 키면 사용자의 API 과금을 씁니다. Owlery는 로그인 화면도, 키 저장도 갖지 않습니다. 사람이 더한 계정은 Owlery가 그 계정의 설정 폴더를 지정해 터미널 칸에서 CLI의 `claude auth login`을 실행하고, 로그인은 브라우저에서 Anthropic의 절차로 끝납니다 |
| 역할 세션 | 헤드리스 모드(`claude -p --input-format stream-json --output-format stream-json`)로 역할 세션을 띄워, 메시지, 도구 호출, 권한 요청, 결과를 이벤트로 받습니다 |
| 원래 화면 | 사용자가 들여다보고 싶으면 역할 세션을 터미널로 엽니다(`claude --resume <세션 ID>`). 이때 상태는 훅으로 판정합니다 |
| 역할 묶음 | 앱에 든 Owlery의 에이전트 정의와 스킬을 데몬이 역할 세션에만 싣습니다(`--plugin-dir`). 사용자의 Claude Code에 설치하지 않으므로, 앱의 버전과 묶음의 버전이 언제나 같습니다. 아래 「세션마다 싣는 것」 |

Anthropic이 공개한 문서 가운데 이 일과 관계있는 것은 둘이고, 어느 쪽도 다른 제품이 사용자가 로그인해 둔 CLI를 헤드리스 모드로 띄우는 일을 다루지 않습니다. 지원 문서 "Use the Claude Agent SDK with your Claude plan"은 `claude -p`와 제3자 앱의 사용량이 여전히 사용자의 구독 한도에서 나간다고 적습니다. Agent SDK overview에는 이 절 첫머리에 적은 claude.ai 로그인에 관한 규칙이 있습니다. 둘 다 2026-11-18에 읽었습니다. Owlery는 Anthropic에 문의를 보내지 않습니다. 헤드리스 역할 세션은 이 두 문서를 놓고 판단하고, 둘 가운데 하나가 바뀌면 다시 판단합니다. 역할 세션은 어댑터로만 띄우므로, 훅으로 읽는 대화형 터미널로 옮기는 비용은 작게 유지됩니다.

"System default"는 아무것도 넘기지 않았을 때 사람의 셸이 주는 로그인이고, 언제나 있습니다. 계정을 더하는 길은 둘이고, 어느 길에서도 사람이 이름을 적지 않습니다. ### 사용량 읽기

앱은 사용자의 구독 한도를 얼마나 썼는지와 언제 다시 채워지는지를 보여 주고, 데몬은 AgenticSeal 프로세스를 시작하기 전에 같은 값을 봅니다. 한 번의 실행이 작업 하나에 단계를 네다섯 번 띄울 수 있으므로, 5시간 한도가 거의 찬 상태에서 시작하면 중간에 멈춥니다. 그럴 때 데몬은 실행을 미루거나 사람에게 알립니다.

Claude Code가 이 값을 직접 넘겨주는 길은 둘입니다. 둘 다 Claude Code 2.1.327 실행 파일에서 찾았습니다(2026-11-18). 상태 줄의 값은 아직 실제로 돌려 보지 않았습니다. 출력 스트림의 이벤트는 역할 세션의 실행 기록 둘에 있습니다.

| 세션 | 값이 오는 곳 | 들어오는 것 |
|---|---|---|
| 터미널로 연 사용자 세션 | Claude Code가 상태줄 명령에 넘기는 JSON의 `rate_limits` | `five_hour`, `seven_day` 각각의 `used_percentage`. 구독자에게만, 첫 API 응답 뒤에 들어옵니다 |
| 역할 세션 | 헤드리스 출력 스트림의 `rate_limit_event` | 이벤트마다의 한도 정보. 상태, 어느 한도인지, 그리고 나열한 구간마다 쓴 비율과 초기화 시각과 상태입니다. 값을 바꿔 보관한 실행 기록 둘에서 읽었으므로, 쓴 비율의 범위와 초기화 시각의 단위는 확인하지 않았습니다 |

- **사용자의 상태줄은 그대로 둡니다.** 데몬은 작은 상태줄 명령을 끼워 넣습니다. 그 명령은 받은 JSON을 데몬에 넘기고, 사용자가 원래 쓰던 상태줄 명령을 불러 그 출력을 그대로 보여 줍니다.
- **값은 마지막 호출 기준입니다.** 아무것도 돌지 않을 때는 마지막으로 받은 값과 다시 채워지는 시각을 보여 줍니다.

다른 길도 있고, 구현할 때 이 경우를 함께 고려해야 합니다. 앱이 Claude Code의 자격 증명 파일이나 키체인에서 사용자의 로그인 토큰을 읽고, 그 토큰으로 공개되지 않은 사용량 주소를 부르는 길입니다. 언제든 지금 값을 받을 수 있지만, 첫 버전에서는 쓰지 않습니다. 까닭은 셋입니다.

- 공개되지 않은 주소라 응답 모양이 예고 없이 바뀔 수 있습니다.
- 요청이 Claude Code인 것처럼 보여야 합니다. 막히면 피해는 사용자의 계정이 받습니다.
- 인증은 사용자의 CLI가 갖는다는 이 문서의 규칙과 어긋납니다.

이 길은 나중에도 쓰지 않고, 세션이 돌지 않는 계정에도 다른 계정과 같이 쓰지 않습니다. Claude Code의 Legal and compliance 문서는 개발자가 Claude.ai 자격 증명이나 세션 토큰을 모으거나 저장하거나 중개해서는 안 된다고 적고(2026-11-23에 읽음), 토큰을 읽는 것은 모으는 일입니다. 세션이 돌지 않는 계정은 그 계정의 세션이 마지막으로 넘겨준 값을 받은 시각과 함께 보여 주고, 세션이 돈 적이 없는 계정은 숫자를 보여 주지 않습니다. Codex가 비슷한 값을 넘겨주는지는 확인하지 않았습니다.

**사람은 세션이 돌지 않는 계정의 사용량을 단추를 눌러 새로 받고, 그 밖의 어떤 것도 새로 받기를 시작하지 않습니다.** 그러면 데몬이 그 계정으로 CLI의 짧은 헤드리스 세션 하나를 도구도 대화 기록도 없이 띄우고, CLI가 출력으로 넘겨주는 한도 값을 받아 둔 뒤 세션을 끝냅니다. 값은 Claude Code가 준 것이고 Owlery가 다른 세션을 띄우듯 띄운 세션에서 읽으므로, Owlery는 여전히 토큰을 읽지 않고 Anthropic의 주소를 직접 부르지 않습니다. 새로 받기는 그 계정의 한도를 조금 쓰므로 타이머도 대화 상자를 여는 일도 새로 받기를 시작하지 않으며, 단추는 누르기 전에 그렇게 알립니다. CLI가 값을 넘겨주지 않으면 계정은 그렇게 알리고 숫자를 보여 주지 않습니다. 한도가 가깝지 않은 턴이 `rate_limit_event`를 넘겨준 실행 기록이 케이스에 둘 있고, 하나는 2026-11-22의 Claude Code 2.1.330입니다. 그 줄은 어느 한도의 것인지 밝히고, 나열한 구간마다 쓴 비율과 초기화 시각과 상태를 담으며, 두 기록 모두 7일 구간만 나열했습니다. 기록의 값은 보관하기 전에 다른 값으로 바꿨습니다. 그래서 한 턴이 어느 구간을 나열하는지, 쓴 비율이 1을 기준으로 한 값인지, 초기화 시각의 단위가 무엇인지, 새로 받기에 얼마가 드는지는 실제 실행에서 읽지 않았고, Owlery는 공개된 타입대로 읽히는 값만 보여 줍니다.

### 세션마다 싣는 것

| 세션 | Owlery 역할 묶음 | 규칙이 들어오는 길 |

| 명령이 역할의 자리 밖에 쓰는 것, 명령이 데몬의 실행 폴더 안을 읽는 것, 사람 자신의 샌드박스 설정 | 데몬이 정한 `sandbox` 블록을 담은 `--settings`. `--setting-sources ""`가 사용자 설정과 저장소 설정을 모두 읽지 않으므로 그쪽의 샌드박스 설정은 세션에 닿지 않음 | proofer의 명령이 워크트리의 파일에 덧붙이려다 `Operation not permitted`로 실패했고, 저장소의 git 폴더에 브랜치를 만드는 `git branch`도 같은 오류로 실패했으며, 작업 폴더에는 그 명령의 클론이 만들어짐(대역 모델을 상대로 한 `pnpm run role:refusal`, Claude Code 2.1.332와 2.1.329, 2026-11-27). 실행 폴더의 `daemon.json`을 읽는 `cat`도 같은 오류로 실패함(같은 스크립트, Claude Code 2.1.332와 2.1.329, 2026-11-27) |

- **`--bare`는 쓰지 않습니다.** `--bare`에서는 Claude Code가 OAuth와 키체인을 읽지 않아 구독 로그인으로 돌 수 없습니다(`claude --help`).
- **떼지 못하는 것은 Claude Code에 내장된 플러그인(`cc-plugin-*`, `builtin`)뿐입니다.** 사용자가 고를 수 없는 Claude Code의 일부이므로 받아들입니다.
- **저장소의 `CLAUDE.md`는 읽고, 저장소의 설정은 읽지 않습니다.** `CLAUDE.md`는 그 저장소의 규칙이라 판정에 필요합니다. 그래서 설정 출처는 비운 채 저장소를 `--add-dir`로 넘기고, 환경 변수 `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1`로 그 디렉터리의 `CLAUDE.md`를 읽게 합니다(2026-11-17 시험: `CLAUDE.md`의 규칙이 지켜지고, 저장소 설정이 켠 플러그인은 실리지 않음). `--setting-sources project`로 읽으면 저장소의 `.claude/settings.json`도 함께 들어와, 그 설정이 켠 플러그인과 권한 규칙까지 역할 세션에 실립니다(같은 날 시험: 저장소 설정이 켠 AgenticSeal 플러그인이 실림).

**역할 세션은 아무것도 설치하지 않습니다. 묶음은 그 세션에만 실리고, Owlery는 사용자의 설정 파일과 플러그인 목록을 쓰지 않습니다.** Claude Code는 세션이 실은 플러그인의 횟수를 자기 상태 파일 `~/.claude.json`의 `pluginUsage`에 적고, 역할 세션은 거기에 `owlery@inline` 항목을 더합니다(2026-11-22 실험, 2.1.330). 이 파일은 CLI 세션이 뜰 때마다 다시 쓰는 파일이고, 설정 파일이 아닙니다. 데몬이 시작할 때 실행하는 `claude --version`은 이 파일에 아무것도 쓰지 않습니다. 같은 실행에서 `settings.json`, `installed_plugins.json`, `known_marketplaces.json`은 쓰이지 않았습니다.

### 이식할 수 있게 지키는 규칙

이식할 수 있는 상태를 지키는 규칙은 넷입니다.

1. **화면은 어느 회사의 에이전트인지 모릅니다.** 데몬과 화면 사이의 프로토콜에는 어댑터가 맞춰 준 형태만 지나가고, 회사마다의 필드는 지나가지 않습니다. 모바일 화면도 같은 프로토콜을 씁니다.
2. **회사마다 다른 기능은 기능 목록으로 다룹니다.** 화면은 기능 목록을 보고 단추를 보이거나 숨깁니다. 이름으로 회사를 가려 분기하지 않습니다.
3. **처음부터 어댑터를 둘 둡니다.** 실제 Claude 어댑터와, 테스트에서 쓰는 가짜 어댑터입니다. 어댑터가 하나뿐이면 연결부의 모양이 Claude에 맞춰 굳어도 알아채기 어렵습니다.
4. **체인의 코드는 세션을 돌리는 에이전트와 따로 섭니다.** 순서, 기록, 불변식은 Owlery의 코드입니다. 체인의 역할을 맡는 에이전트는 같은 어댑터를 거쳐 띄우거나, 같은 정의에서 칸의 세션이 서브에이전트로 띄웁니다. 그래서 판정자를 다른 모델로 바꿀 때 체인의 코드는 바뀌지 않습니다. 데몬의 체인은 사용자 세션과 따로 돌고, 그 세션이 어느 회사의 에이전트든 같습니다. 칸의 체인은 사용자의 Claude Code 세션 위에서 돌고, 첫 버전에서 다른 회사 에이전트의 칸은 체인을 싣지 않습니다.

## AgenticSeal에서 가져오는 것

AgenticSeal은 Owlery가 참고하는 원본이고, Owlery는 그것을 넓힌 제품입니다. Owlery는 AgenticSeal 플러그인을 싣거나 그 버전에 기대어 돌지 않습니다. AgenticSeal의 각 부분을 Owlery의 것으로 가져와 제품에 맞는 자리에 둡니다. AgenticSeal은 MIT 라이선스이므로, 가져온 파일에는 그 저작권 고지를 남깁니다.

**Owlery가 AgenticSeal에서 가져온 것은 가져온 날부터 Owlery의 것이고, Owlery는 AgenticSeal의 릴리스를 따라가지 않습니다.** AgenticSeal은 Owlery가 출발한 자리입니다. Owlery는 역할 묶음과 PR 검사의 스크립트를 비롯한 사본을 자기 데몬에 맞게 고치고, 어떤 테스트도 사본을 AgenticSeal의 바이트에 묶지 않습니다. AgenticSeal에서 뒤에 나온 생각은 다른 생각과 똑같이 Owlery의 이슈로 들어옵니다. 가져온 파일을 둔 폴더마다 AgenticSeal의 라이선스 전문과, 그 파일이 어디서 출발했는지 밝히는 고지를 둡니다.
check: apps/desktop/test/role-bundle.test.ts apps/desktop/test/pr-check.test.ts

| AgenticSeal에 있는 것 | Owlery에서 맡는 자리 |
|---|---|
| 가치와 원칙: 판단이 필요한 곳에만 판단을 쓰고 나머지는 스크립트가 답한다, 각 에이전트는 자기 대상을 독립적으로 판정한다, 사람에게 물을 것은 첫 편집 전에 한 번에 묻는다 | 제품의 원칙으로 그대로 가져옵니다 |
| 네 불변식: 빌드 없는 리뷰 없음, 어떤 회차도 읽지 않은 수정 없음, HEAD에서 전체 검사 없이 인장 없음, 인장 없이 PR 없음 | 제품이 지킵니다. 데몬의 코드와 PR의 검사가 맡고, 어느 에이전트가 만든 작업에도 똑같이 적용합니다 |
| 역할: framer, crafter, proofer, sealer | 역할의 정의(무엇을 읽고, 무엇을 판정하고, 무엇을 남기는가)는 제품이 갖습니다. 실행본은 런타임마다 둡니다. 첫 버전의 Claude 런타임은 AgenticSeal의 에이전트 정의와 스킬에서 시작한 Owlery 역할 묶음을 앱에 함께 넣어 기본값으로 쓰고, 다른 런타임에는 같은 역할 정의를 그 런타임의 형식으로 옮깁니다 |
| 기록 형식: 설계 파일, 회차 기록, `guarantee.md`의 `seal` 블록, `routing.md` | 제품의 기록 형식입니다. 첫 버전은 AgenticSeal 형식과 같고, 여러 에이전트를 받으면서 필요한 칸(만든 쪽, 판정한 모델과 규칙 버전)을 더합니다 |
| 순서를 적은 문서(orchestration) | 데몬의 코드가 실행합니다. 판단만 orchestrator에게 남깁니다 |
| `seal` 명령의 스크립트: `chain_check`, `seal pr-body`, `seal pr-wait`, `seal stamp`, `seal cost` | 같은 일을 Owlery의 데몬과 PR의 검사가 합니다. PR의 검사는 AgenticSeal의 코드를 가져오고, 거기서부터 Owlery가 고칩니다. `chain_check`가 싣는 스크립트는 AgenticSeal 0.38.4에서 출발해 `pr-check/`에 있고, 연결한 저장소의 워크플로가 Owlery의 저장소에서 그것을 받아 옵니다. 지금 다시 짠 검사는 데몬이 기록을 하나도 쓰기 전에 사슬의 모든 기록을 판정해야 합니다. 데몬은 Python을 실행하지 않습니다. 사람의 Mac에 Python이 있다고 기대할 수 없기 때문입니다. 데몬은 자기 코드로 기록을 읽고 쓰며, 나머지 명령이 하던 일은 그 일을 만드는 이슈가 방법을 정합니다 |
| Claude Code에만 있는 장치: 세션 시작 훅이 core를 출력하는 일, Stop 훅이 인장을 그리는 일, 권한과 worktree 훅 | 가져오지 않습니다. 앱과 데몬이 같은 일을 직접 합니다([세션마다 싣는 것](#세션마다-싣는-것)) |
| 질문 묶음(`frame/questions.md`) | 앱의 질문 화면이 됩니다 |

### 플러그인이 아니라서 달라지는 것

AgenticSeal은 Claude Code 플러그인이라 쓸 수 있는 수단이 정해져 있습니다. 에이전트가 읽는 마크다운, 훅 두 개(세션 시작에 core를 출력하는 것, 세션이 멈출 때 인장을 그리는 것), 그리고 `seal` 명령입니다. 그래서 여러 장치가 "에이전트에게 글로 시키고, 지켰는지를 나중에 검사로 확인하는" 모양입니다. Owlery는 데몬, 화면, 저장소를 가진 제품이므로 같은 목적을 구조로 이룹니다. 아래 표는 그 옮김입니다.

| 목적 | 플러그인에서 하는 법 | Owlery에서 하는 법 |
|---|---|---|
| 각 당사자가 자기 대상만 판정 | 에이전트 정의에 proofer와 sealer는 코드를 고치지 않는다고 적고, 회차 기록을 검사로 확인 | 역할마다 쓸 도구를 데몬이 정합니다(`--tools`). proofer와 sealer는 파일을 쓰는 도구를 받지 못하고, 이 둘의 명령은 운영체제의 샌드박스 안에서 돕니다. 샌드박스는 그 명령이 워크트리와 저장소의 git 폴더에 쓰는 것을 거절하고, 그 세션만의 작업 폴더를 줍니다([에이전트 어댑터](#에이전트-어댑터)). 권한 요청은 모두 그 세션의 입출력 스트림으로 데몬에 오고(`--permission-prompt-tool stdio`), 데몬은 그 역할의 규칙으로 답합니다([에이전트 어댑터](#에이전트-어댑터)). 칸에서 판정하는 역할은 서브에이전트이고, 그 정의는 읽고 찾고 명령을 돌리는 네 도구를 이름으로 듭니다(`tools:`). 권한을 묻는 호출에는 사람 자신의 권한 설정이 답합니다 |
| 규칙을 에이전트에게 전함 | 세션 시작 훅이 core 전체를 출력하고, 에이전트 정의의 `skills:` 목록이 core와 에이전트 계약을 실음 | 데몬이 역할과 단계마다 규칙을 시스템 프롬프트에 붙여 넣습니다([세션마다 싣는 것](#세션마다-싣는-것)). 첫 버전은 core와 에이전트 계약 전체를 넣고, 필요한 부분만 넣는 것은 시작 토큰을 잰 뒤에 정합니다(「만들기 전에 잴 것」). 바이트마다 토큰이 들기 때문입니다. 칸의 서브에이전트는 체인 명령이 그 단계를 위해 쓴 파일에서 같은 규칙을 읽습니다 |
| 순서 지키기 | orchestrator가 순서를 적은 문서를 읽고 따름 | Owlery의 코드가 순서를 실행합니다. 데몬의 체인에서는 데몬이, 칸에서는 체인 명령이 실행합니다. 칸의 세션은 다음에 할 단계를 체인 명령에 묻고, 순서를 다시 적은 문서는 없습니다 |
| CI 결과 기다리기 | orchestrator가 `seal pr-wait`를 부르고 종료 코드를 읽음 | 데몬이 기다리고, 끝나면 화면과 알림으로 알립니다. 에이전트는 기다리는 동안 떠 있지 않습니다 |
| 비용 재기 | 끝난 뒤 `seal cost`가 대화 기록 파일을 읽어 계산하고, 이슈에 댓글로 남김 | 데몬이 헤드리스 모드의 결과 이벤트(`total_cost_usd`와 모델별 토큰)를 단계마다 바로 기록합니다. 장부는 데몬이 갖고, 예산 상한도 걸 수 있습니다(`--max-budget-usd`). 구독 로그인이면 이 비용은 실제 청구액이 아니라 API 가격으로 환산한 값이고, 장부에도 그렇게 표시합니다. 칸의 세션이 돌린 단계는 재지 않습니다. 비용을 실어 오는 훅이 없기 때문이고, 그런 인장의 뒷면이 그렇다고 말합니다 |
| 사람에게 묻기 | `frame/questions.md`에 적고 세션이 묻기 | 앱의 질문 화면. 선택지와 기본값이 있는 입력 양식이라, 모바일 화면을 붙이면 휴대폰에도 띄울 수 있습니다. 묶음 뒤에 생긴 질문은 코드와 정책을 기준으로 결정하고, 묻지 않고 내린 결정으로 기록합니다. 코드와 정책으로 답할 수 없고 세션이 스스로 줄 수도 없는 것만 그 작업 하나를 멈춰 두고 작업함의 그 줄에 보이며, 데몬은 다른 작업을 계속 진행합니다. GitHub 이슈에는 질문을 올리지 않습니다. 묻지 않고 내린 결정은 그 작업의 줄에 개수로 보이고, 미리보기와 작업 화면에 근거와 함께 나옵니다. 칸의 세션은 그 칸에서 사람에게 묻습니다. `Automation`이 `yes`이면 질문의 기본값으로 계속 가고 그 질문을 `frame/questions.md`에 씁니다([순서는 코드가, 판단은 orchestrator가](#순서는-코드가-판단은-orchestrator가)) |
| 인장 보여 주기 | 세션이 멈출 때 훅이 터미널에 그림 | 작업함, 인장 뒷면, PR, 알림에서 같은 기록을 읽어 그립니다. 그 기록을 쓴 체인이 데몬의 것이든 칸의 것이든 같습니다. 칸이 싣는 묶음에는 인장을 그리는 훅이 없습니다 |
| 기록을 다른 기기로 옮기기 | `seal export`, `seal import`로 zip을 주고받고, `seal mode`로 저장소에 커밋할지(shared) 로컬에만 둘지(local)를 고름 | 기록은 저장소에 커밋되므로 git으로 옮겨집니다([기록은 저장소에 커밋합니다](#기록은-저장소에-커밋합니다)). 기록을 옮기는 명령은 두지 않습니다. 기기 사이에 옮길 것은 데몬의 상태(진행 상태, 비용 장부, 사람이 무엇을 보았는지)뿐이고, 나중에 기기 사이 동기화로 옮깁니다 |
| 여러 작업을 함께 돌리기 | 세션 하나가 작업을 차례로, 또는 사람이 세션을 여럿 엶 | 데몬이 작업 여럿의 순서와 동시 실행 수를 정하고, 같은 릴리스의 작업끼리 겹치는 곳을 framer에게 넘깁니다 |

이 표가 뜻하는 것은 둘입니다.

- **글로 시키던 규칙 가운데 상당수가 구조가 됩니다.** 구조로 막은 것은 에이전트가 어길 수 없으므로, 그 규칙을 에이전트에게 읽히는 비용도 줄어듭니다. 그래도 판단이 필요한 규칙(무엇이 같은 뜻인가, 이 설계가 맞는가)은 여전히 글로 에이전트에게 갑니다.
- **PR의 검사는 그대로 남깁니다.** 데몬이 구조로 막더라도, PR을 받는 저장소 쪽에서 인장이 HEAD에 있는지 확인하는 검사는 Owlery 밖에서도 돌아야 합니다. 앱을 쓰지 않는 동료가 PR을 볼 때도 같은 판정이 나와야 하기 때문입니다.

### 상태는 세 곳에 둡니다

| 어디 | 무엇 | 왜 |
|---|---|---|
| 사용자의 저장소 | 인장 기록과 그 근거(설계, 회차 기록, 전체 검사 결과), 묻지 않고 내린 결정과 작업을 멈춰 둔 질문을 포함한 작업 기록 전체 | PR의 검사와 앱을 쓰지 않는 사람이 읽어야 하고, 커밋에 묶여야 하기 때문입니다 |

**새 worktree가 받을, git이 무시하는 파일과 새 worktree에서 돌릴 명령은 저장소가 자기 트리에 적고, Owlery는 두 파일을 쓰지 않습니다.** 저장소 메인 체크아웃의 맨 위에 있는 `.worktreeinclude`는 `.gitignore`와 같은 문법의 패턴을 담습니다. ### 기록은 저장소에 커밋합니다

Owlery의 작업 기록은 언제나 사용자의 저장소에 커밋합니다. 커밋하지 않고 로컬에만 두는 모드는 없습니다.

- **커밋되지 않은 기록으로는 인장이 성립하지 않습니다.** PR의 검사가 읽을 기록이 없고, 다른 기기나 다시 받은 클론에서는 기록이 비어 있습니다. "판정의 근거가 커밋에 묶여 따라온다"는 약속을 지킬 수 없습니다.
- **기록 위치가 하나이므로 옮기는 장치도 없습니다.** 기록은 git으로 따라가므로, 기록을 내보내고 들여오는 명령이나 위치를 바꾸는 명령을 두지 않습니다. 기기 사이에 옮길 것은 데몬의 상태뿐입니다.
- **저장소를 처음 연결할 때 기록 자리와 PR의 검사를 함께 만들고, 사람이 먼저 읽은 커밋 하나에 담습니다.** 사람에게 기록 위치를 묻지 않습니다. 앱은 쓰려는 파일 하나하나와 커밋 제목, 커밋이 올라갈 브랜치를 보여 주고, 사람이 확인하기 전에는 아무것도 쓰지 않습니다. 쓰는 것은 기록의 뿌리 `seal/`과 그 안의 `README.md`, `config.json`, 그리고 워크플로 `.github/workflows/owlery-seal.yml`입니다. 저장소가 자기 `seal/`을 따로 쓰고 있으면 뿌리는 `agentic-seal/`입니다. 커밋되어 있는 파일은 그대로 둡니다. 그래서 AgenticSeal의 뿌리와 AgenticSeal의 `hygiene.yml`을 가진 저장소에는 파일을 하나도 쓰지 않고, 그 워크플로는 이름이 아니라 돌리는 검사로 알아봅니다. 앱은 기록 자리를 체크아웃이 서 있는 커밋에서 읽습니다. 클론과 GitHub의 검사가 받는 것이 그 커밋이기 때문입니다. 체크아웃이 기록 자리의 파일을 그 커밋과 같게 갖고 있지 않은 동안에는 기록 자리를 만들지 않습니다. 커밋에는 그 파일만 담고, 저장소의 훅을 그대로 돌리며, 푸시하지 않습니다. 전체 검사 명령은 뿌리의 `config.json`에 있는 `Broad gate` 키이고 같은 단계에서 정하며, 앱은 저장소에 그 값과 그 파일을 보여 줍니다.
check: apps/desktop/test/records-place.test.ts apps/desktop/test/daemon.test.ts apps/desktop/test/view.test.ts

그래서 작업 기록을 트리에 둘 수 없는 저장소(회사 규칙으로 막힌 저장소, 남의 프로젝트에 기여하는 저장소)는 Owlery의 대상이 아닙니다. 앱은 무엇을 쓰기 전에 이 점을 먼저 말합니다. 앱이 쓰려는 파일이나, 작업마다 기록이 놓일 뿌리의 `threads/` 폴더와 그 아래 기록을 git이 무시하고 있으면 앱은 기록 자리를 만들지 않습니다.

**PR의 검사는 앱 없이 GitHub에서 돌고, 작업을 선언한 PR만 판정합니다.** 워크플로는 PR을 체크아웃하고, 그 워크플로를 마지막으로 쓴 릴리스의 태그에서 Owlery 저장소의 `pr-check/`를 받아, Python 3.12 이상에서 `chain_check.py`를 기준 브랜치에 대해 실행합니다. 그 태그가 생기기 전에는 그 릴리스의 브랜치에서 받습니다. 기록의 어느 `routing.md`도 가리키지 않는 브랜치의 PR은 아무것도 선언하지 않은 것입니다. 검사는 아무것도 살피지 않고 그 PR을 통과시킵니다.

**작업의 기록은 묻지 않고 내린 결정과 그 작업을 멈춰 둔 질문이 있는 단 하나의 자리입니다.** 둘 다 작업 폴더의 `decisions.md`에 `seal` 블록으로 하나씩 둡니다. 결정에는 번호, 종류(경로, 기본값을 택함, 범위를 정함, 트리가 답한 질문), 정한 내용, 근거, 상태가 있습니다. 질문에는 번호, 묻는 내용, 근거, 선택지, 기본값, 상태가 있습니다. 데몬은 작업의 워크트리에서 이 파일을 커밋 여부와 상관없이 읽고, 읽지 못한 블록은 읽지 못했다고 밝힐 뿐 그 블록의 값은 하나도 쓰지 않습니다. 사람이 무엇을 보았는지는 데몬의 상태이고, 어떤 기록에도 두지 않습니다.

## 순서는 코드가, 판단은 orchestrator가

Claude Code 세션의 orchestrator는 지금 두 가지를 함께 합니다. 하나는 정해진 순서를 돌리는 일이고, 다른 하나는 판단입니다. 순서를 코드로 옮기면, orchestrator가 매번 읽고 손으로 따라 하던 절차문이 필요 없어집니다. AgenticSeal 0.38.0이 CI 결과를 기다리는 363단어짜리 절차를 `seal pr-wait` 명령으로 바꾼 것이 같은 방향의 앞선 예입니다.

| 데몬의 코드가 실행하는 순서 | orchestrator 에이전트에게 남는 판단 |
|---|---|
| frame → craft → 리뷰 회차 → 전체 검사(gate) → seal → `seal pr-body` → PR → `seal pr-wait` | 작업마다 어느 경로로 갈지(routing) |
| | 리뷰 지적을 설계로 되돌릴지(fold) |
| | 회차가 수렴하고 있는지 |
| | 요청이 맡긴 모든 작업에서 사람에게 물을 것을 한 번에 묶기 |
| | 이슈의 글이 사람에게 남긴 질문에 정책 문서, 설정, 코드, 앞선 작업의 기록이 이미 답했는지 |
| | `agentic`에서 코드와 정책을 기준으로 묻지 않고 무엇을 결정할지, 그리고 늦게 생긴 질문이 코드와 정책으로 답할 수 없고 세션이 스스로 줄 수도 없어서 그 작업을 멈춰 둘 것인지 |

데몬이 띄우든 칸이 싣든 순서는 앱이 맡으므로, 에이전트가 읽는 어떤 문서도 순서를 다시 적지 않습니다. 칸의 세션에 필요한 문서는 하나입니다. 묶음의 `skills/seal/SKILL.md`이고, 다음에 할 단계를 Owlery의 코드에 묻는 법과 역할의 답을 돌려주는 법을 말합니다.

**역할 묶음에는 칸의 세션을 위한 문서 하나와 훅 하나가 있고, 묶음은 순서를 다시 적지 않으며, orchestrator의 정의는 Owlery가 직접 쓴 것입니다.** AgenticSeal의 orchestration 문서를 순서와 판단으로 갈라 가져오지 않았습니다. 순서는 Owlery의 코드이고(`chain.ts#stepOwed`), 그 코드가 돌리는 체인에 맞춰 썼습니다. 묶음의 `agents/orchestrator.md`는 AgenticSeal의 어떤 파일에서도 출발하지 않았습니다. `skills/seal/SKILL.md`는 체인이 체인 명령을 거쳐 어떻게 도는지를 칸의 세션에 말합니다. 역할의 서브에이전트는 뒤에서 돌 수 있고 세션은 그 답을 기다린다는 것, 하네스가 들여쓴 줄의 틀 안에 넣어 돌려준 답은 그 들여쓰기를 뺀 글이라는 것, 체인 명령이 서브에이전트의 id로 받는 값은 서브에이전트 도구의 결과에 있는 `agentId`라는 것, 그리고 수정 단계를 맡은 쪽은 수정을 커밋하되 회차 기록의 닫는 블록은 체인 명령이 커밋하도록 남겨 둔다는 것을 말합니다. 데몬이 orchestrator 에이전트에게 묻는 판단은 두 가지입니다. 리뷰 회차가 수렴하는지, 그리고 단계가 낸 질문을 무엇으로 정할지입니다. 이 에이전트는 어떤 단계도 시작하거나 순서를 바꾸거나 건너뛰지 않습니다. 칸의 세션은 그 두 판단을 스스로 내립니다. 데몬의 체인에 대해서는 마일스톤 2에서 정했고(이슈 #38, #41, #42), 칸에 대해서는 2026-11-24에 정했습니다(이슈 #181).

**칸에서는 세션이 단계를 돌리고, 체인 명령이 순서를 지키고 기록을 씁니다.** 체인 명령은 Owlery의 코드입니다. 빌드가 하나 더 내는 `dist/chain.js`이고, 데몬의 모듈로 만듭니다. 실행 파일 `owl-chain`이 Electron의 Node로 그것을 돌립니다. 체인 명령은 자기가 실행된 워크트리를 읽고, 세션에 건네는 것을 실행 폴더의 `chain/<work item>/` 아래에 둡니다. 단계마다 프롬프트는 그 워크트리를 절대 경로로 밝히고, 다른 경로는 모두 그 꼭대기에서부터 씁니다. 서브에이전트는 자기 세션의 폴더에서 시작하는데, 그 폴더가 저장소의 다른 워크트리일 수 있기 때문입니다. 데몬에는 전체 검사를 돌리기 전에 이 컴퓨터에서 돌 차례를 청하고, 답하는 데몬이 없으면 전체 검사를 바로 돌립니다. 같은 소켓으로 `owed`가 세션에 건넨 단계를 데몬에 알리고, `round`, `fix-pass`, `seal`이 역할의 답을 기록했거나 `owed`가 건넬 단계가 없을 때 그 단계가 끝났다고 알립니다. 그래서 작업의 승인 줄이 그 역할을 일하는 중으로 보입니다. `owed`는 head의 기록을 읽어 순서상 다음에 할 단계를 출력하고, 회차와 수정 단계와 판정에는 그 단계의 프롬프트와 역할의 규칙 파일을 쓰고 묶음의 에이전트 이름을 밝힙니다. 회차의 상한이거나 그 뒤인 회차가 지적을 열어 둔 채 끝나면 `owed`는 `ceiling` 단계를 출력하고 수정 단계를 건네지 않으며, `fix-pass`도 수정 단계를 기록하지 않습니다. 데몬의 체인이 그 자리에서 판단을 묻지 않고 멈추는 것과 같습니다. 사람이 계속하라고 말한 뒤에 세션이 `--persons-word <round>`로 그 한 회차의 멈춤을 넘기고, 이 멈춤은 `Automation`이 `yes`여도 그대로입니다. 세션은 그 에이전트를 서브에이전트로 띄워 둘을 건네고, 답을 체인 명령에 돌려줍니다. `round`는 proofer의 회차 기록을 써서 커밋하고, `fix-pass`는 수정 단계 뒤에 닫는 블록을 커밋하고, `seal`은 sealer의 판정 블록을 채워 `guarantee.md`를 커밋합니다. `start`는 브랜치를 가리키는 디렉터리가 없을 때 작업 디렉터리와 `routing.md`를 만듭니다. `gate`는 저장소의 전체 검사를 직접 돌리고 종료 코드를 읽습니다. `body`는 PR 본문의 두 구역을 씁니다. 이 명령들은 JSON 객체 하나를 출력하고 0으로 끝나거나, 문장 하나를 출력하고 1로 끝나며 아무것도 커밋하지 않습니다. 두 체인이 한 모듈을 부르므로, 체인 명령은 데몬의 체인이 거절하는 것을 똑같이 거절합니다. 세션이 정할 수 없는 질문은 칸에서 사람에게 갑니다. 다만 작업의 `routing.md`에서 `Automation`이 `yes`이면 다음 문단을 따릅니다.

**`Automation`이 `yes`이면 칸의 세션은 질문으로 실행을 멈추지 않고, 묶음의 훅이 이것을 지킵니다.** 묶음의 `hooks/hooks.json`에는 `AskUserQuestion` 도구에 거는 `PreToolUse` 훅 하나가 있습니다. 그 명령은 체인 명령의 `ask`를 돌리고, `OWLERY_CHAIN`이 없으면 아무것도 하지 않습니다. 그래서 owl 체인을 실은 칸에서만 동작합니다. 데몬의 역할 세션은 모든 훅을 끈 채로 뜹니다. `ask`는 워크트리의 브랜치를 가리키는 디렉터리의 `routing.md`를 읽습니다. 그 `Automation` 행이 `yes`이면 `ask`는 2로 끝나 호출을 거절하고, 그 까닭으로 세션이 질문의 기본값으로 계속 가고 그 질문을 기본값과 함께 작업의 `frame/questions.md`에 한 행으로 쓴다고 말합니다. 호출의 질문 가운데 하나가 `No default can be taken: `이라는 말과 까닭으로 시작하면 호출을 통과시킵니다. 브랜치를 가리키는 디렉터리가 없거나 둘이면, `routing.md`에 `Automation` 행이 없으면, 그 행이 `no`이면 호출을 모두 통과시킵니다. 행이 `yes`인데 입력이 그런 호출로 읽히지 않으면 1로 끝나고 입력을 읽지 못했다고 말하며, 이것은 아무것도 거절하지 않습니다. 훅은 질문이 사람이 답할 것인지를 판단하지 않습니다. 기본값을 택할 수 없는 까닭을 세션이 쓰게 할 뿐입니다. `skills/seal/SKILL.md`와 `agents/orchestrator.md`는 실행에서 할 수 있는 일을 줄이는 규칙은 실행이 출처를 댈 수 있을 때만 따른다고 말합니다. 출처는 이 실행에서 사람이 한 말이거나 저장소의 문서이고, 어떤 세션도 앞선 실행의 규칙을 가져오지 않습니다. Claude Code는 대화형 세션에서 `--plugin-dir`로 실은 플러그인의 훅을 돌렸고, 훅이 2로 끝나자 명령이 쓴 까닭과 함께 호출을 거절했습니다(2026-11-24, 2.1.331에서 실험).

**경로를 묻는 질문의 답이 `agentic`이면 orchestrator는 요청 전체에 대해 한 번만 묻고, 그 뒤에는 스스로 결정하거나 작업 하나만 멈춰 둡니다.** orchestrator는 요청의 첫 편집 전에, 그 요청이 맡긴 모든 작업에서 사람에게 물을 것을 모아 한 묶음으로 만듭니다. 이슈의 글이 사람에게 남긴 질문은 묶음에 넣기 전에 정책 문서, 설정, 코드, 앞선 작업의 기록과 대조합니다. 거기에 답이 있으면 묻지 않고, 그 답을 근거가 있는 자리와 함께 기록합니다. 이슈가 사람에게 남긴 선택 가운데 조사의 결과가 나와야 생기는 것은 묶음에 넣지 않습니다. 조사가 찾은 안 가운데 무엇을 택할지가 그런 선택입니다. 그 선택은 결과가 나온 뒤에 묻고, 코드와 정책으로 답할 수 없는 다른 질문처럼 그 작업 하나만 멈춰 둡니다. 묶음 뒤에 생긴 질문은 실행 도중에 사람에게 묻지 않습니다. 그 질문은 먼저 코드와 정책을 기준으로 결정합니다. 정책은 저장소의 문서, 설정, 앞선 작업의 기록입니다. 기록에 기본값이 있으면 그 기본값도 같은 방식으로 택합니다. orchestrator는 그렇게 내린 결정을 근거와 함께 묻지 않고 내린 결정으로 기록합니다. 코드와 정책으로 답할 수 없고 세션이 스스로 줄 수도 없는 것만 사람에게 갑니다. 권한, 인증 정보, 승인이 그런 것입니다. 그때 데몬이 그 작업 하나를 질문과 함께 멈춰 둡니다. Owlery는 GitHub 이슈에 질문을 올리지 않고, 거기서 답을 기다리는 것도 없습니다. 작업 하나를 멈춘 것이 다른 작업으로 번지지 않게 하는 것은 데몬의 코드입니다. 작업 하나를 멈춰 두어도 다른 작업에서는 아무것도 시작되지 않고, 멈추지 않고, 거절되지 않습니다. 사람이 앱에서 답하면 멈춰 둔 것이 풀립니다. 묻지 않고 내린 결정은 근거와 함께 작업의 기록에 있고, 데몬은 그것을 거기서 읽어 그 작업과 함께 보냅니다.

**데몬은 작업의 리뷰 회차와 수정 단계를 한 번에 한 단계씩 돌리고, 작업이 어디까지 왔는지는 커밋된 기록에서 읽습니다.** 데몬의 체인은 데몬이 직접 시작하고(`Daemon#startChain`), 브랜치에 기준 뒤의 커밋이 있는 작업에서 시작합니다. 창에는 이 체인을 시작하는 것이 없습니다. 마일스톤 3부터 이슈를 맡기면 시작되고(이슈 #55), 사람이 직접 모는 브랜치는 그 칸의 체인에서 인장을 받습니다. 회차는 파일만 읽는 새 proofer 세션입니다. 지적을 남긴 회차 뒤에는 crafter의 수정 단계가 오고, 그 단계의 모든 커밋은 뒤의 회차가 읽습니다. 데몬은 위치를 따로 보관하지 않습니다. 단계마다 그 앞에서 회차 기록, 작업의 결정과 질문, 브랜치의 head를 읽고, 그것들이 다음에 돌릴 단계를 정합니다. 그래서 실패했거나 멈췄거나 데몬이 끝나면서 끊긴 체인은 다음에 시작할 때 기록에서 이어 갑니다. 두 번째 회차나 그 뒤의 회차가 지적을 열어 둔 채 끝나면, 데몬은 그 회차 기록의 수정 단계 앞에서 orchestrator 에이전트에게 회차가 수렴하고 있는지 묻고, 그 답을 묻지 않고 내린 결정으로 기록합니다. 열린 지적이 없는 기록에서 뒤집힌 결정만 받아들이는 수정 단계 앞에서는 묻지 않고, 한 기록의 두 번째 수정 단계 앞에서도 묻지 않습니다. 체인이 회차의 상한에 이르면, 지적을 열어 둔 회차는 판단을 묻지 않고 체인을 멈추며, 다음에 시작할 때 그 기록의 수정 단계와 회차 하나를 더 돌립니다. 한 단계의 프로세스는 다음 단계가 시작하기 전에 끝냅니다. 실패했거나 멈춘 단계는 그 작업의 체인 하나만 멈추고, 작업의 줄이 이유를 말합니다.

**체인의 기준은 기록을 따르고, 기준을 떠난 브랜치는 거절합니다.** head에 1회차 기록이 있으면, 기준을 읽는 곳은 모두 그 기록의 `target:` 줄이 말하는 기준을 씁니다. 데몬의 체인, 체인 명령, 인장을 읽는 곳, PR 단계가 그렇습니다. 1회차 전에 데몬의 체인은 작업을 만들 때 기록한 기준을 씁니다. 체인 명령은 `--base`를 받고, 없으면 칸의 환경이 `OWLERY_BASE`로 말하는 기준을 씁니다. 기록된 커밋이 브랜치 head의 조상이 아니거나, 말한 기준과 head가 공유하는 커밋이 없으면 두 체인 모두 시작을 거절합니다. 거절하는 문장은 그 커밋이나 기준을 밝히고 다른 기준을 말하는 법을 알려 주며, 그 법은 체인 명령의 `--base`입니다. 앱에는 작업에 저장된 기준을 바꾸는 조작이 없고, 창이 그리는 개수는 여전히 저장된 기준을 읽습니다.

**리뷰 회차가 끝나면 데몬은 브랜치의 head 커밋에서 저장소의 전체 검사를 돌리고 그 커밋에 대한 판정을 sealer에게 묻습니다. 인장은 전체 검사가 통과한 그 커밋 말고는 어떤 커밋도 가리키지 않습니다.** 전체 검사는 기록 뿌리의 `config.json`에 있는 `Broad gate` 명령이고, 그 커밋에 담긴 값을 씁니다. 데몬은 이 명령을 작업의 워크트리에서 터미널 없이 돌리고, 이것은 다른 컴퓨터의 검사가 명령을 돌리는 방식과 같습니다. Owlery의 코드가 돌린 실행의 종료 코드만 결과로 칩니다. 데몬이 돌린 실행과, 칸에서 체인 명령의 `gate`가 돌린 실행이 그것입니다. 그래서 사람이 돌린 테스트는 전체 검사가 아니고, 전체 검사가 통과했다는 세션의 말도 전체 검사가 아닙니다. 통과한 실행은 `trail/gate.md`의 실행 블록으로 커밋합니다. 실패한 실행은 체인을 멈추고 아무것도 커밋하지 않으며, 명령이 출력한 내용은 데몬의 실행 폴더에 남아 작업 화면이 거기서 읽습니다. 컴퓨터의 부하가 넘친 동안, 명령이 0이 아닌 코드로 끝났거나 Owlery가 보내지 않은 신호로 끝난 실행은 먼저 혼자서 한 번 더 돌리고, 두 번째 실행이 실패해야 체인이 멈춥니다. 사람이 멈춘 실행, 전체 검사의 시간 제한에 걸려 멈춘 실행, 시작하지 못한 명령, 기록이 거부된 실행은 다시 돌리지 않습니다. 부하가 넘쳤다는 것은 실행 중 어느 때든 다른 무거운 명령이 함께 돌았거나, 실행이 시작할 때 데몬이 읽은 부하 평균이 코어 수보다 높았다는 뜻입니다. 두 번째 실행은 다른 무거운 명령이 하나도 돌지 않을 때까지 기다리고, 부하 평균이 코어 수 이하로 내려올 때까지 길어야 10분을 더 기다립니다. 두 번째 실행이 통과하면 `trail/gate.md`가 실행 블록 위의 문장으로 앞선 실행을 밝히고, 실패하면 체인의 문장이 두 실행을 모두 밝힙니다. sealer는 파일만 읽는 새 역할 세션이고, 그 답이 곧 판정입니다. `sealed` 판정이면 체인은 거기서 쉽니다. `withheld` 판정이면 체인이 멈추고, 그 까닭이 작업의 줄에 나옵니다. `undecided` 판정의 질문은 orchestrator 에이전트가 먼저 코드와 정책으로 정하고, 그것으로 답할 수 없을 때만 작업을 멈춰 둡니다. 칸에서는 세션이 정하거나, 그 칸에서 사람에게 묻습니다. 전체 검사가 통과한 커밋 뒤에 마감 기록 말고 다른 것을 바꾼 커밋이 오면 전체 검사를 다시 돌려야 하고, 작업의 기록 밖을 바꾼 커밋이면 그 앞에 회차가 먼저 와야 합니다.

**인장이 찍히면 데몬은 브랜치의 head로 읽은 커밋을 올리고 사람의 `gh`로 PR을 열며, 인장 없이 끝난 체인은 PR을 열지 않습니다.** 이 단계는 작업의 `routing.md`가 작업을 PR로 보낼 때만 돕니다. 데몬은 사람의 git으로 리모트 하나에만 올리고 강제로 올리지 않습니다. push는 그 커밋을 ID로 지정하므로, 읽은 뒤에 브랜치에 올라온 커밋은 그 인장을 단 PR에 들어가지 않습니다. `gh`는 PR을 찾고, 만들고, 고치고, 읽는 데에만 부르며, 리뷰를 쓰지 않고 머지하지 않습니다. 토큰은 읽지도 보관하지도 않습니다. 이 단계는 아무것도 커밋하지 않습니다. 인장이 찍힌 커밋 뒤에 마감 기록이 아닌 커밋이 오면 인장이 깨지기 때문입니다. 이미 열린 PR이 있는 브랜치는 인장 구역만 바뀌고, 두 번째 PR은 열리지 않습니다. 실패한 단계는 그 작업의 체인 하나만 멈추고 작업의 줄이 이유를 말하며, 인장은 그대로 섭니다. 그 뒤로 데몬은 클라이언트가 붙어 있는 동안 타이머에 맞춰 `gh` 호출 한 번으로 열린 PR을 다시 읽고, 그 일로 에이전트도 프로세스도 Mac을 깨워 두는 잠금도 두지 않습니다. 작업의 줄은 검사가 도는지, 통과했는지, 실패했는지를 보이고 처음 실패한 검사의 이름을 말합니다. 작업의 PR이 무엇인지는 데몬의 상태이고 GitHub에서 다시 읽으며, 저장소의 어떤 기록에도 없습니다.

**저장소는 무거운 명령을 정해 두고, 데몬은 모든 작업과 저장소를 통틀어 그 컴퓨터의 상한만큼만 무거운 명령을 동시에 돌립니다.** 무거운 명령은 컴퓨터 전체에 부하를 주는 명령입니다. 전체 검사는 언제나 무거운 명령이고, 기록 뿌리의 `config.json`이 `Heavy commands` 아래에 적은 명령도 무거운 명령입니다. 세션은 이름 붙은 명령을 실행기로 돌립니다. 실행기는 칸의 환경 변수 `OWLERY_RUN`이 가리키는 프로그램입니다. 데몬의 체인과 체인 명령의 `gate`는 전체 검사의 차례를 직접 청합니다. 상한이 찬 동안 청한 명령은 기다리고, 그 작업의 줄에는 "Waiting for the machine"이 나옵니다. 기다리는 명령은 사람이 먼저 기다리는 순서로 돕니다. 전체 검사가 먼저이고, 리뷰 중인 작업의 명령, 아직 만드는 중인 작업의 명령, 어떤 작업의 기록도 가리키지 않는 폴더의 명령이 그 뒤를 따르며, 같은 자리에서는 먼저 청한 명령이 먼저 돕니다. 자리는 커밋된 기록에서 읽고, 데몬은 대기열을 저장하지 않습니다. 도는 명령은 기다리는 명령 때문에 멈추지 않으며, 차례는 명령이 끝나거나 차례를 청한 프로세스가 사라지면 끝납니다. 답하는 데몬이 없으면 명령은 바로 돌고 그렇게 말합니다. 실행기를 거치지 않은 명령은 차례를 받지 않습니다.

| 옵션 | 쓰는 자리 |
|---|---|
| `-p`, `--input-format stream-json`, `--output-format stream-json` | 역할 세션. 데몬이 문장을 보내고 이벤트를 받습니다 |
| `--plugin-dir <path>` | 앱 안의 Owlery 역할 묶음을 그 세션에만 싣습니다. 역할 세션, 그리고 owl 체인을 쓰는 폴더의 Claude Code 칸입니다 |

### AgenticSeal의 변경을 가져오는 법

Owlery는 AgenticSeal의 릴리스를 가져오지 않습니다([AgenticSeal에서 가져오는 것](#agenticseal에서-가져오는-것)). Owlery 역할 묶음은 앱과 함께 릴리스되므로, 앱이 실행하는 순서와 묶음이 어긋나지 않습니다. 묶음이나 PR 검사의 스크립트를 고치는 일은 Owlery의 작업이고, 그때 테스트를 함께 돌립니다.

## 라이선스와 다른 프로젝트의 코드

Owlery는 Apache License 2.0으로 냅니다.

- **Apache-2.0을 고른 까닭.** 오픈소스 메인테이너와 회사가 가장 쉽게 받아들이고, 특허 사용 허락이 들어 있습니다. Apache-2.0 프로젝트에서 가져오는 코드와 조건이 같아 고지를 관리하기도 단순합니다. 카피레프트 라이선스(GPL)는 다른 제품이 우리 코드를 복사하지 못하게 막아 줍니다. 하지만 여기서는 그 보호가 약합니다. AgenticSeal 프로세스가 나온 AgenticSeal이 이미 MIT이고, 발상은 어떤 라이선스로도 막을 수 없기 때문입니다. 대신 비용은 분명합니다. 많은 회사가 GPL 코드에 기여하거나 가져다 쓰는 것을 막고, 플러그인을 만드는 사람은 자기 플러그인이 어떤 라이선스를 따라야 하는지 판단하기 어렵고, GPL은 나중에 휴대폰 앱이 거쳐야 할 iOS App Store 약관과 충돌합니다. Apache-2.0에서 카피레프트로 바꾸는 것은 나중에도 할 수 있습니다. 반대로 바꾸려면 외부 기여자 모두의 동의가 필요합니다.
- **MIT나 Apache-2.0 프로젝트의 코드는 가져와 고쳐 씁니다.** MIT 코드는 저작권 고지와 라이선스 문구를 함께 둡니다. Apache-2.0 코드는 LICENSE와 NOTICE를 함께 가져오고, 고친 파일마다 고쳤다는 표시를 남깁니다. 그런 프로젝트 안에서도 라이선스가 따로 붙은 파일은 하나씩 확인합니다.
- **GPL이나 AGPL 프로젝트의 코드는 가져오지 않습니다.** 코드를 가져오면 앱 전체가 같은 라이선스를 따라야 하므로, 발상만 씁니다.
- **다른 제품의 이름과 로고는 쓰지 않습니다.** 라이선스와 별개인 상표 문제입니다.
- **이름과 엠블럼은 Apache 라이선스의 대상이 아닙니다.** Owlery와 AgenticSeal이라는 이름, 올빼미 엠블럼, 저장소에 있는 그 그림은 권리를 보유하며, 무엇이 적용되는지는 저장소 최상위의 `TRADEMARKS.md`가 밝힙니다.
- **라이선스를 바꿀 여지를 남깁니다.** 외부 기여를 받기 시작할 때 기여자 동의서(CLA)를 두어, 이후 버전의 라이선스를 바꿀 수 있게 합니다. 꼭 요구할지는 「결정을 남겨 둔 것」에 있습니다.

## 플랫폼과 그 순서

첫 버전은 macOS 데스크톱 앱 하나입니다. 다른 플랫폼은 아래 순서로 더합니다.

| 순서 | 플랫폼 | 내는 방법 | 넘어가는 조건 |
|---|---|---|---|
| 1 | macOS 데스크톱 | 서명과 공증을 거치고, GitHub Releases로 업데이트 | |

- **안드로이드는 Play 스토어 밖에서 시작합니다.** 첫 사용자인 오픈소스 메인테이너는 APK를 직접 설치하는 데 익숙합니다. Google 개발자 계정은 처음 한 번 25달러입니다.
- **안드로이드를 내기 전에 알아 둘 것.** 그 단계를 시작할 때 정하고, 지금 정하지는 않습니다.
  - **Google의 개발자 인증.** Google은 Play 스토어 밖에서 설치하는 앱도 인증된 개발자의 것이어야 하게 바꾸고 있습니다. 2026-09-30에 네 나라에서 시작했고 2027년부터 전 세계로 넓힙니다. 인증받지 않은 앱도 설치는 되지만, 개발자 모드를 켜고 재부팅하고 24시간을 기다려야 합니다. 인증은 Play 스토어 등록과 별개이고 같은 25달러입니다. 그래서 이 규칙이 우리 사용자가 있는 나라에 닿으면, Play 스토어에 올리기 전이라도 인증을 받습니다.
  - **패키지 이름과 서명 키는 첫 출시부터 고정합니다.** 나중에 사용자가 다시 설치하지 않고 Play 스토어로 옮기려면 둘이 같아야 합니다. 서명 키를 잃으면 기존 사용자에게 업데이트를 보낼 수 없으므로 백업해 둡니다.
  - **푸시는 처음에는 Google 서비스에 기대지 않습니다.** Firebase Cloud Messaging(FCM)을 쓰면 그 키를 쥔 우리 서버가 필요하고, F-Droid에 올릴 수 없습니다. 앱이 데몬과 이어져 있을 때는 그 연결로 알림을 받습니다. 끊겨 있을 때는 UnifiedPush가 사용자가 고른 푸시 앱(ntfy 등)으로 알림을 전합니다. FCM은 Play 스토어에 등록할 때 붙입니다.
  - **업데이트.** 앱이 GitHub Releases의 새 버전을 사용자에게 알려 줍니다. 소스에서 직접 빌드하고 몇 주씩 심사하는 F-Droid는 앱이 안정된 뒤에 올립니다.
- **리눅스**는 Electron이라 빌드하는 비용이 작습니다. macOS와 함께 커뮤니티 빌드로 낼지는 「결정을 남겨 둔 것」에 있습니다.

**macOS 앱은 Apple 실리콘용 `.dmg`로 내고, 그 버전의 태그에 달린 GitHub 릴리스에 붙이며, 워크플로 하나가 빌드합니다.** 워크플로는 태그 `v<version>`이 푸시될 때와 사람이 태그를 지정해 요청할 때 돌고, PR에서는 돌지 않습니다. 그래서 포크가 시작한 실행은 서명 시크릿을 읽지 못합니다. 저장소에 Developer ID 인증서와 공증 키가 있으면 워크플로는 hardened runtime으로 앱에 서명하고 Apple의 공증을 받습니다. 하나도 없으면 앱에 ad hoc 서명을 하고, macOS는 처음 열 때 시스템 설정의 개인정보 보호 및 보안에서 허용하라고 사람에게 묻습니다. 일부만 있으면 실행이 실패하고 빠진 것의 이름을 알리므로, 서명만 하고 공증하지 않은 빌드는 나가지 않습니다. 패키지는 앱의 파일을 아카이브가 아니라 폴더로 담습니다. 사용자의 `claude`가 그 폴더에서 역할 번들을 읽고, 데몬이 자기 빌드를 알리려고 자기 스크립트를 거기서 읽기 때문입니다. 패키지된 앱은 사용자 데이터를 "Owlery" 아래에 두고, 체크아웃에서 시작한 앱의 것과 섞지 않습니다. ## 밖에서 붙기: 휴대폰과 다른 컴퓨터

첫 버전에는 모바일 앱이 없고, 휴대폰은 안드로이드가 먼저입니다([플랫폼과 그 순서](#플랫폼과-그-순서)). 그래도 휴대폰이나 다른 컴퓨터가 데몬에 닿는 방식은 지금 정해 둡니다. 데몬의 프로토콜 모양이 여기에 달려 있기 때문입니다.

- **먼저 직접 잇고, 안 될 때만 중계합니다.** 휴대폰과 데몬이 각각 밖으로 연결을 열어, 바깥에서 자기가 어떤 주소로 보이는지 알아냅니다. 그다음 둘이 같은 순간에 서로에게 보내면, 양쪽 공유기는 상대가 보낸 패킷을 답장으로 보고 들여보냅니다(홀 펀칭). 같은 와이파이가 아니어도, 다른 네트워크끼리 됩니다. 이렇게 이어지면 데이터는 어떤 서버도 지나지 않습니다. 상대마다 바깥 포트를 바꿔 붙이는 공유기나 UDP를 막는 네트워크처럼 직접 잇기에 실패할 때만 중계를 거칩니다.
- **iroh를 먼저 고려합니다.** iroh는 주소 대신 기기의 공개 키로 기기끼리 잇는 Rust 라이브러리입니다. 직접 연결을 먼저 시도하고, 안 되면 스스로 중계로 넘어갑니다. 데몬에서 쓸 공식 Node 패키지가 있습니다(`@number0/iroh`, Node 20.3 이상). 페어링은 데몬의 공개 키를 담은 QR 코드 하나가 되고, QUIC 연결이라 휴대폰이 와이파이와 LTE 사이를 옮겨도 이어집니다. React Native 휴대폰 앱에서 쓸 수 있는지는 확인하지 않았습니다. 쓸 수 없으면 WebRTC 데이터 채널이 그 자리를 맡습니다. Electron에 들어 있고, 중계(TURN)는 GB 단위로 빌려 씁니다.
- **모든 연결은 종단 간 암호화합니다.** 중계는 읽을 수 없는 바이트만 넘깁니다.
- **운영비는 작게 유지됩니다.** 직접 잇기에 실패한 연결만 중계를 씁니다. 중계는 iroh의 공개 중계나 우리가 띄운 것을 쓰고, 그 코드를 공개해 사용자가 직접 띄울 수도 있게 합니다. Tailscale이나 SSH로 잇는 길도 계속 지원하고, 이 길은 누구에게도 비용이 들지 않습니다.
- **푸시 알림에는 우리 서버가 필요합니다.** 휴대폰에 알림을 보내려면 Apple(APNs)과 Google(FCM)의 발송 키가 있어야 하는데, 이 키는 앱에 넣을 수 없습니다. 작은 푸시 서버가 이 키를 갖습니다.

## 휴대폰: 터미널 세션을 채팅 모양으로

휴대폰은 책상의 터미널에서 도는 세션을 채팅 모양으로 보여 줍니다. 원본은 터미널이고, 휴대폰은 같은 세션을 보는 두 번째 방법입니다. 휴대폰은 사람이 돌리는 모든 에이전트 CLI에 대해 이렇게 하고, 연결은 위의 길로만 오가며 어느 에이전트 회사의 서버도 거치지 않습니다. 휴대폰을 붙일 수 있게 지금부터 두 가지를 지킵니다. 데몬의 WebSocket 프로토콜을 데스크톱 화면에만 맞추지 않고, 화면 쪽에 상태를 두지 않습니다. 테마처럼 한 화면의 겉모습을 정하는 값은 여기서 말하는 상태가 아니며, 그 화면이 스스로 간직합니다.

Claude Code에서는 채팅의 각 부분이 아래에서 옵니다. 2026-11-18에 Owlery가 띄운 대화형 Claude Code 2.1.327 세션에서 훅을 하나씩 실제로 돌렸습니다. 훅 설정은 `--settings`로 넘겼고, 이 설정은 사용자와 프로젝트의 설정에 더해질 뿐 어느 쪽도 바꾸지 않습니다. 모든 이벤트에 `session_id`, `transcript_path`, `cwd`가 들어 있고, `SessionStart`를 뺀 모든 이벤트에 `permission_mode`가 들어 있습니다.

| 채팅의 부분 | 오는 곳 |
|---|---|
| 사람이 보낸 말 | `UserPromptSubmit` 훅 |
| 도구 호출과 그 결과 | `PreToolUse`, `PostToolUse`, `PostToolUseFailure` 훅 |
| 권한 요청 | `PermissionRequest` 훅. `tool_name`, `tool_input`, `permission_suggestions`가 오고 `tool_use_id`는 오지 않습니다. 훅이 휴대폰의 답을 기다렸다가 허용이나 거절을 돌려줍니다 |
| 한 턴의 마지막 답 | `Stop` 훅 입력의 `last_assistant_message` |
| 도구 호출 사이에 에이전트가 쓴 글 | Claude Code가 디스크에 남기는 세션 기록(`~/.claude/projects/<프로젝트>/<세션 ID>.jsonl`)에만 있습니다. 형식이 공개되지 않았으므로 보조로만 읽습니다. 데몬이 해석하지 못하면 휴대폰은 훅 이벤트만 보여 줍니다 |
| 에이전트가 묻는 질문과 선택지 | `AskUserQuestion` 도구의 `PreToolUse` 훅입니다. `tool_input.questions`에 질문마다 `question`, `header`, `options`, `multiSelect`가 있고, 선택지마다 `label`과 `description`이 있습니다. 2026-11-23에 Claude Code의 훅 문서와 2.1.330 실행 파일에서 읽었고, 띄워 보지는 않았습니다 |

- **휴대폰은 터미널 화면을 읽지 않습니다.** 작업함과 같은 규칙입니다. 상태와 내용은 이벤트와 파일에서 가져오고, 화면 출력에서 추측하지 않습니다.
- **휴대폰의 입력은 CLI가 입력을 기다릴 때만 터미널에 넣습니다.** 멈추기는 언제든 그 CLI의 중단 키로 넣습니다.
- **훅은 Owlery가 띄우는 세션에만 넣습니다.** 사용자의 설정 파일은 고치지 않습니다.
- **Codex CLI의 상태, 권한 요청, 대화가 어디서 오는지는 확인하지 않았습니다.** Codex 세션의 줄을 작업함에 들이는 마일스톤 4에서 확인하므로([마일스톤](roadmap.ko.md#마일스톤)), 휴대폰 앱을 만들기 전에 확인하게 됩니다.

에이전트 CLI 가운데에는 Claude Code의 Remote Control처럼 자체 원격 기능을 가진 것이 있습니다. Owlery는 그런 기능을 쓰지 않고, 켜지도 않습니다. 사용자가 어떤 세션에서 그 기능을 켜면 같은 권한 요청이 두 곳에 뜰 수 있습니다. 그때 어떻게 할지는 「결정을 남겨 둔 것」에 있습니다.

## 메모리 설계

**Owlery는 메모리를 될 수 있는 대로 적게 쓰고, 아무도 쓰지 않는 기능은 메모리를 쓰지 않습니다.** 기능이 쥐는 것은 그 기능을 열 때 만들고 닫을 때 놓습니다. 메모리는 열어 둔 작업 수가 아니라 지금 일하는 단계 수에 따라 늘게 합니다.

**장면마다 드는 메모리는 재서 공개하고, 기준 장면의 수치는 기능의 상한이 아닙니다.** 장면은 다시 잴 수 있게 적어 둔 앱의 한 상태입니다. 장면마다 잰 날짜, 커밋, 재는 방법을 함께 공개하고, 비교할 만한 제품에서 같은 장면을 잰 값을 나란히 둡니다. 첫 기준 장면은 터미널 넷이 보이는 앱 자체이고, 약 500 MB였습니다. 2026-11-19에 에이전트가 띄운 앱에서 491.1~503.4 MB를 쟀습니다(`apps/desktop/measurements/memory.md`). 비교할 제품에서 같은 장면을 잰 값은 아직 없습니다. 어떤 기능이 더해져 장면의 수치가 올라가도, 그 까닭으로 기능을 물리지 않습니다.

**기능을 먼저 만들고, 측정이 비용을 보여 주는 곳에서 효율을 높입니다.** 기능은 보통의 주의를 기울여, 쓰지 않는 동안 아무것도 쥐지 않게 만듭니다. 그다음 그 기능의 비용을 잽니다. 효율을 높이는 일은 측정이 비용을 보여 준 곳에서 합니다. 이슈 #9가 숨은 칸마다 창 안에 터미널 화면이 남아 있는 것을 찾아내 없앤 것이 그 예입니다. 기능을 만들기 전에 빠듯한 수치를 정해 두고 설계를 거기에 맞추지 않습니다. 기준 장면은 기능이 들어올 때마다 `apps/desktop`에서 `pnpm run measure:memory`로 다시 잽니다. 그래서 수치가 바뀌면 그것이 드러나고, 그에 맞춰 리팩터링을 일정에 넣습니다. 이 측정을 돌리는 검사는 없습니다. 테스트가 `test/memory.test.ts`를 돌려도 `OWLERY_MEASURE_MEMORY=1`이 없으면 아무것도 재지 않습니다.

**Owlery가 지키는 상한은 사람의 컴퓨터에서 읽어 정한 기본값이고, 사람이 그 값을 보고 바꿉니다.** 동시에 도는 에이전트 수와 worktree 수, 작업 하나의 화면이 한 번에 보이는 칸 수, 그리고 동시에 도는 무거운 명령의 수가 그 상한입니다. 상한마다 그 컴퓨터의 메모리, 코어, 남은 디스크에서 제안값을 내고, 다른 컴퓨터에서 잰 장면의 수치에서 내지 않습니다. 이 상한은 릴리스 0.0.4가 만들었습니다(이슈 #32와 #134). 마일스톤 3의 역할 세션은 이 상한 아래에서 시작합니다([마일스톤](roadmap.ko.md#마일스톤)). 상한마다의 규칙은 이 절의 끝에 있습니다.

아래 네 규칙은 앱이 도는 동안 적게 쥐게 하는 방법입니다.

| 규칙 | 까닭 |
|---|---|
| 터미널 화면과 WebGL 연결은 보이는 칸 수만큼만 만들어 돌려 씁니다. 숨은 터미널의 출력은 데몬이 갖습니다 | 숨긴 WebGL 캔버스도 화면 크기만 한 그림 버퍼를 계속 들고 있어서, 터미널마다 캔버스를 두면 GPU 프로세스 하나가 1 GB를 넘을 수 있습니다(2026-11-17 측정). 화면 객체를 새로 만드는 비용(약 160~190 ms)은 돌려 쓰면 대부분 피할 것 같습니다 |
| 화면에 있는 칸은 스크롤백이 정한 줄 수만큼 기록을 둡니다. 어느 컴퓨터에서나 5,000줄이고, 사람이 Machine 대화 상자에서 1,000부터 50,000까지 다른 수로 정할 수 있습니다. 데몬은 그 한 줄마다 칸의 출력 256글자를 갖고 있고, 그보다 오래된 출력은 어디에도 남지 않습니다 | 같은 창에 터미널 하나를 더할 때 기록 1,000줄이면 약 14 MB, 5,000줄이면 약 20 MB가 늘었습니다. 창에서 기록 한 줄은 열 하나마다 12바이트를 쓰므로, 100열 5,000줄은 약 6 MB, 50,000줄은 약 60 MB입니다. 화면에 있는 칸에서만, 그리고 칸이 그만큼 찍은 뒤에만 그렇습니다 |
| 창은 하나만 씁니다. 내장 브라우저는 두지 않습니다 | 창을 하나 더할 때마다 약 130 MB가 늘었습니다 |
| AgenticSeal 프로세스에서 끝난 단계의 Claude 프로세스는 끝냅니다. 이어서 말을 걸 때는 resume을 씁니다. 사용자가 터미널에서 띄운 세션은 사용자가 닫습니다 | Claude 프로세스 하나가 345~679 MB를 씁니다 |

GPU 터미널 한도는 Chromium 기본값인 16을 그대로 씁니다. 한 화면에 17칸 이상은 둘 수 없다는 뜻입니다. 렌더러의 메모리 상한도 올리지 않습니다.

작업 하나의 화면은 칸 상한이 정한 수까지만 칸을 나란히 보입니다. 데몬은 메모리가 16 GB보다 적은 컴퓨터에서 4를, 16 GB부터 6을, 32 GB부터 8을 제안하고, 사람은 1부터 16까지 정합니다. 넷은 기준 장면을 잰 칸 수입니다. 그 작업의 나머지 칸은 탭으로 남고, 화면에 없는 칸은 창 안에 터미널 화면을 두지 않습니다. 데몬은 칸마다 출력의 마지막 글자를 스크롤백 한 줄에 256글자씩 쳐서 갖고 있고, 기본값에서는 1,280,000글자입니다. 칸이 다시 화면에 나올 때마다 창은 그 출력을 다시 받아 칸을 그립니다. 그래서 다시 나온 칸은 그 글자들이 그리는 만큼만 기록을 갖습니다. 에이전트의 CLI처럼 화면을 자주 다시 그리는 프로그램의 칸에서는 스크롤백이 정한 줄 수보다 적습니다. 스크롤백을 바꾸면 살아 있는 모든 칸의 한도가 함께 바뀌고, 줄이면 오래된 출력부터 버립니다. 데몬이 오래된 출력을 버릴 때는, 남기는 앞쪽 4,096글자 안에 줄바꿈이 있으면 남긴 출력이 줄의 처음에서 시작하게 자릅니다. 그래야 다시 그릴 때 이스케이프 시퀀스 한가운데서 시작하지 않습니다. 줄바꿈이 그보다 뒤에 있으면 글자 수로 센 자리에서 자르므로, 전체 화면 프로그램처럼 줄바꿈 없이 길게 찍는 프로그램도 그 출력을 잃지 않습니다.

**데몬은 가장 늦게 끝난 headless 세션 50개와, 아직 일하는 세션을 모두 지닙니다.** 메모리에 든 목록은 창이 최근 세션을 보여 주는 데 쓰이고, 남아야 하는 결과는 저장소의 기록에 둡니다([기록은 저장소에 커밋합니다](#기록은-저장소에-커밋합니다)). 한도가 없으면 목록은 데몬이 끝날 때까지 모든 실행의 모든 단계만큼 자랍니다. 먼저 끝난 세션이 먼저 빠지고, 모든 클라이언트가 그것을 전해 받습니다.
check: apps/desktop/test/daemon.test.ts

**다시 화면에 나온 칸은, 창이 그 칸의 출력을 다시 그리기 전까지 사람이 거기에 입력하거나 붙여넣은 것을 받지 않습니다.** 그 칸이 쓰는 터미널 화면은 앞의 칸이 떠날 때 비워졌습니다. 출력을 다시 그리기 전의 터미널에는 괄호로 감싼 붙여넣기처럼 칸의 프로그램이 켠 모드가 없어서, 붙여넣은 글이나 키를 그 모드 없이 바이트로 바꾸게 됩니다. 그 사이에 입력한 것은 보관하지 않고 버립니다. 터미널은 키가 눌린 때에 그 키를 바이트로 바꾸기 때문입니다. 창이 페이지를 불러온 뒤 처음 그리는 칸은 예외입니다. 그 출력에 든 질문에 터미널이 하는 답이 칸의 프로그램에 닿아야 하고, 그 답은 사람의 키와 같은 길로 나가기 때문입니다.
check: apps/desktop/test/view.test.ts apps/desktop/test/terminal-basics.test.ts

**데몬은 시작할 때 컴퓨터를 읽고, 상한마다 제안값을 그 값에 쓴 수치와 함께 냅니다.** 읽는 것은 메모리, 코어, 성능 코어, 그리고 worktree 폴더의 남은 디스크입니다. 에이전트 상한은 성능 코어 수와, 메모리의 절반을 에이전트 하나의 프로세스가 쓰는 양으로 나눈 값 가운데 작은 쪽입니다. 성능 코어 수는 macOS가 `hw.perflevel0.physicalcpu`로 주는 값이고, macOS가 그 값을 주지 않으면 전체 코어 수입니다. 그 양은 데몬이 이 컴퓨터에서 에이전트 다섯을 잴 때까지 679 MB이고, 그 뒤로는 마지막으로 잰 스물 가운데 가장 큰 값입니다. 데몬은 에이전트가 살아 있는 동안 1분에 한 번 잽니다. worktree 상한은 지금 있는 worktree 수에, 남은 디스크에서 10 GB를 뺀 값을 이 컴퓨터에서 잰 가장 큰 worktree로 나눈 수를 더한 값이고, 하나를 잴 때까지는 제안하지 않습니다. 사람이 정한 상한은 데몬의 상태입니다. 데몬의 실행 폴더에 두고 모든 클라이언트에 보내며, 사람이 제안값으로 되돌릴 때까지 그대로입니다.
check: apps/desktop/test/machine.test.ts apps/desktop/test/daemon.test.ts

**에이전트 상한을 넘는 headless 세션은 대기열에서 기다리고, 사람이 손으로 여는 것은 기다리지 않습니다.** 도는 에이전트는 상태를 알려 주는 종류의 살아 있는 칸과 일하고 있는 headless 세션입니다. 그 수가 상한에 닿아 있을 때 요청된 headless 세션은 대기 중으로 목록에 오르고, 수가 줄거나 상한이 오를 때까지 프로세스를 시작하지 않습니다. 이미 도는 체인의 단계가 먼저 시작하고, 그다음이 체인의 첫 단계입니다. 칸은 언제나 열리고 수에 들어가며, 상한을 넘었다고 끝내는 것은 없습니다. 작업의 줄은 컴퓨터를 기다린다는 것과 대기열에서의 순서를 말하고, 단계의 시간은 시작한 때부터 셉니다.
check: apps/desktop/test/daemon.test.ts apps/desktop/test/chain.test.ts apps/desktop/test/view.test.ts

**작업을 만들 때 디스크가 그 worktree를 담지 못하거나 worktree 수가 상한에 닿아 있으면 경고하고, 사람이 만들라고 하면 만듭니다.** 데몬은 worktree마다 설정이 끝난 뒤 한 번 크기를 재고, 한 저장소의 새 worktree는 그 저장소에서 잰 가장 큰 worktree만큼 든다고 봅니다. 만드는 창은 남은 디스크, 남겨 두는 10 GB, 그리고 그 크기를 말합니다. 사람이 무엇을 지울지 알고 있을 수 있으므로 아무것도 거절하지 않습니다.

## 화면 프레임워크: Electron

화면은 Electron으로 만듭니다. 시스템 웹뷰를 쓰는 프레임워크가 메모리를 조금 덜 썼지만(같은 시나리오 8개에서 최대 약 10%, 2026-11-17 측정) 그 차이로 고를 정도는 아니었고, 아래 네 가지로 정했습니다.

- **세 OS에서 같은 화면:** Chromium을 함께 넣으므로 macOS, Windows, Linux에서 같은 엔진으로 그립니다.
- **macOS 한글 입력:** 터미널 부품(xterm.js)에서 알려진 입력 문제가 없습니다. 2026-11-18에 사람이 Owlery 터미널 창에 두벌식으로 한글을 셸과 Claude Code 안에서 쳤고, 셸은 친 그대로 UTF-8로 받았습니다.
- **Linux:** Wayland, Nvidia, WebGL에서 열린 문제가 적습니다.
- **업데이트:** 바뀐 부분만 받는 차분 업데이트를 씁니다. 대신 앱이 큽니다(.app 253 MB).

macOS에서도 Electron을 씁니다(2026-11-18 결정). macOS만 시스템 웹뷰로 옮기는 안은 두 기준으로 따졌습니다. 한글 입력은 Electron 창에서 됩니다(위). 앱이 얼마나 가벼워지는가는, 잰 차이가 최대 약 10%라 결정할 만큼 크지 않습니다.

**창은 Owlery 자신의 화면만 보이고, 두 번째 창은 열리지 않습니다.** 메인 프로세스는 창이 자기 화면을 다시 읽는 것 말고는 어디로도 이동하지 못하게 막고, 새 창도 모두 막습니다. 그래서 칸에 찍힌 글자는 창을 바꾸거나 Owlery 안에 웹 페이지를 열지 못합니다. 사람이 창에 끌어다 놓은 파일도 창을 바꾸지 못합니다. 창은 끌어 놓기로 이동하지 않습니다. 칸에 찍힌 링크는 Command 키를 누른 채 클릭하면 시스템 브라우저에서 열리고, 주소가 `http`나 `https`일 때만 열립니다. 칸에 찍힌 경로는 메인 프로세스가 그 자리에서 파일이나 폴더를 찾았을 때만 링크가 됩니다. Command 키를 누른 채 클릭하면, 다른 작업의 worktree는 그 작업의 화면을 앞으로 가져옵니다. 파일은 사람이 Settings에서 고른 편집기로, 칸이 경로 뒤에 찍은 줄과 열에서 열리고, Shift 키를 함께 누른 클릭은 그 파일을 Finder에서 보여 줍니다. Owlery는 파일을 자기 목록에 있는 편집기로만 열고 다른 앱으로는 열지 않습니다. 칸에 찍힌 경로는 사람이 쓴 것이 아니고, 시스템이 그 파일에 정해 둔 앱은 파일을 실행할 수 있기 때문입니다. 사람이 Finder를 골랐거나 Mac에 목록의 편집기가 없으면, 클릭은 파일을 들어 있는 폴더에서 선택된 채로 보여 줍니다. 폴더는 Finder에서 열리지만, 이름의 첫 글자 뒤에 점이 있고 체크아웃이 아닌 폴더는 파일처럼 선택된 채로 보입니다. `OWLERY_BACKGROUND=1`로 띄운 앱은 시스템 브라우저와 Finder에서 아무것도 열지 않고 폴더를 고르는 대화 상자도 열지 않으며, 시스템의 클립보드 대신 자기 클립보드를 읽고 씁니다. 그 앱의 화면은 시스템 알림을 띄우지 않고, 띄웠을 알림의 제목과 본문을 간직해 두며, 테스트는 그것을 읽습니다.

## 만들기 전에 잴 것

- **직접 연결 비율:** 국내 LTE와 5G, 회사 와이파이, 카페 와이파이에서 휴대폰이 중계 없이 데몬에 닿는 비율을 iroh와 WebRTC 각각 잽니다([밖에서 붙기](#밖에서-붙기-휴대폰과-다른-컴퓨터)).
- **화면을 돌려 쓸 때의 전환 지연:** 기록 1,000줄과 5,000줄, 200열 기준으로, macOS, Windows, Linux 각각 잽니다.
- **보이는 터미널 하나가 쓰는 GPU 메모리:** 우리 칸 크기에서 WebGL과 DOM 각각, Retina와 4K 각각 잽니다.
- **데몬의 CPU:** 에이전트 10개가 동시에 출력할 때 터미널 출력을 해석하는 비용을 잽니다.
- **ACP의 범위:** 어떤 에이전트가 ACP로 붙고, 권한 요청, 슬래시 명령, 중간에 끼어들기 가운데 무엇을 지원하는지 확인합니다. 지원하지 않는 기능은 터미널로 열기로 메웁니다.
- **resume의 시간과 토큰:** 멈춘 지 5분 이내와 이후로 나눠 잽니다.
- **권한 요청 훅이 휴대폰의 답을 얼마나 기다릴 수 있는가:** 훅의 시간 제한과, 그 시간이 다 됐을 때 CLI가 무엇을 하는지를 Claude Code와 Codex 각각 확인합니다([휴대폰: 터미널 세션을 채팅 모양으로](#휴대폰-터미널-세션을-채팅-모양으로)).
- **구독 로그인에서 비용 칸이 뜻하는 것:** 헤드리스 결과 이벤트에 `total_cost_usd`, `usage`, `modelUsage`가 구독 로그인에서도 들어 있는 것은 확인했습니다(2026-11-17). 구독은 토큰마다 청구되지 않으므로 이 값은 API 가격으로 환산한 값으로 보입니다. Claude Code는 모델의 요청에 가격표를 적용해 비용을 매기고, 어느 가격표인지를 결과에 모델마다 적습니다(`costBasis`: 내장된 정가, 조직이 정한 요율, 또는 없음). 구독 로그인의 결과에는 정가가 적혀 있었습니다(2026-11-23에 2.1.330 실행 파일과 기록해 둔 스트림에서 읽음). 견줘 보기 전까지 장부는 세션의 로그인이 API 키를 가리키지 않으면 모든 비용을 환산한 값으로 표시합니다([에이전트 어댑터](#에이전트-어댑터)). 남은 일은 같은 작업의 값을 API 키 로그인에서 재어 그 계정의 청구서와 견주는 것이고, 이슈 #140이 합니다.
- **사용량 값:** 구독 로그인으로 세션을 돌려 상태줄 JSON의 `rate_limits`를 확인합니다. `rate_limit_event`의 필드는 값을 바꿔 보관한 역할 세션의 실행 기록 둘에 있으므로, 남은 것은 실제 값으로 읽는 쓴 비율의 범위, 초기화 시각의 단위, 한 턴이 나열하는 구간, 새로 받기에 드는 비용입니다. Codex에 비슷한 값이 있는지도 봅니다([사용량 읽기](#사용량-읽기)).
- **AgenticSeal의 단계별 비용:** `seal payload`와 `seal cost`로 잽니다.
- **구조로 옮긴 규칙만큼 줄어드는 시작 토큰:** 2026-11-17 `seal payload`로 잰 에이전트마다의 시작 묶음(에이전트 정의, core, 에이전트 계약, CLAUDE.md)은 framer 약 12,000, crafter, proofer, sealer 각 약 10,500 토큰입니다(3.2바이트당 1토큰으로 어림). 작업 하나에 proofer가 여러 회차 뜨므로 이 묶음을 여러 번 냅니다. 문장마다 "판단이 필요한가, 데몬이나 권한이나 출력 형식(`--json-schema`)으로 강제할 수 있는가"로 가르고, 강제한 문장을 뺀 뒤의 묶음을 다시 잽니다. 같은 묶음은 프롬프트 캐시로 싸게 읽히므로, 절감은 바이트 비율보다 작을 것 같습니다. 역할 묶음으로 띄운 실제 proofer 라운드 하나는 33,249 토큰에서 시작했고, 이는 2.1.327에서 기록한 보통 세션보다 약 15,600 토큰 많습니다(Claude Code 2.1.330에서 한 번 잼, 2026-11-22, 이슈 #38). 이 합계에는 Claude Code 자신의 프롬프트와 도구, 역할 정의, 그리고 36,274바이트인 덧붙인 규칙 파일이 들어 있고, 그 가운데 덧붙인 파일의 몫은 재지 않았습니다.
- **에이전트가 사람의 컴퓨터에서 앱을 띄울 때는 `OWLERY_BACKGROUND=1`을 주고, 사람이 띄울 때만 드러나는 것은 사람이 잽니다.** 이 값 없이 띄우면 창이 시스템의 포커스를 가져가서, 사람이 치던 키가 에이전트의 칸으로 들어가고 사람이 조합하던 한글이 끊깁니다. 이 값을 주면 창은 포커스를 가져가지 않고 Dock 아이콘 없이 열리며, 마우스를 받지 않습니다. 그래서 사람의 포인터가 창 위를 지나도 창 안에는 아무것도 닿지 않고, 사람의 클릭은 그 아래 창으로 갑니다. 그렇게 띄운 앱에는 Dock 아이콘, 메뉴 막대, 시스템의 포커스, 시스템의 포인터, 시스템 알림이 없고, 창은 불투명도 0으로 그려져 화면에 보이지 않습니다. 그래서 사람이 친 한글 줄, 앞에 둔 창의 메모리, 창 위를 지나는 포인터, 시스템이 띄운 알림, 화면에 보이는 창의 모습처럼 그 여섯 가운데 하나에 기대는 값은 사람이 돌려서 잽니다([마일스톤](roadmap.ko.md#마일스톤), `apps/desktop/measurements/memory.md`).

- **에이전트는 빌드한 앱 파일을, 그 파일의 테스트를 다루는 동안에는 그 파일 하나만 돌리고, 단계 하나나 리뷰를 반영한 수정 한 차례가 끝날 때 전부를 한 번에 돌립니다.** 빌드한 앱 파일은 테스트 도우미 `apps/desktop/test/built-app.ts`에서 `buildApp`을 가져오는 테스트 파일이고, 테스트 설정은 이 가져오기로 그런 파일을 나머지와 가릅니다. 대부분은 돌릴 때마다 빌드한 앱을 띄우고, 측정과 스크린샷처럼 자기 변수가 주어질 때만 띄우는 파일도 있습니다. `apps/desktop`에서 `OWLERY_BACKGROUND=1`을 주고 `pnpm run test:app`을 실행하면 그 파일들만 한 번에 하나씩 돕니다. 저장소의 전체 검사는 이 파일들을 나머지 테스트와 함께 다시 돌립니다. 앱을 띄우는 빌드한 앱 파일은 저마다 자기 앱을 띄웁니다. 앱 하나를 열어 두고 모든 파일이 함께 쓰면 파일 하나에 1초가 안 되는 시간이 줄어든다고 재었고, 파일 사이에 앱의 메인 프로세스가 쥔 것을 모두 비워야 하므로, 파일들은 앱을 함께 쓰지 않습니다(`apps/desktop/measurements/built-app-launch.md`, `pnpm run measure:launch`로 잼).
