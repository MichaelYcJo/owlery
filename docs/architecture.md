# Architecture: app, daemon, agent adapters, the Owl Chain

*English · [한국어](./architecture.ko.md)*

## Conclusions

- **The foundation is the inbox, the Owl Chain and the inspection sheet, and terminals are called on top.** The daemon runs the role sessions of the Owl Chain in the background by launching the user's Claude Code in headless mode (`claude -p`, with `stream-json` input and output), and their results appear in the inbox and on the inspection sheet. In the first version, a session the person drives is the agent's CLI opened in a terminal, so any CLI works there. A Claude Code pane of a repository on the Owl Chain, which is Owlery's default IADD workflow, also carries Owlery's role bundle for that session, and its session takes the branch it built through the review rounds, the broad gate and the inspector ([What each session loads](#what-each-session-loads)). Every other pane is the CLI as it is. A pane's state is read from hooks and from git. The desktop has no chat screen. The phone shows the same terminal session as a chat, read from the CLI's hooks and session log ([The phone: the terminal session as a chat](#the-phone-the-terminal-session-as-a-chat)).
- **Owlery provides no login, and a person may keep several.** Authentication belongs to the user's CLI. In Claude Code, the user picks a subscription login or an API key with `/login`, and Owlery only launches that CLI. A person with more than one login keeps each as an account, signs in to each with the CLI's own command, and binds an account to a repository, a work item or one session ([Authentication of the Claude adapter](#authentication-of-the-claude-adapter)).
- **Owlery is its own desktop app.** It is not a plugin on top of another app. The daemon launches the user's Claude Code directly, and launches role sessions detached from the user's environment, so there is no reason to hand sessions and terminals to another app. The inbox, the Owl Chain and the ledger read the same records inside one product.
- **The UI is built with Electron, and the daemon does the work.** The UI is a thin shell that connects to the daemon only over WebSocket. This keeps open the option of moving to another UI framework later.
- **Owlery's code runs the order of the Owl Chain, in the daemon's chain and in a pane's, and only judgment is left to an agent.**
- **Owlery is one tool that runs IADD, and the Owl Chain is its default workflow.** [docs/iadd.md](iadd.md) defines the method, its records and what a workflow is. Owlery started from AgenticSeal, a Claude Code plugin of the same method, and does not depend on it to run. Owlery ships the roles' agent definitions and skills, and the Owl Chain's workflow file and inspector module, inside the app and uses them as the defaults for role sessions ([Where Owlery started](#where-owlery-started)).
- **Staying light is a goal, and it comes from the app's scope and structure, not from the framework.** Light is relative: Owlery carries less than products that put a chat screen, a terminal, a full editor, a browser, team management and a cloud together. The app uses one window, draws only the visible terminals, and ends Claude processes that are not working.

## Overall layout

```
┌────────────────────────────────────────┐
│ Screen (Electron renderer)             │  inbox, inspection sheet, diffs, terminal panes for user sessions
│ Phone app (later)                      │  inbox, question batch, inspection, each terminal session as a chat
└───────────────────┬────────────────────┘
                    │ WebSocket (the same protocol for both)
┌───────────────────┴────────────────────┐
│ Daemon (outlives the app)              │  runs the order, keeps terminal output, records cost
│  ├─ User sessions (node-pty)           │  any agent CLI opened in a terminal, read through its hooks and session log
│  │   └─ The Owl Chain in a pane        │  a Claude Code pane of a repository on the Owl Chain: the role bundle, and the chain command, which is Owlery's code
│  ├─ The Owl Chain                      │  order, records and invariants are Owlery's code, shared by the daemon's chain and the chain command
│  │   └─ Role implementations           │  first version: the user's Claude Code (claude -p) + the Owlery role bundle shipped in the app
│  └─ git, gh                            │  watches branches and catches a commit that lands after the inspection
└────────────────────────────────────────┘
```

- **The daemon stays alive while the app restarts or updates.** This keeps work from being cut off when a review round runs long. What ends a session, and what brings it back, is in [What a session survives](#what-a-session-survives).
- **Agent state is judged from events, never guessed from what the terminal screen prints.** Role sessions report it through events in the structured output. A user session in a terminal reports it through its CLI's hooks, as Claude Code does, and through the session log the CLI writes where its hooks say nothing, as at a turn the person interrupts. For a CLI whose hooks we have not checked, the inbox shows only whether the branch changed. When the app puts a decision in front of a person, it must never do so by mistake.
- **Permission requests are handled as first-class events.** The daemon launches framer, crafter, proofer and inspector itself, so when one of them finishes or requests permission, the daemon learns of it first and passes it to the orchestrator agent or to the person. When an agent launches child agents of its own, the parent and child relationship is tracked as well. A user session's permission requests are answered in its terminal, or from the phone through the CLI's permission hook ([The phone: the terminal session as a chat](#the-phone-the-terminal-session-as-a-chat)).
- **A CLI that reports through hooks and has sent no event 10 seconds after its pane started is shown as waiting for the person.** A CLI asks its first questions before its session starts and sends no event while it asks. Claude Code 2.1.327, run on 2026-11-19, sent none of its hook events while it asked whether to trust the folder, which it asks in the first worktree of a repository the person has not trusted in Claude Code, and it sent its session's start within two seconds wherever it did not ask. The daemon judges this from the missing event and never from what the pane prints, and the session's first event replaces the state.
check: apps/desktop/test/daemon.test.ts
- **The daemon keeps the Mac from idle sleep while an agent works.** A sleeping Mac stops every agent, and the notification of an agent that begins to wait does not come until a person wakes the Mac. The daemon holds the block because it knows each session's state and is there while the app is closed. It holds it as one child process, `caffeinate -i -w` with the daemon's own process id, so the block ends when the daemon ends, however it ends. The display may still sleep while no heavy command runs, and a closed lid still puts the Mac to sleep. While a heavy command runs, the daemon keeps the display awake too and wakes it at the command's start, since a case that waits on what the page draws fails on a sleeping display. Under "Never" it holds neither. A person chooses among "While an agent works", which is the default, "Always" and "Never". "While an agent works" holds while a pane's live process or a headless session is working. "Always" holds while the daemon runs, and does not keep the daemon from exiting once it has nothing left to do. The choice is the daemon's state: it is kept in the daemon's run directory and sent to every client, so the window, and the phone once it comes, show the same one.
check: apps/desktop/test/keep-awake.test.ts apps/desktop/test/daemon.test.ts
- **A person stops the daemon from the app's menu, the app itself replaces only a daemon of another build that runs nothing, and the app stops no daemon but its own run folder's.** A plain Quit leaves the daemon and its sessions running. "Restart Daemon…" and "Quit Owlery Completely…" first name the running sessions and, apart from them, the sessions that wait for the machine, and on the person's confirmation the app ends the daemon. It sends a signal to the process that `daemon.json` in its run folder names, and only after a daemon answered at that file's address with that file's token. The first entry then starts the daemon of the running build, and the second quits the app and starts none. The app signals because a daemon of any build ends at a signal, and a daemon of an earlier build would not know a message added to the protocol. The daemon writes the SHA-256 of the script it runs into `daemon.json`. Where that value differs from the script the app would start and the daemon runs nothing, the window's load replaces the daemon without a question ([What a session survives](#what-a-session-survives)). Where it differs and the daemon runs something, the status line says the daemon is from another build and names "Restart Daemon…".
check: apps/desktop/test/daemon-client.test.ts apps/desktop/test/daemon-restart.test.ts apps/desktop/test/view.test.ts
- **A session whose agent asks the person a question is shown as waiting, with the question and the choices the agent offers, read from the event that asks.** An agent asks through an event of its own, as Claude Code does through the call of its question tool, and that event carries each question with its choices. The daemon reads them there and sends them as neutral values, and reads none of them from what the pane prints. The event that asks is sent before the person answers, so the session waits from that event on, whichever event the CLI sends after it.
check: apps/desktop/test/agent-events.test.ts apps/desktop/test/daemon.test.ts
- **A turn the person interrupts leaves its session waiting for the person, read from the session log.** Claude Code sends no hook event when a person interrupts a turn: its `Stop` hook does not run, and the pane asks what to do instead. It writes the interruption into the session log as an entry of the person's whose text is `[Request interrupted by user]` or `[Request interrupted by user for tool use]`. The recording `apps/desktop/test/fixtures/claude-interrupted-turn.json` holds both interruptions and names the version of Claude Code and the date it was made with. Every hook event names the log's file, and the daemon watches it only while the pane is working, reads the lines appended to it, and keeps none. The session then waits, and an end of the interrupted tool call that arrives later does not return it to working. An entry of a subagent's, and one written because a message the person sent cut the turn, is no such interruption. The log's format is not public, so a line the daemon cannot read changes nothing, and the hook events alone decide.
check: apps/desktop/test/daemon.test.ts apps/desktop/test/agent-events.test.ts apps/desktop/test/agent-state.test.ts apps/desktop/test/session-log.test.ts

- **A turn that ends on an API error leaves its session waiting for the person.** Claude Code runs its `StopFailure` hook in place of `Stop` for such a turn, and also for a subagent's turn that ends on an API error, whose input then names the subagent's `agent_id`; the daemon reads only the session's own, and the hook's input holds the error's kind in `error` and the error's text, as the pane shows it, in `last_assistant_message`. The daemon reads the event as a turn that failed: the session waits, and the inbox shows the error's text. The agent did not finish what it was asked, so the session is not called finished. `apps/desktop/test/fixtures/claude-stop-failure.json` holds the event as Claude Code's hooks reference gives it and names the date the reference was read and the version of Claude Code whose declared input was read beside it.
check: apps/desktop/test/agent-state.test.ts apps/desktop/test/agent-events.test.ts apps/desktop/test/hooks.test.ts apps/desktop/test/daemon.test.ts

- **A pane's process that has ended, and a pane whose start failed, leave no pseudo-terminal open in the daemon.** macOS gives the whole machine 511 pseudo-terminals by default (`kern.tty.ptmx_max`), and the daemon lives through every pane a person opens and closes. node-pty 1.1.0 opened a spare pseudo-terminal at each start on macOS and closed neither it nor the pane's slave in the daemon, so the daemon kept two descriptors for each pane it had ever started. Where the spawn failed after the master was open, as it does at the user's process limit, it left that master open too, though no process held it. The repository patches that version (`patches/`) the way node-pty's later source closes them.
check: apps/desktop/test/pty.test.ts

## What a session survives

**A session's process lives as long as the daemon that started it, and its conversation outlives both.** The daemon holds each pane's pseudo-terminal and each role session's pipes. So closing the window or quitting the app ends nothing, and the end of the daemon ends every process it started that takes the hangup of its terminal. Whether a Claude Code pane takes it has not been run, and the first real session of issue #61's work answers it. A role session has no terminal and leads a process group of its own. A stop of the daemon signals it and waits for its end, and whether it ends when the daemon crashes has not been run. Owlery does not keep those processes alive past their daemon. It keeps the daemon alive under them, and it brings the conversation back where the process is gone. The table says what each event does once the two rules below it are built, and each rule names the issue that builds it.

| What happens | A pane's process | A role session | What brings the work back |
|---|---|---|---|
| The window closes, or the app quits | Lives | Lives | Nothing is needed |
| The app is updated | Lives, in the daemon the earlier build started | Lives, and its run goes on | Nothing is needed. The daemon is replaced once it runs nothing, or on the person's word |
| A person chooses "Restart Daemon…" | Ends, after the dialog named it | Ends, after the dialog named it | A Claude Code pane resumes its conversation on the person's word, and a run starts the cut stage again |
| The daemon crashes, or the Mac restarts | Ends | Ends with the Mac. After a crash of the daemon, not run | The same |

**An update of the app ends no session: the daemon an earlier build started keeps running, and it is replaced only once it runs nothing or on the person's word.** The window of the newer build attaches to that daemon, and the status line says that it is of another build ([Overall layout](#overall-layout)). A daemon that holds no live pane, no role session that works or waits for the machine, and no running chain is replaced at the window's next load, without a question. The app reads this from the lists the daemon sends in answer to a hello, which a daemon of 0.0.2 and of each build after it sends, and it keeps a daemon whose lists it cannot read. An app replaces a daemon of one build once while the app runs. Where it finds a daemon of that build again, another app of that build runs on the same run folder, so it keeps the daemon and the status line says that the daemon is of another build. What goes with it is what its own exit lets go: the output of panes whose process has ended, and the list of role sessions that ended. A daemon that holds any of them is kept until the person chooses "Restart Daemon…", whose dialog names what runs. Replacing it sooner would cut an agent in the middle of a turn, and a cut turn is work that a person has to notice and ask for again. Until its daemon is replaced, the newer build shows what the older daemon can do: the window reads a field the daemon does not send as a feature that is off. A daemon answers a request whose kind it does not know with a refusal that says so, and the window shows in its place a sentence that names "Restart Daemon…". A daemon of a build before that answer leaves such a request unanswered. Against such a daemon the window ends each request but a creation that has no answer after 10 seconds, with a sentence that names "Restart Daemon…". A kept daemon goes on reading its own build's script, node-pty's native files and the role bundle, so an update has to leave those files in place. The `.dmg` of issue #78 holds the app's files as a folder ([Platforms and their order](#platforms-and-their-order)), and issue #266, which builds the update itself, holds a kept daemon to them. The daemon writes one line into its log when it stops, with why it stopped, how many panes were alive and how many agents were working. A daemon that an error of its own code ends writes the line before it ends, and a daemon that is killed, or whose Mac lost power, writes nothing. Either leaves its `daemon.json`, so the daemon that starts after it writes that the one before it ended without stopping. Each line carries the daemon's process id and the time, and holds counts and no prompt, path or title.
check: apps/desktop/test/daemon-client.test.ts apps/desktop/test/daemon-restart.test.ts apps/desktop/test/daemon.test.ts apps/desktop/test/view.test.ts

**A conversation comes back by its session id, after any end of its process.** The daemon keeps a record of each pane in its run folder: its work item, its kind, its folder, the name and the colour a person gave its tab, and the session id that its agent's hook events carry. Until that record is built, a pane's name and colour live on the daemon's session, as long as the pane. It keeps the latest id, because a person can move a pane to another conversation, as Claude Code's `/resume` does. After a restart of the daemon, a crash or a restart of the Mac, the work item's view offers the pane again, and on the person's word the daemon starts the agent's CLI on that conversation, which is `claude --resume <session ID>` for Claude Code. The process is new, so a turn that was under way is cut, and the pane says so. Before it resumes, the daemon checks that no process still runs that conversation: a process that ignores the hangup of its terminal outlives the daemon (probed 2026-11-22 with a stand-in for the agent), and one conversation is not opened in two processes. The id stays in the daemon. The protocol carries only that a kind of pane can resume ([Rules that keep it portable](#rules-that-keep-it-portable)). A shell pane has no conversation, and its process is not brought back. A run of the Owl Chain that the daemon's end cut starts the cut stage again from the records, which are committed. Before it does, the daemon checks that the cut stage's process no longer runs in that worktree, and ends it or waits where it still does, since whether a role session ends when its daemon crashes has not been run and one worktree does not hold two agents. Issue #61 builds the panes' part in milestone 4, and issue #55 the run's part in milestone 3. Until then a Claude Code pane returns to the latest conversation of its folder with `--continue` ([Options for launching Claude Code](#options-for-launching-claude-code)).

**Nothing holds the terminals apart from the daemon.** The ways below each keep a working agent alive through a restart of the daemon, which the two rules above leave to a person's choice. Each adds something that has to be kept in step with the daemon from build to build. They were weighed on 2026-11-22, and the decision is a row of [Open decisions](#open-decisions).

| Way | What it keeps that the two rules do not | What it costs | Decision |
|---|---|---|---|
| A process of its own that holds the terminals, which a new daemon adopts | A working agent, through a restart of the daemon and through its crash | A process that runs while any pane is open. One that held two pseudo-terminals and nothing else read 13.0 MB of macOS `phys_footprint` (probed 2026-11-22). A second protocol, between the daemon and that process, with versions of its own. Role sessions are no terminals and stay with the daemon | Not built |
| Handing each terminal's descriptor to the next daemon | A working agent, through a restart a person chose, and not through a crash | No process while unused. A handover both builds know, pane ids that go on from one daemon to the next, and a resize on a descriptor node-pty did not open, which node-pty 1.1.0 does not publish. A stand-in pane outlived its holder, and a process that inherited the pane's descriptor from the holder read the pane and resized it, and the pane took the new size (probed 2026-11-22). A handover to a daemon the stopping one did not start was not run | Not built. The first to weigh |
| A daemon for each version of the protocol | A session through an update, which the kept daemon already gives | A whole daemon for each generation, and the state one run folder holds once | Ruled out |
| tmux or zellij under each pane | The same as the process of its own | A program macOS does not include, and a second terminal between the agent and the pane, which takes over the pane's scrollback and needs settings of its own for Shift+Enter and for notifications | Ruled out. A person can run tmux inside a shell pane |
| Claude Code's own background sessions (`claude --bg`, `claude attach`) | A Claude Code session through a restart or a crash of the daemon, which the study expects from `claude --help` of 2.1.330 and did not run | It serves Claude Code alone. Whether Owlery's hook settings reach such a session is not known, and the session enters the person's own list of background agents | Not built, and not run |

## Agent adapters

When the daemon deals with an agent in a structured way, it goes only through one connector per vendor (an adapter). In the first version there is one real adapter, the Claude adapter, and it runs the role sessions of the Owl Chain. A user session in a terminal needs no adapter, because the daemon only launches its CLI in a terminal. Adapters exist only for role sessions. When another company's model takes a role (after the phone app), Codex app-server and ACP attach at the same place.

| Direction | What the adapter fits to the daemon |
|---|---|
| Daemon to agent | Sending text, interrupting and stopping midway, slash commands, answers to permission requests |
| Agent to daemon | Messages, tool calls, edited files, permission requests, state (working, waiting for input, finished), tokens and cost per model, usage limits |
| What the adapter declares | Its list of supported features. For example: does it accept slash commands, and is sending `!` output to the agent that CLI's habit |

**A headless run ends at its limit of 60 minutes or when a client stops it, and a CLI that does not exit at the signal is killed 2 seconds later.** Nothing else ends a CLI that never prints its result, and role sessions run while the person is away. The limit counts from the run's start. A long tool call prints nothing for minutes and a looping agent prints without end, so neither silence nor output tells a stuck run from a busy one. The adapter sends the termination signal to the CLI's process group, and the kill follows where the CLI is still running. Claude Code 2.1.330 exited 0.4 seconds after the signal while it waited for its first message (probed 2026-11-21). The app waits 5 seconds for the daemon to be gone, and the daemon waits for the runs it stops. A run stopped either way is `failed`, and its session says whether the limit or a request stopped it.
check: apps/desktop/test/daemon.test.ts apps/desktop/test/claude-adapter.test.ts

**A headless session carries the last 2,000 characters its CLI printed on its error stream, and the window shows them under a failed session's error.** A CLI that dies before its result names the cause only there. Claude Code 2.1.330 printed `error: unknown option '--no-such-option'` for an option it did not know, and `Error parsing streaming input line (type=unknown, 21 chars): SyntaxError` for an input line that was not JSON, and nothing on its output stream (probed 2026-11-21). A failure the CLI reports as an error result, such as no login or a refused API key, comes on the output stream, and the error stream stayed empty then. The last characters are kept because a crash prints its cause last.
check: apps/desktop/test/claude-adapter.test.ts apps/desktop/test/daemon.test.ts apps/desktop/test/view.test.ts

**A role session holds only the tools its role is granted, and the daemon answers its permission requests by that grant, never through the person.** A crafter at a fix pass holds the tools that read, search, run a command and write a file. The daemon allows its writes inside the work item's worktree, refuses its writes anywhere else, the role bundle's folder among them, and allows its commands. A proofer at a round, an inspector at the inspection and the orchestrator at a judgment hold no tool that writes a file. The daemon allows a proofer's and an inspector's commands, and refuses each of the orchestrator's commands that reaches it as a request. The operating system's sandbox refuses the commands of all three the worktree and the repository's git folder, and gives a proofer's and an inspector's a scratch folder of that session's own, so none of them changes the tree it judges. Every other request of a role session is refused. A refusal tells the agent why, and tells it to name the step that needed the call in its report. The head of a role's rules file names the tools the session holds. A written rule can be broken, and a refused call is not made. The daemon does not read a command to judge what it changes: it answers by the role alone, and the operating system's sandbox bounds where the command writes. The daemon starts a role session only through an adapter whose feature list names `role-tools` and `permission-requests`.
check: apps/desktop/test/daemon.test.ts apps/desktop/test/claude-adapter.test.ts apps/desktop/test/fake-adapter.test.ts

**A role session's commands run in the operating system's sandbox, which gives them the role's own place to write and refuses them the places the launch names.** The Claude adapter turns on Claude Code's own sandbox in the `--settings` value the launch already passes, and on macOS that sandbox runs each command under `sandbox-exec` with a profile Claude Code writes. A crafter's commands write in the work item's worktree and in the repository's git folder, less that folder's `hooks` and `config`, so a commit is made and a command plants no hook through either. A proofer's and an inspector's commands are given a scratch folder the daemon makes new when that session starts, `scratch/<session id>-<six characters>/` of the run folder, and are refused the worktree and the repository's git folder, so a command moves no branch of the repository it judges. The id alone does not name the scratch folder, because ids count from 1 in each daemon and a session of an earlier daemon may still write its folder. The prompt names the folder, the session's file tools read it, and the daemon removes it when the session's process has exited. The orchestrator's commands are given no place and are refused the same two folders, and every role's commands are refused the role bundle's folder. The daemon asks git for the repository's folder at every role's start, and a role whose worktree git names no repository for starts no session. A command cannot ask to run outside the sandbox (`allowUnsandboxedCommands: false`), a session whose sandbox cannot start does not start (`failIfUnavailable: true`), and a sandboxed command still reaches the daemon as a request (`autoAllowBashIfSandboxed: false`), so the grant answers it as before. A sandboxed command reaches no host but the loopback (`strictAllowlist: true` with no domain, and `allowLocalBinding: true`). The daemon itself listens on the loopback, and a client that names its port and its token has it act as a window does, outside the sandbox. Both stand in `daemon.json` of the run folder, so every role's commands are refused each read in the run folder (`filesystem.denyRead`). The launch gives back (`filesystem.allowRead`, which wins over `denyRead`) a proofer's and an inspector's session's scratch folder inside it, and `shell-snapshots` of the session's config folder. Claude Code starts each command from its snapshot of the person's shell setup, kept in that folder, and reports no error where it cannot read it. The folder Owlery makes for an added account stands in the run folder, so without the entry a session of such an account runs its commands without the person's aliases and functions; a folder the person handed over stands where it stood. The rest of that config folder stays refused, its `.claude.json` among it. On macOS the CLI keeps the account's login in the Keychain, which the refused read does not hold: a sandboxed command reached the Keychain service on Claude Code 2.1.332 and 2.1.329 (2026-11-27), and whether it reads a login there was not run. That a command starts from the snapshot under the entry was shown for a config folder that holds the snapshots itself (2026-11-27, Claude Code 2.1.332 and 2.1.329, `pnpm run role:refusal` against a stand-in model). It was shown the same way for an account's folder that Owlery made, where `shell-snapshots` is a link into the person's own config folder and the entry names the link's own path, by one run on each of the two versions that the `role:refusal` scripts do not repeat. The sandbox holds a command and not the session's file tools, which read in Claude Code's own process. Claude Code asks the daemon before a file tool reads outside the session's folders, and the daemon refuses the call by the role's rule. `pnpm run role:refusal`, `role:refusal:inspector` and `role:refusal:crafter` try that for the run folder: a read by the file's path, a read through a link a command made, a search and a listing. A command still reads the person's other files, and reaches every other service that listens on the loopback. Each place the daemon refuses is a deny entry of the profile, and a deny entry wins over what Claude Code lets a command write by default. A place the launch names neither way is written where that default allows it. Measured on 2026-11-27 with Claude Code 2.1.332, the default allowed Claude Code's own temporary folder, `/tmp/claude-<user id>`, where the person's other Claude Code sessions keep their temporary files, and it stays writable to every role's commands; it also allowed the session's folder and the git folder of a linked worktree's repository, which the launch therefore refuses to the roles that do not write them; plain `/tmp`, a folder of the person's home and the folder above the worktrees were refused. In the same measurement a command opened no terminal device and bound no Unix socket, and the launch grants neither, so a test that needs one fails in a role session and runs at the broad gate, which the daemon runs outside any role session. A sandboxed session's Claude Code also leaves an empty folder `.claude/.cc-writes/` in the worktree, which `git status` does not show; it is Claude Code's own and no settings file, and Owlery does not remove it. The sandbox holds a command while a role session runs it. What the daemon runs afterwards is its own process, outside the sandbox: its commit in the worktree runs the repository's hooks, and the broad gate runs the repository's command, each on files a crafter's commands wrote. A daemon that answered a command by reading it would guess, and a write the system refuses is not made.
check: apps/desktop/test/claude-adapter.test.ts apps/desktop/test/daemon.test.ts apps/desktop/test/role-session.test.ts

**An adapter reports what a turn used in one neutral shape, and every cost carries whether it is a value converted at API prices.** The shape holds the turn's cost in US dollars and, for each model, the input tokens, the output tokens, the tokens read from the cache, the tokens written to it and that model's cost. The Claude adapter reads them from the `result` line of the headless stream (`total_cost_usd` and `modelUsage`), and reads the login from the stream's first `init` line; a result that comes before any `init` line reads as converted. It takes a cost as what the account is billed only where `apiKeySource` names a key: `ANTHROPIC_API_KEY`, `apiKeyHelper` or `/login managed key`, the three values the executable of Claude Code 2.1.330 gives a key (read 2026-11-23). Under every other value, a subscription login's `none` among them, the cost is marked as converted. A value nobody has set beside a bill is not shown as a charge, so a login the adapter does not know reads as converted. No cost crosses the protocol without the mark, and no field of Claude Code's does. The fake adapter reports the same shape in the cases.

### Authentication of the Claude adapter

The Claude adapter attaches in only one way: the daemon launches the `claude` CLI that the user installed and logged into. It does not use the Agent SDK. The Agent SDK documentation does not allow third-party products without prior approval to offer claude.ai login or subscription usage limits (Agent SDK overview, read 2026-11-18). When the daemon launches the user's CLI, authentication is the user's from the start.

| What | How |
|---|---|
| Authentication | The user picks it with `/login` in Claude Code. A subscription login uses the user's subscription limits, and an API key uses the user's API billing. Owlery has no login screen and stores no keys. For an account a person adds, Owlery runs the CLI's own `claude auth login` in a terminal pane with that account's config folder, and the sign-in completes in the browser through Anthropic's own flow |
| Role session | Launched in headless mode (`claude -p --input-format stream-json --output-format stream-json`), the role session delivers messages, tool calls, permission requests and results as events |
| Original screen | If the user wants to look inside, a role session opens in a terminal (`claude --resume <session ID>`). State is then judged by hooks |
| Role bundle | The daemon loads the Owlery agent definitions and skills shipped in the app only into role sessions (`--plugin-dir`). They are not installed into the user's Claude Code, so the app's version and the bundle's version are always the same. See "What each session loads" below |

Anthropic publishes two documents that bear on this, and neither addresses another product launching the user's own logged-in CLI in headless mode. The support article "Use the Claude Agent SDK with your Claude plan" says that `claude -p` and third-party app usage still draw from the user's subscription limits. The Agent SDK overview holds the rule on claude.ai login stated at the top of this section. Both were read on 2026-11-18. Owlery sends Anthropic no inquiry. It judges headless role sessions against these two documents, and judges again when either changes. Role sessions are launched only through the adapter, so moving them to interactive terminals read through hooks stays cheap.

**A person keeps several logins as accounts, each a config folder of the CLI's, and every session is launched with the account its nearest setting names.** One account is the default. A repository, a work item and one session can each be set to another, and a session takes its own setting first, then its work item's, then its repository's, then the default. The daemon passes the account's folder to the CLI as `CLAUDE_CONFIG_DIR`, the way Claude Code's own documentation keeps a work and a personal account apart (Authentication, "Log in with multiple accounts", read 2026-11-23). A role session gets it among the named variables of its cleared environment, so the account's own plugins, hooks and settings stay out of a verdict as before. A Claude Code pane gets it in its command, after the login profile ran, because a profile's own export replaces a value of the pane's environment (probed 2026-11-23 with a stand-in). "System default" is the login the person's shell gives with nothing passed, and it is always there. A person adds an account in one of two ways, and types no name in either: Owlery makes a folder in the daemon's run folder and at once runs `claude auth login` with it in a terminal pane, or the person hands over a folder that exists, which Owlery neither links into nor deletes. A folder Owlery made becomes an account only when its first sign-in ends with a login. Where that sign-in ends with none, Owlery removes the folder and keeps no account. An account is named once, when it is added, by the email `claude auth status` prints for its folder's login, which the CLI reads from `oauthAccount.emailAddress` of the folder's `.claude.json` (read in the executable of Claude Code 2.1.332, 2026-11-26). Where the CLI names no email, a folder Owlery made is named "Account" with its id, and a folder handed over is named by the last name of its path. A name another account holds takes a number in brackets. So a second login to one Claude account is kept and told apart, and nothing is signed out or removed because two emails are equal. The person renames an account afterwards. Owlery reads no credential file and no Keychain entry, passes no token in a variable, and learns whether a login stands, and the email it names, from `claude auth status`. That a real login prints the email has not been run. Anthropic's Legal and compliance page for Claude Code says that sign-in to a Claude account must complete through Anthropic's own flow and that developers may not collect, store or intermediate credentials, and it does not prevent a person from signing in to the unmodified CLI with their own subscription (read 2026-11-23). The daemon never chooses an account, at a usage limit or anywhere else: only a person's setting does. Separate folders do not keep two Claude Console sign-ins without an API key apart, because the CLI stores that sign-in outside the folder. Where Owlery reads a person's Claude Code folder to launch a pane, as it does to learn which plugins the pane's session enables, it reads the folder of the pane's account. Whether an agent has accounts is a feature its adapter declares.

### Reading usage limits

The app shows how much of the user's subscription limit is used and when it resets, and the daemon checks the same values before it starts the Owl Chain for a work item. A run can launch four or five stages for one work item, so a run started near the five-hour limit stops halfway. In that case the daemon holds the run back or tells the person.

Claude Code itself hands these values over in two ways. Both were found in the Claude Code 2.1.327 executable (2026-11-18). The status line's has not been run yet. The stream's event stands in two recorded runs of a role session.

| Session | Where the values come from | What comes in |
|---|---|---|
| The user's session in a terminal | The `rate_limits` field in the JSON that Claude Code passes to the status line command | `five_hour` and `seven_day`, each with `used_percentage`. Present only for subscribers, and only after the first API response |
| Role sessions | `rate_limit_event` in the headless output stream | Limit information for each event: a status, the name of the limit, and for each window it lists a used share, a reset time and a status. Read from two recorded runs whose values were replaced, so the range of the used share and the unit of the reset time have not been checked |

- **The user's status line stays as it is.** The daemon puts in a small status line command. It passes the JSON to the daemon, then runs the user's own status line command and prints its output unchanged.
- **The values are as of the last call.** When nothing is running, the app shows the last values it received and the reset time.

There is another way, and implementation should keep it in mind. The app could read the user's login token from Claude Code's credentials file or the keychain, and call an undocumented usage endpoint with it. That gives current values at any time. The first version does not take it, for three reasons.

- The endpoint is not documented, so its response shape can change without notice.
- The request has to present itself as Claude Code. If it is blocked, the user's account takes the hit.
- It goes against the rule in this document that authentication belongs to the user's CLI.

Owlery does not take it later either, for an account that runs no session as for any other. Anthropic's Legal and compliance page for Claude Code says that developers may not collect, store or intermediate Claude.ai credentials or session tokens (read 2026-11-23), and reading the token is collecting it. An account that runs no session shows the last values a session of it handed over, with their time, and an account that has run none shows no number. Whether Codex hands over similar values has not been checked.

**A person refreshes the usage of an account that runs no session by a press, and nothing else starts a refresh.** The daemon then starts one short headless session of the CLI under that account, with no tool and no transcript, keeps the limit values the CLI hands over in its stream, and ends it. The value is Claude Code's own, read from a session Owlery launched as it launches any other, so Owlery still reads no token and calls no address of Anthropic's itself. A refresh spends a little of that account's limit, so no timer and no opening of a dialog starts one, and the control says so before the press. Where the CLI hands over no value, the account says so and shows no number. A turn with no limit near handed over a `rate_limit_event` in the two recorded runs the cases keep, one of them of Claude Code 2.1.330 on 2026-11-22: the line names the limit it speaks of and holds a used share, a reset time and a status for each window it lists, and each run listed the seven-day window alone. The recordings' values were replaced before they were kept. So which windows a turn lists, whether the used share is a fraction of 1, the unit of the reset time and what a refresh costs have not been read from a real run, and Owlery shows a value only where it reads as the published type gives it.

#### Role sessions run detached from the user's environment

Role sessions run on the user's Claude Code. Launched as is, a role session brings in the user's installed plugins, hooks, skills, MCP servers, global `CLAUDE.md`, auto memory and permission mode. A verdict must not depend on the user's environment, so the daemon launches role sessions as below. Everything was tested on 2026-11-17 with Claude Code 2.1.326 under a subscription login (`claude.ai`).

| What comes in | How it is removed | Test result |
|---|---|---|
| Hooks, enabled plugins, permission rules, user skills, MCP servers and the global `CLAUDE.md` from user settings and repository settings | `--setting-sources ""` | User hooks went from 9 to 0. Enabled plugins, user skills and MCP servers dropped out, and the rule in the global `CLAUDE.md` (answer in Korean) disappeared |
| Other hooks | `--settings '{"disableAllHooks": true}'` | 0 hooks |
| Other MCP configuration | `--strict-mcp-config` | 0 MCP servers |
| Auto memory | `--settings '{"autoMemoryEnabled": false}'` | Left on, a memory index matching the repository comes in. Turned off, there is no memory path |
| Plugins and settings that come in through environment variables (e.g. `CLAUDE_CODE_PLUGIN_DIRS`) | The daemon clears the environment and passes only what is needed (`HOME`, `USER`, `PATH`, `LANG`, `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD`, and `CLAUDE_CONFIG_DIR` where the session's account has a config folder or the person's login shell holds one) | Plugins that came in through environment variables dropped out, and the subscription login still worked |
| Permission mode | The daemon sets `--permission-mode` | With user settings removed, it becomes `default`. The daemon passes `default` for every headless session, so each call Claude Code would ask a person about reaches the daemon, which answers a role session's call by the role's grant. `claude --help` of 2.1.330 lists the mode as `manual`, and the CLI still reads `default` (probed 2026-11-22) |
| Writes of a command outside the role's place, its reads in the daemon's run folder, and the person's own sandbox settings | `--settings` with a `sandbox` block of the daemon's own. `--setting-sources ""` reads neither the user's nor the repository's settings, so their sandbox settings do not reach the session | A proofer's command that appended to the worktree's file failed with `Operation not permitted`, its `git branch` in the repository's git folder failed the same way, and its clone in the scratch folder was made (`pnpm run role:refusal` against a stand-in model, on Claude Code 2.1.332 and 2.1.329, 2026-11-27). Its `cat` of the run folder's `daemon.json` failed the same way (the same scripts on Claude Code 2.1.332 and 2.1.329, 2026-11-27) |

- **`--bare` is not used.** Under `--bare`, Claude Code does not read OAuth or the keychain, so it cannot run on a subscription login (`claude --help`).
- **The only things that cannot be removed are the plugins built into Claude Code (`cc-plugin-*`, `builtin`).** They are a part of Claude Code that the user cannot choose, so we accept them.
- **The repository's `CLAUDE.md` is read, and the repository's settings are not.** `CLAUDE.md` holds that repository's rules, so verdicts need it. So the daemon leaves the setting sources empty, passes the repository with `--add-dir`, and sets the environment variable `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1` so that the `CLAUDE.md` in that directory is read (tested 2026-11-17: the rules in `CLAUDE.md` were followed, and plugins enabled by the repository settings were not loaded). Reading it with `--setting-sources project` brings in the repository's `.claude/settings.json` as well, and the plugins and permission rules those settings enable are loaded into the role session too (tested the same day: the AgenticSeal plugin enabled by the repository settings was loaded).

**A role session installs nothing: the bundle is loaded for that session alone, and Owlery writes no settings file and no plugin list of the user's.** Claude Code keeps a count of the plugins a session loaded in its own state file, `~/.claude.json`, under `pluginUsage`, and a role session adds the entry `owlery@inline` there (probed 2026-11-22 on 2.1.330). Every session of the CLI rewrites that file, and it is no settings file. The daemon's `claude --version` at its start writes nothing there. The same run wrote no `settings.json`, no `installed_plugins.json` and no `known_marketplaces.json`.

### Rules that keep it portable

Four rules keep the design portable.

1. **The UI does not know which vendor's agent it is showing.** Only the shapes the adapter produces pass over the protocol between the daemon and the UI. Vendor-specific fields do not. The mobile UI uses the same protocol.
2. **Features that differ by vendor are handled through the feature list.** The UI shows or hides buttons by reading the feature list. It does not branch on a vendor's name.
3. **There are two adapters from the start.** One is the real Claude adapter, and the other is a fake adapter for tests. With only one adapter, it is hard to notice when the shape of the connector hardens around Claude.
4. **The chain's code stands apart from the agent that runs a session.** The order, the records and the invariants are Owlery's code. The agents that take the chain's roles are launched through the same adapters, or as subagents of a pane's session from the same definitions, so switching the judge to another model does not change the chain's code. The daemon's chain runs separately from the user's session, whichever vendor's agent runs that session. A pane's chain rides on the user's Claude Code session, and in the first version no other vendor's pane carries it.

| Mechanisms that exist only in Claude Code: the session-start hook that prints core, the Stop hook that draws the seal, the permission and worktree hooks | Not taken. The app and the daemon do the same work directly ([What each session loads](#what-each-session-loads)) |
| The question batch (`frame/questions.md`) | Becomes the app's question screen |

### What changes because Owlery is not a plugin

AgenticSeal is a Claude Code plugin, so the means it can use are fixed: markdown that agents read, two hooks (one prints core at session start, the other draws the seal when the session stops), and the `seal` command. That is why many of its mechanisms take the shape "tell the agent in writing, then check later whether it complied." Owlery is a product with a daemon, a UI and its own storage, so it reaches the same goals through structure. The table below maps one onto the other.

| Goal | How the plugin does it | How Owlery does it |
|---|---|---|
| Each party judges only its own subject | The agent definitions state that proofer and sealer do not edit code, and a check confirms it from the round records | The daemon sets each role's tools (`--tools`). proofer and inspector receive no tool that writes a file, and their commands run in the operating system's sandbox, which refuses them the worktree and the repository's git folder and gives them a scratch folder of the session's own ([Agent adapters](#agent-adapters)). Every permission request reaches the daemon on the session's own streams (`--permission-prompt-tool stdio`), and the daemon answers it by the role's rule ([Agent adapters](#agent-adapters)). In a pane a judging role is a subagent whose definition names the four tools that read, search and run a command (`tools:`), and the person's own permission settings answer a call that asks for permission |
| Passing the rules to the agent | The session-start hook prints all of core, and the `skills:` list in the agent definition loads core and the agent contract | The daemon appends the rules to the system prompt for each role and stage ([What each session loads](#what-each-session-loads)). The first version includes all of core and the agent contract. Whether to include only the parts needed is decided after measuring startup tokens ("Measure before building"), because every byte costs tokens. A pane's subagent reads the same rules from the file the chain command writes for its stage |
| Keeping the order | The orchestrator reads the documents that write down the order and follows them | Owlery's code runs the order: the daemon in its own chain, and the chain command in a pane, where the session asks which step is owed and no document restates the order |
| Waiting for CI results | The orchestrator calls `seal pr-wait` and reads the exit code | The daemon waits, and when CI finishes, it reports through the UI and a notification. No agent stays running while waiting |
| Measuring cost | After the work ends, `seal cost` reads the transcript files, computes the cost and leaves it as a comment on the issue | The daemon records the result events of headless mode (`total_cost_usd` and per-model tokens) at each stage as they arrive. The daemon owns the ledger and can also set a budget cap (`--max-budget-usd`). Under a subscription login, this cost is not the actual charge but a value converted at API prices, and the ledger labels it that way. The stages a pane's session runs are not measured, since no hook carries a cost, and the inspection sheet of such a work item says so |
| Asking the person | Written in `frame/questions.md`, and the session asks | The app's question screen. It is an input form with choices and defaults, so it can also be shown on a phone once a mobile UI is attached. A question that arises after the batch is decided from the code and the policy and recorded as a decision made without asking. Only what they cannot answer and the session cannot give itself parks its one work item, with the question on that work item's inbox line, while the daemon goes on with the others. No question is posted on a GitHub issue. A decision made in place of asking is counted on its work item's line, and the work item's preview and view list it with its grounds. A pane's session asks the person in the pane, and under `Automation` `yes` it goes on with the question's default and writes the question into `frame/questions.md` ([Code runs the order, the orchestrator judges](#code-runs-the-order-the-orchestrator-judges)) |
| Showing the result | A hook draws a seal in the terminal when the session stops | The inbox, the inspection sheet, the PR and notifications read the same records and draw the inspection, whichever chain wrote them, the daemon's or a pane's. The bundle a pane carries holds no hook that draws one |
| Moving records to another machine | Exchange a zip with `seal export` and `seal import`, and choose with `seal mode` whether to commit records to the repository (shared) or keep them local only (local) | Records are committed to the repository, so they move with git ([Records are committed to the repository](#records-are-committed-to-the-repository)). There is no command for moving records. The only thing to move between machines is the daemon's state (progress, the cost ledger, what the person has seen), and it will later move through sync between machines |
| Running several work items together | One session runs work items one after another, or a person opens several sessions | The daemon sets the order of several work items and how many run at once, and hands the overlaps between work items in the same release to framer |

The table means two things.

- **Many rules that were given in writing become structure.** An agent cannot break what structure blocks, so the cost of having agents read those rules drops too. Rules that need judgment (what counts as the same meaning, whether this design is right) still reach agents in writing.
- **The PR check stays.** Even when the daemon blocks things through structure, the check on the repository that receives the PR, which confirms the inspection is cleared at HEAD, must also run outside Owlery. A colleague who does not use the app must get the same verdict when they look at the PR.

| The daemon | Progress, session events and output, each pane's record with the id of its conversation, the cost ledger, what the person has seen, schedule | They change often, and there is no reason to commit them to the repository |
| What is given to the agent | The rules that role and that stage need, and the previous stage's files | An agent starts fresh every time, and every byte it reads costs tokens |

### Records are committed to the repository

Owlery always commits work records to the user's repository. There is no mode that keeps them only locally without committing.

- **Uncommitted records cannot support an inspection.** The PR check has no records to read, and on another machine or a fresh clone the records are empty. The promise that "the grounds for a verdict travel bound to the commit" cannot be kept.
- **Records have one place, so there is no mechanism to move them.** Records travel with git, so there is no command to export or import records or to change where they live. The only thing to move between machines is the daemon's state.
- **When a repository is first connected, the place for records and the PR check are created together, in one commit the person reads first.** The person is not asked where the records go. The app shows each file it would write, the commit's subject and the branch it lands on, and writes nothing until the person confirms. It writes the records' root `iadd/`, with a `README.md` whose first line is IADD's marker and a `config.json`, and the workflow `.github/workflows/owlery-inspection.yml`. The root has one name: where the repository keeps an `iadd/` of its own without that marker, the setup refuses and says so. A file that is committed is kept as it is. A repository whose records stand in the earlier form is offered their move, below, and no setup. The app reads the place from the commit the checkout stands at, as a clone and the check on GitHub get it, and refuses the setup while the checkout does not hold a file of the place as that commit does. The commit holds those files alone, runs the repository's hooks, and is not pushed. The broad gate command is the `Broad gate` key of the root's `config.json`, set in the same step, and the app shows its value and its file on the repository.

## Code runs the order, the orchestrator judges

The orchestrator in a Claude Code session does two things at once today. One is running a fixed order, and the other is judgment. Moving the order into code removes the procedure text the orchestrator had to read and follow by hand each time. An earlier example in the same direction is AgenticSeal 0.38.0, which replaced a 363-word procedure for waiting on CI results with the `seal pr-wait` command.

## License and code from other projects

Owlery is released under the Apache License 2.0.

- **Why Apache-2.0.** Open-source maintainers and companies accept it most easily, it carries a patent grant, and the code we take from Apache-2.0 projects comes under the same terms, which keeps the notices simple. A copyleft license (GPL) would stop other products from copying our code. That protection is weak here, because AgenticSeal, where the Owl Chain's files started, is already MIT and ideas are not protected by any license. Its costs are real: many companies forbid contributing to or reusing GPL code, plugin authors cannot tell which license their plugin must take, and GPL conflicts with the iOS App Store terms that a later phone app needs. Moving from Apache-2.0 to a copyleft license later stays possible. Moving the other way would need every outside contributor's consent.
- **Code from MIT or Apache-2.0 projects may be taken and adapted.** For MIT code, its copyright notice and license text stay with it. For Apache-2.0 code, its LICENSE and NOTICE come along, and each changed file carries a note that it was changed. Files inside such a project that carry a license of their own are checked one by one.
- **Code from GPL or AGPL projects is not taken.** Only their ideas are used, because taking the code would put the whole app under the same license.
- **Other products' names and logos are not used.** That is a trademark matter, separate from the license.
- **The names and the emblem are not under the Apache License.** The Owlery and AgenticSeal names, the owl emblem and its drawings in the tree are reserved, and `TRADEMARKS.md` at the top of the repository states what they are under.
- **The owner keeps room to change the license.** When outside contributions start, a contributor license agreement (CLA) is added, so the license of later versions can still change. Whether to require it is in "Open decisions".

## Connecting from outside: phones and other machines

The first version has no mobile app, and Android comes first ([Platforms and their order](#platforms-and-their-order)). How a phone or another machine reaches the daemon is settled now anyway, because it shapes the daemon's protocol.

- **Connect directly first, and relay only when that fails.** The phone and the daemon each open an outbound connection and learn the address the outside world sees for them. Then both send to each other at the same moment, so each router takes the other side's packets as replies and lets them in (hole punching). This works across different networks, not only on the same Wi-Fi. Once it works, the traffic passes through no server. Only when it fails, for example behind a router that gives each destination a different outside port or on a network that blocks UDP, does the traffic go through a relay.
- **iroh is considered first.** iroh is a Rust library that connects devices by public key instead of by address. It tries a direct connection and falls back to a relay by itself, and it has official Node bindings for the daemon (`@number0/iroh`, Node 20.3 or later). Pairing becomes a QR code that carries the daemon's public key, and its QUIC connections survive a phone moving between Wi-Fi and cellular. Whether a React Native phone app can use it is not confirmed. If it cannot, WebRTC data channels take its place. They are built into Electron, and their relay (TURN) is rented per gigabyte.
- **Everything is end-to-end encrypted.** A relay passes bytes it cannot read.
- **The running cost stays small.** Only connections that fail to go direct use the relay. The relay is iroh's public one or one we run, and its code is published so users can run their own. Connecting over Tailscale or SSH stays supported and costs no one anything.
- **Push notifications need a server of our own.** Sending a notification to a phone needs Apple's (APNs) and Google's (FCM) keys, which cannot ship inside the app. A small push gateway holds them.

## The phone: the terminal session as a chat

The phone shows a session that runs in a terminal on the desk as a chat. The terminal stays the original, and the phone is a second way to see the same session. The phone does this for every agent CLI the person runs, and its traffic goes only over the connection above, through no agent company's server. Two rules hold from now on so the phone can attach: the daemon's WebSocket protocol is not fitted only to the desktop UI, and no state lives on the UI side. A client's own appearance, such as its theme, is not that state, and the client keeps it.

For Claude Code, each part of the chat comes from the places below. Each hook was run on 2026-11-18, with Claude Code 2.1.327 in an interactive session that Owlery launched with its hook settings passed through `--settings`, which add to the user's and the project's settings and change neither. Every event carries `session_id`, `transcript_path` and `cwd`, and every event but `SessionStart` carries `permission_mode`.

| Part of the chat | Where it comes from |
|---|---|
| The person's messages | The `UserPromptSubmit` hook |
| Tool calls and their results | The `PreToolUse`, `PostToolUse` and `PostToolUseFailure` hooks |
| Permission requests | The `PermissionRequest` hook, which carries `tool_name`, `tool_input` and `permission_suggestions` but no `tool_use_id`. The hook waits for the answer from the phone and returns allow or deny |
| The agent's last reply in a turn | `last_assistant_message` in the input of the `Stop` hook |
| Text the agent writes between tool calls | Only in the session log Claude Code writes to disk (`~/.claude/projects/<project>/<session ID>.jsonl`). Its format is not public, so the phone reads it only as a supplement. When the daemon cannot parse it, the phone shows the hook events alone |
| A question the agent asks, with its choices | The `PreToolUse` hook of the tool `AskUserQuestion`, whose `tool_input.questions` holds each question as `question`, `header`, `options` and `multiSelect`, and each option as `label` and `description`. Read from Claude Code's hooks reference and from the 2.1.330 executable on 2026-11-23, and not run |

- **The phone never reads the terminal screen.** The same rule as the inbox: state and content come from events and files, never from guessing at what the screen prints.
- **Input from the phone goes into the terminal only while the CLI waits for input.** A stop goes in as the CLI's interrupt key at any time.
- **Hooks are added only to the sessions Owlery launches.** The user's own settings files are not changed.
- **Where Codex CLI's state, permission requests and conversation come from has not been checked.** It is checked in milestone 4, which brings a Codex session's line into the inbox ([Milestones](roadmap.md#milestones)), and so before the phone app is built.

Some agent CLIs have a remote feature of their own, such as Claude Code's Remote Control. Owlery does not use or turn on such a feature. When a user turns one on for a session, the same permission request can appear in two places. What to do then is in "Open decisions".

## Memory design

**Owlery spends as little memory as it can, and a feature costs nothing while nobody uses it.** What a feature holds is made when it opens and let go when it closes, and memory grows with the stages working right now, not with the work items left open.

**What a scene costs is measured and published, and no number of a reference scene is a limit on a feature.** A scene is one state of the app, written down so that it can be measured again. Each scene is published with its date, its commit and its method, beside the same scene in comparable products. The first reference scene is the app itself with four terminals visible, which read about 500 MB: 491.1 to 503.4 MB in an agent's start on 2026-11-19 (`apps/desktop/measurements/memory.md`). No comparable product has been measured in that scene yet. A feature is not refused because a scene it adds to reads more.

**A feature is built first, and made efficient where a measurement shows its cost.** It is built with ordinary care, so that it holds nothing while unused, and its cost is then measured. Efficiency work follows where a measurement shows the cost, as issue #9 found that each hidden pane kept its terminal screen in the window, and removed it. A tight number set before a feature is built is not a design input. The reference scenes are measured again as features land, with `pnpm run measure:memory` in `apps/desktop`, so a change in their numbers is seen and a refactor is scheduled for it. No check runs that measurement: the suite's run of `test/memory.test.ts` measures nothing without `OWLERY_MEASURE_MEMORY=1`.

**The limits Owlery keeps are defaults read from the person's machine, which the person sees and changes.** They are how many agents and how many worktrees run at once, how many panes a work item's view shows at once, and how many heavy commands run at once. Each is proposed from the machine's memory, cores and free disk, never from the number of a scene measured on another machine. Release 0.0.4 built them (issues #32 and #134), before milestone 3's role sessions start under them ([Milestones](roadmap.md#milestones)). The rules at the end of this section state each.

The four rules below are how the app holds little while it runs.

| Rule | Reason |
|---|---|
| Terminal screens and WebGL contexts are created only for as many panes as are visible, and are reused. The daemon holds the output of hidden terminals | A hidden WebGL canvas still holds a framebuffer the size of the screen, so with one canvas per terminal a single GPU process can exceed 1 GB (measured 2026-11-17). Reuse should avoid most of the cost of creating a new screen object (about 160–190 ms) |
| A pane on screen holds as many lines of history as the scrollback names: 5,000 on every machine, until a person sets another number from 1,000 to 50,000 in the Machine dialog. The daemon keeps 256 characters of each pane's output for each of those lines, and nothing older is kept anywhere | Adding one terminal to the same window added about 14 MB with 1,000 lines of history and about 20 MB with 5,000 lines. In the window a line of history takes 12 bytes for each of its columns, so 5,000 lines of 100 columns take about 6 MB and 50,000 take about 60 MB, only in a pane on screen and only once the pane has printed that much |
| Only one window is used. There is no built-in browser | Each extra window added about 130 MB |
| Claude processes for finished stages of the Owl Chain are ended. Resume is used to talk to them again. Sessions the user launched from a terminal are closed by the user | One Claude process uses 345–679 MB |

The GPU terminal limit stays at Chromium's default of 16. This means one screen cannot hold 17 or more panes. The renderer's memory cap is not raised either.

A work item's view shows side by side at most as many panes as the cap on panes names. The daemon proposes 4 on a machine with less than 16 GB of memory, 6 from 16 GB and 8 from 32 GB, and a person sets from 1 to 16. Four is the count the reference scene was measured at. The other panes of the work item stay as tabs, and a pane that is not on screen holds no terminal screen in the window. The daemon keeps the last 256 characters of each pane's output for each line of the scrollback, 1,280,000 at the default, and the window draws a pane from that replay each time the pane comes back on screen. So a pane that comes back holds what those characters draw, which is fewer lines than the scrollback names where its program redrew its screen often, as an agent's CLI does. A change of the scrollback moves the limit of every pane that lives, and a smaller one drops the older output. Where it drops older output, what it keeps opens at a line's start where a line break stands within the first 4,096 characters, so a replay does not open inside an escape sequence. Past that, the cut stays where the count of characters puts it, and a program that prints a long stretch without a line break, as a full-screen program may, keeps that stretch.

**The daemon keeps the 50 headless sessions that ended last, and every session still working.** The list in memory serves the window's view of recent sessions, and a result that must outlive it belongs in the repository's records ([Records are committed to the repository](#records-are-committed-to-the-repository)). Without a bound the list grows with every stage of every run until the daemon exits. The session that ended first leaves first, and every client is told.
check: apps/desktop/test/daemon.test.ts

**A pane that comes back onto the stage is sent nothing a person types or pastes there until the window has drawn its replay.** The screen it takes was emptied when the pane before it left. Until the replay is drawn, the terminal holds none of the modes the pane's program set, such as pastes in brackets, and it would encode a paste or a key without them. What a person types in that moment is dropped and not held, since the terminal encodes a key when it is pressed. A pane the window draws for the first time since its page loaded is the exception: the terminal's answers to the questions in that replay must reach the pane's program, and they leave by the same path as a person's keys.
check: apps/desktop/test/view.test.ts apps/desktop/test/terminal-basics.test.ts

**The daemon reads the machine at its start and proposes each cap with the numbers it used.** It reads the memory, the cores, the performance cores and the free disk of the worktrees' folder. The cap on agents is the smaller of the performance cores and half of the memory divided by what one agent's own process uses: 679 MB until the daemon has measured five agents on this machine, and then the highest value among the last twenty it measured. The performance cores are what macOS gives under `hw.perflevel0.physicalcpu`, and all the cores where it gives none. It measures while an agent lives, once a minute. The cap on worktrees is the worktrees that stand plus the free disk less 10 GB, divided by the largest worktree measured there, and nothing is proposed until one is measured. A cap a person sets is the daemon's state, kept in its run folder and sent to every client, and it stays until the person returns it to the proposal.
check: apps/desktop/test/machine.test.ts apps/desktop/test/daemon.test.ts

**A headless session over the cap on agents waits in a queue, and what a person opens by hand never waits.** The agents that run are the live panes of a kind that reports its state and the headless sessions that are working. A headless session asked for while that count is at the cap is listed as queued and starts no process until the count falls or the cap rises. A stage of a chain that is already running starts first, then a chain's first stage. A pane always opens and counts, and nothing over a cap is ended. The work item's line says that it waits for the machine and its place in the queue, and a stage's time counts from its start.
check: apps/desktop/test/daemon.test.ts apps/desktop/test/chain.test.ts apps/desktop/test/view.test.ts

**Creating a work item warns where the disk would not hold its worktree or the worktrees are at their cap, and creates it on the person's word.** The daemon measures each worktree once, after its setup, and a new worktree of a repository is taken to need what the largest measured worktree of that repository takes. The form states the free disk, the 10 GB kept free and that need. It refuses nothing, since the person may know what they are about to remove.
check: apps/desktop/test/daemon.test.ts apps/desktop/test/view.test.ts

**How many heavy commands run at once is one of the limits, and its default is one for each 8 cores or one for each 16 GiB of memory, whichever gives fewer, and never under one.** One run of a suite takes most of a machine's cores by itself, and two at once failed timed cases on a Mac of 10 to 12 cores, so a machine of that size runs one, and a second runs from 16 cores. The 16 GiB is a first value, set before any heavy command's memory was measured. The person sees the default with its arithmetic in the Machine dialog and changes it there, and the value is the daemon's state. The daemon keeps, for each run of a heavy command, how long it took, its peak memory and the load beside it, and the dialog shows them beside the default so that the default can be checked against what ran. No measurement moves the default by itself. The daemon reads the load and a command's memory only while a heavy command runs or waits and when a person asks.
check: apps/desktop/test/machine.test.ts apps/desktop/test/machine-turns.test.ts apps/desktop/test/heavy-run.test.ts

## Screen framework: Electron

The UI is built with Electron. Frameworks that use the system webview used somewhat less memory (up to about 10% across the same 8 scenarios, measured 2026-11-17), but the gap was not large enough to decide on. The four points below decided it.

- **The same UI on three OSes:** Chromium ships with the app, so macOS, Windows and Linux draw with the same engine.
- **Korean input on macOS:** The terminal component (xterm.js) has no known input problems. A person typed Korean with the Dubeolsik layout into the Owlery terminal pane on 2026-11-18, in the shell and in Claude Code, and the shell received it as typed, in UTF-8.
- **Linux:** There are fewer open issues with Wayland, Nvidia and WebGL.
- **Updates:** Delta updates download only the changed parts. In exchange, the app is large (.app 253 MB).

Electron stays on macOS too (decided 2026-11-18). Moving macOS alone to the system webview was weighed on two criteria: Korean input, which works in the Electron pane (above), and how much lighter the app becomes, which the measured gap of up to about 10% does not decide.

**The window shows Owlery's own page and nothing else, and no second window opens.** The main process refuses every navigation of the window but a reload of its own page, and refuses every new window. So nothing a pane prints can replace the window or open a page of the web inside Owlery, and a file a person drops on the window does not replace it either: the window does not navigate on a drop. A link a pane prints opens in the system browser, on a click with the Command key held, and only where its address is an `http` or `https` one. A path a pane prints is a link only where the main process finds a file or a folder at it. A click on it with the Command key held puts the view of another work item in front where the path is that work item's worktree. On a file it opens the file in the editor the person chose in Settings, at the line and the column the pane printed after the path, and the same click with the Shift key shows the file in Finder. Owlery opens a file in an editor of its own list and in no other app, since a path a pane printed is not the person's and the app the system gives a file may run it. Where the person chose Finder, or the Mac holds no editor of the list, the click shows the file selected in its folder. A folder is opened in Finder unless its name holds a dot after its first character and it is no checkout. An app started with `OWLERY_BACKGROUND=1` opens nothing in the system browser or in Finder and opens no folder dialog, and reads and writes a clipboard of its own in place of the system's. Its page raises no system notification, and keeps the title and the body of each one it would have raised, which the cases read.
check: apps/desktop/test/terminal-basics.test.ts apps/desktop/test/navigation.test.ts apps/desktop/test/links.test.ts apps/desktop/test/paths.test.ts apps/desktop/test/clipboard.test.ts apps/desktop/test/pick-folder.test.ts apps/desktop/test/work-item-form.test.ts apps/desktop/test/notifier.test.ts apps/desktop/test/notification-click.test.ts

**On macOS, closing the window hides it, and the app keeps its page.** The window's page raises the notifications, so a session that begins to wait while the window is closed still notifies. A click on the notification or on the Dock icon shows the window again, and Quit ends the app. An app started with `OWLERY_BACKGROUND=1` closes its window as before and quits with it: it has no Dock icon that could bring a hidden window back.
check: apps/desktop/test/background.test.ts

**A press in the window outlasts the lists the daemon sends: a click whose press and release fall on the same line or button does what that line or button does.** While the person holds the mouse's main button down in the window, the window takes each `inbox`, `accounts` and `machine` message at once and raises its notifications. It waits until the button is released to draw each part of the window that the message changed and whose lines or buttons a draw replaces: the sidebar, the screen in front, the dialogs that name what the daemon lists, the Accounts dialog and the Machine dialog. It then draws each of them once, after the click has reached the element that was pressed. A draw replaces every line and button it draws, and Chromium sends no click at all for a press whose element left the page before the release. Without the wait, the line of a work item pressed while an agent works would not open. The wait ends where the main button is released, also while another button is still down, and a cancelled press and a window that loses the focus end it as a release does. A press of another button alone holds nothing. A draw the person's own act asks for, such as the view a click opens, is drawn at once.
check: apps/desktop/test/press.test.ts apps/desktop/test/inspection-sheet-view.test.ts

**A paste into a pane gives its program text, and a file or an image on the clipboard reaches it as a path.** Where the clipboard holds files copied in Finder, the pane is handed their paths, written as the paths of dropped files are. Where it holds text, the pane is handed the text. Where it holds an image and no text, the main process writes the image as a PNG file into a folder of its own in the system's temporary folder, readable by the person alone, and the pane is handed that file's path, so the CLI of any agent reads the image as a file. Each such write removes the files of that folder older than seven days. Control+V stays the key of the pane's program, and Claude Code reads the clipboard itself at that key. An app started with `OWLERY_BACKGROUND=1` reads no image of the system's clipboard and opens no editor.
check: apps/desktop/test/clipboard.test.ts apps/desktop/test/view.test.ts apps/desktop/test/openers.test.ts

**A press of the sidebar's refresh button has the daemon read again what a client's hello has it read from outside, and the window draws the lists the daemon sends back, keeping what the person had in front.** The daemon outlives the window for days, and between its timers what it read can stand behind git and GitHub: an open pull request whose checks have ended is read again only every `PR_REST_POLL_MS`. The window sends `readLists`. The daemon takes what to read from one list in its code, which the hello reads too. At release 0.0.5 that list is the notice of its agent where one stands, every open pull request it watches, through `gh`, and from git each work item's branch, or the commit its worktree's `HEAD` stands at where it has no branch yet, and its record, whether a commit holds each word of the person's its record holds, and each repository's records place. Every read the press asks for starts after the message arrived, once a read of git under way has ended, and a read of a pull request that was under way leaves that pull request to be read again at once. The daemon answers the window that asked with the four lists in an `inbox`, and then `done`, once git has been read and the reads of the pull requests have ended or 5 seconds have passed. A pull request read after that reaches every window in the watch's own `inbox`. The window draws the answer as it draws any `inbox`, so the screen in front, the view's pane in front and the filter stay, and a press held at its arrival delays the draw until the release. While the answer is on its way, the button's arrows turn and a second press sends nothing. A refusal is said in the status line in the daemon's words. Where no answer comes within 15 seconds, the status line says so. Against a daemon of a build before `answersUnknown`, which does not know the message, the window's wait of 10 seconds on each request ends the press first, with its own sentence ([What a session survives](#what-a-session-survives)).
check: apps/desktop/test/daemon.test.ts apps/desktop/test/refresh.test.ts apps/desktop/test/notification-click.test.ts apps/desktop/test/view.test.ts apps/desktop/test/daemon-restart.test.ts

## Measure before building

- **Direct connection rate:** Measure how often a phone connects to the daemon without the relay, on Korean LTE and 5G, office Wi-Fi and café Wi-Fi, for iroh and WebRTC each ([Connecting from outside](#connecting-from-outside-phones-and-other-machines)).
- **Switching latency when screens are reused:** Measure on macOS, Windows and Linux each, with 1,000 and 5,000 lines of history at 200 columns.
- **GPU memory one visible terminal uses:** Measure at our pane size, for WebGL and DOM each, and for Retina and 4K each.
- **Daemon CPU:** Measure the cost of parsing terminal output when 10 agents print at once.
- **ACP coverage:** Check which agents attach through ACP, and which of permission requests, slash commands and interrupting midway they support. Features they do not support are covered by opening the agent in a terminal.
- **Time and tokens of resume:** Measure separately for sessions stopped within the last 5 minutes and for older ones.
- **How long a permission hook can wait for the phone:** Check the hook's time limit and what the CLI does when it runs out, for Claude Code and Codex each ([The phone: the terminal session as a chat](#the-phone-the-terminal-session-as-a-chat)).
- **What the cost field means under a subscription login:** We confirmed that headless result events carry `total_cost_usd`, `usage` and `modelUsage` under a subscription login too (2026-11-17). A subscription is not billed per token, so these values appear to be converted at API prices. Claude Code prices a model's requests from a price table, which its result names for each model (`costBasis`: its built-in list prices, an organization's own rates, or none), and a result under a subscription login named the list prices (read in the executable of 2.1.330 and in a recorded stream, 2026-11-23). Until the comparison is run, the ledger marks every cost as converted unless the session's login names an API key ([Agent adapters](#agent-adapters)). What is left is to set the values for the same work under an API key login beside that account's bill, which issue #140 runs.
- **Usage limit values:** Run a session under a subscription login and confirm the `rate_limits` field in the status line JSON. Two recorded runs of a role session show the fields of `rate_limit_event` with their values replaced, so what is left of it is the range of the used share, the unit of the reset time, the windows a turn lists and what a refresh costs, read from real values. Also check whether Codex has similar values ([Reading usage limits](#reading-usage-limits)).
- **AgenticSeal's cost per stage:** Measure with `seal payload` and `seal cost`.
- **Startup tokens saved by the rules moved into structure:** The startup bundle per agent (agent definition, core, agent contract, CLAUDE.md), measured with `seal payload` on 2026-11-17, is about 12,000 tokens for framer and about 10,500 tokens each for crafter, proofer and sealer (estimated at 1 token per 3.2 bytes). In one work item proofer is launched for several rounds, so this bundle is paid for several times. Sort each sentence by "does it need judgment, or can the daemon, permissions or the output format (`--json-schema`) enforce it", remove the enforced sentences, and measure the bundle again. The same bundle is read cheaply from the prompt cache, so the savings will likely be smaller than the byte ratio. One real proofer round launched with the role bundle started at 33,249 tokens, about 15,600 more than a plain session recorded on 2.1.327 (measured once on Claude Code 2.1.330, 2026-11-22, issue #38). That total holds Claude Code's own prompt and tools, the role's definition and the appended rules file of 36,274 bytes, and the share of the appended file in it is not measured.
- **A start of the app that an agent makes on a person's machine sets `OWLERY_BACKGROUND=1`, and what only a person's start shows is measured by a person.** Without it the window takes the system's focus, so the person's keys reach the agent's pane and a Korean composition the person has under way ends. With it the window opens without the focus and without a Dock icon, and it ignores the mouse, so the person's pointer passing over it reaches nothing in it and their clicks land in the windows under it. Such a start lacks the Dock icon, the menu bar, the system's focus, the system's pointer, the system's notifications and the window on the screen, which is drawn at opacity 0, so a reading that rests on one of them, such as a typed Korean line, the memory of a window kept in front, a pointer passing over the window, a notification the system shows or what the screen shows of the window, is a run the person makes ([Milestones](roadmap.md#milestones), `apps/desktop/measurements/memory.md`).
- **An agent runs one built-app file alone while it works on a case of that file, and all the built-app files in one batch when a phase or a fix pass ends.** A built-app file is a test file that imports `buildApp` from the suite's helper, `apps/desktop/test/built-app.ts`, which is how the suite's configuration tells such a file from the others. Most of them start the built app in every run, and some start it only where a variable of their own is set, as the measurements and the screenshots do. `pnpm run test:app`, run in `apps/desktop` with `OWLERY_BACKGROUND=1`, is the batch: it runs those files one at a time and no other file. The repository's broad gate runs them again with the rest of the suite. Each built-app file that starts the app launches one of its own. One app left open for every file was measured to save less than a second for each file, and a reset between files would have to clear everything the app's main process holds, so the files share no app (`apps/desktop/measurements/built-app-launch.md`, measured with `pnpm run measure:launch`).

|---|---|---|
| May the user's Claude Code be launched headless | Run role sessions in headless mode / launch them only in a terminal and read state through hooks | What Anthropic's published documents say, judged again when they change ([Authentication of the Claude adapter](#authentication-of-the-claude-adapter)). Whether to cut down to the latter depends on whether the repository only needs to hold what the PR check and people outside the app must read, and on what the settle (folding records into the policy documents after a release) reads |

| Sessions with the CLI's own remote feature on | Owlery leaves that session's permission requests to that feature / both show them, and the first answer counts | Claude Code has no hook that reports Remote Control is on, so the daemon cannot tell when the person turns it on themselves |
| When branches built by other agents get an inspection | After the first version, as now / pull it into the first version | Are the first users people who already run Codex alongside Claude Code? What draws these users in is a branch Codex built getting Claude's inspection |
| Connection library | iroh / WebRTC data channels | Can the React Native phone app use iroh, and which reaches the daemon directly more often on the networks people actually use ([Connecting from outside](#connecting-from-outside-phones-and-other-machines)) |
| Contributor agreement | Require a CLA / take contributions under the Developer Certificate of Origin (DCO) only | A CLA keeps the license changeable but adds a step that turns some contributors away. A DCO only certifies that the contributor may submit the code, so the license could no longer change without everyone's consent ([License and code from other projects](#license-and-code-from-other-projects)) |
| Linux | Ship a community build next to macOS / wait until after Windows | Electron makes the build cheap and many open-source maintainers work on Linux, but every supported platform needs its own testing, and Linux has more open terminal issues around Wayland, Nvidia and WebGL ([Platforms and their order](#platforms-and-their-order)) |
| Holding the terminals apart from the daemon | Nothing, as now / hand each terminal's descriptor to the next daemon / a process of its own that holds them / Claude Code's own background sessions | How often the daemon's log shows a restart that ended a working agent, and how often it shows a crash, what a resume costs in time and tokens once it is measured, and whether a background session of Claude Code carries Owlery's hooks ([What a session survives](#what-a-session-survives)) |
