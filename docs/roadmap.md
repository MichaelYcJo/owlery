# Roadmap: what Owlery builds, in what order, and when it is done

*English · [한국어](./roadmap.ko.md)*

This document holds one section for each goal of Owlery, and a goal gets its section when its scope is decided. Today that is the first version alone. A goal is named by what it builds and never by a version number, because a release takes its number only when it is cut ([Releases and the tracker](#releases-and-the-tracker)).

## The first version

### Goal

**A person works at the desk in Owlery all day, and every PR goes out with a cleared inspection.**

The first version is the macOS desktop app only ([Platforms and their order](architecture.md#platforms-and-their-order)). It names a goal and not a release: release 0.1.0, the first public release, holds the minimum to publish and not milestones 3 to 5, and the first version is done when its [done criteria](#done-criteria) hold, in whichever release that is.

### Milestones

Each milestone is in use before the work on the next one starts ([Releases and the tracker](#releases-and-the-tracker)).

### Why this order

The order stands on four grounds.

1. **The process comes right after the shell, and the inspection sheet comes with the process.** The shell comes first because the AgenticSeal plugin already shows the value of the process inside Claude Code, so what Owlery has to establish first is an app a person hands work to and steps away from. The process is built on the skeleton milestone 1 connects, for the reason [Build order](architecture.md#build-order) gives. The inspection sheet shows, in the user's own numbers, whether the inspection is worth what it costs. If it came late, it would read as one more count of review findings.
2. **The person's review tools read the inspection.** A hand commit lapses it, a line comment reaches the crafter as a review finding, and the merge button asks whether it is cleared ([File explorer and editor](product.md#file-explorer-and-editor)). Built before the inspection, each of them is built once without it and again with it.
3. **The process is the part whose structure can still change.** Whether role sessions may run headless is a judgment that is made again when its grounds change (the "May the user's Claude Code be launched headless" row of [Open decisions](architecture.md#open-decisions) in architecture.md). A move to terminals read through hooks costs less while less is built on the daemon.
4. **Daily use does not wait for milestone 4.** Milestone 1 carries what makes a terminal usable all day. The Owl Chain was to judge this repository's pull requests from the pull request of issue #176 on, which moved to release 0.0.5 on 2026-11-25, to the milestone `owner: by hand` on 2026-11-26, to `release: 0.1.0` on 2026-11-27 on the owner's word, and later that day to `after launch: first findings and conveniences`. The owner builds that one in a Claude Code pane of the build that holds issues #181 and #146, and issue #184 records the walk. The Owl Chain inspects this repository's pull requests from this repository's own move to IADD's forms on: issue #354 moved its records to `agentory/` and its check to `owlery-inspection.yml` at 0.2.0 in one commit right after the tag `v0.2.0`, once the AgenticSeal plugin's release 0.40.0 had taken IADD's names. The pull requests before it carry the seal of the AgenticSeal plugin. Those of releases 0.0.1 and 0.0.2 do because Owlery gave no seal until milestone 2 was built. Every pull request of release 0.0.3 does, #181 and #146 among them, and so does every pull request of release 0.0.4: the Owl Chain ran #225's first review rounds in the owner's pane, and the plugin's chain finished its rounds and its seal. Every pull request of releases 0.0.5, 0.1.0 and 0.2.0 carries the plugin's seal too. The pane that carries the Owl Chain is what #181 builds, this repository's check was the plugin's until the pull request of issue #146, and the last of them, #160's, opened before #176's. So the first done criterion holds from the first PR the project's own work opened. This repository's pull requests are checked by Owlery's own check from the pull request of issue #146 on ([Where Owlery started](architecture.md#where-owlery-started)).

**The milestone `workflows: a person's own, and shared` comes after milestone 3 and before milestone 4.** Issue #324 placed it so on 2026-11-28, after #322 wrote the Owl Chain as the first workflow file. Milestone 3 gives the Owl Chain its frame and craft stages (#52, #54, #55) and a stage's default model (#129), and the format of a workflow settles once those stage kinds exist, so a person's own workflow is read after them. The window's editor of a workflow stands on milestone 4's file view (#180), so it is built in milestone 4 (#350).

The process is split into milestones 2 and 3 because inspecting a branch that exists is the smaller half. It needs only the branch, and it produces the first numbers on the inspection sheet. That half is where a driven branch's inspection comes from. Milestone 2 built it as the daemon's chain behind a button. Since release 0.0.3 the pane's own session runs it as the Owl Chain, and the daemon's chain waits for milestone 3, which starts it for a handed-over issue.

The rejected order builds milestone 4 before the process. The staging, the hand commit, the line comments and the merge button would then ship without the inspection and be reworked in the milestone after.

**An issue labelled `owner runs` is the owner's, and no agent takes it.** The owner does it by hand or runs it through Owlery itself, so an issue in another milestone than `owner: by hand` can carry the label too.

**A new issue takes the first milestone below whose test it meets, read from the top.** The tests stand in an order because one issue can meet two of them, and then the order decides.

1. It blocks the checks or the publication of the release that is open: that release's milestone, `release: <version>`, and on the owner's word only.
2. It builds what a row of [Milestones](#milestones) names, and the table above names a milestone for that row: that milestone.
3. Only the owner can do it: `owner: by hand`.
4. It is a defect or a gap that a person met in what has shipped: `after launch: first findings and conveniences`.
5. It is a boundary or an edge case that building found and no person has met yet: `hardening: boundaries and edge cases`.

**An issue with no milestone, and with no line on it that says why, is not yet sorted.** A person outside the repository cannot set a milestone, because GitHub lets only an account with triage access or more set one, so their issue arrives with none. The orchestrator sorts such an issue by the list above and leaves one line on the issue that says which test placed it. Tests 2 to 5 wait for nobody. Under test 1 the line names the release and what the issue blocks, the orchestrator asks the owner, and the issue keeps no milestone until the owner's word. Where the release ships without that word, the orchestrator sorts the issue again by tests 2 to 5. The list does not decide an issue that meets none of its tests, nor one that asks for what [Not in the first version](#not-in-the-first-version) or [After the first version](#after-the-first-version) holds outside the first version, whichever test it meets. The orchestrator asks the owner then and writes the answer on the issue, also where the answer leaves the issue with no milestone, as work that waits for what comes [after the first version](#after-the-first-version) is left.

**From release 0.0.3 the Owl Chain in a pane runs from the review rounds to the inspection, on what the session built.** The pane's session is the builder, and the bundle holds no framer. Design and implementation as stages of the process, and the daemon's chain started for a handed-over issue, come with milestone 3 (issues #54 and #55). Owlery reads no cost of a pane's stages, since no hook carries one, and the inspection sheet of such a work item says so. The first reading of what a pane's session used is issue #73's, in the milestone `after launch: first findings and conveniences`, which reads the subscription's usage limit through the pane's status line.

- **Owlery stays on 0.x.** It moves to 1.0.0 only when the owner decides so in words, and an agent never chooses it.
- **A public release's number comes from the change since the last public release that a person feels most.** The minor number moves where a person would feel a new workflow or capability. The patch number moves where the release holds fixes, polish and improvements within what exists. The orchestrator proposes the number with its grounds, and the owner approves it, when the release branch is cut until issue #279 lands and at the release's close from then on, as the two bullets below state.
- **0.1.0 is the first public release, and no 0.0.x release follows it.**
- **Each release is built on a release branch of its own.** The branch `release/v<version>` is cut from `main` when the work on the release starts, after the release before it has merged there, and every pull request of the release merges into it. The first of those pull requests moves the version. When the release is done, one pull request merges the branch into `main` and closes the release's issues, and that merge is tagged `v<version>`. So `main` always holds the last release. Until issue #279 lands, the orchestrator proposes the number when it cuts the branch, by the measure above and from the issues the release is cut for, and the owner approves it then. The number stays after the cut, because a connected repository's check clones the branch `release/v<version>` of its pinned version until the tag exists (`apps/desktop/src/daemon/records-place.ts`).
- **Later, pull requests merge into `main`, and a release branch is cut only when a release is cut.** That change is issue #279, in the milestone `after launch: first findings and conveniences`, and the pin of the check `inspection` and the settle change with it. The orchestrator's proposal then moves to the release's close.
- **Later, a beta channel lets a release soak before it is stable.** It comes once Owlery has users, and issue #280, in the same milestone, holds it.
- **Every release is a git tag with a GitHub Release, whose note is built from the release's changelog fragments.** From release 0.0.5 on, the workflow of issue #78 builds a `.dmg` at the release's tag and attaches it to the GitHub release. The `.dmg` is signed and notarized from the first build made after the Developer ID certificate's secrets are in the repository, and is signed ad hoc until then ([Platforms and their order](architecture.md#platforms-and-their-order)). The releases below 0.1.0 are the owner's own, and 0.1.0 is the first published for others. The settle removes the work items' records with their fragments, and its pull request merges into the release branch before the release merges into `main`, so the note is built from the fragments as they stood at the commit before the settle removed them.
- **A release of this repository is settled with the AgenticSeal plugin's `agentic settle --apply`, run directly.** This repository's records stand under `agentory/` since issue #354 ([Where Owlery started](architecture.md#where-owlery-started)), where both the plugin's settle and Owlery's settle command read them. `pnpm --filter @owlery/desktop run settle` reads every work item's `decisions.md` under a repository's `agentory/threads/` with the daemon's reader, and names each directory that holds a `reversed` decision, an `open` question or a block it cannot read, with each row that keeps it. With `--list` it prints the decisions made without asking in the release, which the release's pull request and its note carry. It removes no directory and runs no other tool. A settle of Owlery's own, which removes the directories, is issue #139's.
  check: apps/desktop/test/settle.test.ts
- **A release's pull requests merge into its branch by squash, and the release branch merges into `main` by a merge commit.** GitHub rulesets on the repository enforce both, and the repository's admins may bypass them (the owner, 2026-11-20). So each work item is one commit on the release branch.
- **A job of the `check` or the `package` workflow that GitHub cancelled because no hosted runner took it is run again by the repository, and no other job is.** GitHub gives up on a macOS job it could not place in about 15 minutes and marks it cancelled, with the annotation `The job was not acquired by Runner of type hosted even after multiple attempts`. The workflow `.github/workflows/rerun-unstarted.yml` reads each completed attempt of those two workflows and reruns a job only where it was cancelled with no runner, no step and that annotation. It reruns no job that ran, none that a newer push or a person cancelled, none of a pull request whose branch has moved, and none of an attempt numbered 5 or more, so a fifth such cancellation stays for whoever waits on the run. The workflow starts from the copy of its file on `main`, so it runs from the merge into `main` of the release that holds it.
  check: apps/desktop/test/rerun-unstarted.test.ts
- **A case that fails under load or on the hosted runner and passes alone gets an issue that finds its cause, and the load is not its cause until a run shows it.** A run again alone, or a rerun of the job, lets the pull request merge, and the issue keeps the case. Every such case that release 0.1.0 diagnosed, some of them open since release 0.0.4, had a cause in the code or in the case: node-pty left two pseudo-terminals open in the daemon for each pane it started (#300), cases pressed or read in a dialog before the daemon's answer was drawn (#244, #207), a case's stand-in missed a prompt that #127 had changed (#321), and the "New work item" form took a late close event as its own (#328). Two of those causes were the shipped app's.
- **A work item that makes a bullet of an earlier changelog fragment of the same release untrue rewrites that bullet in its own pull request.** The release's note is built from its fragments, so a bullet left as it was would ship beside the one that contradicts it. The release's settle reads every fragment against the release branch's head before it removes the records, and rewrites a bullet no work item rewrote.
- **A decision that shapes an open issue goes into that issue's body, as a section with its date, and not into a new issue.** A comment the decision supersedes is edited to point at that section. A new issue is for a follow-up that no open issue covers, such as a defect found while building.
- **A defect of the review chain is filed in both repositories, and each fixes it with its own means.** A defect found in this repository's own runs of the chain, such as a kind of finding that keeps costing review rounds, is diagnosed once. Then it gets an AgenticSeal issue, which changes the plugin's rules and scripts, and an Owlery issue, which designs what Owlery's daemon holds in code: the order the roles run in, the tools each session gets, and the exact checks between them. The Owlery issue designs and does not port: the role bundle is Owlery's own and follows no AgenticSeal release (`apps/desktop/role-bundle/README.md`). A rule whose question is one of meaning stays a rule of the bundle, and the daemon may report it and blocks on none. AgenticSeal issues #1612 to #1615 and Owlery issue #206 were the first pair (the owner, 2026-11-25).
- **Each milestone has to be in effect before the next one's work starts.** The owner works in the build of milestone 1 while building milestone 2, and the Owl Chain inspects Owlery's own PRs from this repository's own move to IADD's forms on ([Why this order](#why-this-order), ground 4).
- **A number fixed when a release's milestone opens was the rule until 2026-11-26, and each change of scope moved it.** Milestone 3 and every release after it moved one number on 2026-11-25, and the owner's cut of 0.1.0 as the minimum to publish on 2026-11-26 left the three numbers that milestones 3, 4 and hardening held on no release. A number set when a release's branch is cut is set for that one release alone, and from issue #279 on a number set when the release is cut follows what merged.
- **A single milestone for every issue of the first version would mark no goal as done.** No event in the tracker would then mark a milestone as done.
- **A 1.x number at launch, which Orca took, is not taken.** It tells a user that the product is stable, which only the owner decides.

### Work that runs beside the milestones

The trial on other people's PRs needs no milestone, because it runs on the AgenticSeal plugin. It takes open-source PRs that are already merged, resets each to its state before the merge, runs the AgenticSeal process on it, and counts the defects the process caught that a human reviewer or a later commit fixed. It starts before milestone 2 is done, because a weak result changes the direction.

No milestone of the first version waits on Anthropic. The judgment on headless launches is made against published documents, and its home is the "May the user's Claude Code be launched headless" row of [Open decisions](architecture.md#open-decisions) in architecture.md.

### Done criteria

The first version is done when all five hold.

| Criterion | How a person checks it |
|---|---|
| Every PR opened from one of the project's own work items carries a passed check of its chain | Take the merged PRs whose commits name a work item in the repository's records. Each has that check passed at its merged head. The check is the one the repository's installed workflow posts: the AgenticSeal plugin's until the pull request of issue #146, Owlery's check `seal` from it on until issue #354's move, and Owlery's check `inspection` from that move on. A PR that an outside contributor sends is not counted |
| The ledger is public | The published ledger opens without the app. For each work item it shows the cost of each stage beside the defects caught |
| The Korean input regression test passes | At the release that checks these criteria, the replayed case passes in the app's checks, and the typed run a person makes for that release exits without a failed line ([Milestones](#milestones)) |
| What the reference scenes cost is measured and published, beside the same scenes in comparable products | The published measurements of the app itself, the four-terminal scene of about 500 MB among them, each with its date, its commit and its method, and with the agents' processes counted apart. The same scenes measured in comparable products stand beside them. No number decides the criterion, because no number of a scene is a limit on a feature ([Memory design](architecture.md#memory-design)) |
| At least one result of the trial on other people's PRs is out | The published result, with its target repositories, the number of PRs and the count of defects |
