# Changelog: the app ships the roles its background sessions take

Issue #38. Owlery could start a background session of your `claude`, with no window, and that session had no role. The app held no definition of a reviewer, of a builder that fixes what a review found, or of the party that gives the final verdict, so nothing could start one. Nothing read the version of your `claude` either.

- **The app now ships a role bundle.** It is a folder of documents inside the app: the definitions of four roles and the rules they work by. The roles are the proofer, which reviews, the crafter, which fixes what a review found, the sealer, which gives the final verdict, and the orchestrator, which judges whether the review rounds are converging and rules on a question a stage asks. The orchestrator's definition came with the review rounds (#41).
- **The documents are taken from AgenticSeal 0.38.4, under its MIT License.** The licence text is in the bundle as `LICENSE`. The bundle's `README.md` names the release its files started from; from #40 on they are Owlery's own. The bundle holds documents only: no hook, no script and no drawing.
- **Owlery's background process, the daemon, can start a session as one of the four roles.** It gives your `claude` the bundle for that session alone, picks the role's definition, and appends the role's rules to the session's system prompt. "Get a seal" in a work item's view starts the review rounds, the fix passes, the orchestrator's judgments and the sealer's verdict, each a session of its role.
- **A role session installs nothing into your Claude Code.** Owlery writes no settings file and no plugin list of yours. Claude Code itself counts the plugins a session loaded in its own state file, `~/.claude.json`, under `pluginUsage`, and a role session adds the entry `owlery@inline` there.
- **A role session that did not get its role is failed.** Claude Code 2.1.330 starts a plain session, with no error, where the bundle or the role's name is wrong. Owlery reads the session's first line, and where it does not list the role, Owlery stops the session and shows why.
- **The oldest version of Claude Code that Owlery's role sessions were checked on is 2.1.326.** The daemon reads the version of your `claude` when it starts. Where yours is older, the status line at the foot of the sidebar reads: `Claude Code 2.1.300 is older than 2.1.326, the oldest version Owlery's role sessions were checked on. Run "claude update" in a terminal.`
- **An older version still runs.** Owlery starts a session on it all the same, because an older version may work. Where it does not, the session's line shows what `claude` printed.
- **The notice goes after you update.** While the notice stands, the daemon reads the version again each time a window connects to it, so the next time you open Owlery the line is gone. A window that stays open keeps the line until then.
- **Each start of the daemon now runs your login shell once, in the background.** It asks the shell where `claude` is, as the first background session did before, and then runs `claude --version`. Where no `claude` is found, the status line says nothing of it, and the first session says what failed.
- **After an update, the notice is not shown until Owlery's daemon restarts.** A daemon started by the build before this one reads no version. The status line already says that such a daemon is from another build.
- **For a client of the daemon:** `ask` takes an optional `role`, a pair of `role` and `stage`: `proofer` at `round`, `crafter` at `fix-pass` or `sealer` at `seal`. Any other pair is answered with the error `no role <role> at the stage <stage>`, and nothing starts. Each headless session carries `role`, which is null for a session with none. `ready` carries `agentNotice`, the sentence above or null, and a new message `agentNotice`, with `notice`, follows whenever it changes.
- **For a contributor:** `pnpm --filter @owlery/desktop run role:run` starts one real proofer session on your own Claude login and spends your usage. The suite never runs it.
