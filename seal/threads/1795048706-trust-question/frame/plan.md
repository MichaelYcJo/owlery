# Implementation Plan: a Claude Code pane that waits before its session starts

## Technical context

The tree as read at `0844f96`, and read again at `54fc0ac`, after pull requests #33 (issue #19) and #37 (issue #18) merged into `release/v0.0.1` and this branch was rebased onto it. The coordinates below are the later reading's.

`apps/desktop/src/daemon/daemon.ts` holds the panes. `startSession` (line 379) starts a pane's process and lists it with `state`, `stateSince`, `stateText` and `stateTool` null. `agentEvent` (line 136) is the one place a state changes: it maps the hook's name with `agentEventFor`, returns where the name is not mapped, and gives a pane of a kind that reports state what `agentStateAfter` says. Where the state changed it also sets the state's time from the daemon's clock and its text and tool from `agentSaid`, and sends the inbox. A pane leaves in three places: its process's exit (`terminal.onExit`, line 396), a client's `close` (line 267) and `Daemon#close` (line 153). `DaemonOptions` (line 33) already carries the times a case shortens, `idleExitMs`, `commitPollMs` and `readyWaitMs` among them, and `now`, the clock a case sets. The cases of `apps/desktop/test/daemon.test.ts` wait on real timers.

`apps/desktop/src/daemon/main.ts` (line 48) gives a Claude Code pane the command of `claudePaneCommand` and the two `OWLERY_` variables the hook's relay reads. The window is `apps/desktop/src/renderer/`: `view.ts` holds what it says as functions with no page, and `list.ts`, `sidebar.ts`, `summary.ts`, `work-item-view.ts` and `renderer.ts` draw it. It reads a pane's `state` and `stateSince`, and `stateText` and `stateTool` where they are not null; `frame/design.md` *Grounding* lists what each part shows for a pane that waits with neither. Tests run with vitest in Electron's Node (`pnpm run test`), and `pnpm run check` is the typecheck and the tests. The installed Claude Code was 2.1.327 when the probes ran.

No agent starts the app, and the built daemon runs with no window (`frame/design.md` *Grounding*). The phase therefore drives the daemon as a client and leaves the drawn window, scenario 8, not run.

What Claude Code does at the trust question is in `frame/design.md` *Grounding*, from the probes.

**The failure scenario of the chosen approach.** The rule calls a pane waiting on the clock. A start that takes longer than 10 seconds, such as a CLI that updates itself first or a login shell with a slow profile, is shown as waiting by mistake: its line moves under "Waiting for you", the sidebar's bell counts it, a person who is not looking at the pane is notified once, and a window opened in that time offers "Answer the first question" for it. The session's start then takes the state away. A CLI release that stops sending an event at its session's start leaves every pane `waiting` from its tenth second until the first prompt. A CLI release that starts sending an event at the trust question makes the rule do nothing there, and the line then says whatever that event maps to. The rule also fires at every other question a CLI asks before its session starts, a login among them, which is what the line should say there, though no probe ran one.

## Alternatives considered

| Approach | Failure scenario | Verdict |
|---|---|---|
| Keep `SessionInfo.state` as `AgentState \| null`, and let the daemon set `waiting` where a pane's first event is missing after a fixed time | The scenario above: a start slower than the time is notified once by mistake | Chosen. The premise that keeps the structure is that every reader of the state reads three states and null and no more. Checked at `54fc0ac` with `git grep` for `.state`, `stateSince`, `stateText` and `stateTool` under `apps/desktop/src` (`executed`), and with `view.ts` and `daemon.ts` read whole. The readers are `view.ts` (`inboxLine`, `inboxSummary`, `inboxGroups`, `matchWorkItems`, `historyLines`, `changesSince`, `summaryControls`, `saidBy` and `notificationFor`), the pages that draw them (`list.ts`, `sidebar.ts`, `summary.ts`, `work-item-view.ts`, `renderer.ts`) and `daemon/last-look.ts`. Each reads the four state fields and nothing else of a pane's start, and each takes a null text and a null tool as nothing said |
| Replace the structure: give the protocol a state for the time before the first event (`starting`, with the pane's start time), and let each client decide when a start has lasted too long | The decision of what waits moves into the window, and the phone repeats it with a clock of its own, against `docs/architecture.md` *The phone: the terminal session as a chat* ("no state lives on the UI side"). The new value reaches every reader of the state the first row lists: the groups, the filter, the summary and the notification. `last-look.ts#isSession` takes a file as a look only where each state is one of today's three or null, so a look written with the new value is no look to a daemon of an earlier build. Issue #9's protocol edits meet it as well | Rejected: the daemon holds the clock, and the protocol's types stay as they are |
| List a pane as `waiting` from its start, with no timer, until its first event | Every pane is `waiting` for the 1.1 to 1.4 seconds before its session's start, so every pane opened behind another one notifies "Waiting for you" by mistake | Rejected by `docs/architecture.md` *Overall layout*: a decision is never put in front of a person by mistake |
| Count the time from a line the pane's shell sends to the hook socket just before `exec claude`, so the login shell's start is not counted | The hook socket gains a second writer and a second line format. The whole start, shell included, was 1.1 to 1.4 seconds in the probes, so there is nothing measured to take out | Rejected until a start is measured that the shell makes slow |
| Read `~/.claude.json` to learn whether the repository is trusted, and list the pane as waiting at once where it is not | The file's format is not public, and the entry is kept under the repository's folder and not the worktree's. A release that moves the record shows nothing, with no error. The daemon would also read a file of the user's CLI that no adapter owns | Rejected |
| Write the trust record for the worktree before the pane starts, or start `claude` with an option that bypasses its checks | The first changes a file of the user's CLI and answers a safety question in the person's place. The second turns the CLI's checks off | Rejected by `docs/architecture.md` *The phone* ("The user's own settings files are not changed") and `docs/roadmap.md` *Milestones* row 1 ("Owlery never turns a permission check off") |
| Find the question's words in the pane's output | The words change with the CLI's version and language, and a program in the pane that prints them is taken for the question | Rejected by `docs/architecture.md` *Overall layout*: state is never guessed from what the terminal prints |
| Change nothing in the daemon and record the run alone, since the question is asked once per repository | The first work item of a repository new to Claude Code is the first thing a new user of Owlery does there, and its line says nothing while the session waits | Rejected by the owner, who answered `frame/questions.md` Q1 with option (a) on 2026-11-19 |

## Operational impact

A Claude Code pane that has sent no event 10 seconds after its start is listed as waiting, with the time it was called so and with no text and no tool. Its work item's line moves under "Waiting for you" and the sidebar's bell counts it, and a pane that is not in front of a focused window then raises the "Waiting for you" notification. A person sees this at the trust question of a repository new to Claude Code, and at any other question the CLI asks before its session starts. No dependency, environment variable or migration is added. The version does not move.
