## Scope

1. **A pane that says nothing after its start is shown as waiting.** For a pane of a kind that reports state (`PaneKindInfo.reportsState`), the daemon waits a fixed time from the pane's start. Where the pane is still alive, is still on the daemon's lists, and no event has arrived under its id, the daemon sets the session's `state` to `waiting` and its `stateSince` to the daemon's clock at that moment, which is `options.now ?? Date.now` as in `agentEvent`. It leaves `stateText` and `stateTool` null, because no event said anything and the daemon does not know what the CLI asks. It then sends the inbox, as any change of state does.
2. **The time is 10 seconds by default**, held in `DaemonOptions` as `silentStartMs`, so a case sets a short one. `apps/desktop/src/daemon/main.ts` passes none. Ten seconds is seven times the slowest report seen (*Grounding*), which keeps a slow start from being called waiting, and a person who walked away is still notified within the minute.
3. **The first event ends the wait for good.** Any event `Daemon#agentEvent` receives under the pane's id cancels the timer, whichever hook it names. The cancel therefore stands before the return `agentEvent` makes for a hook name `agentEventFor` does not map (`apps/desktop/src/daemon/daemon.ts:138` at `3e715e4`). The timer is also cancelled when the pane's process exits, when a client closes the pane, and in `Daemon#close`. It runs once for a pane and is never started again.
4. **A state set by silence is replaced as any state is.** `agentEvent` is not changed beyond the cancel of item 3, so the next event `agentStateAfter` maps gives the session its state, its time, its text and its tool. After the person answers the question, the session's start gives no state and no time, and a prompt gives `working` with the time of the prompt. An event that maps to `waiting` and arrives while the pane waits by silence changes nothing, as for any state an event leaves as it was (*Grounding*), so the session keeps the time of the silence and carries neither the event's text nor its tool. No launch of the probes reached this: the first event of each was the session's start, which clears the state. A pane whose process exits gives its line no state, as today.
5. **The comments of `apps/desktop/src/shared/protocol.ts` that the silent start makes false say the new fact** (coordinates at `3e715e4`).
   - On `SessionInfo.state` (`:92`): the state is null until the agent's first event or until the silent start is over, whichever comes first.
   - On `AgentState` (`:19`), which says a state is what the agent's last event says: `waiting` is also what a pane that sent no event after its start is called.
   - On `SessionInfo.stateText` (`:96`) and `SessionInfo.stateTool` (`:98`), each of which names "the event that began `state`": each is also null for a state that no event began.
6. Out of scope:
   - Saying on the line why the pane waits. The daemon does not know whether the CLI asks about trust, a login or something else, and the person reads it in the pane.
   - Answering the question for the person, opening the pane past it, and reading or writing `~/.claude.json`.
   - A change to the window. The line, its group, the sidebar, the preview, the view, the summary and the notification read `SessionInfo.state` and `stateSince`, and already show a `waiting` state that carries neither a text nor a tool (*Grounding*).
   - A change to what an event does to a session that is already in the state the event maps to, which pull request #37 decided (*Scope* item 4).
   - A change to `agentStateAfter` or to the events Owlery listens to.
   - What a session sends when it sits idle for longer than 75 seconds or compacts its conversation, which `seal/threads/1795019054-inbox/gaps.md` *Not verified* leaves to a person.
