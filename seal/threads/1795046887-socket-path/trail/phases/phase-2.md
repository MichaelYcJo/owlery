## What this phase found

**The frame holds.** The five files `frame/design.md` *Data & interfaces* names outside `hooks.ts` were opened at `d3a05cf` and are as *Grounding* states them: `src/daemon/main.ts` ends with `void main();`, `src/main/daemon-client.ts#ensureDaemon` polls for 10 seconds whatever became of the process it started, `src/main/main.ts` lets the rejection through the handler of `Channel.daemon`, and `connect` in `src/renderer/renderer.ts` awaits `window.owlery.daemon()` with nothing to catch it. No case imported `src/main/daemon-client.ts`. The ticket's failure was reproduced in the built app before the records were written; *The drive* below has it.

**What was built.** The build is `47a5e27`.

- `src/daemon/main.ts` catches a failure of `main`, writes the error's message alone to its error stream, and exits with code 1.
- `ensureDaemon` listens for the exit of the process it started. At its next look, at most 100 ms later, it rejects with the sentence of *Data & interfaces*. The line is the last line that is not empty of what the log gained in this start: the log's size is read before the process starts, and only the bytes after it are read.
- The handler of `Channel.daemon` answers `{ error }` with the rejection's message. `connect` writes that sentence into the status line and returns, so it opens no connection and sets no reload.
- `DaemonFailure` and the new answer of `OwleryApi.daemon` are in `src/shared/ipc.ts`.

**Departures from the frame, each with its grounds.**

- *`ensureDaemon` takes a third argument, `timeoutMs`, 10 000 by default.* *Scope* item 5 says a daemon that lives and does not answer is refused as today. The change rewrites the loop that refusal lives in, and a case that waits the 10 seconds out would add them to every run of the suite. The case gives 600 ms and expects the refusal between 600 ms and 3 seconds, with the message of today. The app's one call gives no third argument. `answers` in the same file already takes its wait as an argument. Judged against *Scope* item 5.
- *A daemon that a signal ended is named by the signal.* *Data & interfaces* gives `(exit code <N>)`. Node gives no exit code for a process a signal ended, so the sentence would read `exit code null`. It reads `(signal SIGKILL)` there, with the line in front of it where the process wrote one. Judged against *Scope* item 6: the sentence is what a person reads.
- *The line is trimmed.* A line of the log that holds only spaces counts as empty, and the line shown loses the spaces at its ends.
- *Two cases beyond scenario 5.* "gives the discovery of the daemon it started" starts a script that answers as a daemon does, because the loop that returns the discovery is the loop this phase rewrote and no case covered it. "names the exit code alone where the daemon wrote nothing in this start, whatever an earlier start left in the log" writes a line into the log first, because the log is appended at every start and the sentence must not show an earlier start's line.
