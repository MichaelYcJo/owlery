## Scope

In scope, as numbered items. The **pane in front** is the pane `work-item-view.ts` holds as `front`: the one with the keyboard, in the view on screen.

1. **The window shows its own page and nothing else.** The main process refuses every navigation of the window whose URL is not the URL the window already shows, so the reload of `renderer.ts:368` passes and nothing else does. It refuses every new window the page asks for. Both are set on the window `main.ts#createWindow` makes.
2. **A file dropped on a pane types its path.** A pane's element accepts a drag that carries files. At the drop, the window reads each file's path through the preload, in the order the drop gives them. It leaves out a file that has no path on disk and a path that holds a control character (a code below 32, or 127). It writes the paths that are left as one text: each path with a backslash before every ASCII character that is not a letter, a digit or one of `/ . _ - + = : , @ %`, the paths joined by one space, and one space after the last. A character outside ASCII is written as it is. The text is handed to that pane's terminal as a paste (`Terminal.paste`), so a program that asked for bracketed paste receives it as one. The pane that took the drop becomes the pane in front. A drop that leaves no path types nothing. A drop anywhere else in the window does nothing.
3. **A URL in a pane opens in the system browser on Command+click.** Each terminal screen loads `@xterm/addon-web-links`. A click on a link opens it only where the Command key is held (the Control key where the keyboard has none), and a click without it does what it does today. A link a program prints with the OSC 8 sequence is opened under the same rule, through the terminal's `linkHandler` option, in place of xterm's own question. The window asks the main process to open the address over a new channel. The main process opens an address only where it parses as a URL whose scheme is `http` or `https`, and answers whether it opened it.
4. **Who opens the address.** Where the app's environment holds `OWLERY_OPENER`, the main process runs that program with the address as its one argument, through `execFile` and no shell. Otherwise, in an app started in the background (`OWLERY_BACKGROUND=1`), it opens nothing and answers `false`. Otherwise it calls Electron's `shell.openExternal`. The main process takes `OWLERY_OPENER` out of its environment at load, as it takes `OWLERY_BACKGROUND`, so the daemon and the panes' processes start without it.
5. **Shift+Enter sends a line feed.** A press of Enter with the Shift key and no other modifier, outside a composition, sends the one byte `0a` to the pane, through the path a typed key takes, and the terminal sends nothing else for that press. Outside a composition means that the key event's `isComposing` is false and its `keyCode` is not 229. This holds for every kind of pane. Enter and Option+Enter send what they send today.
6. **The app has a menu of its own.** The main process sets the application menu before it makes the window. On macOS it holds: the app's menu with "About Owlery", the Services menu, "Hide Owlery", "Hide Others", "Show All" and "Quit Owlery"; "File" with "Close Window" on Shift+Command+W; and "Edit", "View" and "Window" with the items Electron's default menu holds today, as the probe's output lists them. On another platform "File" also holds "Quit". No item of the menu is bound to a key `view.ts#commandKey` reads.
7. **Cmd+W closes the pane in front.** `view.ts#commandKey` reads W with the Command key, under the conditions it reads K and N. The window then closes the pane in front, as a press of that pane's "×" does (item 8). Where no pane is in front, on any screen, the key does nothing. The window keeps the key from the terminal in both cases.
8. **Closing a pane whose session is working asks once.** A session is working where its `alive` is true and its `state` is `working`. A press of the "×" of such a pane's tab, or Cmd+W with such a pane in front, opens a dialog in the window. The dialog says "<the tab's label> is working. Closing the pane ends its session." and holds "Cancel", where the keyboard starts, and "Close pane". "Close pane" sends the `close` and closes the dialog. "Cancel" and Escape close the dialog and send nothing. Where the daemon no longer lists the pane while the dialog is open, the dialog closes. After the dialog closes, the keyboard goes to the pane in front. Any other pane closes at the first press, as today. While the dialog is open the window reads none of its keys: the renderer tells `commandKey` and `inboxKey` that a dialog is open where any `dialog` element of the page is open.
9. **The changelog fragment** `changelog.md` says what a person newly sees. Phases 3 and 4 each add what items 10 to 19 change for a person, and rewrite in place the lines of the fragment that those items change: the line on `OWLERY_OPENER`, and the line on Shift+Command+W.
10. **Which text a pane prints is a path.** The window registers one link provider of its own on each terminal screen, beside the add-on of item 3. For the line under the pointer, read whole where it wraps over several rows, the provider takes each run of characters between spaces as a candidate where the run holds a slash and does not hold `://`. It cuts from the candidate's ends the quotes, brackets and punctuation that stand around a path in a sentence, and from its end a line number and a column, written as `:12` or `:12:5`. It asks the main process about the candidates of the line in one request, over a new channel, with the worktree of the pane's work item, or null for a pane that has none. The main process reads a candidate that opens with `/` as it stands, one that opens with `~/` from the person's home folder, and any other from the worktree, and it answers nothing for that last kind where the request names no worktree. It answers, for each candidate, the whole path with every `.` and `..` resolved and whether a folder or a file stands there, or nothing where neither does. A candidate becomes a link only where the answer names a path, and the link covers the candidate as cut, on every row it stands on. Nothing is kept between two requests.
11. **What a link leads to.** A link has one of three targets. A **web address** is the address of a link of item 3, where it parses as a URL whose scheme is `http` or `https`. A **work item's worktree** is a path of item 10 that is the `worktree` of a work item the window lists, other than the one whose view is on screen. **Another path** is every other path of item 10, a folder or a file. A link of item 3 whose address is no web address has no target: no card shows for it, and a click on it asks the main process as phase 2 built, which opens nothing.
12. **What a click on a link does.** One function of `view.ts` answers it from the target, the click's keys and whether the keyboard is a Mac's, and it replaces `view.ts#linkOpens` (`## Removes` row 2). The key is the Command key, and the Control key where the keyboard has none. A click without the key does what it does today. On a web address, a click with the key opens the address as items 3 and 4 state, with or without the Shift key. On a work item's worktree, a click with the key puts that work item's view in front, and a click with the key and the Shift key shows the folder in Finder (item 14). On another path, a click with the key shows the path in Finder, with or without the Shift key.
13. **The card.** `index.html` gains one element, with the id `link-card`. Where the pointer rests on a link that has a target for 300 milliseconds, the card shows under the row the pointer is on, with its left edge at the pointer, moved where it would pass the window's edge. The terminal underlines the link while the pointer is on it, as xterm does for a link. The card's first line is the whole target: the address as the URL parser writes it, which for a link behind a name is the address and not the name, or the whole path. Under it stands one row for each thing the person can do, with the keys that do it at the row's end. A web address has "Open in browser", with "⌘ Click", and "Copy link", with no key. A work item's worktree has "Open work item", with "⌘ Click", and "Open in Finder", with "⇧ ⌘ Click". Another path has "Show in Finder", with "⌘ Click", and "Copy path", with no key. Where the keyboard has no Command key the keys read "Ctrl Click" and "Shift Ctrl Click". Each row is a button, and a press of it does what the row names and takes the card away. The buttons do not take the keyboard from the terminal. A second function of `view.ts` gives the card's lines from the target, and it and the function of item 12 read one table, so a row never names a key the click does not answer. The card leaves 200 milliseconds after the pointer is on neither the link nor the card, and at once at a key pressed in the pane, at a press of a button of the mouse outside the card, and when the pane's menu (item 16) or a dialog opens.
14. **Who shows a path in Finder.** The window asks the main process over a new channel, with the whole path, and the main process answers whether it showed it. It reads the disk again at the request and shows nothing where the path is not a whole one from `/` or nothing stands at it. A file is shown selected in its folder. A folder is opened, except a folder whose name holds a dot after its first character and that holds no `.git` at its top: that one is shown selected in the folder above it, as a file is. No path is ever handed to `shell.openPath` unless it is a folder that this rule opens. Who acts is chosen as item 4 chooses the opener of an address, by the same function: where `OWLERY_OPENER` names a program, that program is run with the path as its one argument for either act; otherwise an app started in the background shows nothing and answers `false`; otherwise Electron's `shell.showItemInFolder` selects and `shell.openPath` opens.
15. **The clipboard.** A row that copies, and the Copy and the Paste of item 16, reach the clipboard through the main process, over two new channels: one writes a text, and one answers the text the clipboard holds. An app started in the background keeps a clipboard of its own in the main process, a text that starts empty, and neither reads nor writes the system's. Any other start reads and writes the system's through Electron's `clipboard`. The channel that writes has the name and the signature issue #93's work item gives its own, `copyText: "owlery:copy-text"`.
16. **A pane's menu.** A `contextmenu` event on a pane's element, which a press of the right button and a press with the Control key both raise, opens a menu drawn in the page, with its corner at the pointer, moved where it would pass the window's edge. The system's own menu does not open. The pane becomes the pane in front. The menu is an element with the role `menu` and the id `pane-menu`, and its items are buttons with the role `menuitem`, in this order: "Copy", "Paste", "Select All", then a rule, "Clear Screen", "Reset Terminal", then a rule, "Close Pane". On a Mac keyboard "Copy" shows "⌘C", "Paste" shows "⌘V" and "Close Pane" shows "⌘W", and no other item shows a key. On another keyboard no item shows a key. "Copy" is disabled where the terminal holds no selection, and it writes the selection to the clipboard (item 15). "Paste" hands the clipboard's text to the terminal as a paste, as a dropped path is handed (item 2), and does nothing where the text is empty. "Select All" selects everything the terminal holds. "Clear Screen" empties the terminal but for the row the cursor is on (`Terminal.clear`), and "Reset Terminal" puts the terminal back to its first state (`Terminal.reset`), which ends every mode a program set, such as mouse reporting or pastes in brackets. Both first have the daemon forget what the pane printed (item 17). "Close Pane" closes the pane as a press of its tab's "×" does (item 8). A press of an item closes the menu and gives the keyboard back to the terminal. Escape, a press outside the menu and a second `contextmenu` close it, and the up and down arrows move through its items. While the menu is open the window reads none of its keys: the renderer's read of an open dialog (item 8) also answers true where an element with the role `menu` stands in the page.
17. **The daemon forgets a pane's output when asked.** The protocol gains one message from the window, `forget`, with a pane's id. The daemon empties what it keeps of that pane's output, so the next replay holds only what the pane printed afterwards. It does nothing for an id it does not list. A daemon of an earlier build does nothing on the message, as on any type it does not know, and its next replay then draws the old output again.
18. **Three editing keys of macOS.** On a Mac keyboard, a press with the Command key and no other modifier, outside a composition as item 5 defines it, sends one byte to the pane through the path a typed key takes, and the terminal sends nothing else for that press: the left arrow sends `01` (Control+A, the line's start), the right arrow sends `05` (Control+E, the line's end), and Backspace sends `15` (Control+U, which deletes to the line's start). This holds for every kind of pane. On a keyboard without the Command key the three presses stay the terminal's. The application menu binds none of the three.
19. **On macOS, closing the window hides it.** In an app on macOS that was not started in the background, a close of the window, by Shift+Command+W, by the red button or by any other way, hides the window and does not destroy it. Its page stays loaded and connected to the daemon, so a session that begins to wait while the window is hidden still raises its notification. One pure function of `background.ts` says whether a close hides: it takes the platform, whether the app started in the background, and whether the app is quitting. The app is quitting from Electron's `before-quit` on, and a close then closes, so "Quit Owlery" ends the app as today. A window that is full screen leaves full screen first and hides once it has left. A hidden window is shown again at the app's `activate` event, which a click on the Dock icon raises, and at a click on a notification, by the `comeForward` of issue #31's work, which this work does not change. The menu's "Close Window" keeps its role and its key (item 6), so the hide is the window's and not the menu's. An app started in the background, and an app on another platform, closes its window as today, and quits with it as `quitsWithLastWindow` answers.

Out of scope.

- An image that is on no disk: one dragged out of a browser, or held on the clipboard. It has no path to type.
