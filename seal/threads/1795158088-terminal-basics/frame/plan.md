**The failure scenario of the chosen approach.** Cmd+W closes a pane only while no menu item is bound to that key, because a menu item takes its key before the page sees it. In six months a work item adds a menu item for something the page reads as a key, such as "New Work Item" on Command+N. The page then never sees that key, the form's key stops working, and no case that types through the debugging port notices, because that port sends a key to the page past the menu. Scenario 9's case is what holds this: it reads the menu Electron built and fails where an item is bound to a key `commandKey` reads. The second scenario is an upgrade of xterm that changes when it calls a custom key handler, or of the link add-on apart from xterm. Scenario 7's case reads the exact bytes, and scenario 8's file reads a composition, so either upgrade fails a case.

**The failure scenarios of what the fold adds.** The first is the window that hides. In six months the page of a hidden window has stopped: its renderer crashed, or a later Chromium freezes a page nobody sees. No notification comes, and the person has no window that would show it, where today a closed window at least tells them that nothing watches. Nothing in this work holds that. `frame/questions.md` Q6 has the owner measure the hidden page once, and raising notifications from the main process is the answer the row on it below leaves to an issue of its own. The hidden page also keeps its terminals, so closing the window frees no memory, as a minimized window frees none today. The second is the provider of paths. A pane prints a path on a volume that answers slowly, the pointer crosses the row, and the main process waits on the disk. The main process therefore reads the disk without blocking (`fs.promises.stat`), and a slow answer only means the text is no link yet. The third is a daemon of an earlier build, which outlives the app: it does nothing on `forget`, so "Clear Screen" clears the window's terminal and the next replay draws the old output again, until that daemon ends. `changelog.md` says so. The fourth is the page's menu beside issue #93's: after that work merges, the page holds two ways to draw a menu until #93's rounds make them one (*Overlap with the release*).

## Operational impact

One dependency is added: `@xterm/addon-web-links` at `0.12.0`. A worktree that takes this work runs `pnpm install` before it builds.

The app reads one new variable of its environment, `OWLERY_OPENER`: the path of a program the main process runs with an address as its one argument, in place of the system's opener. The app takes it out of its environment once it has read it. An app started with `OWLERY_BACKGROUND=1` and without `OWLERY_OPENER` opens no address.

Two keys change for a person. Cmd+W no longer closes the window: it closes the pane in front, and does nothing where none is. Shift+Command+W closes the window. Shift+Enter in a pane sends a line feed where it sent a carriage return.

The suite gains one start of the built app, in `test/terminal-basics.test.ts`, with the window opened in the background as `test/korean-input.test.ts` opens it.

The fold of 2026-11-20 adds the following.

`OWLERY_OPENER` is read more widely: the program it names is also run with a path as its one argument, in place of Finder. An app started with `OWLERY_BACKGROUND=1` and without `OWLERY_OPENER` shows nothing in Finder, and it reads and writes a clipboard of its own, so nothing it copies reaches the system's clipboard.

On macOS, in an app that was not started in the background, the window's close hides the window, and the app's page, its terminals and its connection to the daemon stay. Closing the window therefore frees no memory. Only Quit ends the app. A click on the Dock icon or on a notification shows the window again.

Three more keys change for a person on a Mac: Command with the left arrow, with the right arrow and with Backspace send Control+A, Control+E and Control+U to the pane.

The main process reads the disk when the pointer comes over a line of a pane that holds a text with a slash: one `stat` for each such text, without blocking, and nothing is kept.

No migration. The protocol gains one message from the window, `forget`. A daemon of the build before this one works with this window, with one limit: it does nothing on `forget`, so a pane cleared or reset in the window is drawn with its old output again at the next replay, until that daemon ends. The version does not move.
