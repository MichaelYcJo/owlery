# Phase 1: 1795268971-panes-nothing-can-close

## What this phase found

There is no `frame/`: issue #28 is the frame, and `routing.md` leaves the crafter the one choice it names. It is recorded here with its grounds.

**The choice: an exited pane is closed from the window, and no rule drops it from the list.** Judged against issue #28 *Done when* and the tree at `5d4615e`.

- `paneTabs` in `apps/desktop/src/renderer/view.ts` lists a work item's panes from the daemon's list, "whether their process runs or has exited", and `tabElement` gives each tab its "x"; `closeAsks` asks only for a pane that is alive and working, so an exited pane closes at one press. This came with `5814c92` (release 0.0.1, "give an exited pane its tab from the daemon's list"). The second line of the issue was written against the records of #18, before that commit, and holds no longer for a pane of a work item. Read in `view.ts` and `view.test.ts` *paneTabs* (the cases that list an exited pane among the tabs); the window was not driven for this, so the claim is `read`.
- What remained without a tab was the pane with `workItemId` null: `runningSessions` and the tabs only ever drew a work item's panes. Refusing a start without a work item (the first line) makes that pane impossible, so no pane the daemon lists since this phase lacks a tab and a close, except the case in the next point.
- The pane of an archived work item: an archive ends its panes, and they stay listed as exited (`daemon.ts`, the archive's comment "the pane is listed as exited once its process ends"). The window has no view for an archived work item, so those panes have no tab until the work item is restored, and then each is a tab with its close. Kept on purpose: the restore returns the work item with its panes' last output, and a delete of the work item takes them off the list (`dropWorkItems`). This is the rule that stands, stated here and in the changelog; no code moves for it.
- A rule that dropped every exited pane at its exit was not chosen: it would take from a person the last output of a pane that just failed, which the window shows on purpose (the exit line is kept for the replay).

**The first line.** `Daemon`'s `start` now answers a `workItemId` that is no number with the `error` "a pane opens in a work item", before the check of `continueLatest`, and starts nothing. `DaemonOptions.cwd` and `OWLERY_CWD` in `src/daemon/main.ts` (with its `homedir` import) are removed; `startSession` takes the worktree and a number. `ClientMessage`'s `start` types `workItemId` as required. The window already sent `workItemId` in every start (`work-item-view.ts`, `send({ type: "start", ... workItemId: held.viewing ...})`), so no renderer code moved.

**Kept, with grounds.** `SessionInfo.workItemId` stays `number | null` in `protocol.ts` and its comment now says null comes only from a daemon built before this change. A window can meet such a daemon still running, `last-look.ts` reads a look an earlier build wrote, and `view.ts` / `work-item-view.ts` still test for null; narrowing the type would make those reads wrong for those cases and is a separate change.

**Tests.** The cases of `test/daemon.test.ts` that started a pane without a work item (a script found them by the start message they send, and the full file run then showed the one it converted wrongly, "handles nothing of a client that left before its `ready`", which keeps its own run folder and is back on `daemon`). Each now starts it in work item 1 of a run folder made by `runFolderWithWorkItem` (a new top-level helper `daemonWithWorkItem` wraps it); their `workItemId: null` expectations became 1. Three needed more than that: "lists an archived work item..." provokes its inbox with a `setWorkItem` where it used a start (its stored work items have no real folder); "answers the client that asked before it sends the inbox..." keeps its own `createWorkItem` and its work item 1; "replaces the look..." expects the seeded work item in the look.

**Seen red.** The new case "refuses a start that names no work item with an error, and starts nothing, a start that asks to continue among them" was run alone against the code of `5d4615e`: it timed out at 5000 ms waiting for the `error`, because the daemon answered `started`. Executed. With the one guard `if (typeof message.workItemId !== "number") {` replaced by `if (false) {`, it fails again (0.3 s); executed through `seal mutate` over `src/daemon/daemon.ts`, which restored the file.

**Mutation.** One unit adds behaviour, that guard, and one run was made (above). The removal of `cwd` and `OWLERY_CWD` adds none.

**Run.** `node scripts/test-in-electron.mjs test/daemon.test.ts test/view.test.ts` and `pnpm run typecheck` in `apps/desktop`: both files and the typecheck ran green except that one case (577 of 578 passed), which was then fixed and run alone, green; the two files were not run again whole after that fix. The built-app cases (`terminal-basics.test.ts` and the others that start the app) and the broad gate were not run: they are the orchestrator's.
