**Decisions made while building, each with its grounds.**

- **A work item carries no `seal` exactly where the map `branches` holds no entry for it.** `workItemOf` spreads `seal` in only where `branches.get(item.id)` is not `undefined`. A work item the daemon creates gets an entry with a null seal as it is made (`daemon.ts`, the `createWorkItem` handler), so it carries `seal: null` from its first message: its branch was cut at the base commit a moment ago and holds no seal. Judged against `frame/design.md` *Scope* item 1 and *Data & interfaces*, which name the entry as the line between absent and null.
- **The look copies a seal's three fields, keeps a null and leaves an absent field out.** `lookOf` writes `seal` only where the work item it is given carries the key, and then as `{ state, commit, why }` or null. `isSeal` takes a record whose `state` is `sealed` or `broken`, whose `commit` is a text, and whose `why` is a text or null. A file whose `seal` is anything else, a seal without `commit` or `why` among it, is no look, as a file with any other field of the wrong type is no look. Judged against `frame/design.md` *Scope* item 2, scenario 2 and *Data & interfaces*.
- **The fixture work item of `test/last-look.test.ts` now carries a broken seal.** Every case that records or reads `WORK_ITEM` then holds the seal too, as it holds `chain` and `pullRequest`: "keeps the lists as they stood" changes the seal's sentence after the record, and "reads only the fields of a look" gives the seal a field no seal has. The new case reads a look written without `seal` and records four work items, `sealed`, `broken`, null and with no key, and reads each back with `"seal" in`, since `toEqual` does not tell an absent key from one holding `undefined`.
