# Phase 1: 1795388701-agent-choices-and-behind

## What this phase found

**The frame holds, but for one sentence of `frame/design.md` *Data & interfaces*.** It says that the tool's name and the names of the payload's fields "stand in this file and in no other of `src/`", the file being `apps/desktop/src/daemon/agent-events.ts`. At `9fe0c0c`, and at this phase's commit, `apps/desktop/src/daemon/daemon.ts` reads `payload.tool_name` for the `agent` message in `agentEvent`, and `apps/desktop/src/daemon/adapters/claude.ts` reads `request.tool_name` and names `AskUserQuestion` in the session's `--disallowedTools`. Both stood before this work and are of the daemon and of the vendor's adapter, which `docs/architecture.md` *Rules that keep it portable* allows. The search of scenario 12 holds as the frame states it: `git grep -n 'AskUserQuestion\|tool_input\|tool_name' -- apps/desktop/src/shared apps/desktop/src/renderer apps/desktop/src/main` printed nothing and exited 1 (`executed`). The same pattern over `apps/desktop/src` printed the lines of `agent-events.ts`, so the pattern finds what it looks for (`executed`). The names this phase adds, the question tool's and those of its input, stand in `agent-events.ts` alone. The phase did not move the read in `daemon.ts`: that would change code the request does not name.

**The card lists the questions in place of the agent's text.** *Scope* item 8 says the card shows under its head each question's text and its choices. The daemon sets `stateText` to the first question's text (*Scope* item 2), so a card that kept its text and added the questions would say the first question twice. `shared.ts#detail` draws the questions where `stateSays` gives one or more, and the text alone where it gives none. Judged against `frame/design.md` *Scope* item 8 and `docs/design.md` *Principles* 2.

**The words under a question that takes more than one choice have a function of their own.** `view.ts#choiceNote` gives "More than one may be chosen." or nothing, and a case in the `stateSays` block of `apps/desktop/test/view.test.ts` pins the words. *Data & interfaces* names no such function. It is there because a sentence the window shows is pinned by a case (contract rule 14), and `detail` is drawn only in the built app.

**The reader keeps the first 8 questions that have a text, not the first 8 entries.** An entry without a question's text is left out before the count, and so is an option without a label. A case pins it: an entry with no text before nine questions still leaves eight questions. Judged against *Scope* item 2, "keeps the first 8 questions".

**`silentStartOver` writes nothing of the questions.** *Data & interfaces* says it holds `stateQuestions` at null. The silent start ends at the pane's first event, so the field is still the null the pane's start gave it, as `stateText` and `stateTool` are. The case of a silent pane in `apps/desktop/test/daemon.test.ts` reads the whole session, the null questions among it.

**`frame/questions.md` Q2, answered by the work: `apps/desktop/test/notification-click.test.ts` serves scenario 11.** Its `feed` takes the event's fields, and the case is the file's fourth, so the file still starts the app once. The case closes the form the second case leaves open, and feeds `UserPromptSubmit` before the question tool's `PreToolUse`. The third case leaves Alpha waiting, and an event that leaves the state as it was changes nothing (*Scope* item 3), so a question asked while the session already waits would not show. The Status cell of Q2 is the orchestrator's to write, since this crafter does not write `frame/questions.md`.
