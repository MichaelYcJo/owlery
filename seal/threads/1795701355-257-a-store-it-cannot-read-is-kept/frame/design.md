## Scope

In scope, numbered for `plan.md`'s Delivers cells:

1. **The store tells a file it refused from a file it read.** In `RepositoryStore`'s constructor, a `repositories.json` that stands and is not read is refused. That is a value `readJson` gives as `null`, which covers a file the daemon cannot open, a folder at the path, a text that is no JSON and the text `null`, and a value that is neither a store nor a list of repositories. A file holding `[]`, and a store holding no repository, are read as they are and refused for nothing. A `repositories.json` that does not stand is no refusal: the store starts from `work-items.json` as before.
2. **A refused file is kept aside, under a name of its own, in the run folder.** The store renames it to `repositories-unread-<stamp>.json` in the same folder, where `<stamp>` is the UTC time of the store's `now()` written `YYYYMMDDTHHMMSSZ`, as `20261126T123005Z`. Where a file or a folder stands at that name, the store takes `repositories-unread-<stamp>-2.json`, then `-3`, and on, so no file kept earlier is replaced. The rename keeps the file's bytes and its mode. The store then starts with no repository, under the counts of item 8, and does not read `work-items.json` in its place. Right after the rename succeeds, it writes that store, with no repository and those counts, to a new `repositories.json` (round 1, finding 2). So a daemon that stops before any change, by a crash, by "Quit Owlery Completely…" or by a restart, leaves a store the next start reads, and that next start does not read `work-items.json` either. The rename and the write act in the one run folder the rename has just shown writable. A write that fails there leaves the kept file whole: the store throws nothing at its start, and the next change writes again and throws what refuses it, as any change does.
3. **A refused file the store cannot move stays as it stands, and nothing writes over it.** Where the rename throws, the store keeps no file: it holds its repositories in memory alone until the daemon stops, as a store given no run folder does, and `write()` writes nothing. It takes up the counts of item 8 all the same, since the files the daemon keeps under a work item's id are written whether the store's file is or not.
4. **The store answers what it did.** `RepositoryStore#setAside()` gives `null` where the store read its file or found none, and otherwise `{ refused: string; keptAs: string | null }`: the absolute path of the file it refused, and the absolute path it kept the file at, or `null` where the rename failed. The sentence a person reads is `setAsideNotice(setAside)` of `repositories.ts`, exported, which gives, for a kept file:

   `Owlery could not read its list of repositories, so it kept the file as <keptAs> and started with none. Nothing in that file was changed.`

   and for a file it could not move:

   `Owlery could not read its list of repositories at <refused>, nor move it aside. The file stays as it is, and no change to the repositories is kept once the daemon stops.`
5. **The daemon says so to every window.** `Daemon`'s constructor reads `setAside()` once, after the store is made, and holds the sentence of item 4. `ready` carries it as `storeNotice` where it stands, and carries no such key otherwise, as `keepAwake` and `machine` are sent (`shared/protocol.ts`: `storeNotice?: string`, with the comment's sentence that a daemon that read its file, and a daemon of an earlier build, send none, and that a client reads its absence as nothing to say). No other message carries it: the notice does not change while the daemon runs.
6. **The window's status line says it.** `held.storeNotice` (`renderer/shared.ts`) is set from each `ready`, `null` where the key is absent. `statusNotice(own, daemon, store, agent)` gives `own || daemon || store || agent || ""`: the window's own notice, then the other build's, then the kept file, then the agent's. The kept file stands before the agent's notice because it names a loss the person can still undo, and after the other build's because a restart is what the other build's notice asks for, and the restart changes which daemon reads the file. `showStatus` passes `held.storeNotice`. A case of the built app reads the line (round 1, finding 3): `BuiltApp.start`'s `writeRun` (`apps/desktop/test/built-app.ts:197-208`) writes a `repositories.json` that holds no JSON into the run folder before the daemon starts, and the case reads that `#status` says the first sentence of item 4, naming a path under `<userData>/run/repositories-unread-`, and that it carries the `notice` class. The case stands in `apps/desktop/test/role-bundle.test.ts` beside *the built app's notice of an old CLI* (`:495`), which reads the status line the same way, and it runs in the batch of built-app cases at the end of the fix pass.
7. **Every text that states the old behaviour is rewritten in place** (contract rule 19). The class was listed by `git grep -n "read as no repository" -- apps/desktop/src` at `5370d534`, which prints `daemon.ts:1020` and `repositories.ts:227`, and both change here. The `RepositoryStore` docstring's "A file that is neither is read as no repository." becomes the set-aside of items 1 to 3. The comment at `daemon.ts:1020`, "Where that file was lost or read as no repository", becomes one that says when ids begin again and when they do not: where the file was lost, or was refused and stated no counts, its ids begin again and what the daemon keeps under the id given now is dropped; a refused file that states its counts keeps them (item 8), so no id given after it is one of that file's. It no longer says that a start which misreads `repositories.json` "loses nothing that file still holds", since a refused file that states no counts does lose its work items' record times and gate output to the ids given again. The `RepositoryStore` docstring says that a refused file's counts are taken up where it states them, and that the empty store is written at once after the rename, in place of "writes a new `repositories.json` at its first change". The same two facts replace "its first change writes a new `repositories.json` beside the kept file" in the work item's `changelog.md`, which the fix pass writes. The docstrings of `statusNotice` (`apps/desktop/src/renderer/view.ts#statusNotice`, its docstring), of `showStatus` (`apps/desktop/src/renderer/sidebar.ts#showStatus`) and of `held.agentNotice` (`apps/desktop/src/renderer/shared.ts`, its docstring) name the store's notice in the order of item 6. The comment over the `ready` member of `ServerMessage` in `apps/desktop/src/shared/protocol.ts` names `storeNotice`.
8. **A refused value that states the three counts keeps them** (round 1, finding 1). `isCounted(value)`, a unit of `repositories.ts` beside `isStored` and not yet in the tree, answers whether a value is a record whose `nextWorkItemId`, `nextRepositoryId` and `nextGroupId` are each a number, whatever its repositories hold. In the refusal path, before the set-aside of items 2 and 3, the store sets its counts to the value's where `isCounted` holds. The counts are taken as the file states them: the store reads none of the refused file's ids, so it cannot raise a count that stands below one of them. The ids a refused file gave are not given again, so nothing the daemon keeps under a work item's id is read as, or dropped for, the work item that gets the next id. The places that key on a work item's id, listed from every file and folder the daemon keeps in its run folder (*Grounding*, the item on the run folder's files), are `record-times.json`, which a creation drops the new id from (`daemon.ts#handle`, its `createWorkItem` case, `this.times.drop`); `gate-output/<id>.txt`, which a creation removes (the same case's `this.dropGateOutput`, and `daemon.ts#dropGateOutput`); `ledger.jsonl`, whose entries a work item reads from its creation on (`daemon.ts#handle`, its `readLedger` case, and `ledger.ts:136`); `last-look.json`, whose work items are copied by id (`last-look.ts:169`); `heavy-runs.jsonl`, whose runs name a work item's id (`heavy-runs.ts:25`); and `pull-request-<id>.md`, a body file a pull request's stage writes and removes (`daemon.ts#pullRequestBodyFile`). The counts reach every one of them at once, since they decide the id. What a refused value that states no counts cannot give: a file that holds no JSON, one the store cannot open, a folder, and a list of repositories alone carry no counts the store can read. After such a refusal the ids begin at 1 again, as they did before this work, and the first work item made drops what the run folder keeps under id 1, and so on. *What the daemon could do beyond the issue* names what would close it.

Out of scope:

- **The other files of the class** (*Grounding*, the last item). `accounts.json` is the one whose loss a person feels: the accounts' names and which folder each one has. The issue's *Done when* names the repositories file, and the release ships on 2026-11-29. *What the daemon could do beyond the issue* names an issue for it.
- **A build before this one.** `v0.0.5` and every earlier build still write over a file they refuse, and nothing a later build ships changes them. #217's way round, a copy of `repositories.json` before an earlier build runs, stays the way round for those builds (`plan.md` *Operational impact*).
- **Bringing a kept file back.** The person renames it by hand while the daemon is stopped. An offer in the window is in *What the daemon could do beyond the issue*.
- **Reading part of a refused file.** The store reads the whole file or none of it, as the issue's *Done when* asks (`plan.md` *Alternatives considered*).
- **Keeping the fields a build does not know.** The store reads "only the fields of the store, whatever else the file's entries carry" (the comment in `repositories.ts#RepositoryStore`'s constructor), so a file an earlier build can read loses the later build's fields at its next write. That is a quieter loss of the same kind, and *What the daemon could do beyond the issue* names it.

## Data & interfaces

- `apps/desktop/src/daemon/repositories.ts`: `RepositoryStore#setAside(): SetAside | null`, with `export interface SetAside { refused: string; keptAs: string | null }`; `export function setAsideNotice(setAside: SetAside): string`. The name's stamp is read from the `now` the constructor is handed (`repositories.ts#RepositoryStore`'s constructor), so a case fixes it.
- `apps/desktop/src/daemon/repositories.ts`, module-private, beside `isStored`: `function isCounted(value: unknown): value is Counts`, true where `value` is a record whose `nextWorkItemId`, `nextRepositoryId` and `nextGroupId` are each a number (*Scope* item 8). `isStored` keeps its own test of the counts and its repositories, and the read of a file the store reads does not change.
- `RepositoryStore`'s set-aside, private, writes the store through `write()` right after a rename that succeeded, and catches what that write throws (*Scope* item 2).
- `apps/desktop/src/shared/protocol.ts`: the `ready` member of `ServerMessage` gains `storeNotice?: string`.
- `apps/desktop/src/renderer/shared.ts`: `held.storeNotice: string | null`, `null` at the start.
- `apps/desktop/src/renderer/view.ts`: `statusNotice(own: string, daemon: string, store: string | null, agent: string | null): string`.
- On disk: `repositories-unread-<YYYYMMDDTHHMMSSZ>[-<n>].json` in the run folder, the refused file renamed, which the daemon never writes after.

## What the daemon could do beyond the issue

The orchestrator takes what is cheap and in scope, and files an issue for the rest.

- **Keep `accounts.json` the same way.** `AccountStore` starts with no account on a file it refuses and writes over it at its first change (`accounts.ts:109-116`), so an earlier build loses every account's name and folder, and gives the next account the id after System default's again. Whether a new account Owlery makes then meets a folder of `accounts/` that an account of the lost file had was not read. The set-aside of this work moves into a module both stores call once a second store takes it. An issue.
- **Offer to bring a kept file back.** A daemon that finds a `repositories-unread-*.json` it can read could name it in the window and, on the person's word, read its repositories in beside the ones it holds. Which of two stores wins where both name one folder is a product choice. An issue for the owner.
- **Keep the fields an earlier build does not know.** The store copies each entry's known fields alone (`repositories.ts#RepositoryStore`'s constructor, the copy under "Only the fields of the store"), so a later build's field that an earlier build can parse past is dropped at the earlier build's next write. Carrying the unknown fields through would close the quieter loss. An issue.
- **Give no id again after a refused file that states no counts.** A file that holds no JSON, one the store cannot open and a list of repositories alone leave the store with no counts to take up (*Scope* item 8). The store could count past the ids the run folder's other files hold under a work item's id: the keys of `record-times.json`, the names under `gate-output/`, and the `workItemId` of each line of `ledger.jsonl` and `heavy-runs.jsonl`. That reads four more files at each start that refuses, and a ledger that is never trimmed grows with the machine's history. It would close the loss of a corrupted file, which no build's shape change makes. An issue.
- **Write why the file was refused into `daemon.log`.** The status line names the kept file and not the reason, and it goes when the daemon stops. One line in the daemon's log (`main/daemon-client.ts#ensureDaemon`, where it opens `daemon.log`) with the read's error code, or "no JSON", or "a shape this build does not read", would keep the reason. Cheap, and outside the issue's *Done when*.
