# Implementation Plan: a daemon that cannot read its repositories file keeps it (#257)

## Technical context

The tree as read at `5370d534`.

The work changes one read and one sentence's road to the window. The read is `RepositoryStore`'s constructor (`apps/desktop/src/daemon/repositories.ts:258-292`): `readJson` (`:203-215`) gives `undefined`, `null` or a value, and the refusal is the early `return` at `:272`. The counts are read at `:273`, after that `return`, so the refusal path gives up the counts a refused store states; *Scope* item 8 reads them before the set-aside. The set-aside goes in that path, before the `return`, and is the only place where the store renames anything. It reads the store's `now` (`:260`) for the stamp, so the cases fix the name. The write stays `writeWholeFile` (`apps/desktop/src/daemon/whole-file.ts:23-36`), and a store whose rename failed sets its `file` to `undefined`, the path a store with no run folder already takes in `write()` (`:459-460`).

The sentence's road is the one `agentNotice` takes, less the message that changes it: the daemon's constructor (`apps/desktop/src/daemon/daemon.ts:604-626`) holds it, `accept`'s `ready` (`:974`) sends it, the window's `ready` handler (`apps/desktop/src/renderer/renderer.ts:1899`) holds it in `held` (`apps/desktop/src/renderer/shared.ts:25-26`), and `showStatus` (`apps/desktop/src/renderer/sidebar.ts:85-89`) draws it through `statusNotice` (`apps/desktop/src/renderer/view.ts:920-922`).

The cases build on the existing harnesses: `runDir()` and the `PLACE`, `OWN`, `UNSET` and `PLAIN` fixtures of `apps/desktop/test/repositories.test.ts:14-37`, and `daemon()`, `client()` and `repository()` of `apps/desktop/test/daemon.test.ts`, with a run folder made as the case at `:886-900` makes one. The `addRepository` message is `{ type: "addRepository"; requestId; folder }` (`shared/protocol.ts:878`).

The failure scenario of the chosen approach, six months on: a person moves between two builds several times. Each start of the earlier build keeps one more `repositories-unread-*.json` in the run folder, and nothing reads any of them. A person who adds repositories before reading the status line has a new store with what that build was given, while the work items of the kept file stand on disk unlisted, their worktrees and branches whole. Getting them back is a rename by hand while the daemon is stopped, which the notice names the path for. *What the daemon could do beyond the issue* in `frame/design.md` names the offer that would make it a press. A file that holds no JSON states no counts, so after its refusal the ids begin at 1 again and the first work items made drop the record times and the gate output that the kept file's work items of those ids had (*Scope* item 8, the stated limit).

## Operational impact

- No migration. A file the store reads is read as before, and a file it refuses is renamed, never rewritten. A new `repositories.json` with no repository, under the refused file's counts where it states them, is written in its place at the same start.
- `ready` gains an optional `storeNotice`. A window of an earlier build ignores the key. A window of this build on a daemon of an earlier build reads its absence as nothing to say.
- The run folder may gain files named `repositories-unread-<UTC time>[-<n>].json`, readable by the user alone as `repositories.json` was, and the daemon never removes them.
- The protection holds for a move back to this build or a later one alone. `v0.0.4` and earlier builds write over a file they refuse, so #217's way round stands for them: copy `repositories.json` before running such a build (`seal/threads/1795610869-217-a-new-work-item-picks-its-branch/changelog.md`). The changelog fragment of this work says both.
- No new dependency, environment variable or version move.
