# Changelog: heavy commands wait their turn on the machine, across every work item and repository

Issue #134. Several work items ran their broad gates and test suites at once, and timed cases failed under the load. The order was kept by hand. Nothing kept the display awake for a built-app run, which fails on a sleeping display.

- **A repository names its heavy commands in its records root's `config.json`.** The key is `Heavy commands`, an object of names and command lines, each run at the worktree's top. The `Broad gate` command is always heavy. A repository without the key has one heavy command, its broad gate.
- **A session runs a named command through the runner.** The environment of a shell pane, a Claude Code pane and a worktree setup pane names the runner in `OWLERY_RUN`. A sign-in pane's does not, so a heavy command typed there takes no turn. `"$OWLERY_RUN" test -- test/view.test.ts` asks the daemon for a turn, says on its error output that it waits, for example "test waits for the machine (1 ahead).", runs the command with the session's own input and output once its turn comes, with each word after `--` added, and exits with the command's exit code. A name the repository does not hold is refused with exit code 64 and a sentence that lists the names it holds. Where no daemon answers, the command runs at once and says "No daemon of Owlery answered, so test runs now without waiting its turn on the machine." A session outside a pane reaches the runner by the launcher `owl-run` in the daemon's run folder.
- **The daemon gives as many heavy commands a turn at once as the limit says, across every work item and repository.** The default is one for each 8 cores or one for each 16 GB of memory, whichever gives fewer, and never under 1: 1 on a Mac of 12 cores and 36 GB. A command that asks while the limit is full waits. Those that wait go in this order: a work item's broad gate, which is one step from its seal, then a command of a work item under review, then one of a work item still being built, then one in a folder no work item's records name, and within each the one that asked first. A running command is never stopped for one that waits. A turn ends with its command, or when the process that asked for it is gone. The daemon stores no queue: a command that waits when the daemon restarts asks again.
- **The daemon's own chain and the chain command's `gate` take a turn before the broad gate runs.** A gate that waits is listed as the chain's stage "Broad gate", and the chain's sentence says "The broad gate waits for the machine."
- **The inbox says which work item's heavy command waits, and how many go before it.** The line's second row reads "Waiting for the machine (2 ahead)", in the words of the agent cap's wait. Where a work item waits for both, the line shows the wait that began first.
- **A broad gate that failed while the machine was over its load runs once more, alone.** The machine was over its load where another heavy command held a turn during any part of the run, or where the load average the daemon read at its start was above the cores. The second run starts once no other heavy command runs, and waits up to 10 minutes for the load average to come to the cores or under. A run that was stopped, by the person or at the gate's time limit, one that did not start and one whose record was refused run once. Where the second run passes, `trail/gate.md` names the earlier run above the run block, for example "An earlier run on <commit> ended with exit code 1 while the machine was over its load (load average 13.1 on 12 cores, 1 other heavy command). The run below ran alone." Where it fails, the chain's sentence names both runs.
- **The daemon keeps what each heavy command took.** One line for each run in `heavy-runs.jsonl` of its run folder: the folder, the repository and the work item, the command's name, when it asked, started and ended, its exit code, its peak memory, the load at its start and the highest during it, whether another heavy command ran beside it, and whether it ran alone as a second run.
- **The Machine dialog gains the limit on heavy commands.** Its row "Heavy commands at once" has a field, "Use the default" and the sentence "The default is 1: one for each 8 cores gives 1, one for each 16 GB gives 2, and the fewer is taken." The daemon refuses a value over the machine's cores, for example "The limit on heavy commands at once is a whole number from 1 to 12." The value is kept under `heavyCommands` of `limits.json`. Under the row, "Running and waiting" lists the heavy commands in the queue's order, each with its state, its command, the reason for the place of one that waits and its age. "What ran" lists each command of each repository with its runs, the longest, the most memory and the highest load, "not read" where no reading was made. The daemon reads the runs' file when the dialog opens.
- **While a heavy command runs, the daemon keeps the display awake too, and turns it on at the command's start.** This holds under "While an agent works" and "Always", and a heavy command that holds a turn is itself a reason to hold the Mac under "While an agent works". Under "Never" the daemon holds and wakes nothing.
- **The role bundle tells a session where a heavy command goes.** Rule 2 of its agent contract says to run each command the repository's `Heavy commands` names through `"$OWLERY_RUN" <name> -- <words>` where the environment names the runner.
- **This repository names its heavy commands:** `test`, the desktop suite, `test:app`, its built-app files as one batch, and `install`. `.worktreesetup` still runs `pnpm install` with no turn.
- **The screenshot run shows this work's rows in the Machine dialog.** In `pnpm run screenshots`, two commands ask for their turn on the daemon's turn socket, so the dialog lists one running and one waiting, and the run writes a runs' file, so it lists what ran.
- **What no run has shown yet.** No case has run a heavy command in a pane of the built app, and no case has watched the display while one runs. Whether `caffeinate -u` turns the owner's sleeping display on is unmeasured, and so is the load a broad gate drives with nothing beside it.
- **After an update, the order holds once the daemon restarts.** A daemon of an earlier build answers no turn, so the runner and `gate` run at once and say so. A window of an earlier build shows neither the wait nor the dialog's new rows.
- **For a client of the daemon:** a work item carries `machineWait`, `{ name, since, ahead }` or null. A gate stage that waits carries `gate.waits: true`. `machine` carries `heavy`: `proposed`, `byCores`, `byMemory`, `set` and `queue`, each entry `{ workItemId, folder, name, place, state, since }`. `setCaps` takes `heavyCommands`, a number or null. The client message `readHeavyRuns` is answered with `heavyRuns`, one row for each command of each repository: `repo`, `repoName`, `name`, `runs`, `longestMs`, `mostMemory` and `highestLoad`. The turn socket `turns.sock` of the run folder takes one line of JSON for each message, named by its field `is`: `ask`, `waits`, `turn`, `ended` and `ran`.
