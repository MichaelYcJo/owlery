# Implementation Plan: heavy commands wait their turn (#134)

## Technical context

The tree as read at `404b9cd`. Every path below is under `apps/desktop/` unless it opens with another folder.

- **Where a heavy command starts today.** `src/daemon/gate.ts:95` (`startGate`) starts one command line with `/bin/sh -c`, detached, so the shell leads a process group. `src/daemon/daemon.ts:3171` (`runGate`) is the daemon's own chain: it reads the command, starts it at `:3193`, lists the stage, waits for the end, and records a pass. `src/daemon/chain-command.ts:331` (`gate`) is the pane's: it starts the command, waits, and records a pass. No other code calls `startGate`, and neither caller waits for anything before the start.
- **How a pane's command finds Owlery.** `src/daemon/chain-command.ts:187` (`stageFolder`) takes the run folder from `OWLERY_RUN_DIR`, or from the folder of the launcher `OWLERY_CHAIN` names. `src/daemon/pane-chain.ts:64` (`writePaneChain`) writes that launcher at each start of the daemon, and `src/daemon/hooks.ts:174` (`paneCommands`) puts its path in the environment of a pane that carries the owl chain. The daemon already listens on one Unix socket of the run folder, the hook socket (`src/daemon/hooks.ts`, `HookServer`).
- **Where the repository's command is read.** `src/daemon/records-place.ts:174` (`readRecordsPlace`) reads `config.json` of the worktree's records root and gives `broadGate`.
- **Where the hold stands.** `src/daemon/keep-awake.ts:80` (`holdAwakeFor`) starts `caffeinate -i -w <pid>`, and `:25` (`wantsAwake`) decides when. The daemon is given the holder as an option, so its cases start no process.
- **Where the person reads a work item's state.** `src/renderer/view.ts:1609` (`lineText`) picks the second row of a line. `src/renderer/index.html:648` is the sidebar's foot, which holds the Accounts button and the "Keep awake" choice.
- **Where a gate's record is written.** `src/daemon/seal-records.ts:151` (`gateText`) keeps what stands in `trail/gate.md` unchanged and appends one run block. Both readers read the blocks alone.

Constraints:

- A role session's environment is the names `src/daemon/adapters/claude.ts:116` (`claudeEnv`) gives and no other, by policy, so the runner does not reach a role session of the daemon's own chain in this work.
- The chain command is built without `ws` (`build.mjs`, the entry `src/daemon/chain-main.ts`), so the turn travels over a Unix socket with Node's own `net`.
- The daemon runs on one thread, so the turn keeper needs no lock: an ask and a grant are each one synchronous step.
- A built-app test file runs alone, one at a time, with `OWLERY_BACKGROUND=1`, as `vitest.config.ts` and the policy state.

**The failure scenario of the chosen approach.** In six months most heavy commands still start from a session's own command line, because a session forgot the runner or runs outside a pane. The queue then sees the gates and little else, the limit reads as kept while the machine is overloaded, and timed cases fail again. The runs' file shows it: few runs beside the gates, and gates whose highest load is far above the cores. The second scenario is the rule of the second run: the daemon reads the load at a run's start alone, so a gate that another command overloaded part way fails once and counts, unless that command went through the runner.

## Operational impact

- **A new key of a repository's `config.json`,** `Heavy commands`. A repository without it loses nothing: its broad gate is its one heavy command. The AgenticSeal plugin's readers of the same file ask for keys by name (read in part, `frame/design.md` *Grounding*), so the key should change nothing for a session of the plugin. That is unverified, and the orchestrator answers it at the first pull request check of this branch.
- **A new name in every pane's environment,** `OWLERY_RUN`, and a new launcher, `owl-run`, in the run folder.
- **New files of the run folder:** `heavy-runs.jsonl` and the turn socket, `turns.sock`, and one key more in #32's `limits.json`. A line of `heavy-runs.jsonl` names the folder its command ran in, as the person's machine names it. `heavy-runs.jsonl` grows by one line for each run and is never trimmed, as `ledger.jsonl` is.
- **The display stays on while a heavy command runs,** and is turned on at a command's start, under "While an agent works" and "Always". A person who wants the display left alone chooses "Never", which also drops the hold from idle sleep.
- **A broad gate may start later than it did,** and a gate whose command fails by itself under load takes one more run before it says so (`frame/design.md` *Scope* item 9).
- **A window of an earlier build** reads none of the new fields and shows neither the wait nor the dialog. A daemon of an earlier build sends no `machine`, and the window then hides the dialog's button.
- **No new dependency and no migration.**
- **The version** stays as the release branch holds it. This pull request does not move it. Phase 5's commit adds `changelog.md`.
