## Scope

A **heavy command** is a command a repository names as one that loads the whole machine. A **turn** is the daemon's word that one heavy command may run now. The **limit** is how many heavy commands hold a turn at once on this machine.

In:

1. **A repository names its heavy commands in its records root's `config.json`.** The key is `Heavy commands`: an object whose keys are names and whose values are command lines, each run at the worktree's top. The `Broad gate` command is heavy whether or not the key stands. A repository with no such key has one heavy command, its broad gate.
2. **The limit's default comes from the reading of the machine, which issue #32 builds.** This work adds no reader. It reads the cores, the memory and the load average of the last minute from #32's reading. The default limit is one heavy command for each 8 cores, or one for each 16 GiB of memory, whichever gives fewer, and never under one. Its formula and its sentence stand beside #32's in `apps/desktop/src/shared/machine.ts`. A value the person sets replaces the default until they take the default back, and it is kept under this work's own key of #32's `limits.json`. A daemon given no reader of the machine keeps a limit of 1.
3. **The daemon gives turns: at most as many heavy commands run at once as the limit says, across every work item and every repository.** A command that asks while the limit is full waits. The daemon orders those that wait by what the person waits on first, in these places:
   1. the broad gate of a work item, which is one step from its seal;
   2. a heavy command of a work item whose branch holds a review round's record, so it is under review;
   3. a heavy command of a work item whose branch holds no round record, so it is still being built;
   4. a heavy command run in a folder no work item's records name.

   Inside one place, the command that asked first goes first. A command that runs is never stopped for one that waits. A turn ends when its command ends, and also when the process that asked for it is gone, so a crashed command holds nothing. Lowering the limit stops nothing: it holds for the next start.
4. **The daemon's own chain takes a turn before it starts a broad gate.** While the gate waits, it is listed as the chain's stage, and the chain's sentence says that the gate waits for the machine.
5. **Any session takes a turn through one command, the runner.** The daemon writes a launcher, `owl-run`, into its run folder, and every pane's environment, a setup pane's among them, names it in `OWLERY_RUN`. `"$OWLERY_RUN" <name>` looks the name up in the worktree's `Heavy commands`, asks the daemon for a turn, says on its error output that it waits, runs the command line with the session's own input and output, and exits with the command's exit code. Words after `--` are added to the command line, each as one word. A name the repository does not hold is refused with exit code 64 and a sentence that lists the names it holds.
6. **The chain command's `gate` takes a turn the same way**, so a pane's broad gate waits behind the gates and commands of other work items.
7. **A command runs at once where no daemon answers.** The runner and the chain command's `gate` say so in one sentence on the error output and run the command with no turn. The same holds where the daemon ends while the command waits.
8. **A work item's line says "Waiting for the machine" while a heavy command of it waits for its turn.** The words, their count, as in "Waiting for the machine (2 ahead)", and their place in the line's second row are #32's, which words a session that waits for the agent cap so. This work gives the line a second source of the same words. Where a work item waits in both queues, the line shows the wait that began first. The work item's view says the same at the stage that waits. A second run of item 9 that holds its turn and waits only for the load to come down is not among these waits: the chain's sentence and the stage say that wait (*Data & interfaces*, the protocol), and `frame/questions.md` Q17 holds whether the line says it too.
9. **A broad gate whose command failed by itself while the machine was over its load is run once more, alone, before it counts as failed.** The command failed by itself where it exited with a code other than 0, or where a signal that Owlery did not send ended it. Every other failed run runs once: a run the person stopped, a run stopped at the gate's time limit of 60 minutes, a run stopped because the work item's sessions ended, a command that did not start, and a run whose record was refused. Each of those is Owlery's own end or a fault no load explains. A pane's gate that no daemon gave a turn also runs once, since nothing read the machine during it. The machine was over its load during a run where another heavy command held a turn during any part of it, or where the load average the daemon read at its start was above the number of cores. Alone means that no other heavy command runs beside it: the daemon lets those that run end and starts no other. The second run also waits, for 10 minutes at most, until the load average is at or under the number of cores. A second failure counts, whatever the load. This holds in the daemon's chain and in the chain command's `gate`.
10. **The record names both runs.** Where the second run passes, `trail/gate.md` holds one sentence above the run block: that an earlier run on the same commit failed while the machine was over its load, with how it ended and what the load was. Where it fails, the chain's sentence, and in a pane the command's refusal, names both runs. In the daemon's chain each run is a stage of its own with a ledger entry of its own.
11. **The daemon keeps what each heavy command took.** One line for each run, in a file of the run folder: the folder it ran in, the repository and the work item whose worktree that folder is, the command's name, when it asked, started and ended, its exit code, its peak memory, the load at its start and the highest load during it, whether another heavy command ran beside it, and whether it ran alone as a second run. The repository and the work item are null for a folder that is no work item's worktree. A run whose command was cut off before it told the daemon how it ended still has its line, with a null exit code and a null peak memory. Peak memory is the highest sum of the resident memory of the command's process and its descendants, read every 5 seconds.
12. **While a heavy command runs, the daemon keeps the display awake, and wakes it at the command's start.** This holds under the choices "While an agent works" and "Always" of "Keep awake", and not under "Never". Under "While an agent works", a heavy command that holds a turn is itself a reason to hold the Mac, as a working session is, whoever started it. The display's hold ends with the last heavy command.
13. **The Machine dialog, which #32 builds, gains this work's rows.** One row for the limit, "Heavy commands at once", in the form of #32's rows: a number field, the default's sentence with its arithmetic, and "Use the default". Under it the heavy commands that run and wait, in the queue's order, each with the reason for its place. Under those, for each heavy command that ran: how many runs, the longest, the most memory and the highest load. *Data & interfaces* shows the words. This pull request rewrites #32's row "The Machine dialog" of `docs/design.md` *Components and their states* in place, in both editions, as that document's *Principles* item 8 asks, so *Rule changes* holds no operation on the row.
14. **This repository names its own heavy commands.** `seal/config.json` gains `Heavy commands` with `test`, the desktop suite's command, which takes test files after `--`, `test:app`, its built-app files as one batch, and `install`, the install.
15. **The role bundle says where a heavy command goes.** `apps/desktop/role-bundle/skills/agent-contract/SKILL.md`, rule 2, gains one sentence: a command the repository's `config.json` names under `Heavy commands` is run through the program `OWLERY_RUN` names, where the environment names one.

Out:

- **A cap on agents, worktrees and panes, and everything of the machine both work items share.** Issue #32 builds the caps, the reading, the store, the dialog and the line's words, and merges first (*Grounding*, the row of #32's frame). **How the two queues meet:** #32's queue holds sessions that wait to start, and this work's queue holds commands that a running session or the daemon's chain asks to run. A session that waits in #32's queue runs nothing, so it asks for no turn, and a broad gate is no agent, so #32's count does not hold it. Nothing waits in both queues for the same act. Their orders differ because they order different things, and they agree in direction: #32 starts a chain that already ran a stage before a chain's first stage, and this work runs the gate of a work item one step from its seal before a command of one still being built.
- **A command nobody runs through the runner.** A command a person types, or one a session starts by its own command line, takes no turn and is not seen. No hook reads a command's text to guess that it is heavy (`frame/plan.md` *Alternatives considered*).
- **A role session of the daemon's own chain.** Its environment holds the names policy gives it and no other, and nothing in the window starts that chain in this release. Issue #55 starts it, and the runner reaches it with one more name there.
- **Stopping a running command for a more urgent one, and moving a command up the longer it waits.**
- **A default that moves by itself from what was measured.** The measurements are shown beside the default, and the person decides.
- **A limit for one repository.** The limit is the machine's.
- **The repository's `.worktreesetup`.** It stays `pnpm install`, run as a new worktree's setup with no turn. A repository that wants its setup in the queue writes the runner into that file itself, and the setup pane's environment names the runner for it.
- **A second run for a heavy command that is no broad gate.** Its caller reads its exit code.
- **Windows and Linux.** The display's hold is macOS's `caffeinate`, as the hold from idle sleep is. Node gives no load average on Windows, so no run there is ever over its load.

## Data & interfaces

Each name below is this design's proposal. A phase that finds a better name takes it and says so in its phase record. The shapes are the contract.

**The repository's key**, in `config.json` of the records root, read from the worktree's file by a function of its own, `records-place.ts#readHeavyCommands`, which gives each name with its command line. `readRecordsPlace` does not read it: what it gives, `RecordsPlace`, is a type of the protocol that the daemon sends each window, and no window reads a command line.

```json
{ "Heavy commands": { "test": "pnpm --filter @owlery/desktop run test", "test:app": "pnpm --filter @owlery/desktop run test:app", "install": "pnpm install" } }
```

A value that is no object, and an entry whose value is no text or is empty, names nothing. The runner's refusal lists the names the key holds, or says that it holds none.

**The machine's reading** is #32's: `apps/desktop/src/daemon/machine.ts#readMachine(env, given?)` gives a `MachineReader`, and the reader's `read(folder)` gives a `MachineReading`, of which this work reads `cores`, `memoryBytes` and `load`. Each `read` reads the load again, and the disk of the folder with it. This branch holds no `machine.ts` before #32 merges. Until phase 5 of `frame/plan.md`, the daemon is therefore given its reading of the load and the cores as options of its own, `DaemonOptions.load` and `DaemonOptions.cores`, which a case gives. A daemon given neither reads no run as over its load by its load, and its second run waits for no load. `apps/desktop/src/daemon/main.ts` gives neither, so the built app makes no second run by the load until phase 5 fills both from #32's reader, and with the limit of 1 no two turns overlap, so it makes none at all. This work adds one function to #32's `apps/desktop/src/shared/machine.ts`: `heavyProposal(reading)` gives `{ proposed, byCores, byMemory }` as `max(1, min(floor(cores / 8), floor(memory GiB / 16)))`, with the sentence that states it.

**The limits' store** is #32's `limits.json`. This work adds the key `heavyCommands`, as in `{ "heavyCommands": 2 }`. An absent key follows the default. The store reads a value that is no whole number from 1 as absent, as it reads every cap. The daemon reads a value over the machine's cores as none (`Daemon#heavySet`), since the store reads the file before the daemon reads the machine.

**The turn keeper**, a new module `apps/desktop/src/daemon/machine-turns.ts` that imports nothing of the `Daemon` class and starts no process. It takes asks, each with the folder, the command's name, its place of *Scope* item 3 and whether it must run alone, and gives each a turn by the limit and the order. Its answer to an ask says whether the ask waits and how many of those that wait go before it. The asker's going is an `AbortSignal` of the ask. `watch()` takes any number of watchers and calls each after every change of the queue or the limit: the daemon, which then sends the inbox, and each connection of the turn socket, which then tells its asker its count. It is given its clock, its limit and its reading of the load, so its cases run with none of them and phases 1 to 4 of `frame/plan.md` need nothing of #32's. Of each turn it keeps the load it read as it gave the turn, the highest load of the readings the daemon asks of it every 5 seconds while the turn is held, and how many other commands held a turn during any part of it. A turn's `restart(load)` starts its highest load again from the load given. The giver calls it for a second run once that run's wait for the load has ended, so the highest load of a second run holds no reading taken during the wait. It knows the load and not the cores.

**The giver**, `apps/desktop/src/daemon/turn-socket.ts#turnGiver`, stands between the keeper and every asker, and the daemon holds one (`Daemon#turnGiver`). It names the folder of an ask as the paragraph under the turn socket's table says, asks the keeper, and hands out each turn, which is where a heavy command starts. The ten-minute wait of *Scope* item 9 is the giver's: once the keeper has given an ask that must run alone its turn, the giver waits until the load is at the cores or under, and it holds the keeper's turn meanwhile, so no other command starts. When that wait ends, the giver reads the load again, hands out the turn with that reading as its `load` in place of the one the keeper read, and starts the turn's highest load from it through `Turn.restart`. The line of a second run (*Scope* item 11) therefore holds the load read as its wait ended as the load at its start, and its highest load counts from there. When a command has ended, the giver ends the turn, reads the run as over the machine's load or not, and has the run's line kept.

**The turn socket**, `turns.sock`, a Unix socket of the run folder beside the hook socket, readable by the user alone. One connection is one command, which the runner or the chain command's `gate` opens. Each message is one line of JSON, named by its field `is`:

| From | Message | Says |
|---|---|---|
| the command | `ask` | the worktree's top as `git rev-parse --show-toplevel` prints it, the command's name, the place of *Scope* item 3, and whether the run must be alone. A gate's place is `gate`. The runner reads its place from the committed records: `review` where the one directory that names the branch holds a round record at HEAD, `build` where it holds none, and `outside` where HEAD names no branch, or where no directory or more than one names it |
| the daemon | `waits` | how many of those that wait go before it, sent when the ask begins to wait for its turn and each time that count changes. A second run that holds its turn and waits for the load is sent none |
| the daemon | `turn` | the command may start, with the load the daemon read, or null where it was given no reading |
| the command | `ended` | the exit code and the peak memory, each null where the command read none |
| the daemon | `ran` | `over`, whether the machine was over its load during the run; `highest`, the highest load; `beside`, how many other heavy commands held a turn during any part of it; and `cores`, the cores the daemon compares a load with, or null where it was given none. A pane's gate writes the sentence of the earlier run from `beside` and `cores`, since the chain command reads no machine |

A connection that closes ends its ask or its turn. One that closes while it holds its turn, before it says `ended`, ends the run with no exit code and no peak memory. The daemon closes the socket before it ends, so a command that waits then runs at once. The daemon's own chain asks the same giver as the socket's connections do, in process, and opens no socket, so the two paths share the wait for the load, the reading of a run and the run's line.

The giver renames the folder of every ask before it asks the keeper (`daemon.ts`, `Daemon#worktreeNamed`, given to the giver as `folderOf`). Git prints a worktree's top by its real path, and the daemon keeps a work item's worktree under the path it was given, which may run through a link. The folder asked with becomes the worktree's path of the work item whose worktree has the same real path, and stays as asked where no work item has one. A work item's `machineWait` is found by that path.

**The runner**: `owl-run <name> [-- <words>]`. It is the subcommand `run` of the chain command's script, started by the launcher `owl-run` as `chain.js run "$@"`. The launcher sets the run folder in `OWLERY_RUN_DIR` for it, so the launcher's path serves a session outside a pane too. Exit code: the command's own, 128 and the signal's number where a signal ended the command, 127 where `/bin/sh` did not start, or 64 for a refusal of the runner's. The runner refuses, and runs nothing, for a run with no name, for words that do not follow `--`, for a folder in no worktree, and for a name the repository does not hold.

**The protocol** (`apps/desktop/src/shared/protocol.ts`). `WorkItem.machineWait` and the field `setCaps` gains are optional, so a daemon of an earlier build sends neither and a window reads its absence as null. `Machine.heavy` is required: it ships in the same release as #32's `machine`, so no daemon sends a `machine` without it:

- `WorkItem.machineWait`: `{ name, since, ahead }` or null. `ahead` counts the asks that wait before this one and not those that run, so a command that waits alone reads 0. Where several commands of one worktree wait, it is the one that began to wait first. It is null while a second run waits for the load alone: that run holds the keeper's turn, so the keeper lists it as running.
- A gate that waits is a `working` stage of `ChainStage` with `gate.waits: true`, and the daemon's sentence says the wait. For a second run the sentence is `chain.ts#GATE_AGAIN_SAYS`, "The broad gate failed while the machine was over its load, and runs once more, alone.", and it stands with `gate.waits` where the giver answers that the run waits: for its turn, or for a load the giver read above the cores as the run asked.
- #32's `Machine` gains `heavy`: `{ proposed, byCores, byMemory, set, queue }`, where `queue` lists `{ workItemId, folder, name, place, state, since }` in order. `folder` is the folder as the giver named it: a command in a folder no work item names has no repository, and a work item's repository follows from `workItemId`. The daemon sends #32's message `machine` when the heavy queue or the limit changes too.
- #32's client message `setCaps` gains `heavyCommands?: number | null`, where null follows the default.
- `readHeavyRuns`: answered with one row for each command's name and repository, from the runs' file.

**The runs' file**, `heavy-runs.jsonl` of the run folder, one line for each run, appended and never rewritten, as `ledger.jsonl` is: the fields of *Scope* item 11, as `apps/desktop/src/daemon/heavy-runs.ts#HeavyRun` names them. `folder` is the folder as the giver named it. `repo`, the repository's folder, and `workItemId` are null where that folder is no work item's worktree. `exitCode` and `peakMemory` are null for a run cut off before `ended`, and `peakMemory` is null too where no reading found the command's process. The memory is read with `/bin/ps -axo pid=,ppid=,rss=`, over the tree of the command's process and its descendants and not over a process group, since a command the runner starts stays in the pane's process group.

**The gate record's sentence**, prose above the run block of the second run, in no `seal` block (`chain.ts#earlierRunSays`):

```
An earlier run on <commit> ended with exit code <n> while the machine was over its load (load average <x> on <cores> cores, <k> other heavy commands). The run below ran alone.
```

`<commit>` is the full hash, as the run block below it names it. Where a signal ended the earlier run, "exit code <n>" reads "the signal <name>". `<x>` has one decimal place. Where no load was read, the parenthesis opens "no load average read" in place of the load and the cores. Where `<k>` is 1, the sentence reads "1 other heavy command".

**The hold**, `keep-awake.ts`: the holder takes whether the display is held too. With it, the child is `caffeinate -d -i -w <pid>`. The daemon keeps one hold: where a heavy command takes the first turn or the last one ends, it releases the hold that stands and starts one of the other kind, and tells the windows nothing, since the Mac stays held. The wake is no part of the holder. It is a daemon option of its own, `DaemonOptions.wakeDisplay`, which runs `caffeinate -u -t 5` once at each call (`keep-awake.ts#wakeDisplayFor`). The giver calls it as it gives each turn, in the daemon's chain and on the socket alike, under every choice but "Never". A second run that waits for the load holds its turn, so the display is held during that wait and woken after it.
