## What this phase found

**The frame holds for phase 3, as folded at `3fb8fe9`.** The coordinates phase 3 builds on were opened at that commit: `daemon.ts#runGate` with its wait from phase 1, `seal-records.ts#gateText` and `stage-records.ts#recordGate`, `gate.ts#startGate`, `turn-socket.ts` and the keeper's option `load`. **Departures from `frame/design.md` *Data & interfaces*, each with where it lands.**

- `ran` carries two fields more than the frame's row: `beside`, how many other heavy commands held a turn during the run, and `cores`, the cores the daemon compares a load with. A pane's gate writes the sentence of the earlier run, which names both (*Scope* item 10), and the chain command reads no machine of its own.
- The ten-minute wait for the load is the giver's, `turn-socket.ts#turnGiver`, and not the keeper's. The keeper knows the load and not the cores, as the fold says. The giver holds the keeper's turn while it waits, so no other command starts meanwhile, which is what *Scope* item 9 calls alone. The daemon's own chain now asks through the same giver as the socket does (`Daemon#turnGiver`), so the two paths share the wait, the reading of a run and the run's line.
- While a second run waits for the load, it holds the keeper's turn, so the keeper lists it as running and the work item's `machineWait` shows no wait. The chain's sentence says the wait (`chain.ts#GATE_AGAIN_SAYS`), and the stage carries `gate.waits`. The line says nothing of it: `frame/questions.md` Q17 stands at its default (a), so phase 5 adds no words for this wait.
- The sentence of `frame/design.md` *The gate record's sentence* names an exit code. A first run that a signal ended is named "ended with the signal <name>". Where no load was read the parenthesis reads "no load average read". One other command is "1 other heavy command". The commit is the full hash, as the run block below it names it.
- A run's line in `heavy-runs.jsonl` also holds the folder it ran in, and holds null for the repository and the work item where that folder is no work item's worktree.
- A connection that closes while it holds its turn, before it says `ended`, ends the run with no exit code and no peak memory, and its line is kept with both null. *Scope* item 11 asks for one line for each run.
- Peak memory is read over the tree of the command's process and its descendants, with `/bin/ps -axo pid=,ppid=,rss=`, and not over a process group, which the probe in `frame/design.md` *Grounding* timed as `/bin/ps -axo pgid=,rss=`. The runner starts its command with the session's own input and output, so the command stays in the pane's process group, which holds the runner's own process too. *Scope* item 11 names the command's process and its descendants.

**Decisions made while building, each judged against the document named.**

- A first run runs once more only where its command exited with a code other than 0 or a signal the daemon did not send ended it, and where the daemon read the run as over the machine's load (`machine-turns.ts#overLoad`). A run the person stopped, one stopped at the gate's time limit of 60 minutes, one whose sessions ended, one whose command did not start, and one whose record was refused (a head that moved, a change left outside the work item's directory) runs once. Each of those is either the daemon's own end or a fault no load explains. A run stopped at the time limit already took an hour, and a second run would double that wait. Judged against `frame/design.md` *Scope* item 9, "A broad gate that failed". `chain.ts#endedWith` holds the rule, and the pane's gate uses it too.
- The machine is over its load during a turn where another command held a turn during any part of it, or where the load the keeper read as it gave the turn was above the cores. With the daemon's limit of 1 until phase 5, no two turns overlap, so in this release the second part decides. The keeper counts the overlap all the same, and its case shows it at a limit of 2. Judged against *Scope* item 9.
- The keeper reads the load as it gives a turn, and again each time the daemon calls `MachineTurns#sample`, which reads nothing while no turn is held. The daemon calls it every 5 seconds (`DaemonOptions.loadEveryMs`) while a heavy command holds or waits for a turn, where it was given a reading of the load, and runs no timer otherwise. The highest load of a turn is the highest of those readings while it was held. Judged against *Scope* item 11, "the highest load during it", and `frame/design.md` *Grounding* row 2, "No timer runs otherwise".
- **A follow-up after the record was first written.** The first build started that timer in the daemon's constructor wherever a reading of the load was given, so it read the load with no heavy command, and `sample` read it with no turn held. The framer's fold at `cd16010` found it against *Grounding* row 2 and the *Rule changes* line for *Memory design*. The fix starts the timer at the first ask and stops it at the end of the last (`Daemon#readLoadWhileAsked`). Two cases were seen red against `cd16010`, executed: the keeper's "reads the load for a sample only while a command holds a turn" read 1 where it wants 0, and the runner's "reads the load the daemon is given only while a heavy command holds or waits for a turn" read 12 with no command where it wants 0. Mutated after the commit `22b59fb`, executed: the keeper's guard (`MachineTurns#sample` with its first line removed) went red. The daemon's three (the timer started on every change, never stopped, or started again while one runs) survived at first, since the keeper reads nothing with no turn held; the runner's case now also counts the keeper's samples (`fb2ee2c`), and all three went red.
- The daemon takes `load`, `cores`, `calm` and `loadEveryMs` as options. A daemon given none reads no run as over its load by its load, and a second run waits for no load. `main.ts` gives none yet, so the built app runs no second run until phase 5 fills `load` and `cores` from #32's reader. Judged against `frame/design.md` *The machine's reading*.
