# Phase 1: 1795559735-heavy-commands-wait-their-turn

## What this phase found

**The frame holds for phase 1.** Each coordinate of `frame/plan.md` *Technical context* that phase 1 builds on was opened at `b48b722`: `daemon.ts#runGate` lists the gate when its process starts, `stopGate` is reached by the client message, by `endSessions` and by the daemon's close, and the store reads a gate's run through `chain.ts#chainOf`, which copies three fields. None of them contradicts the frame.

**Two departures from `frame/design.md` *Data & interfaces*, each left to the phase that builds what it serves.**

- An ask carries no "whether the run must be alone" yet. That field serves *Scope* item 9, which `frame/plan.md` gives to phase 3, and phase 1 has no case that could hold it. Phase 3 adds it to `TurnAsk`.
- The keeper takes a reading of the load and gives each turn the load it read as the turn was given (`Turn.load`). The daemon gives it no reading in phase 1, so every turn of the daemon's carries null. The reading is #32's `readMachine()`, and phase 3 is the first phase whose rule reads the load.

**Decisions made while building, each judged against the document named.**

- `MachineTurns#ask` gives `{ waits, turn }`, where `waits` says whether the ask waits rather than holding its turn at once. The daemon lists a waiting stage only where `waits` is true, so a gate whose turn is free is listed once, as it starts, exactly as before. Without `waits`, every gate would show "The broad gate waits for the machine." for the time of a git read. Judged against `frame/design.md` *Scope* item 4 and the third row of *Removes*. Phase 2's runner needs the same answer for its sentence that it waits.
- After a wait, the daemon reads the head and the tree again with `stage-records.ts#gateOwed` before the command starts. `runGate`'s comment states that the command runs on the commit the order was read at, and a wait of minutes falls between that read and the start. A head that moved during the wait now stops the chain before the command starts, with the sentence `gateNotRunSays` already gives. Without the second read, the command would run, and its record would be refused afterwards by `recordGate`. Judged against the comment of `daemon.ts#runGate` and the third row of *Removes*.
- A gate stopped before its command starts fails with the clause "it was stopped before its command started", whatever stopped it, and enters no run in the ledger. The ledger keeps one entry for each run of a gate that ended (`daemon.ts`, the comment of the field `ledger`), and no run started. The time limit runs from the command's start, since `GATE_LIMIT_MS` is how long a command may run. Judged against that comment and `DaemonOptions.gateLimitMs`.
- `machineWait.ahead` counts the asks that wait before this one and not the ones that run, so a lone waiter reads 0. #32's frame at `205554a`, `frame/design.md` *Scope* item 8, gives the words "Waiting for the machine" for a wait with none ahead.
- The broad gate's name in the queue is "Broad gate", from scenario A and the dialog of `frame/design.md` *Data & interfaces*.
- A work item's wait is found by its worktree, since an ask names the folder it runs in. Phase 2's asks come from the runner with the worktree's top. Whether that path matches `WorkItem.worktree` as the store holds it (a real path against one with a link) is phase 2's to check.
- The store keeps no `waits`. `chainOf` copies a gate run's three fields, so a daemon that ended during a wait reads that stage at its next start as a gate the daemon ended. Judged against `frame/design.md` *Grounding*: the daemon stores no queue.
- `test/chain-run.ts#standing` takes `apart: true`, which gives each title after the first a repository of its own with its own remote. Scenario A asks for two work items of two repositories.
