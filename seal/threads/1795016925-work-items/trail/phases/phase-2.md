**What the window does now.**

- The top bar has "+ Work item". It opens a form with the repository folder (a text field and a "Browse…" button), a title and the kind of pane, Claude Code first. "Create" sends `createWorkItem`. At `workItemCreated` the form closes, the work item joins the window's list and its pane opens in a new tab. At `error` the form stays open with the daemon's message in it, and the terminal prepared for the request is removed.
- The side panel lists the work items above the hook events, one line each: the title, then the branch. The list is what `ready` carried plus each work item this window created.
- "Browse…" calls `window.owlery.pickFolder()`, a second channel of the preload (`owlery:pick-folder`). The main process opens Electron's folder dialog as a sheet of the window that asked and returns the folder, or null.

**Decisions made while building, each judged against `frame/design.md` *Scope* item 8 unless another document is named.**

- *A tab reads `<title> · <kind> <id>`, not the title alone.* Departure from item 8, which says the tab is labelled with the title. Two work items may carry one title (scenario 3), and one work item may hold more than one pane (item 7), so the title alone gives tabs nobody can tell apart. A pane with no work item keeps the label it had, `<kind> <id>`. A tab longer than 240 pixels is cut, and its tooltip holds the whole label.
- *A session whose work item the window does not hold is labelled as a pane with no work item.* `ready` carries the sessions and the list together, so this is reached only where the list file was lost while the daemon ran.
- *The form refuses an empty folder and an empty title before sending anything.* Addition to item 5, which has the daemon refuse a folder outside a repository. The daemon passes the folder to `execFile` as the working directory, and Node runs a process given an empty one in its own directory (run once: `execFile("pwd", [], { cwd: "" })` printed the caller's directory). An empty folder from the window would therefore make a work item of whatever repository the daemon was started in. The window trims both fields and sends neither when one is empty. The daemon itself still accepts an empty `repo` from another client; that is in `gaps.md` *Not done*.
- *The folder stays in the form between two openings, and the title is cleared.* The next work item is often of the same repository.
- *One creation per answer.* "Create" is disabled from the send until the daemon answers, so a second click cannot send the same title twice and make a `-2` nobody asked for.
- *A form closed while its creation runs does not cancel it.* The protocol has no message that cancels. The pane opens when the daemon answers, and a refusal that arrives after the form closed is shown in the top bar's status line, where a failed `start` is shown too. The status line is cleared when the next pane opens.
- *The pure parts sit in two new modules the frame does not name.* `src/renderer/view.ts` holds what a tab and a list line say and what the form sends, and `src/main/pick-folder.ts` holds the dialog's call with the dialog passed in. The repository's tests run in Electron's Node with no page (`frame/plan.md` *Technical context*), so code that touches the page or Electron's `dialog` cannot be reached by a case, and these two can. Grounds: the plugin's `skills/implement/SKILL.md` *2. Implement test-first, and let each rule name its test*.
- *`src/shared/ipc.ts` now says two channels.* Its opening comment said one channel joins the window and the main process; the comment was rewritten in place, and `src/main/main.ts`'s opening comment with it.
