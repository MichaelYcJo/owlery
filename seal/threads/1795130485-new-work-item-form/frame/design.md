## Scope

In scope, as numbered items.

1. **Owlery makes a name.** A new module `apps/desktop/src/shared/names.ts` exports a function that returns `<word>-<word>`, two words drawn at random, each from a list of its own that the module holds. Every word is of the letters `a-z` alone, so `slugFor` returns a generated name unchanged, and the longest pair fits `slugFor`'s 40 characters. The function takes its source of randomness as an argument, which a case replaces. The window and the daemon both import it.
2. **What names the branch and the folder.** `slugFor` returns an empty string where a title leaves nothing, and no longer `work-item`. The name is the first of these that is not empty: the slug of the title; the slug of `name`, a field the client may send; a name the daemon generates. The branch is `owlery/<name>` and the folder `<root>/<repository's folder name>/<name>`, and `-2`, `-3` and so on are appended to both as at `47c4f61`.
3. **What the work item is called.** The stored `title` is the title as sent, with the white space at its ends removed. Where that is empty, the title is the name of item 2 with its appended number.
4. **A base and the default base.** A base is a local branch or a remote's branch as the person's clone holds it. It is named as a person reads it: a local branch by its name, such as `main`, and a remote's branch by the remote's name, a slash and the branch's name, such as `origin/main`. The daemon reads a base's name as the local branch of that name where one exists, and as the remote's branch otherwise. A `baseBranch` stored before this work therefore keeps naming a local branch. A remote's `HEAD` entry is no base, and neither is a local branch that names another ref, such as a `main` that stands for `master`.

   The daemon reads a repository's default base from the refs of the person's clone alone, with no network and no fetch. With the candidate names `init.defaultBranch`'s value, `main` and `master`, in that order, the default base is the first of these that exists:
   - the remote's branch that a remote's `HEAD` names, the remote `origin` first and the other remotes in the order of their names;
   - a remote's branch of a candidate name, the remotes in the same order and, within one remote, the candidate names in theirs;
   - the local branch of a candidate name;
   - the local branch the checkout stands on.

   Where none exists, the repository has no default base.
5. **Where the branch is cut.** A creation takes `base`, the name of a base as item 4 names one. The daemon cuts the work item's branch at the ref item 4 reads that name as, with `--no-track`, so the new branch has no upstream whatever the base and whatever the person's `branch.autoSetupMerge` says. It stores `base` as `baseBranch`. A creation without `base` uses the default base of item 4. Where the repository has no default base, the branch is cut at the checkout's commit and `baseBranch` is `null`. A `base` that is no string, or that is none of the bases item 6 lists, is refused with an error that names it, and no branch, no folder and no list entry is made. The branch the person's checkout stands on no longer decides where a work item starts.
6. **A plan of a creation.** A new client message asks what a creation in a folder with a title and a `name` would give. The daemon answers with the branch and the folder of item 2, the repository's bases in two lists and its default base. The local list holds the branch the checkout stands on first, then the other local branches, without a local branch that names another ref, the newest commit first. The remote list holds the remotes' branches, the newest commit first, without a remote's `HEAD` entry and without a branch whose name a local branch bears. The daemon creates nothing for a plan, and a plan does not wait behind `Daemon#creating`. A folder outside any git repository is answered with the `error` message a creation gets.
7. **The form's name.** The field `work-item-title` stands under the label "Name" and may stay empty. Each time the form opens, the window generates one name with item 1's function and shows it as the field's placeholder. The window sends the field's text as `title` and the generated name as `name`, in the plan's request and in the creation. The ids `work-item-repo`, `work-item-title`, `work-item-kind`, `work-item-create` and `work-item-error` keep their names and meanings, so `apps/desktop/test/memory.ts#openWorkItem` and `apps/desktop/test/korean-pane.ts#openReceiverPane` are not edited.
8. **The form shows the branch.** Under the name the form shows the branch and the folder the plan's answer gave. The window asks for a plan when the form opens with a repository, when the repository field changes and when the name changes. It shows only the answer to its latest request. Where the daemon answers a plan with an error, the form shows the error's message in the place of the branch and not in the window's status line. Where no answer comes, as from a daemon of an earlier build, the form shows no branch.
9. **The form shows the base.** A new field `work-item-base`, a menu under the label "Starts from", holds the bases of the plan's answer: the default base first and chosen (where the answer has no default base, the first base listed is chosen), then the local list under the group label "Local", then the remote list under the group label "Remote". The default base stands once, at the top, and not again in its group. A choice the person made is kept while the form stays open, the repository field's text stays the same and the answer still lists that base; each opening of the form starts from the default base, as the issue's third *Done when* sets. The creation sends the chosen base as `base`. Where the form holds no answer, or the answer lists no base, the menu is disabled and the creation sends no `base`.
10. **How far ahead of a remote's branch.** `aheadOf` reads `baseBranch` as item 4 reads a base's name, at every read, so the count against a remote's branch moves when a fetch moves that branch. Where the name is neither a local branch nor a remote's branch any more, the count is `null`. The window's facts and the preview's sentence print `baseBranch` as stored, so they read "origin/main · 6 ahead" and "6 commits ahead of origin/main", and `apps/desktop/src/renderer/view.ts#ahead` is not changed.

Out of scope.

- Starting a work item from an issue number, a URL or an existing branch, and a "create more" switch. The owner put only the *Done when* lines into release 0.0.1.
- A fetch before the cut, and any other use of the network. The owner's answer to `frame/questions.md` Q1 has Owlery not fetch, so a remote's branch is as old as the person's last fetch.
- A person editing the branch's name apart from the work item's name. The issue asks that the form show the branch.
- A name made from a title written in Korean by writing its sounds in Latin letters. Such a title gets a generated name, by item 2.
- A creation in a repository with no commit. It fails with git's message, as at `47c4f61`.
- Renaming the protocol's field `title` or the id `work-item-title`. Every list in the window reads `title`, and both drivers fill the id.
- The look of the reference dialog. The form keeps the window's own styles in `index.html`.

## Data & interfaces

`apps/desktop/src/shared/protocol.ts`:

- `createWorkItem` gains two optional fields, `name?: string` and `base?: string`. Its `title` stays a string and may be empty.
- A new client message, `{ type: "planWorkItem"; requestId: number; repo: string; title: string; name?: string }`.
- A new server message, `{ type: "workItemPlan"; requestId: number; branch: string; worktree: string; localBases: string[]; remoteBases: string[]; defaultBase: string | null }`. The two lists hold the names of the repository's bases as *Scope* item 6 orders them, and `defaultBase` is a name of one of the two lists or `null`.
- `WorkItem` keeps its fields. The comment on `baseBranch` says what *Scope* item 5 makes it: the branch the work item's branch was cut at, local or a remote's, named as *Scope* item 4 names a base, or `null` where it was cut at the checkout's commit and for a work item made before this was recorded.

`apps/desktop/src/shared/names.ts` is new and holds the two lists and the function of *Scope* item 1.

`apps/desktop/src/daemon/worktrees.ts`: `createWorktree`'s options gain `name` and `base`. The choice of the name with its appended number, the read of a base's name, the read of the default base and the two lists of bases become functions the plan and the creation both call. `aheadOf` reads its base through the read of a base's name. `Worktree` keeps its fields.
