**Decisions made while building.** Each is the work's, judged against `frame/design.md` *Scope* items 2, 4 and 5.

- **Names.** `view.ts#screenMoves` is scenario 3's function and `view.ts#replayStep` scenario 6's, with their cases in `test/view.test.ts` beside `paneTabs` and `paneInFront`. In `work-item-view.ts`, `pool` is the screens, `newScreen` makes one, `take` puts a pane on one, `giveBack` takes it back, `stageShows` applies `screenMoves`, and `screenOf` finds a pane's screen.
- **A screen is emptied by a reset written into the terminal, not by a call.** xterm.js draws what it is handed later, in order (`@xterm/xterm` 6.0.0, `src/common/input/WriteBuffer.ts`, `read`). A call of `reset()` at the hand-over would run before output of the pane that left that the terminal had not drawn yet, and that output would land in the next pane's screen. `giveBack` writes the reset sequence `ESC c`, which the terminal takes in order and answers with the same `reset()` (`src/common/InputHandler.ts#fullReset`, `read`).
- **The window counts the replays it asked for, per pane, and not per screen.** A pane that left the stage may have a replay on its way and come back on another screen. `replayStep` writes a replay only where it is the last one asked for, and output only where none is awaited. A replay nobody asked for is not written.
- **A pane that comes on takes the first free screen, one given back in the same step among them.** A press on another tab therefore hands the one screen from pane to pane and makes none.
- **A new screen is made visible and taken at once.** A terminal is opened in a displayed element, as before the work. A screen is made only for a pane that is coming onto the stage, so no screen is ever made hidden.
- **The size is told once when a pane takes a screen.** The screen is fitted while it is still free, so the fit's own event sends nothing, and the size is sent after it whether or not the fit changed it.
- **`paneOnScreen` still answers the pane in front.** With one pane on the stage that is every pane on the stage. Phase 4 widens it with item 1.
- **A closed pane's screen is given back through the same path as any other**, so the window sends `detach` for a pane the daemon no longer lists. *Scope* item 3 says that changes nothing.
