# Implementation Plan: four visible terminals keep the app under about 500 MB

## Technical context

The plan was drawn at `69b25ba` and folded at `7e33c8a`, which holds `release/v0.0.1` at `ea78b7b` (`frame/design.md` *Grounding*). Every coordinate here is a coordinate at `7e33c8a`.

`apps/desktop`: the window is `src/renderer/`. `renderer.ts` holds the connection and which of the four screens is in front, `work-item-view.ts` a work item's view and its terminals, `view.ts` the window's decisions as pure functions with their cases in `test/view.test.ts`, and `index.html` the page. The daemon is `src/daemon/` (`daemon.ts`, and `buffer.ts` with the output each session keeps), with its cases in `test/daemon.test.ts`. `src/shared/protocol.ts` is what the two exchange. The tests run with vitest in Electron's Node (`pnpm run test`). One case loads the page: the Korean input case starts the built app through `test/built-app.ts` (`BuiltApp.start`) and drives its window through Chromium's debugging port. The app is Electron 45.3.3 with `@xterm/xterm` 6.0.0, `@xterm/addon-webgl` 0.19.0 and `@xterm/addon-fit` 0.11.0.

These facts shape the build.

- **The window keeps one terminal per pane it ever showed.** `work-item-view.ts#terminalFor` makes it the first time the pane is in front, and `work-item-view.ts#dropClosed` disposes of it only when the daemon stops listing the pane. A person who visits eight panes holds eight terminals and their WebGL canvases, seven of them hidden. The probes read 610 MB after four panes were each in front once, against 457 to 462 MB with one (`frame/design.md` *Grounding*).
- **The stage shows one pane.** `#stage` holds every pane's element, absolutely placed, and `work-item-view.ts#showView` hides all but the one in front. Nothing in the window shows two terminals at once.
- **A client cannot stop receiving a session.** `Daemon#clients` gives each client a set of sessions that only grows, so a window that gave a pane's screen away would still be sent its output.
- **The window, and not the daemon, writes the exit line,** into the terminal it holds (`renderer.ts#onMessage`). A terminal that is given away loses it, and `view.ts#paneTabs` gives an exited pane a tab only while the window holds its terminal.
- **The kept output is cut at a character,** 256K characters per session, in memory alone.
- **The stage is 764 by 789 pixels in a window that opens 1440 by 900,** between a sidebar of 256 pixels and a right column of 420. A tile of two columns and two rows is 358 by 380 pixels, 49 columns by 27 rows, where a terminal alone is 102 by 54 (`frame/design.md` *Grounding*, the probes).
- **There is no room under 500 MB on the machine the probes ran on.** One WebGL terminal that draws read 457 to 462 MB, and four as tiles 508 to 557 MB, of which the GPU process held 321 to 330 MB. Four with the DOM renderer read 434 to 443 MB. The probes forced the tiles and are not the measurement, which phase 4 takes.
- **A start under `OWLERY_BACKGROUND=1` may show the page nothing to draw for.** The window opens without the focus, and in two of the probes' starts the page reported `hidden`. A hidden page drew no frame and read 194 to 195 MB with four terminals. With `Emulation.setFocusEmulationEnabled` the page drew 60 frames a second in every sample.
- **`BuiltApp.start` already does what a measurement needs of a start:** a build of `dist/`, a user data folder of its own, a free debugging port, the calls on the page, the daemon's process id, and a stop that leaves no process and no folder. It is TypeScript under `test/` and runs in Electron's Node, where `process.execPath` is the app's binary.
- **The daemon starts in a run folder of any length** since issue #19 merged, so the measurement's folder needs no short path.

**The failure scenario of the chosen approach.**

- Every time a pane comes onto the stage, its screen is drawn from the daemon's raw output. A full-screen program whose output passed the kept 256K characters is drawn from the middle of its stream, so its screen is wrong until the program redraws, and a replay written into a tile of another size wraps where the process did not. The fit that follows an attach sends the process its size; whether each agent's CLI redraws its whole screen at that is not checked by anything here.
- The kept output is counted in characters and the window's history in lines, so a pane that prints many escape sequences comes back with fewer than 1,000 lines.
- A screen is handed from pane to pane. A composition a person left open in one pane, or a mode a program set, is ended by the terminal's reset alone. The Korean case types into one pane and never changes the pane on a screen, so nothing checks a composition across a hand-over.
- The number is one machine's, on its displays, at the window's default size, on the day it was taken. The probes' machine has 4K displays at a scale of 2. Milestones 2 to 4 add screens to the window, and nothing runs the measurement again: the criterion of `docs/roadmap.md` *Done criteria* is checked at 0.1.0, where issue #75 measures the caps, and whoever checks it then has to run it.
- The runs this work publishes are an agent's, under the switch, of a page told that it has the focus. A person's start has a Dock icon, a menu bar and a window in front, and nobody has measured what those add or take. Where the emulation itself changes what Chromium keeps for the page, the published number differs from a person's, and only the owner's run shows it (`frame/questions.md` Q5).
- The measurement moves the window by its controls' ids. It runs only under its variable, so a change of the pane bar or of the form breaks it without a red check, and the break shows the next time somebody runs it.
- Free screens stay in the pool, so a window that once showed four panes holds four hidden screens while the inbox is in front. The probes read 269 MB on the inbox after four terminals, against 158 MB before any. The measurement reports that number, and nothing here lowers it.
- Four tiles in the stage are small: 49 columns by 27 rows at the default window size, under the 80 columns an agent's CLI is drawn for. A person who wants wider tiles widens the window, and the two side columns keep their widths (`frame/questions.md` Q4).
- The number is likely over 500 MB with WebGL (`frame/questions.md` Q2). This work then publishes a number that does not meet the issue's first line, and what follows is the owner's (Q3).

## Alternatives considered

## Operational impact

No dependency is added. The protocol gains the client message `detach`. A daemon left running by an earlier build ignores it, as it ignores any message it does not know, and goes on sending a hidden pane's output, which the window drops. Such a daemon appends no exit line, so an exited pane's screen ends without it until that daemon exits. The other way round, a window of an earlier build on this daemon shows the line twice.

An exited pane keeps its tab across a reload until a person closes it, where it had none before.

`apps/desktop/package.json` gains the script `measure:memory`. The suite gains `test/memory.test.ts`, whose cases run in every `pnpm run test` and whose measurement runs only under `OWLERY_MEASURE_MEMORY=1`. The tree gains `apps/desktop/measurements/memory.md`. The measurement needs macOS and its `footprint` command, and opens a window on the machine that runs it.

The version does not move: `0.0.1` was moved by the first pull request into `release/v0.0.1`.
