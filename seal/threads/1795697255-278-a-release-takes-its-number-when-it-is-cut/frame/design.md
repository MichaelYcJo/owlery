## Scope

The work rewrites, in place, each sentence of the policy documents and the READMEs that names a goal, a milestone or an unreleased release by a version number, or that states the old rule. Each item holds in both editions. The Korean edition states the same in its own words, with the same headings and the same table rows. Korean text says 인장 and never 도장. New text names no `v0.x` and no release number above 0.1.0.

1. ***Releases and the tracker*, its opening paragraph** (`docs/roadmap.md:47`), reads: "A release holds what has merged when it is cut, and it takes its number then. A GitHub milestone is named by its goal and never by a version, so an issue keeps its milestone whichever release ships it. A milestone titled `release: <version>` holds a release whose number is already set: 0.0.5, built on its branch, and 0.1.0, which a rule below fixes. The owner set these rules on 2026-11-26 (issue #278), and the two tables state the releases and the milestones as the tracker holds them that day."
2. **The release table** keeps its three columns and the rows 0.0.1 to 0.0.4. The 0.0.3 row's "and are now in 0.0.5" becomes "and are now in the milestone `owner: by hand`". The row 0.0.5 reads `| 0.0.5 | Between 0.0.4 and 0.1.0: the walk release | ... |`. Its purpose says that what the owner found using the built app on 2026-11-25 is fixed, with what was already built on the branch when the owner split it from 0.1.0 on 2026-11-26: the `.dmg` (#78), a daemon of another build replaced (#133) and a turn that ends on an API error (#188) among them. It says that the owner's own walk of the owl chain and the rest of milestone 2 (#184, #110), and the broken seal's sentence (#176), are in the milestone `owner: by hand`. The rows 0.0.6, 0.0.7 and 0.0.8 go. The row 0.1.0 reads `| 0.1.0 | The first public release | ... |`, and its purpose is milestone #9's: the minimum for Owlery to be published, what must hold before a stranger downloads the app and nothing more. The build published on Sunday 2026-11-29 is the release. Beside the `.dmg` (#78) and the daemon of another build (#133) that release 0.0.5 carries, it holds #257, #127 and #132, each named by what it does.
3. **A second table follows the first**, `| Milestone | Goal |`, after one sentence: "A milestone named by its goal takes no number, and its issues ship in the release they merge into." Its rows name each open goal milestone by its title in backticks, in this order:
   - `after launch: first findings and conveniences`: what the launch of 0.1.0 and its first users find, and the conveniences the owner's walk of 2026-11-25 named that the launch left out.
   - `milestone 3: hand over an issue`: row 3 of [Milestones](#milestones).
   - `milestone 4: the person's hands on the work`: row 4 of [Milestones](#milestones).
   - `hardening: boundaries and edge cases`: the boundaries and edge cases found while milestones 1 and 2 were built.
   - `milestone 5: after the PR, and limits`: row 5 of [Milestones](#milestones), and the check of the first version's done criteria.
   - `owner: by hand`: work only the owner can do, such as a walk of the built app, a drawing, a choice between sheets or a build in a pane, which the orchestrator asks the owner about at the end of each release.

   The table states no order beyond the one *Why this order* gives milestones 1 to 5.
4. **Rules 1 to 3 replace the bullet "The release that closes milestone 5 is 0.1.0"**, as the first three bullets of the list:
   - "**Owlery stays on 0.x.** It moves to 1.0.0 only when the owner decides so in words, and an agent never chooses it."
   - "**A public release's number comes from the change since the last public release that a person feels most.** The minor number moves where a person would feel a new workflow or capability. The patch number moves where the release holds fixes, polish and improvements within what exists. At the release's close the orchestrator proposes the number with its grounds, and the owner approves it."
   - "**0.1.0 is the first public release, and no 0.0.x release follows it.**"
5. **The bullet "Each release is built on a release branch of its own" keeps its sentences and gains two at its end:** "While the branch is cut when the release's work starts, the orchestrator proposes the number when it cuts the branch, by the measure above and from the issues the release is cut for, and the owner approves it then. The number stays after the cut, because a connected repository's check clones the branch `release/v<version>` of its pinned version until the tag exists (`apps/desktop/src/daemon/records-place.ts`)." Rules 5 and 6 follow it as two bullets:
   - "**Later, pull requests merge into `main`, and a release branch is cut only when a release is cut.** That change is an issue of its own after the launch, and the seal check's pin and the settle change with it. The orchestrator's proposal then moves to the release's close."
