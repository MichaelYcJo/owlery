**The failure scenario of the chosen approach.** In six months a stage or a person writes a block into `decisions.md` that the reader refuses, such as a value over two lines. The inbox then shows no decision for it and names the line as not read, and nothing is decided on it: the loss is visible, and the record's writer is the place to change. The second failure: the daemon's commit of a person's word meets a git operation of a session it did not see working, such as a commit a person makes in a shell pane, and fails on the index's lock. The file stays written, not staged and uncommitted, and the next commit of the work item's records carries it. The daemon's own commits of one worktree run one after another, so two of them never meet on the lock. A word given while the worktree is off its branch or in the middle of an operation is refused and written nowhere, so the person sends it again once the operation has ended. An operation a person starts in a shell pane between the daemon's question to git and its write, or its `git add`, still takes the word or the commit in, since that window is one command of git long. The third: `record-times.json` is lost or the work item moves to another machine, and every age starts again, so a question that waited three days reads "less than a minute". The fourth: a work item gathers hundreds of blocks, and every `inbox` carries all of them to every client at each change of any list. The daemon then needs a bound on what it sends, as its list of headless sessions got one in #26. The fifth: the pass reads every work item's `routing.md` files and its record every few seconds while a window is connected, and a repository with many directories under `threads/` makes the pass slow. The sixth: a checkout holds a link or a file that is no record where the daemon reads one. The daemon reads `decisions.md` and each `routing.md` of a work item's worktree, and the `README.md` at each name of a records root, the root's `config.json`, `.github/workflows/hygiene.yml` and `package.json` of the main checkout, only as a plain file of at most 1,048,576 bytes, and the first two never through a link, so a record over the bound is one unread line and a stage has to keep it smaller. A work item's directory that is itself a link is still followed, the write's rename replaces a link put at the record's path between the write's read and its rename, and a link put at the partial file's path `decisions.md.<pid>` is written through: #152 carries both limits.

## Operational impact

No dependency and no environment variable is added. `docs/product.md`, `docs/architecture.md` and their Korean editions change in this pull request. The daemon's run folder gains `record-times.json`, readable by the user alone, and a daemon of an earlier build ignores it. No released build wrote `decisions.json` or `asked.json`, and a build of this branch that did leaves them where they stand, unread. The daemon reads `decisions.md` in each work item's worktree, and writes it at a person's reversal or answer. It reads `decisions.md` and each `routing.md` of a work item's worktree, and the `README.md` at each name of a records root, the root's `config.json`, `.github/workflows/hygiene.yml` and `package.json` of the main checkout, only as a plain file of at most 1,048,576 bytes, and the first two never through a link, so a repository that keeps a record as a link shows it as one unread line, and one that keeps a `routing.md` as a link shows its work item with no directory. It refuses a reversal or an answer, and writes nothing, where the worktree's HEAD is not the work item's branch or a rebase, merge, cherry-pick, revert or `git am` is under way in it. After a write it makes a commit of that file alone on the work item's branch, with the person's git identity and the repository's hooks, where no session of the work item is working, and where the worktree still stands on that branch with no such operation under way. The protocol gains the fields `decisions`, `questions` and `unread` on a work item, in `ready`, `inbox` and the look, and the client messages `reverseDecision` and `answerQuestions`. A window of this build reads a work item without the fields as one with none. A `last-look.json` written before this build is still read. The version does not move: `apps/desktop/package.json` reads `0.0.2`.
