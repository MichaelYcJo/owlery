The four additions:

- **The commits of one worktree run one after another.** Two words can be written within a few milliseconds, and a second `git add` beside a commit under way fails on the index's lock. `Daemon#commitWord` keeps, for each worktree, the last commit it was asked for, and each commit starts when the one before it has ended. Whether a session is working is read when the commit's turn comes, not when the word was written. Judged against `frame/plan.md` *Technical context*, the second failure, which names the index's lock.
- **A commit carries the file as it stands at its turn, and a turn that finds it committed commits nothing.** Where a second word is written before the first commit's `git add`, the first commit holds both, and `git commit` then exits 1 for the second with "nothing to commit". That is not a failure, so `commitAlone` asks `git diff --cached --quiet -- <path>` after the `git add` and returns where git exits 0. The first run of the case of two reversals sent together showed it: one commit, and git's words in the log.
- **A commit that fails takes the record out of the index again.** The frame says the file stays written. `git add` has staged it by then, and a staged record would go into whatever commit a person next makes in that worktree by hand. `commitAlone` runs `git reset --quiet -- <path>` before it throws, as `setUpRecords` unstages its paths. A record a person or a stage had staged before is unstaged with it, and the file itself is not touched.
- **The daemon's close waits for a commit under way.** A close that returned first would leave a `git commit` at work in a worktree, and a case's cleanup would remove the folder under it. No frame sentence names the close.

**Decisions made while building.** Each was judged against the document named.

- **The commit is made after the `done`, and its outcome changes no answer.** The handler writes the file, answers `done`, sends the `inbox`, and the commit runs afterwards without the handler waiting.
