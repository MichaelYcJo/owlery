**Decisions made while building, each with its grounds.**

- `HeadlessLine` gains two fields, `errorOutput` and `stop`. `headlessLines` decides both, so a case on `view.ts` pins each, as `frame/design.md` scenario 9 asks ("cases on the decisions of `apps/desktop/src/renderer/view.ts`"). `errorOutput` is the session's `errorOutput` where it `failed`, and `""` otherwise. `stop` is true where the session is `working`. Judged against *Scope* item 9, which shows the error output on a failed line alone.
- The error output is a part of its own under the error, `.error-output` in `index.html`, in the monospace face with the line breaks kept. It is not joined to the error's text. Judged against `frame/plan.md` *Alternatives considered*, the row that rejects appending the tail to `error`: the daemon's sentence and the CLI's output stay apart for the reader too.
- `withoutHeadless`, a new function of `view.ts`, takes the dropped session out. `dropHeadless` in `work-item-view.ts` holds the result and draws the section again. At `headlessDropped`, `renderer.ts` redraws no dialog. The daemon drops only a session that ended, and the dialogs name only the running ones. Judged against *Scope* item 7 as folded at `8f2b9cc`.
- "Stop" is a `quiet` button at the end of the line's first row. A press sends `{ type: "stopHeadless", requestId, id }`. The button stays pressable until the `headless` message that carries the session as failed. A second press is answered `done` and changes nothing, by the daemon's own rule (*Scope* item 4). The answer `done` clears the status line as every `done` does. The answer `error`, `no headless session <id>`, reaches the status line through the switch's last branch, because no dialog or form owns the request.
- A window of this build against a daemon of an earlier build shows no error output, because `if (line.errorOutput)` reads the missing field as empty. A press of "Stop" there does nothing, because the earlier daemon's switch ignores a message type it does not know (`git show dc82f88:apps/desktop/src/daemon/daemon.ts`, the `default: return`). Read.

**The window keeps a deleted work item's ended sessions until it loads again.** No message after a delete or a repository's removal carries a headless list: `inbox` carries none (`src/shared/protocol.ts`, the `inbox` member), and the daemon sends no `headlessDropped` for them. So the window keeps them in `held.headless`. It draws none of them, since their work item has no view, and none counts as running, since the delete stopped each first. `frame/design.md` *Data & interfaces*, the `headlessDropped` bullet, says that "the `headless` list it sends already leaves them out". No message of HEAD sends such a list after a delete, so the sentence is named in the hand-back for the orchestrator to fold. The prune is in `gaps.md` *Not done*.
