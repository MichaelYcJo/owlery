# Implementation Plan: 1795636142-223-a-stage-a-pane-runs-shows-at-work (#223)

## Technical context

The tree as read at `8b026e67`.

The approval line is composed in the window from the work item alone (`renderer/view.ts#approvalPlaces`, `:707-717`): an open question of the role, then the daemon chain's newest stage (`#byChain`, `:681-688`), then the records (`#byRecords`, `:645-670`). The daemon's chain is the only source of "at work", and no client message starts it (`shared/protocol.ts:497-498`), so a stage a pane's session runs reads "Not started" until its record is committed.

The chain command (`daemon/chain-command.ts`) is a short process: `owed` prints the step and exits, the session then runs the role for minutes, and `round`, `fix-pass` or `seal` commits the answer. Its one channel to the daemon is the turn socket (`daemon/turn-socket.ts`), whose server reads one first line per connection and destroys a connection whose line is no `ask` (`:205-232`). A pane's environment names the pane in `OWLERY_PANE_ID` (`daemon/hooks.ts:173`). The daemon composes each work item per send in `workItemOf` (`daemon.ts:2892-2911`), with `machineWait` read from the keeper's queue as the pattern of a field it stores none of. A pane leaves the lists at `closePane` (`:2026-2036`), and its process's end reaches `terminal.onExit` (`:2588-2622`).

The approach: the chain command tells the daemon, on the turn socket, the stage `owed` handed and that it ended; the daemon holds one stage per work item for a live pane of it, drops it when that pane is closed, when the daemon ends it at an archive or a removal, and at every exit of its process, and sends it as `WorkItem.paneStage`, with a broad gate the command runs read from the keeper's queue; the window draws it with the notes the daemon's chain already uses.

**Failure scenario, six months on.** A pane's session runs `owed` to look at the step and then does something else in the same pane, or its subagent dies without the session noticing, so the proofer's place reads "Round 1" at work for as long as the pane lives, which can be days. The line then says the opposite of the truth in the other direction. What bounds it is the pane's close or its process's end, the next call of the command, and the person's eye on the pane, which shows no subagent; `frame/questions.md` Q1 holds whether a bound by time or by the pane's agent state is wanted. A second scenario: milestone 3's daemon chain (issue #55) starts in a worktree where a pane's stage is held. The daemon chain's running stage stands over the pane's (*Scope* item 6), so the line stays right, but two parties then run one worktree, which `docs/architecture.md` *What a session survives* refuses for a resume and nothing here refuses for a start. #55's frame owns that refusal.
