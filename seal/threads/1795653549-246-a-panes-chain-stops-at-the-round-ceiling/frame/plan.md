# Implementation Plan: a pane's chain stops at the round ceiling

## Technical context

The tree as read at `c9975af0`.

The daemon's chain stops at its ceiling in its runner: before a fix pass, `Daemon#runChain` (`daemon.ts:3131-3132`) asks `chain.ts#gateBefore` (`chain.ts:457-464`) and stops where it answers `ceiling`. The step itself, `chain.ts#stepOwed` (`chain.ts:404-417`), is a function of the records and knows no ceiling. A pane's chain has the same step and no runner in code: the session runs the loop of `apps/desktop/role-bundle/skills/seal/SKILL.md`, and `chain-command.ts#owed` (`chain-command.ts:252-268`) prints what `stepOwed` gives. So the gate before a fix pass belongs where `owed` hands the pass (`:265`) and where `fix-pass` records one (`:320-337`).

Each call of the command is its own process (`chain-main.ts`) and stores nothing between calls. The daemon tells a person's start from its own (`byPerson`, `daemon.ts:3099`), which is state of a run. The command has no such state, so the person's word reaches it as an option of the call, and the option names the round so that it cannot be carried to a later stop.

`gateBefore` takes the daemon's stored stages and a run's `judged` and `first`. The command passes no stage. It passes `judged: true`, since the command asks for no judgment: a pane's session makes it by the bundle's text. It passes `first` as whether `--persons-word` names the step's round. With these, the function answers `ceiling` or `none` and never `judgment`.

The cases of the command run it in their own process through `apps/desktop/test/chain-command-run.ts#commandOn`, with answers the case writes. A case reaches round 2 with the helpers the existing case opening "records a fix pass's close blocks" uses (`chain-command.test.ts:109`). The cases that pin the bundle's text are in `apps/desktop/test/role-bundle.test.ts`: the pane's document at `:99-121`, and the orchestrator's sentences at `:194-221`. The same file holds built-app cases that compare `dist/bundle` with the tree, so the phase runs them in its end-of-phase batch of built-app files (`docs/architecture.md` *Measure before building*, the bullet opening **An agent runs one built-app file alone**).

Two later works change the same code. #223 (release 0.0.5) may have `owed` tell the daemon the stage it handed out, and #220 (release 0.0.6) changes `start` and `owed` for the route. Both read this work's step `ceiling` as a step that hands no stage.

Failure scenario of the chosen approach, in six months: a pane's session passes `--persons-word` with no word from the person, because a model that wants to finish reads the option's name and types it. The command cannot tell, so the bound is then the text of the bundle alone, as it is today. What the option still buys is that the session cannot go on by doing nothing: from the ceiling on, `owed` hands no pass and `fix-pass` records none until the session states, in a command the person can read in the pane, that the person said to go on. `frame/questions.md` Q1 holds whether that is bound enough. A second scenario: a run that merges its base several times reaches round 6 with few findings, since the round is the record's number and a merge owes a round. It then stops at the first finding from round 6 on, as the daemon's chain does, and the person passes it with one word.

## Operational impact

No migration, no environment variable, no dependency. One change of behaviour a person meets: a pane's chain that reaches round 6 with a finding open now stops and waits for the person's word, where it went on before. The chain command gains one step of `owed`'s output and one option, and nothing outside the app's own bundle reads either. This pull request moves no version: release 0.0.5's version already stands.
