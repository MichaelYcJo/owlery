# Implementation Plan: a new work item makes a worktree, and its branch is picked or made later (#217)

## Technical context

The tree as read at `f1bab823`.

The creation is one function. `daemon.ts`'s `createWorkItem` handler (`daemon.ts:911-945`) calls `worktrees.ts#createWorktree` (`worktrees.ts:521-536`), which resolves the base, fetches a remote's base through `BaseFetches`, takes `{ branch, worktree }` from `placeFor` (`worktrees.ts:209-218`) and runs `git worktree add --quiet --no-track -b <branch> <folder> <start>` (`worktrees.ts:533`). The store's `addWorkItem` keeps `branch` as a `string` (`repositories.ts:328-333`). Every later read keys the work item's git state by that name: `readBranch` counts `refs/heads/<branch>` (`daemon.ts:4153-4182`), the records are found by the `routing.md` whose `Branch` row names it (`decision-record.ts:161-189`), and a delete runs `git branch -D` on it (`daemon.ts:2106-2118`, `worktrees.ts:833-836`).

What this builds on, and where it must hold:

- `worktrees.ts#listedWorktrees` (`worktrees.ts:715-733`) already parses `git worktree list --porcelain`, the branch each worktree holds and `detached` among it. The plan's `held` (Scope item 8) and the refusal of a held branch (Scope item 5) read it.
- `worktrees.ts#readLoss` already reads the worktree's own `HEAD` beside the branch (`own?.head`, `worktrees.ts:787`), so the commits of a detached worktree are already named as a loss. It needs only the branch to become `string | null`.
- `worktrees.ts#whyNoCommit` already refuses a detached `HEAD` (`worktrees.ts:864-874`), so every daemon path that commits a record refuses a work item with no branch before anything is written. The sentences are what change.
- `planBranchRename` (`worktrees.ts:555-584`) already numbers `owlery/<slug>` against the local branches. `branchName` is that loop, taken out, and the making of Scope item 6 and the rename share it.
- The window and the daemon can be of different builds: a newer window attaches to a daemon of an earlier build (`docs/architecture.md` *What a session survives*). Each new field is optional and read by its absence.
- The commits are read every `commitPollMs`, 3000 ms by default, and only while a window is connected (`daemon.ts:4026-4035`). Tests set `commitPollMs` low, as the suite's other cases of `readBranch` do.

The failure scenario of the chosen approach, six months on: an agent in a work item with no branch commits, and no window is connected for an hour. The commit is safe in the worktree's `HEAD` (probe 3 of `frame/design.md` *Grounding*), but for that hour the work item has no branch, so nothing can push it and no chain can start on it. Milestone 3 runs chains with no window, and its work items are named from their issue at once (Scope item 11), so they do not meet this. A pane-driven work item left alone meets it, and *What the daemon could do beyond the issue*'s first item, a watch of the worktree's `HEAD`, is the answer once that matters.

## Operational impact

- `repositories.json` gains `ownsBranch` on each work item, and `branch` may be `null` there. A stored work item without `ownsBranch` is read as one whose branch Owlery made, so no migration runs. A daemon of an earlier build that reads a file this build wrote would refuse a work item whose `branch` is `null` (read: `repositories.ts:96`, `:155`), which matters only where a person goes back to an earlier build.
- The ledger in the run folder may hold `branch: null`, with the same note.
- No new dependency, environment variable or version move. #237 moves the version to 0.0.5.
- A daemon of an earlier build, with a window of this build: the plan carries no `held`, so the form draws no branch field, and the creation cuts a branch as before.
