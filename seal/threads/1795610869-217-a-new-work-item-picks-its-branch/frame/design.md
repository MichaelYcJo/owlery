## Scope

In scope, numbered for `plan.md`'s Delivers cells:

1. **A work item may have no branch.** `WorkItem.branch` becomes `string | null` in `shared/protocol.ts`, `StoredWorkItem.branch` in `daemon/repositories.ts` likewise, and the look (`daemon/last-look.ts#isWorkItem`) and the ledger (`daemon/ledger.ts#entryOf`, `HeadlessSession.branch`) read a null branch. `OldWorkItem.branch`, an entry of `work-items.json`, stays a `string`: that file is read only where `repositories.json` does not stand and is never written (read: `repositories.ts:11-12`), so no entry of it holds a null.
2. **Owlery knows which branches it made.** A new field `ownsBranch: boolean` on `WorkItem` and `StoredWorkItem`: true where Owlery made the branch, false where the work item has no branch, where the person picked a local branch, and where the worktree's `HEAD` took up a branch by itself (item 6). A stored work item with no such field was cut by Owlery, so the store reads its absence as true, and stores an entry read from `work-items.json` with it true. A daemon of an earlier build sends no such field, and a client reads its absence as true. The look (`daemon/last-look.ts#lookOf`) keeps no `ownsBranch`, as it keeps no `recorded`, `accountId` or `machineWait`: the window reads the menu and the delete dialog from the lists and never from the look, so the look's copy reads the absent field as true and nothing is decided by it.
3. **Each reader of the branch has a no-branch state, and a reader that removes or renames a branch touches only one Owlery made.** The table *The readers of a work item's branch* below lists each reader and its state. The cases are named in *User scenarios & acceptance*.
4. **A creation makes a worktree, detached at the base, and no branch,** where the person picked none: `createWorktree` runs `git worktree add --quiet --detach <folder> <start>` in place of `-b`. The folder takes the slug of the title, of `name`, or a generated name, as now. `baseCommit` is the commit `HEAD` stands at. A title typed in the form names the work item and, later, its branch, and makes no branch at creation.
5. **A creation can check out an existing branch** of the repository, local or a remote's, named as `WorkItem.baseBranch` names one. `createWorkItem` gains `branch?: string`. A local branch is checked out as it stands, and nothing new is made: `ownsBranch` is false. A remote's branch is fetched through the daemon's `BaseFetches` keeper, as a base is, and checked out as git's own `git worktree add <folder> <name>` does it: a local branch of the remote branch's name that tracks it. Owlery makes that branch with `git branch --track <name> <remote>/<name>`, naming the one remote `remoteOf` gives, since git's own guess refuses where two remotes hold the name and `checkout.defaultRemote` is unset, and then checks it out with `git worktree add <folder> <name>`. Where git refuses the checkout, the branch made for it is removed again. That local branch is Owlery's, so `ownsBranch` is true, and a delete removes the local copy alone; the remote's branch stays. Where a local branch already bears the remote branch's name, that local branch is checked out, as git does, and nothing is made: it is the person's, so `ownsBranch` is false, as `frame/questions.md` Q2's default keeps a branch the person has. `baseCommit` is `git merge-base <base> <branch>` where a base stands and git gives one, and the branch's tip otherwise. A creation on a picked branch reads the branch at once (`readBranch`) before `workItemCreated` goes out, since the branch holds whatever commits it holds; one detached at its base keeps the counts of a work item with nothing new. A branch another worktree holds is refused before git runs, with Owlery's own sentence, "The branch <name> is checked out in <folder>, so a new work item cannot check it out.", in the shape of the delete's refusal of a held branch: git prints nothing then, and its words differ between versions.
6. **Where no branch was chosen, the branch is made later, from the work's name.** At each read of the work item (`daemon.ts#readBranch`), for a work item with no branch, `worktrees.ts#headStands` reads what the worktree holds for one:
   - where the worktree's `HEAD` names a branch, the work item takes that branch up, with `ownsBranch` false. An agent that ran `git switch -c` itself keeps its branch, and Owlery never renames it.
   - where `HEAD` is detached at a commit no local branch, no remote's branch and no tag holds (probe 2), and that is not the work item's `baseCommit`, Owlery makes the branch at that commit and puts the worktree on it, with `worktrees.ts#makeBranch`, and `ownsBranch` true. The test takes both halves because each misses what the other catches: a commit the base holds is not `baseCommit` (`frame/plan.md` *Alternatives considered*, the row of `HEAD` other than `baseCommit`), and the base commit itself is held by no ref once the base branch is deleted, as after a squash merge, or rewritten by a rebase or a force-push (`trail/rounds/round-1.md` finding 1, its probe). So `headStands(worktree, baseCommit)` gives no commit where `HEAD` stands at `baseCommit`. `readBranch` asks `headStands` at each read of a work item with no branch, at the base commit too: `HEAD` there can name a branch the worktree took up before any commit, as an agent's `git switch -c` makes one, and the first bullet takes it up at the next read, as the rename dialog says. An idle work item with no branch, whose `HEAD` still stands detached at its base, so runs one `git rev-list` over the refs at each read (`gaps.md` *Not done*; `frame/plan.md` *Alternatives considered*, the row of a guard on the base commit).
   - `makeBranch` runs `git switch --quiet -c <name>` in the worktree (probe 4), one command that git refuses mid-rebase (probe 8). Git's switch does not check that `HEAD` still names the commit it read, so a commit made in the worktree during the switch is left off the branch: 4 of 300 racing runs did so on git 2.54.0 (`trail/phases/phase-2.md` *Q5*). So `makeBranch` then reads `HEAD@{1}`, the commit `HEAD` stood at before the switch. Where that commit is not the branch's tip and descends from it, the branch is moved on to it with `git update-ref`, which checks the branch's old value, so a commit made on the branch after the switch is never moved back off it. Where git keeps no reflog of `HEAD`, the branch stays where the switch made it.
   - The name is `worktrees.ts#branchName`: `owlery/<slug of the title>`, numbered `-2`, `-3` and so on while a local branch bears it, by the loop `planBranchRename` uses too, and `owlery/<slug of the worktree's folder name>` where the title leaves no slug. A title that is still the random name gives `owlery/<random name>`, as the issue states.
   - The making runs on `this.changing`, behind the creations and the renames, in a turn of its own, `daemon.ts#branchUp`, which reads the worktree again. The turn does nothing where the work item has a branch by then, as one a rename that waited ahead of it made, so a rename and a read never both make a branch. It does nothing where the work item was archived while it waited, since the daemon reads git for no archived work item, and nothing where the daemon closed. Where git refuses, for a rebase under way or any other reason, nothing is stored, the log says why, and the next read tries again.
7. **A rename of a work item with no branch makes its branch,** named from the new title as item 6 names it, at the commit the worktree's `HEAD` stands at, committed or not. `planRename` answers it from `worktrees.ts#planBranchMaking`: the name `branchName` gives, and `blocked` "The branch cannot be made while <operation> is under way in the worktree." where an operation is under way, "The worktree is on the branch <name>, which becomes the work item's at Owlery's next read." where the worktree's `HEAD` already names a branch, and git's words where git cannot read the worktree. `renameWorkItem` with `branch: true` reads that plan again and makes the branch with `makeBranch`. `planBranchRename` refuses to rename a branch Owlery did not make: "The branch <name> is not one Owlery made, so it keeps its name."
8. **The plan lists the branches a creation can check out and which are held.** `workItemPlan` gains `held: { branch: string; folder: string }[]`: each local branch a worktree of the repository has checked out, the main checkout among them, read from `git worktree list --porcelain`. The branches offered are `localBases` and `remoteBases`, which the plan already sends. A daemon of an earlier build sends no `held`, and the window reads its absence as a daemon that cuts a branch at creation: the form then shows no branch field and the plan's branch as today.
9. **The form makes a worktree, and its branch is a choice under the base.** In `renderer/index.html`'s `#work-item-dialog`, a field "Branch" stands under "Starts from", built by `view.ts#branchMenu`. Its first option, the default, is "No branch yet". Under it stand the groups "Local" and "Remote", from the plan's lists.
   - A branch another worktree holds stands as a disabled option labelled "<branch>, checked out in <folder>", in the words of the daemon's refusal. So does a remote's branch whose local branch of its name a worktree holds, since the creation would check that local branch out and the daemon refuses it.
   - The field shows from the form's opening. Before the plan answers, and where the daemon refused the plan, it holds "No branch yet" alone and is disabled, as "Starts from" is then, so the form's fields do not move at the plan's first answer. A plan with no `held` hides it (Scope item 8).
   - A choice the menu no longer offers enabled, such as a branch a worktree took between two plans, falls back to "No branch yet", as `baseMenu` falls back to the default base.
   - `view.ts#planLine(plan, repo, picked)` gives the branch place under the name as parts, each a word or a name, and `renderer.ts#showPlan` draws a name in `--font-fact` and the words in the dialog's sans. It says what the creation does:
     - "No branch yet. The first commit or a rename makes owlery/<slug>." for no branch;
     - "Checks out <name>." for a local branch, and for a remote's branch whose local branch of its name stands, which the creation checks out (Scope item 5);
     - "Checks out <name>, tracking <remote>/<name>." for a remote's branch with no local branch of its name.
   - A plan with no `held` shows the plan's branch as one name, in `--font-fact`, as a daemon that cuts it gives it.
   - The plan names no remote apart from a remote's branch, so `view.ts#localOf` reads its local name at the first slash, after matching a local branch by its whole name. For a remote whose own name holds a slash, the form's words and the option's state then name the wrong local branch, while the creation, which reads the remote from `git remote` (`worktrees.ts#remoteOf`), checks out the right one. *What the daemon could do beyond the issue* names the fix.
   - The "+" button and a repository's add button say "Create a work item: a new worktree in a repository, on a branch picked in the form or made later. …" and "Create a work item in <repository>: a new worktree.", where they said "a new branch and worktree" (`view.ts#NEW_WORK_ITEM_SAYS`).
   The form takes no new branch name typed in it (Alternatives, `plan.md`).
10. **The window draws each no-branch state** the table below gives for the renderer, and the rename dialog says "The rename makes the branch <name>." with its box checked and disabled for a work item with no branch. `view.ts#renameChoice(plan, branched)` tells a making from a rename by whether the work item has a branch, which the window holds, so the protocol gains no field, and a daemon of an earlier build, whose work items all have one, is read the same way. ### The readers of a work item's branch

The list was made by `git grep -nE '\.branch\b|branch:'` and `git grep -nE '\{[^}]*\bbranch\b[^}]*\} *='` over `apps/desktop/src`, and by the callers of each `worktrees.ts` and `decision-record.ts` function that takes a branch (executed at `f1bab823`). That is a sample by rule 12 of the contract: a reader that passes the branch on under another name is missed by a search. The method that makes the list whole is the type change of Scope item 1: once `branch` is `string | null`, the broad gate's `tsc --noEmit` refuses each reader that still reads it as a `string`, and the crafter adds that reader to this table in the phase record.

## Data & interfaces

- `shared/protocol.ts#WorkItem`: `branch: string | null`, its comment saying when it is null; `ownsBranch?: boolean`, absent read as true.
- `shared/protocol.ts` `createWorkItem`: `branch?: string`, an existing branch named as `WorkItem.baseBranch` names one. Absent: no branch, the worktree detached at the base. The comment above the message is rewritten in place: the sentence "The work item's branch and folder are named by the title ..." becomes one about the folder alone, and the branch's rules follow Scope items 4 and 5.
- `shared/protocol.ts` `workItemPlan`: `branch` keeps its type and names the branch a making from this title would give now, `branchName(repo, title, <the planned folder>)`, since a creation stores the folder's name as the title where none is typed; `held?: { branch: string; folder: string }[]`, absent read as a daemon that cuts a branch at creation.
- `shared/protocol.ts` `renameWorkItem`: `branch: true` renames the work item's branch, or makes it where it has none. The comments of `planRename`, `renameWorkItem` and `renamePlan` state Scope item 7.
- `daemon/worktrees.ts`: `createWorktree` takes `branch?: string` and returns `branch: string | null` and `ownsBranch`; the private `folderFor`, in place of `placeFor`, numbers the folder alone; `planWorktree` returns `held`; a new `makeBranch(worktree, name)` runs `git switch --quiet -c <name>` in the worktree and then moves the branch on to `HEAD@{1}` as *Scope* item 6 states; a new `headStands(worktree, baseCommit)` gives `{ branch }`, `{ commit }` or null, as *Scope* item 6 reads it, and null where `HEAD` stands at `baseCommit`; a new `branchName(repo, title, folder)` gives the name of *Scope* item 6; a new `planBranchMaking(repo, worktree, title)` gives the `RenamePlan` of *Scope* item 7 for a work item with no branch; `branchName` and `planBranchRename` share a private loop, `numberedBranch(repo, slug, own)`, and `planBranchRename` does not call `branchName`, since the two differ where a name leaves no slug: `branchName` falls back to the folder, and `planBranchRename` refuses; `planBranchRename(repo, branch, title, owned)` takes `owned` as a required argument, so no caller passes a branch the person picked by leaving it out; the marker reading moves out of `whyNoCommit` into a private `underWay(worktree)`, which `planBranchMaking` uses too; `readLoss(repo, branch: string | null, worktree)`.
- `daemon/repositories.ts#StoredWorkItem`: `branch: string | null`, `ownsBranch: boolean`. `repositories.json` keeps its file and version: a field added with its absence read as true needs no migration.

## What the daemon could do beyond the issue

The orchestrator takes what is cheap and in scope, and files an issue for the rest.

- **Read a work item's `HEAD` while no window is connected.** `scheduleCommitRead` reads nothing without a client, so an agent's first commit in a pane is branched only once a window connects again. A watch on the worktree's own `HEAD` file in the common git folder, `worktrees/<name>/HEAD`, for the work items with no branch alone, would make the branch within a moment of the commit, window or not. This matters once milestone 3's chains run with no window, and costs one watcher for each work item with no branch. An issue.
- **Take up the branch at the chain command's own call.** `chain-command.ts#here` refuses a detached `HEAD`, and a session that commits and runs `start` at once can meet it in the seconds before the read. The command could ask the daemon, over the pane's socket, to make the branch now. An issue, since it adds a message to the pane's socket.
- **Offer to remove the `owlery/` branches no work item names.** The creations before this work left such branches, the pile the owner found odd. The daemon can list them per repository, with the commits each holds that nothing else holds, as a delete's dialog does, and remove them on the person's word. An issue.
- **Name a work item that still carries its random name from its first commit's subject.** At the first commit the title may still be `eager-heron`, so the branch is named after nothing, as before. The daemon could propose the commit's subject as the name. The issue states that the branch is named from the title, so this changes what the owner chose: an issue for the owner.
- **Name each remote branch's remote in the plan.** The form reads a remote's branch's local name at the first slash (*Scope* item 9), so for a remote whose own name holds a slash its words and the option's state name the wrong local branch. A field of `workItemPlan` naming the remote of each entry of `remoteBases`, read as `worktrees.ts#remoteOf` reads it, would let the window name the right one. Remote names with a slash are rare, and the field serves them alone. An issue.
- **Keep aside a `repositories.json` the store cannot read, in place of writing over it.** A daemon of an earlier build refuses this build's file where a work item has no branch, starts with no repositories, and writes the file over at its first change, so a person who goes back to an earlier build loses every repository and work item Owlery kept (`frame/plan.md` *Operational impact*). The same holds for each later change to the stored shape. A store that moves a file it refuses to a name of its own before it writes a new one would lose nothing, for this change and every later one. It helps only a build that carries it, so it cannot save a downgrade to a build before it. An issue.
- **Show how far behind its base a work item with no branch stands.** `readBranch` reading the worktree's `HEAD` gives the behind count at no added cost, so a person sees the base move before the first commit. In scope: Scope item 3, the first row of the readers' table.
