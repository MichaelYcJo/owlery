## Not done

- **`OldWorkItem.branch` was left a `string`**, though `frame/design.md` *Scope* item 1 names it. `work-items.json` is never written, and every entry of it carries a branch (`trail/phases/phase-1.md`).
- **The log line of a refused making is not deduplicated.** While a rebase is under way in the worktree of a work item with no branch and a window is open, the daemon tries again at each read, every `commitPollMs` (3000 ms by default), and logs git's refusal each time. `frame/design.md` *Scope* item 6 asks that the log say why and that the next read try again. A line every three seconds costs log bytes only for the length of the rebase, and keeping the last reason for each work item would be state with no case behind it.
- **The form reads a remote's branch's local name at the first slash.** For `origin/release` the form says "Checks out release, tracking origin/release.", and it disables a remote's branch whose local branch of that name a worktree holds. The plan names no remote apart from its branch, and the daemon reads the remote from `git remote` (`worktrees.ts#remoteOf`). So for a remote whose own name holds a slash, the form's words and the option's state name the wrong local branch, while the creation checks out the right one. A field of the plan would fix it. Remote names with a slash are rare, and the protocol would gain a field for them alone.
- **The rename dialog's choice keeps the label "Rename the branch too" where the rename makes the branch.** `frame/design.md` *Scope* item 10 states the sentence under the choice and the box checked and disabled, and names no other label. The sentence says what the rename does.
- **`readBranch` asks `headStands` at the base commit too, so an idle work item with no branch is not spared its `rev-list`.** `frame/plan.md` *Alternatives considered* rejects the guard that would ask only where the head it read differs from `baseCommit`, in its row "Guard `readBranch` so that it asks `headStands` only where the head it read differs from `baseCommit`", and leaves a check inside `headStands` that would spare the `rev-list` to the orchestrator. A worktree whose `HEAD` stands at the base commit can name a branch the worktree took up before any commit, as an agent's `git switch -c` makes one, and that guard would leave it untaken until the first commit, while the rename dialog says the work item takes it up at the next read. The case "takes up the branch its worktree's HEAD names at the base commit, before any commit is made there" in `daemon.test.ts` went red with that guard added. So an idle work item with no branch still runs one `git rev-list` over the refs at each read, as before round 1. `headStands` itself gives no commit at the base commit, which is what finding 1 asks.
