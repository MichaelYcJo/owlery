# Phase 1: 1795610869-217-a-new-work-item-picks-its-branch

## What this phase found

### The frame holds, with one reader missing from its table

The readers' table of `frame/design.md` *The readers of a work item's branch* was checked by the method its own paragraph names. `WorkItem.branch`, `StoredWorkItem.branch` and `LedgerEntry.branch` became `string | null`, and `tsc --noEmit` then listed each reader that still read a `string` (executed at `c06eaef6` plus the type change). It listed `daemon.ts` at the lines the table cites, `repositories.ts`, `seal-state.ts:91`, and `view.ts:261`, `:1233`, `:1776` and `:2299`. `list.ts:119` and `work-item-view.ts:1271` came in through `InboxLine.branch`, which the table already names. In the tests it listed `approval-line.test.ts`, `screenshots.test.ts`, `seal-back-view.test.ts`, `chain-run.ts`, `daemon.test.ts` and `repositories.test.ts`.

One reader is missing from the table: `daemon.ts#commitWord` (`daemon.ts:2902` at `f1bab823`), which commits a person's word or a renamed routing on the work item's branch. Its state for a work item with no branch is to commit nothing. No path reaches it with a null branch: `#personWrote` refuses the word first, and a rename of the branch is refused for such a work item. The orchestrator folds this row into the table.

### Decisions settled while building, each with its grounds

- **`OldWorkItem.branch` stays a `string`.** `frame/design.md` *Scope* item 1 names it with the others. `work-items.json` is read once, where `repositories.json` does not exist, and is never written (`repositories.ts:11-12`). Every entry a build wrote there carries a branch. A null there would be a value no build ever wrote, so the reader is left as it stands. Judged against `skills/core/SKILL.md` *The rule a mechanism is kept against*: nothing is added that answers no fact. A work item read from that file is stored with `ownsBranch: true`, since a build before the repositories made every work item's branch.
- **The look keeps no `ownsBranch`.** `last-look.ts#lookOf` copies the fields it keeps by name, and the window reads the menu and the delete dialog from the lists, never from the look. The look's copy of a work item therefore reads its absent `ownsBranch` as `true`, which decides nothing. The design is silent here, and the protocol's rule for a field the look does not keep (`recorded`, `accountId`, `machineWait`) is followed.
- **The sentence about a kept branch stands in `view.ts#deleteSays`, not in `#lossSections`.** `lossSections` already named no branch where the loss named none, and it is unchanged. #214 rewrites its lists, as the spawn says. `deleteSays` now takes the work item and appends "The branch <name> stays, since Owlery did not make it." where the delete can run. It also says "A delete removes the work item's worktree, and takes the work item off Owlery's lists." where the loss names no branch. The design's row names "the dialog's sentence" beside `lossSections`, so this is the same row's other half, built where it does not meet #214.
- **A work item's `ownsBranch` decides which branch a delete removes, through `daemon.ts#removedBranch`.** The daemon hands `readLoss` the branch only where `ownsBranch` is true, at the `readLoss` message and in `#deleteOne`. With null, `readLoss` names no branch, sees no other worktree's checkout as a block, and counts the commits the worktree's `HEAD` holds that no branch, remote or tag holds. A branch that stays holds its own commits, so they are no loss. This is the design's row for `workItemLoss` and `#deleteOne`, built as written.
- **`readBranch` reads a work item with no branch at its worktree's `HEAD` through `worktrees.ts#headCounts`.** It gives the count after `baseCommit` and the commit at the same `HEAD`, so the commits, the changes, the counts ahead and behind, and the seal are read from that commit. `newCommits` now goes through a private `commitsAfter`, which takes a ref or a commit. The branch path of `readBranch` is unchanged.
- **The phase-1 state of a rename of a work item with no branch is a refusal.** `planRename` answers `{ branch: null, blocked: "The work item has no branch yet, so there is none to rename." }`, and `renameWorkItem` with `branch: true` refuses with the same sentence. A rename of the name alone runs. *Scope* item 7, in phase 2, replaces this with the making of the branch. The case that pins the refusal is `daemon.test.ts`, "answers a `planRename` and a rename of the branch of a work item with no branch yet with the reason, renames nothing, and renames its name alone". Phase 2 rewrites that case.
- **The chain's loop narrows the branch through `daemon.ts#chainBranch`.** It throws a `ChainStop` with the start's refusal, "The work item has no branch yet. Owlery makes one at the first commit in its worktree, or when it is renamed.". `#chainDirectory`, `#placeOf` and `#runPullRequest` read the branch through it, so the code after it reads a `string`. `stage-records.ts#Place.branch` stays a `string`.
- **The line's last fact for a work item with no branch is drawn as words, not as a name.** `lineText` gives `{ says: "branch", text: "No branch yet" }`, as the design states. `list.ts` then draws it with the class `says branch none`, so the `.branch.none` rule of `index.html` sets it in the sans and muted, and it marks no letters of it while a search is typed. `matchWorkItems` does not match those words. The place of the branch in the preview and the view's head is drawn through `view.ts#branchPlace`, with the same class.
- **The menu's Delete reads `ownsBranch` alone** (`51dc5526`). A work item with no branch has `ownsBranch` false, so a second check of the branch decided nothing, and `seal mutate` showed it survived its removal. A daemon of an earlier build sends no `ownsBranch`, and its work items read as ones Owlery made.
- **Two refusals promise what phase 2 builds.** `chain-command.ts`'s refusal of a `HEAD` that names no branch now says "Owlery makes the work item's branch at its first commit, within a few seconds while Owlery's window is open; run the command again once it has.", and the chain's start refusal says the first commit or a rename makes one. Both are the design's words. They hold once phase 2 lands, and no release ships between the phases.
