# Design: 1795396351-seal-breaks-after-a-commit

Issue #44: a commit pushed after the seal leaves the inbox and the pull request saying sealed.

This frame keeps the words of the three frames it builds on in the sense they give them: the **chain**, a **stage** and the **step owed** of `seal/threads/1795388700-review-rounds/frame/design.md`; the **gate's commit**, the **closing records** and a **seal** of `seal/threads/1795393338-broad-gate-and-sealer/frame/design.md`; and the **pull request stage**, the **seal section** and the **seal check** of `seal/threads/1795395059-pull-request-and-seal-check/frame/design.md`. It adds four, each used in one sense. The **sealed commit** is the commit that the `target:` line of a seal names. The **head reading** is the values the order's function takes, each read from the commit at the branch's head and from nothing else. A seal **holds at the head** where the order's function, given the head reading, answers that the chain is `sealed`. A seal is **broken** where the newest verdict block of `guarantee.md` at the branch's head commit is a seal and that seal does not hold at the head.

## Scope

### The seal's state

1. **A work item carries the state of its seal, as neutral values.** `WorkItem` gains `seal`, a `Seal` or null. A `Seal` holds its state, `sealed` or `broken`, the sealed commit, and, where it is broken, one sentence that says why. *Data & interfaces* gives the type. The value is null where the head commit holds no seal and where the daemon has read none yet. The field travels in `ready` and `inbox`, and no message is added.
2. **The daemon decides the state from the head reading alone.** For a work item whose directory `decision-record.ts#workItemDirectory` finds, the daemon reads at the branch's head commit: each round record, `trail/gate.md` and `guarantee.md`, as `chain.ts#standingOf` already reads them with `worktrees.ts#fileAt`, and `decisions.md`, which `standingOf` reads in the worktree. `standingOf` gains one parameter that says where it reads `decisions.md`: in the worktree, as the chain's run passes it, or at the head commit. The daemon gives the head reading to `chain.ts#stepOwed`. For the state it reads no record of the worktree, no stored chain, no output of a pane and no event of a session. The one thing the worktree gives is the directory's place: `workItemDirectory` finds it by the `routing.md` the worktree holds, as every reader of the daemon does, and every record under it is then read at the head commit. A worktree that holds no directory for the branch, or two, gives null.
3. **The state is one of three answers, and the first that holds decides.**

   | What the head commit holds | `seal` |
   |---|---|
   | No `guarantee.md`, a `guarantee.md` with a line the reader refuses or with no verdict block, or a newest verdict block that reads `withheld` or `undecided` | null |
   | A newest verdict block that is a seal, the repository holds the sealed commit, the head contains it, and `stepOwed` answers `sealed` | `sealed`, with the sealed commit |
   | A newest verdict block that is a seal, and the repository holds no commit of the sealed commit's name, or the head does not contain it, or `stepOwed` owes a round, a fix pass, the gate or the seal, answers `parked`, or `standingOf` throws because a record does not read | `broken`, with the sealed commit and the sentence of item 4 |

   The first row is read through `chain-records.ts#lastVerdict` on the text of `guarantee.md` at the head commit, before any round record is read. Whether the sealed commit exists and the head contains it is read next, before `stepOwed`, so a head that does not contain the sealed commit reads `broken` whatever `stepOwed` answers (scenario 8, *Scope* item 9).

   So a commit after the seal that changes a file of the source, a round record, `decisions.md` or any path that is no closing record breaks the seal, and so does a merge of the base. A commit that changes closing records alone leaves it. A change in the worktree that no commit holds changes nothing: a file git ignores, an edit not yet committed and a `guarantee.md` that is written and not committed are each read by no part of the head reading.
4. **A broken seal says why in one sentence.** The sentence names the first path that is no closing record and differs between the sealed commit and the head, read with `worktrees.ts#pathsBetween` and `chain.ts#closingRecord`. `Standing.sinceGate` is not that list: it is read from the gate's commit, which is another commit than the sealed one once a gate has run after the break. Where no such path differs, the sentence says which step the order owes. Where a record does not read, it says what the `ChainStop` says. Where the repository holds no commit of the sealed commit's name, or the head does not descend from it (`worktrees.ts#holdsCommit`), it says that. The window shows the sentence as it is.
5. **The state is read when a branch's head moves and when the daemon starts, and is stored nowhere.** `daemon.ts#readBranch` reads it where the head is another commit than the one its map `branches` keeps, which is where it reads the branch's commits and changed files, and so once for each branch after the daemon starts. The daemon keeps the answer in memory beside the branch's commits, and `workItemOf` sends it. A chain's run asks for the read when the chain rests or stops, so the window does not wait one interval for the seal its own stage wrote. An archived work item is not read, as its branch is not.
6. **No stored value says that a work item is sealed.** `Chain.state` loses `sealed` and gains `rested`: the chain's run ended and owes no stage. `daemon.ts#runChain` rests the chain `rested` where `stepOwed` answers `sealed`, with the sentence of `chain.ts#sealedSays`, which says what that run ended with. Whether a seal holds is `WorkItem.seal` alone. The step `stepOwed` answers keeps its name, `sealed`. A stored chain whose state is `sealed` is read as no chain, as `chain.ts#chainOf` reads one stored `reviewed`: `sealed` stays in `WRITTEN_STATES` and in the type `WrittenChain`, since a chain that `isChain` refused would fail the guard of its whole file. No release has shipped a build that stores one.

### The check

7. **The seal check's outcome names a broken seal.** In the function that gives the check's outcome (#43's *Scope* item 19), one row is added before the row "Ready, and the guarantee arm refused". It holds where the pull request is ready, the newest verdict block of a judged work item is a seal, and the rounds arm, the gate arm or the guarantee arm refuses a record as behind HEAD or as naming a commit HEAD does not descend from. The conclusion is `failure` and the exit code is 1, as today. The title says that the seal is broken and names the sealed commit. The summary holds the newest verdict block and each refused line. A draft is judged as #43's rows have it.
8. **The printed line of the guarantee arm says the same.** The sentence the arm prints for a seal that does not hold says that the seal is broken, names the first differing path and the sealed commit, and says that a new seal is owed at HEAD. It names no `seal` command.
9. **The guarantee arm reads two trees, as the daemon does.** In `chain_check.py#guarantee`, the call of `follows` with `only=CLOSING_RECORDS` is replaced. The arm refuses where the sealed commit does not resolve, where HEAD does not descend from it, and where `git diff --name-only` between that commit and HEAD prints a path that is no closing record of the work item's directory. `follows` loses its parameter `only`. One other call passes it at `fbebc4f`, in `pr_body.py`, a file #43's *Scope* item 23 removes. Where that file still stands when phase 4 starts, its call takes the arm's comparison of two trees, through one function both call, and the phase record says so. So a merge commit after the seal, and a change made in one, fails the check. The rounds arm and the gate arm keep `follows`.
10. **The seal section says that a seal binds one commit.** The fixed sentence of the seal section that `github.ts` composes (#43's *Data & interfaces*) is replaced by the sentence *Data & interfaces* gives below. It says that the seal binds the commit it names and that the check `Owlery seal` says whether it holds at the pull request's head commit. So a body that nobody rewrote after a later push says nothing untrue. The section on the seal check in `README.md` and `README.ko.md` (#43's *Scope* item 29) each gain one sentence: a commit pushed after the seal fails the check until a new seal is given.
11. **The daemon and the check give one answer for one history.** One case builds each history of scenario 9 in a temporary repository, asks the daemon's reading for the state and runs `chain_check.py` on the same repository. The check exits 0 where the state is `sealed`, and 1 where it is `broken` or null. Each verdict block of the case holds the daemon's four lines, as `seal-records.ts#guaranteeText` writes them. ## Data & interfaces

**`apps/desktop/src/shared/protocol.ts`.** No field names a vendor, and none holds a session's id.

```ts
/** The seal the branch's head commit holds, as the daemon read it from git and the committed records. */
export interface Seal {
  /** `sealed` where the seal holds at the head. `broken` where the head holds a seal that a later commit broke. */
  state: "sealed" | "broken";
  /** The sealed commit: the commit the newest verdict block's `target:` names, whole as git names it, or as the block writes it where the repository holds no commit of that name. */
  commit: string;
  /** Why the seal is broken, as a sentence the window shows as it is, 2,000 characters of it at most. Null where it holds. */
  why: string | null;
}
```

- `WorkItem` gains `seal?: Seal | null`. It is optional because `Look.workItems` is a `WorkItem[]` and a look keeps no `seal`. The daemon sends it with every work item.
