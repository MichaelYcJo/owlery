# Implementation Plan: one press adds and names an account (#218)

## Technical context

The tree as read at `c6ea6fb9`.

Adding an account is two requests today. `addAccount` (`apps/desktop/src/daemon/daemon.ts:1025-1042`) stores an account under a typed name: `AccountStore.addHanded` for a folder the person hands over, or `AccountStore.addMade` (`apps/desktop/src/daemon/accounts.ts:221-236`), which makes `accounts/<id>` of the run folder. `signIn` (`daemon.ts:1808-1823`) then starts a pane for a stored account with the command `AccountLogins.signIn` gives, and marks the pane with `signsIn`. When the pane's process ends, `watchProcess` (`daemon.ts:2493-2503`) calls `readLogin` (`:1750-1754`), which keeps what `AccountLogins.status` says. The Claude adapter's `status` runs `claude auth status` and reads the exit code and `loginExpiresAt` (`apps/desktop/src/daemon/adapters/claude-accounts.ts:108-119`).

This work joins the two requests in the daemon. The parts it builds on, and what each constrains:

- **The end of a sign-in pane is already the one place the daemon asks the agent.** The add's outcome is decided there, so a pane the person closes, a login that fails and a login that succeeds take one path. The branch runs before the check of whether the pane is still listed (`daemon.ts:2494` against `:2508`), so a closed pane reaches it too. A daemon that is closing reads nothing there (`!this.closed`), which is why the id must outlive the daemon in `accounts.json`.
- **`startSession` takes the pane's account from `signsIn`** (`daemon.ts:2427`), and `foldersOf` (`:1734-1737`) reads a folder only from a stored account. A sign-in pane's command comes whole from the adapter (`commandOf`), with the folder as its working folder, so the pane of a folder that is no account yet needs the folder passed and no lookup of an account.
- **`running` (`daemon.ts:1756-1765`) and the refusal of a second sign-in (`:1813`) read `info.signsIn`.** They keep working for a stored account. An id under `adding` reaches neither, because every request that names it is refused first.
- **The store decides what is removed.** `AccountStore.remove` deletes a folder only where the account is `made`, and the constructor reads `made` as true only for `accounts/<id>` of the run folder (`accounts.ts:116`). The act that removes an id under `adding` holds the same check, so an edited `accounts.json` cannot have the daemon delete another folder.
- **The window draws the sign-in pane of the request it sent.** `renderer.ts:1886-1890` routes a `started` whose request the Accounts dialog sent to `sign-in-pane.ts#takeSignInStarted`, and `askedSignIn` notes the account. The add's `started` takes the same route. The head is built from `accountName`, which is empty for an id the window holds no account of, so the head needs its own words for an add.
- **The senders of `addAccount` are the cases' way to get an account.** `frame/design.md` *Grounding* lists them. Most need an account for another subject. One helper in the cases that adds an account without a name keeps the rewrite to the helper and the assertions on names.
- **A built-app case that presses "Add an account" starts whatever CLI the app's shell names.** The case names a stand-in through the shell's lookup answer, as `apps/desktop/test/fixtures/sample-pane.sh` does for the screenshot run. A case that left the lookup to the person's shell would start the person's own `claude auth login` and open their browser.

The failure scenario of the chosen approach: a later version of the CLI renames `email` in `auth status`, or stops printing it for a kind of login. Every new account is then named `Account <id>`, with no error, because the fallback is a valid outcome. The cases stay green, since they pin the stand-in and not the CLI. The row still reads as signed in and the person can rename it, so nothing is lost but the convenience. What notices it is a person adding an account. The sentence of `docs/architecture.md` that *Rule changes* writes names the version the field was read in, so the next reader knows what to compare.

A second one: `adding` is a list beside the accounts that has to stay true to the folders on disk. It is written by the store alone, in the same whole-file write as the accounts, and a daemon that starts settles every id it holds, so an id cannot stay there past one start.

## Operational impact

- **`accounts.json` gains the key `adding`.** A daemon of 0.0.4 that reads the file ignores the key and writes the file without it. A folder whose login ran at that moment then stands in `accounts/` with no record, and a later add passes its id over.
- **A window of this build that meets a daemon of 0.0.4 cannot add an account.** The app does not replace a running daemon of another version (`frame/design.md` *Grounding*). That daemon refuses the add in its own words, "An account is added with a name, and the absolute path of its folder where the person hands one over.", and the dialog says them. "Restart Daemon…" in the menu ends it. The changelog fragment says so.
- **The protocol's `addAccount` no longer carries `name`, and an add with no folder is answered with `started`.** No other client of the daemon sends the message (`frame/design.md` *Grounding*, the senders).
- No new dependency, no environment variable and no migration. This pull request does not move the version: `routing.md` *Why this way*.
