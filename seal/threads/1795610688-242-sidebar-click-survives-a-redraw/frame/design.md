### What the probes showed

The probes ran in Electron 45.3.3 (Chrome 156.0.8078.100), the version `apps/desktop/package.json` pins. The worktree's `electron` package holds no `dist/`, so the probes ran the binary that the main checkout's `node_modules/.pnpm/electron@45.3.3` installed. They ran no code of the repository. The files are in the framer's scratch directory under `test_tmp_click/` (`main.js`, `hold.js`, `socket.js`). Each drives the page with CDP `Input.dispatchMouseEvent`, as `BuiltApp.click` drives the app.

1. **When the pressed element leaves the document between the press and the release, Chromium fires no `click` at all.** No `click` reaches the new button, the old button, or a listener on `document`. This holds for each of four changes made between the press and the release: the whole tree replaced; the button kept and its children replaced; the button kept and moved into a new `li`; and both of the last two together. A `click` fires only where nothing changed, or where the pressed `span`'s text was changed in place. `pointerdown` and `pointerup` fire in every case. (executed: `Electron main.js`)
   - So the triage's claim that "a press and release on different elements fire click on their common ancestor" does not hold here. Its conclusion still holds: a listener on `#repositories` receives no `click` either. Keeping each button across draws does not cure the defect alone, since a moved button loses the click as a replaced one does.
2. **A draw asked for while the press is held, run in a task after the release, lets the click reach the pressed button.** The order was the release, the microtask, the `click` on the first button, and then the deferred draw. A press released on another element ran the deferred draw and fired no click on the line. A microtask queued at the release runs before the `click`, so the deferred draw has to run in a task (`setTimeout`), not in a microtask. Two requests made during one press drew once. (executed: `Electron hold.js`)
3. **A case can listen to the page's own WebSocket from outside.** CDP `Runtime.queryObjects` on `WebSocket.prototype` found the one socket that a closure held, and `Runtime.callFunctionOn` added a `message` listener to it. That listener counted the message the server sent, after the page's own listener ran. (executed: `Electron socket.js`)

## Scope

In scope:

1. A hold on draws: while the mouse's main button is held down anywhere in the window, a draw that a daemon message asks for waits. It runs once, in a task after the release, so the click goes first to the element that was pressed. A press of another button begins no hold. The hold ends at the release of the main button, at a `pointercancel` and at the window's `blur`. Chromium sends that release as the one `pointerup` once no button is down, which can name another button, or, where another button is still down, as a `pointermove` whose `buttons` no longer holds the main button (round 1, finding 1, executed in `trail/rounds/round-1.md` *Probes*). A second button pressed and released while the main button stays down ends no hold. A press that begins while a deferred draw waits keeps it waiting until that press is released. Its logic is a module of its own, `apps/desktop/src/renderer/press.ts`, which touches no DOM when imported, so the unit project can import it.
2. One function in `apps/desktop/src/renderer/renderer.ts` draws what the daemon's lists change: the sidebar, the archived screen's fallback to the inbox, the list in front, the view, the summary and the six dialogs that name what the daemon lists. `takeLists`, the `accounts` case and the `machine` case call it through the hold, in place of their own copies of those draws. The notifications, `dropClosed`, the held state and the registration's `openRecords` stay where they are and run at once.
   - At the `accounts` and `machine` messages, the open dialog that the message redraws goes through the hold too, each as a draw of its own (round 1, finding 2). At `accounts`, that is the Accounts dialog (`renderer.ts#showAccounts`, where the dialog is open), which replaces each account's row with its buttons and its rename field. At `machine`, that is the Machine dialog (`machine.ts#showMachine`, where the dialog is open), which replaces the rows of its lists of agents and heavy commands.
   - The list of draws these messages make was built from the three message cases that the rule names, by reading each case's body in `renderer.ts#onMessage` at `062c21d6`. At `inbox`: `takeLists`, which draws through the hold, and `showSignIn` where the Accounts dialog is open, which shows or hides the sign-in pane and replaces no element. ## Data & interfaces

- `apps/desktop/src/renderer/press.ts`, new. It exports the hold's logic and the function that wires it to the window. The logic takes the function that schedules a task, so the unit project drives it without a DOM. It answers a press, a release and a request to draw. A request to draw runs the draw at once where no press is held. Otherwise it keeps the draw, once per function, until the release schedules the kept draws. The wiring listens on the window in the capture phase for a `pointerdown` of the main button (`event.button === 0`), for every `pointerup`, for a `pointermove` whose `buttons` no longer holds the main button (`(event.buttons & 1) === 0`) and for `pointercancel`, and on the window for `blur`. A release where no press is held changes nothing, so a `pointermove` with no press costs one test of a flag. It schedules with `setTimeout`, per probe 2. The names are the crafter's.
- `apps/desktop/src/renderer/renderer.ts`: one function holds the draws of *Scope* item 2, with a docstring saying that a daemon message which changes the lists draws through the hold. `takeLists`, `case "accounts"` and `case "machine"` call it through the hold. `case "accounts"` and `case "machine"` also hand the hold a draw of their dialog: one function each, defined once at module level so that the hold keeps it once per press, which draws the dialog where it is open. `renderer.ts#showNarrowed` stays as it is, since it draws what the person types, which no press interrupts.
- No message of `apps/desktop/src/shared/protocol.ts` changes, and the daemon is not touched.

## What the daemon could do beyond the issue

This work holds the window's draws during a press. The daemon decides how often there is something to draw. Each item below says what it costs and whether it is in this work's scope. The orchestrator takes what is cheap and in scope, and files issues for the rest. None of them is in this work's scope.

- **Send an `inbox` only where the lists changed.** At a hook's event the daemon sends the whole lists. Where nothing a client draws has changed, such as a second event that reports the same state, the window draws everything again for nothing. A daemon that compares the lists with the last ones it sent, and sends nothing where they are equal, spares every client a draw. It is cheap in the daemon, but it changes when the cases that wait on an `inbox` receive one. It is for an issue.
- **Coalesce the `inbox` messages of a burst.** A chain's stage can raise several hook events within a few milliseconds, and each one sends the lists. A daemon that sends the last lists of a burst once, within one turn of its event loop, cuts the draws of a busy machine with no visible delay. It is for an issue, measured against the window's draws per minute in the four-terminals scene of `apps/desktop/measurements/memory.md`.
- **Count what it sends.** The daemon could count the `inbox` messages it sends per minute and publish the count beside the memory measurements. Whether the two items above are worth building would then be read from a number. It is for an issue.
- **Carry a revision in each `inbox`.** A number that grows at each change would let a window skip a draw it already made, and let a client that reconnects ask for what it missed. It changes `protocol.ts`, which issue #224 also changes in this release. It is for an issue after #224 merges.
