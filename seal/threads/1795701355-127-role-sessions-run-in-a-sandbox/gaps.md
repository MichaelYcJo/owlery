## Not done

The daemon does not sweep `scratch/` of the run folder when it starts. A daemon that crashed leaves the scratch folders of its working sessions on disk, and no later daemon removes them: each new folder gets a name of its own (`trail/phases/phase-1.md`). A sweep at start could remove a folder whose session still runs. A role session leads a process group of its own, and whether it ends when the daemon crashes has not been run (`docs/architecture.md` *What a session survives*). A sweep that is safe needs a record of which process holds which folder, and `frame/design.md` frames none.

The head of a role session and the scratch paragraph say that the system refuses a write to the places the launch refuses by name, and not that it refuses every other write (`trail/phases/phase-2.md`). Phase 3's runs answered `frame/questions.md` Q3: Claude Code's own temporary folder stays writable to every role's commands, so the wider sentence would be false and the narrow ones stay (`trail/phases/phase-3.md`).

The daemon starts the adapter for a role session that a stop or a time limit ended while git was naming the repository's folder, and stops the run at once. With the Claude adapter that is one launch of the CLI that does nothing. Phase 1 built this for the crafter, and phase 3 gave it to every role. Not starting the run would change what the cases that count a stop count, and `frame/design.md` frames no such change (`trail/phases/phase-3.md`).

The empty folder `.claude/.cc-writes/` that a sandboxed session leaves in the worktree is not removed. The fold of `frame/questions.md` Q4 accepts it as Claude Code's own and states it in `frame/design.md` *Rule changes*. Removing it would delete in a folder Claude Code owns, which a pane of the person's in the same worktree may use (`frame/plan.md` *Alternatives considered*, the row on removing the folder, and *Judgments of the run*, Q4).
