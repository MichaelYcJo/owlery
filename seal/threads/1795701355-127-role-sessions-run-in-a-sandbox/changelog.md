# Changelog: a role session's commands run in the operating system's sandbox

Issue #127. A role session the daemon launched was bounded by its tool list and the daemon's answer to each request, and nothing else. A crafter's commands could write anywhere the person can, and the daemon refused each command of a proofer and a sealer that asked for permission, so a round could not clone the branch or run a test, and the seal could not check a claim by running it. A command Claude Code runs without asking, such as an `ls`, ran for them.

- **Every role session's commands run in Claude Code's own sandbox, which on macOS is `sandbox-exec`.** The daemon turns it on in the `--settings` value it already passes, so no settings file of the person's is read or written. A command cannot ask to run outside the sandbox, a session whose sandbox cannot start does not start, and a sandboxed command still reaches the daemon as a request, which the role's grant answers as before.
- **A crafter's commands write in the work item's worktree and in the repository's git folder, so a fix pass commits.** The system refuses their writes to the role bundle's folder and to the git folder's `hooks` and `config`, so a command plants no hook through either.
- **A proofer's and a sealer's commands are now allowed, and write in a scratch folder of their session's own.** The daemon makes the folder new when the session starts, as `scratch/<session id>-<six characters>/` of its run folder, names it in the session's prompt, and removes it once the session's process has ended. The system refuses their writes to the worktree, to the repository's git folder, so a command cannot move the branch under review, and to the role bundle's folder. A proofer may clone the branch and run a probe there, with a `## Probes` row for each run; a clone holds no installed dependency, so a repository's own tests may not run in it. In a pane's session, a proofer's or a sealer's command still waits for the person.
- **The orchestrator's commands that ask are still refused, and its commands are given no place to write.** The system refuses their writes to the worktree, to the repository's git folder and to the role bundle's folder.
- **A role session's commands reach no host but the loopback, and read nothing of the daemon's run folder but their own scratch folder and the shell snapshots their session starts from.** A fix pass cannot install a package or call `gh`, and says so in its report. The run folder's `daemon.json` holds the port and the token with which a client on the loopback has the daemon act as a window would, outside any sandbox, so the system refuses a command that reads it. The run folder also holds the folders Owlery makes for the accounts the person adds, of which a command reads only `shell-snapshots`, the snapshots of the person's shell setup that Claude Code starts each command from. In such a folder `shell-snapshots` is a link into the person's own Claude Code folder where theirs holds one, and a command reads the snapshot through that link too, so the person's aliases and functions still reach a session of an added account; and the run folder holds the scratch folders of proofers and sealers, which a command reads in its own session's folder alone.
- **What the system still lets a command write.** Claude Code's own temporary folder, `/tmp/claude-<user id>`, stays writable to every role's commands; the person's other Claude Code sessions use it too. A sandboxed session also leaves an empty folder `.claude/.cc-writes/` in the worktree, which `git status` does not show. A command in the sandbox cannot open a terminal device or bind a Unix socket, so a crafter's tests that need one should fail in a fix pass.
- **A role session starts only on Claude Code 2.1.329 or newer, the oldest version on which a run showed the sandbox refusing a role's write.** Before, the minimum was 2.1.326 and a role session started on any version. A role session whose Claude Code names an older version fails with the sentence the window's notice gives, which says to run `claude update`. One whose Claude Code names no version fails with "the session did not say which version of Claude Code it is, so its sandbox was not checked". In both cases the CLI is stopped at its first line, as it is for a session that does not hold the role's agent. A pane's Claude Code starts on any version.
- **A role session's start now waits for git to name the repository's folder**, for every role, so a role whose worktree git does not know fails with a sentence that says so.
- **For a contributor:** `pnpm run role:refusal`, `role:refusal:sealer` and the new `role:refusal:crafter` run the real `claude` against a stand-in model at no cost, and show the system refusing each role's write outside its places and its read of the run folder's `daemon.json`. `OWLERY_ROLE_CLI` points them at another installed version, such as one of `~/.local/share/claude/versions/`.
