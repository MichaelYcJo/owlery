**The scratch paragraph changes cases that phase 2 has to rewrite.** The paragraph was tried in this phase and taken out again. Appended to the prompt, it failed ten cases of `apps/desktop/test/daemon.test.ts` *headless sessions*, because their adapters pick a behaviour by `options.prompt` or compare the answer with the quoted prompt. The fake adapter's default answer quotes the whole prompt it was given. The ten cases are "lists a finished session, with its answer, to a client that connects later", "stops at its limit a session whose adapter is still starting…", "stops a working session at a client's request…", "keeps the sessions that ended last…", "changes nothing at a start that fails after its session ended…", the ledger's "keeps one entry for each session that ends…" and "keeps what a failed session reported…", and the two proofer and sealer cases of *permission requests*. The prompt parsers of `apps/desktop/test/chain-run.ts` (`givenRound`, `givenFix`, `givenSeal`) match single lines, so they are not expected to break. That expectation was read, not run.

**The places are resolved in the daemon, and the grant names only their kind.** `RoleGrant.commands` is `"worktree" | "scratch" | "nowhere"` in `role-grants.ts`, which names no vendor's option. `Daemon#commandsOf` turns the kind into absolute folders. A first draft put the resolution into `role-grants.ts` as a pure function. That function needed two branches no caller could reach, a crafter with no git folder and a scratch grant with no folder, so it was dropped. Judged against `frame/design.md` *Data & interfaces*, which has the daemon resolve the places in `startHeadless`.

**The scratch folder is made when the session starts, not when it is listed.** *Data & interfaces* says the daemon makes the folder in `beginHeadless`. It is made in `startHeadless`, which `beginHeadless`'s start closure calls. A session that waits for the machine therefore holds no folder, and a session stopped while it waits leaves none behind.

**The folder is removed at three points, because the two adapters end differently.** It goes at the run's `exit` event, where the adapter's start rejects, and when a stop of the run settles. The daemon wraps the run's `stop` for the third point. The fake adapter reports no `exit` after a stop, and the Claude adapter's stop settles once the CLI's process has ended (`RoleRun.stop`). Removal uses the asynchronous `rm`, so a large clone does not hold the daemon's event loop. `frame/questions.md` Q2's default (a), removal when the process has exited, is what was built.

**Each scratch folder is new, named `scratch/<id>-<six characters>/`, not `scratch/<id>/`.** This departs from `frame/design.md` *Scope* item 5. Headless ids count from 1 in each daemon process. A folder named by the id alone would hand a new session the clone an earlier daemon's session left. The first build emptied such a folder before reuse, and that is no answer either. A role session leads a process group of its own, and whether it outlives a crashed daemon has not been run (`docs/architecture.md` *What a session survives*), so the folder may still be written. `mkdtemp` under `scratch/` gives a folder no other session holds, readable by the person alone. The case "gives each role's session the places…" plants an earlier daemon's `scratch/1-before/` and shows it untouched. The framer folds the name into *Scope* item 5, into the `add` of *Rule changes* that says `scratch/<session id>/`, and into its Korean twin. Folders a crashed daemon left stay on disk, recorded in `gaps.md` *Not done*.

**A crafter's session does not start where git names no common git folder.** The bound cannot be computed, so the session fails with "git named no repository's folder for the worktree, so the crafter's commands have no place to write: …" and the adapter is never called. This follows `RoleAdapter.start`'s contract that a role with no places starts no session.

**The Claude adapter refuses a role start that carries no places.** It throws "the Claude adapter launches a role only with the places its commands may write, and was given none" before it writes a rules file. The fake adapter launches nothing, so it records what it was given (`FakeAdapter.starts`) and refuses nothing. Judged against `frame/design.md` *Scope* item 6.

**A crafter's run starts after git answers.** Runs started together for several pairs therefore start in no set order. "launches each pair the protocol lists" now waits for all four starts and compares them as a set. No code path of the daemon depends on the order: a chain starts one stage at a time.

**Git already prints the common git folder as a real path.** A probe in the scratch directory wrote a worktree's `.git` file with a `gitdir:` that ran through a link. `git rev-parse --path-format=absolute --git-common-dir` printed the folder with the link followed (executed). `gitFolderOf` therefore takes git's answer as it is. The daemon does resolve the worktree and the run folder, and the places case reaches both through links so that each resolution is watched.
