# Implementation Plan: 1795701355-127-role-sessions-run-in-a-sandbox

## Technical context

The tree as read at `88ad5244`.

The work builds on #39's grants and the Claude adapter's launch. `role-grants.ts:31-36` holds the four grants and `:135-145` the daemon's rule; `adapters/claude.ts:80-104` builds a role launch's arguments, and its `--settings` value is a JSON string the adapter already writes; `daemon.ts:2342-2397` starts a role session with `cwd` the worktree and answers each request by `verdictOn`; `daemon.ts:2440-2470` makes the session, and its start closure calls `startHeadless`, where the work makes the scratch folder; `chain.ts:641-743` builds the round's and the seal's prompts. The bundle's `agents/proofer.md` and `agents/sealer.md` are read by both launches, the daemon's role session and a pane's subagent, so their text states both cases. `test/role-session.test.ts` already runs the real CLI against a stand-in model at no cost, which is where the system's refusal is shown.

Constraints the build meets:

- Claude Code's macOS sandbox is `sandbox-exec` underneath (`frame/design.md` *Grounding*, the row on the OS mechanism), and a `sandbox-exec` cannot start inside another (the same *Grounding*, the probe's row: `sandbox_apply: Operation not permitted`, exit 71). So the daemon cannot both wrap `claude` and let Claude Code sandbox its commands.
- A commit in a linked worktree writes the repository's git common dir (the commit probe's row), so the crafter's place is two folders.
- `filesystem.denyWrite` takes precedence over `allowWrite`, so the scratch folder must sit under no folder refused a write. The run folder is refused no write, and its other files stay unwritable because no allowed place holds them. Every read in the run folder is refused (`filesystem.denyRead`), and `filesystem.allowRead`, which takes precedence over `denyRead`, gives back the session's scratch folder inside it, so for reads the order of the two keys is the reverse of the order for writes (`frame/design.md` *Grounding*, the rows on the launch after the fix pass and on the fix pass's runs).
- The daemon listens on the loopback, which the `network` block lets a command reach, and answers a client that names its token as it answers a window. The token stands on disk in `daemon.json` of the run folder, so the bound on a command's writes holds only while a command cannot read that file.
- `--add-dir` takes every argument after it as a folder (`claude.ts:100`), so the scratch folder joins the end.
- The scratch folder's path is the daemon's to know only when the session starts, after the chain built the prompt, so the daemon appends the paragraph that names it, and the chain's prompts say nothing of a path.

The failure scenario of the chosen approach, six months on: a Claude Code release changes what its sandbox writes by default, for example lets every `--add-dir` folder be written, or renames a key, and the `--settings` value no longer bounds what it bounded. The deny entries of *Scope* item 4 keep each place they name refused whatever the default, and `failIfUnavailable` keeps a session that cannot sandbox from starting. A place the launch does not name is not kept: phase 3 found the git folder of a linked worktree's repository writable by default, and the launch names it since (`frame/design.md` *Grounding*, the measurement's row). A renamed key is the case nothing catches at launch: Claude Code ignores a key it does not know. The three `role:refusal` scripts are what catches both, run when `MIN_CLAUDE_VERSION` moves or the launch changes. Since the fix pass of round 1 they also try the read of the run folder's `daemon.json` for every role, and the crafter's tries the worktree's `.git` file and `commondir`, which Claude Code's own protections refuse and the launch does not name. A person's Claude Code updates without those scripts running, so a release that drops one of its own protections opens that place until the scripts next run; the deny entries and the refused read are the launch's own and do not depend on them. A Claude Code older than the minimum is the same case from the other side, and *Scope* item 10 fails its role launch.

What phase 3 measured adds two constraints:

- A sandboxed command opens no pseudo-terminal and binds no Unix socket, and reaches the loopback's TCP. A role session therefore runs a repository's tests that need neither, where the worktree holds their dependencies, and fails those that need one. In Owlery's own repository the second kind holds the tests that open a pane through `node-pty` and those that start `HookServer` or `TurnServer`. That a fix pass's run of them fails is derived from the probe and was not run.
- Claude Code's own process, not a command, makes `.claude/.cc-writes/` in the worktree of a sandboxed session, so no deny entry of the launch keeps it out.

## Operational impact

- No migration, no new dependency, no environment variable. The run folder gains `scratch/`, where the daemon makes a folder for each proofer's and sealer's session and removes it when that session's process has ended. A folder a crashed daemon left stays there (`gaps.md`).
- A role session now fails to start where Claude Code's sandbox cannot start (`failIfUnavailable: true`). On macOS that is a Claude Code too old for the keys or a broken install, and the adapter already shows the CLI's error output for a failed launch.
- A crafter's commands reach no host but the loopback: a fix pass that needs to install a package or call `gh` is refused by the system and says so in its report (`frame/questions.md` Q1).
- A role's commands read no file of the daemon's run folder but of their own session's scratch folder. A command that needs a file there, such as an added account's config folder or another session's scratch folder, is refused by the system.
- The daemon's commit in a worktree runs the repository's hooks, and the broad gate runs the repository's command, outside the sandbox and on files a crafter's commands wrote. In a repository that keeps its hooks in the tree, or whose config sets `extensions.worktreeConfig` or `include.path`, a crafter's command can change what the daemon's commit runs (`frame/design.md` *Out*).
- A role's commands open no terminal device and bind no Unix socket. A fix pass in a repository whose tests need one cannot run those tests and says which step was refused; the broad gate runs them, outside any role session (`frame/questions.md` Q6).
- Every role's commands can write Claude Code's temporary folder, `/tmp/claude-<user id>`, which the person's other Claude Code sessions use (`frame/questions.md` Q3).
- A role session leaves an empty folder `.claude/.cc-writes/` in the worktree, which `git status` does not show (`frame/questions.md` Q4).
- A role session does not start on a Claude Code older than 2.1.329, and fails with the sentence that says to run `claude update`. Before this work it started on any version (`frame/questions.md` Q5).
- No version move: the release's version is the release branch's to set.
