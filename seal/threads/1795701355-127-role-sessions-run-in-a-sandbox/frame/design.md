## Scope

In:

1. **Each grant names where its commands write.** `RoleGrant` gains `commands: "worktree" | "scratch" | "nowhere"`. The crafter at a fix pass: `worktree`. The proofer at a round and the sealer at the seal: `scratch`. The orchestrator at a judgment: `nowhere`. The grant stays neutral, in `role-grants.ts`, and names no vendor's option.
2. **#39's command rule is lifted for the proofer and the sealer.** Their grants become `runs: true`, so `verdictOn` allows their commands as it allows the crafter's. The orchestrator keeps `runs: false`, and its commands that ask are refused with the rule `no-command` as today.
3. **Every role session the daemon launches runs its commands in the operating system's sandbox, through Claude Code's own.** The Claude adapter adds to the `--settings` value it already passes: `sandbox.enabled: true`, `failIfUnavailable: true`, `allowUnsandboxedCommands: false`, `autoAllowBashIfSandboxed: false`, `filesystem.allowWrite` and `filesystem.denyWrite` from the places of item 4, `filesystem.denyRead` from the folder item 4 refuses a command's reads in, `filesystem.allowRead` from the folders item 4 gives back, which are the session's scratch folder and `shell-snapshots` of the session's config folder, and `network` `{ strictAllowlist: true, allowedDomains: [], allowLocalBinding: true }`. ## Data & interfaces

- `role-grants.ts`: `RoleGrant` is `{ writes: "worktree" | "nowhere"; runs: boolean; commands: "worktree" | "scratch" | "nowhere" }`. `GRANTS`: `proofer at round` `{ writes: "nowhere", runs: true, commands: "scratch" }`, `crafter at fix-pass` `{ writes: "worktree", runs: true, commands: "worktree" }`, `sealer at seal` `{ writes: "nowhere", runs: true, commands: "scratch" }`, `orchestrator at judgment` `{ writes: "nowhere", runs: false, commands: "nowhere" }`. `verdictOn` keeps its shape.
- `adapters/adapter.ts`: `RoleAdapter.start`'s options gain `commands?: { write: readonly string[]; refuse: readonly string[]; unread: readonly string[] }` and `scratch?: string`. The daemon gives `commands` with every `role` and never with `refresh`, and `scratch` exactly where the grant's `commands` is `scratch`. `write` and `refuse` are absolute folders the daemon resolved from the grant (*Scope* item 4): for the grant `worktree`, `write` is the worktree and the git common dir and `refuse` is that dir's `hooks` and `config`; for `scratch`, `write` is the scratch folder and `refuse` is the worktree and the git common dir; for `nowhere`, `write` is empty and `refuse` is the same two. `unread` is the folders a command reads no file of, and no grant picks it: for every grant it holds the real path of the daemon's run folder, and it is empty where the daemon has none.
