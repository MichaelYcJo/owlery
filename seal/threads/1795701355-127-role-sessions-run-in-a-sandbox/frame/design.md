## Scope

In:

1. **Each grant names where its commands write.** `RoleGrant` gains `commands: "worktree" | "scratch" | "nowhere"`. The crafter at a fix pass: `worktree`. The proofer at a round and the sealer at the seal: `scratch`. The orchestrator at a judgment: `nowhere`. The grant stays neutral, in `role-grants.ts`, and names no vendor's option.
2. **#39's command rule is lifted for the proofer and the sealer.** Their grants become `runs: true`, so `verdictOn` allows their commands as it allows the crafter's. The orchestrator keeps `runs: false`, and its commands that ask are refused with the rule `no-command` as today.
3. **Every role session the daemon launches runs its commands in the operating system's sandbox, through Claude Code's own.** The Claude adapter adds to the `--settings` value it already passes: `sandbox.enabled: true`, `failIfUnavailable: true`, `allowUnsandboxedCommands: false`, `autoAllowBashIfSandboxed: false`, `filesystem.allowWrite` and `filesystem.denyWrite` from the places of item 4, and `network` `{ strictAllowlist: true, allowedDomains: [], allowLocalBinding: true }`. The refresh launch holds no tool and is unchanged.
4. **The places, as absolute paths the daemon resolves.** A crafter's commands write in the worktree and the repository's git common dir (`git -C <worktree> rev-parse --path-format=absolute --git-common-dir`), and are refused that dir's `hooks` and `config`, so a commit is made and no hook that would run outside the sandbox is planted. A proofer's and a sealer's commands are given the session's scratch folder, and are refused the worktree and the repository's git common dir, so a command moves no branch of the repository it judges. The orchestrator's commands are given no place and are refused the same two. Every role is refused the role bundle's folder. The daemon asks git for the common dir at every role's start, and a role whose worktree git names no repository for starts no session. Each refused place is a `denyWrite` entry, and a deny entry wins over what Claude Code lets a command write by default. A place the launch names neither way is written where that default allows it: phase 3 measured the default of Claude Code 2.1.332 as its own temporary folder `/tmp/claude-<user id>`, the session's folder and the git common dir of a linked worktree's repository (`frame/questions.md` Q3; *Grounding*, the measurement's row). The launch refuses the last two to the roles that do not write them, and the temporary folder stays writable to every role's commands (*Out*, the row on that folder). Whether a folder after `--add-dir` other than the session's is writable by default was not measured, and the two such folders, the bundle and the scratch folder, are each named.
5. **The daemon makes each proofer's and sealer's session a scratch folder of its own.** It is a new folder that `mkdtemp` makes under `scratch/` of the daemon's run folder, named `<headless session id>-<six characters>/` and readable by the person alone, or one made the same way under the system's temporary folder where the daemon has no run folder. The id alone does not name it: ids count from 1 in each daemon process, and a session of an earlier daemon may still write the folder it was given. The daemon makes it when the session starts (`Daemon#commandsOf`, called from `startHeadless`), so a session that waits for the machine holds none. The adapter is given it, adds it to `--add-dir` so the session's `Read`, `Glob` and `Grep` reach it, and lets the session's commands write there. The daemon removes it once the session's process has ended: at the run's `exit` event, where the adapter's start rejected, and when a stop of the run settles, since the fake adapter reports no `exit` after a stop (`frame/questions.md` Q2). A folder a crashed daemon left stays on disk.
6. **The adapter contract carries the bound.** `RoleAdapter.start` takes the places of item 4 and the scratch folder; its doc says an adapter that launches a role bounds the session's commands to them, or rejects the start with a sentence a person reads. The fake adapter records what it was given.
7. **What a role is told.** The session head of `claude-roles.ts#rulesHead` says that the session's commands run in the operating system's sandbox, and then one sentence picked by the grant's `commands` (`claude-roles.ts#COMMANDS_WRITE`): a crafter writes with them only in the worktree and its repository's git folder, and the system refuses their writes to that folder's `hooks` and `config` and to the bundle's root; a proofer and a sealer write with them only in the scratch folder their prompt names, and the system refuses their writes to the worktree, to its repository's git folder and to the bundle's root; the orchestrator writes nothing with them, and the system refuses the same three. Each sentence tells the role where to write and names the places the system refuses; none says that the system refuses every other write. `roundPrompt` and `sealPrompt` drop "run no command" and keep "write no file of that worktree". The daemon appends to the prompt of a session that has a scratch folder one paragraph: the folder's path, that a clone, a probe and what they print go there, that the system refuses a write to the worktree, and that the folder is removed when the session ends. Neither the head nor the paragraph says that every other write is refused, because phase 3 measured Claude Code's own temporary folder writable to every role's commands (`frame/questions.md` Q3). The test cases whose adapters pick a behaviour by the prompt or compare an answer with the quoted prompt are rewritten with the paragraph: the cases of `apps/desktop/test/daemon.test.ts` and `apps/desktop/test/accounts.test.ts` that `trail/phases/phase-2.md` lists, found by a search of `test/` that the record calls a sample of spellings. `convergencePrompt` and `rulingPrompt` keep their sentence. The pane head and the pane launch are unchanged.
8. **The bundle's proofer and sealer.** `proofer.md` *Job* and the paragraph **A round reads, and runs nothing.**, and `sealer.md` *Job*, are rewritten: in a role session of the daemon the role writes no file of the worktree, its commands run in the sandbox, which refuses their writes to the worktree, the role writes with them only in the scratch folder its prompt names, and a proofer clones and runs narrow tests there with a `## Probes` row for each; in a pane's session a command that asks waits for the person, as today. The first item of each role's *Never* list, which says "Write a file", now says "Write a file of the worktree", since a command of either role now writes files in its scratch folder. The bundle's `docs/forms/the-guarantee.md` is rewritten with them: *The guarantee* says the sealer "reads that record and runs nothing", and **How it errs.** says "It reads and runs nothing, so a claim that only a run would refute passes". Both state the rule this work changes, and both keep the pane's case.
9. **Runs that show the system refusing.** `test/role-session.test.ts`'s stand-in case runs per pair and gains the crafter. The stand-in's command:
   - for the proofer and the sealer, `git clone -q --no-local <worktree> <scratch>/clone && printf x >> <scratch>/clone/README.md && cat <scratch>/clone/README.md && { git -C <worktree> branch probe; printf x >> <worktree>/README.md; }`, so the write to the worktree is tried whatever the branch step did;
   - for the crafter, `printf x >> <worktree>/README.md && git -C <worktree> commit -qam probe && printf x >> <kept>/outside.txt`, where `<kept>` is the case's own folder outside the worktree.

   The case asserts that the request reached the daemon and was allowed, that the tool result the stand-in received names `Operation not permitted`, and the bytes of each file. After the proofer's and the sealer's runs it also asserts that the system refused the lock file `refs/heads/probe.lock`, that no branch `probe` exists, and that `git status --porcelain` in the worktree prints nothing. `package.json` gains `role:refusal:crafter`. The three scripts run once each at the phase's close, never in the suite. What the proofer's run prints is what the third cell of the `## Rule changes` table row states; where it differs, the phase record says so and the framer folds the cell.
10. **A role session starts only on a Claude Code whose sandbox was shown to bound it.** `MIN_CLAUDE_VERSION` becomes `2.1.329`, the oldest version on which a run of `role:refusal` showed the system refusing a role's write (`frame/questions.md` Q5). `claude.ts#roleCheck` also fails a role launch whose `init` line names a version older than the minimum, with the sentence `versionNotice` gives for that version, and one whose `init` line names no version, with "the session did not say which version of Claude Code it is, so its sandbox was not checked". It reads the version before the agent, and the adapter stops the CLI as it does for a missing agent. The reason is the lift of item 2: the daemon now allows a proofer's and a sealer's commands, and a Claude Code that ignored the launch's `sandbox` block would run them bounded by nothing, with no error at the launch. A refresh launch holds no tool and is not checked. The notice at the daemon's start and a pane's launch are unchanged but for the number. The recorded `init` lines of `apps/desktop/test/claude-adapter.test.ts` and of `apps/desktop/test/fixtures/` that a role launch's case reads gain a `claude_code_version` where they hold none, and the cases and fixtures that pin `2.1.326` as the minimum follow the number: `git grep -n -F '2.1.326' -- apps/desktop` lists them, in `src/daemon/adapters/claude.ts`, `test/claude-adapter.test.ts`, `test/role-bundle.test.ts` and `test/view.test.ts` at `bdc74b26`.

Out, each with the issue the orchestrator files:

- **Where a command's network reaches, per role.** Item 3 lets a sandboxed command reach no host but the loopback, which tests that start a local server need. An allowlist per role, a package registry or GitHub for the crafter, is a product choice (`frame/questions.md` Q1) and an issue of its own: "a role session's commands reach no host, so a fix pass cannot install a package".
- **What a command reads.** The sandbox bounds writes; a command can still read the person's files outside the worktree, such as `~/.ssh` or a cloud CLI's credentials, and the network bound alone keeps it from sending them. An issue: "a role session's commands can read the person's credential files".
- **A pane's subagent roles.** A proofer or a sealer started as a subagent of the person's own Claude Code pane is answered by the person's permission settings, and its commands run in whatever sandbox those settings set. An issue: "a pane's owl-chain roles are bounded only by the person's own settings".
- **The crafter's writes in the git common dir.** Item 4 lets a crafter's commands write any ref and object of the repository, other branches' among them. An issue: "a crafter's commands can move refs of branches other than its work item's".
- **A proofer's tests that need installed dependencies.** A clone in the scratch folder has no `node_modules`, and installing them needs the network or a writable package store. That Owlery's own suite runs in a proofer's clone is not claimed. An issue: "a proofer's clone cannot install a repository's dependencies".
- **Claude Code's temporary folder.** Every role's commands write `/tmp/claude-<user id>`, which Claude Code's sandbox allows by default and names as `TMPDIR`, and the person's other Claude Code sessions keep their temporary files there (*Grounding*, the rows of the measurement and of who else writes the folder). A deny entry for it would leave a command no temporary folder, and the launch cannot name another: Claude Code sets `TMPDIR` inside the sandbox. An issue: "a role session's commands can write the temporary folder the person's other Claude Code sessions use".
- **A terminal device and a Unix socket.** A sandboxed command opens no pseudo-terminal and binds no Unix socket, and the launch grants neither (`frame/questions.md` Q6; `frame/plan.md` *Alternatives considered*, the rows on `allowPty` and on Unix sockets). A fix pass in a repository whose tests open one, as Owlery's own daemon tests do, cannot run those tests and says in its report which step was refused; the broad gate, which the daemon runs outside any role session, runs them. An issue: "a role session's commands open no terminal and bind no Unix socket, so a fix pass cannot run a repository's tests that need one".

## Data & interfaces

- `role-grants.ts`: `RoleGrant` is `{ writes: "worktree" | "nowhere"; runs: boolean; commands: "worktree" | "scratch" | "nowhere" }`. `GRANTS`: `proofer at round` `{ writes: "nowhere", runs: true, commands: "scratch" }`, `crafter at fix-pass` `{ writes: "worktree", runs: true, commands: "worktree" }`, `sealer at seal` `{ writes: "nowhere", runs: true, commands: "scratch" }`, `orchestrator at judgment` `{ writes: "nowhere", runs: false, commands: "nowhere" }`. `verdictOn` keeps its shape.
- `adapters/adapter.ts`: `RoleAdapter.start`'s options gain `commands?: { write: readonly string[]; refuse: readonly string[] }` and `scratch?: string`. The daemon gives `commands` with every `role` and never with `refresh`, and `scratch` exactly where the grant's `commands` is `scratch`. `write` and `refuse` are absolute folders the daemon resolved from the grant (*Scope* item 4): for the grant `worktree`, `write` is the worktree and the git common dir and `refuse` is that dir's `hooks` and `config`; for `scratch`, `write` is the scratch folder and `refuse` is the worktree and the git common dir; for `nowhere`, `write` is empty and `refuse` is the same two. The adapter adds its own bundle's folder to `refuse`.
- `adapters/claude.ts#claudeArgs`: the role launch's object gains `sandbox: { allowWrite: string[]; denyWrite: string[] }` and `scratch: string | null`. The `--settings` value becomes `{"disableAllHooks":true,"autoMemoryEnabled":false,"sandbox":{"enabled":true,"failIfUnavailable":true,"allowUnsandboxedCommands":false,"autoAllowBashIfSandboxed":false,"filesystem":{"allowWrite":[…],"denyWrite":[…]},"network":{"strictAllowlist":true,"allowedDomains":[],"allowLocalBinding":true}}}`. `--add-dir` stays last, followed by `cwd`, the bundle, and the scratch folder where there is one. The block holds no `allowPty` and no `allowUnixSockets` (*Out*, the row on a terminal device and a Unix socket).
- `adapters/claude.ts#MIN_CLAUDE_VERSION` is `"2.1.329"`. `roleCheck(line, agent)` keeps its shape, `{ seen: boolean; failure: string | null }`, and for an `init` line gives the failure of *Scope* item 10 before it reads the agents: `versionNotice(<the line's claude_code_version>)` where that is a sentence, and the sentence on a missing version where `claude_code_version` is no string or holds no version.
- `daemon.ts`: `HeadlessSession` gains `scratch: string | null`. `Daemon#commandsOf`, called from `startHeadless`, asks git for the repository's common dir for every role, resolves the places and makes the folder; the daemon appends the scratch paragraph to the prompt the adapter is given (phase 2), and removes the folder on the run's `exit` event, where the adapter's start rejected, and when a stop of the run settles, the daemon wrapping the run's `stop` for the last. The run folder gains the subfolder `scratch/`.
- `chain.ts`: `roundPrompt` and `sealPrompt` change their last instruction (*Scope* item 7); `chain.test.ts`'s pins follow.
- `role-bundle/agents/proofer.md`, `role-bundle/agents/sealer.md`, `role-bundle/docs/forms/the-guarantee.md`: the text of *Scope* item 8.
- `test/role-session.test.ts`, `package.json`: the stand-in case per pair and the script `role:refusal:crafter` (*Scope* item 9).
