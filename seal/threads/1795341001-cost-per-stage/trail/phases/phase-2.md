**Each headless session gets its entry in one place, and at most once.** `headlessChanged` already runs one block once for each session that has just ended, so the entry is written there, for a result, an error result, an exit with no result and a stop at the limit or at a request. A flag `entered` on the session holds the bound of one entry. The handler of a rejected start sets it before it fails the session, so that session gets none. `close` writes the entry of each session still working before it stops the session's run, because a run's stop can report the process's exit at once, and the entry has to say that the daemon stopped it and not that the process exited. The case of the daemon's close holds both: its adapter reports an exit inside `stop`. Judged against `frame/design.md` *Scope* items 9 and 10.

**An entry's usage is the session's, with no branch on what stopped it.** Only a result sets `HeadlessInfo.usage`, and the daemon takes no result after a stop (`startHeadless`), so a session that a stop or the daemon's close ended carries null. Judged against `frame/design.md` *Scope* item 9.

**The repository's folder and the branch are taken when the session is asked.** The session keeps both from the store at the `ask`, and its entry names them as they stood then (read: the `ask` case of `src/daemon/daemon.ts`). Judged against `frame/design.md` *Scope* item 9 and *Data & interfaces*.

**Three readings that *Scope* item 8 leaves open were settled in `src/daemon/ledger.ts`.**

- A last line that a crash cut stays in the file, and the next entry starts on a line of its own after it. Without the line break the next entry would join the cut line, and `read` would count both as one unread line, so a write would lose the entry it wrote. An empty file gets no line break before its first entry. Judged against *Scope* item 8, "A line it cannot read stays in the file", and the plan's row on `ledger.jsonl` in *Alternatives considered*: "no write can lose one that was written".
- A file that exists and cannot be read is logged with `console.error`, and `read` then gives the entries held in memory alone, with `unread` 0. The scenario "A failed append loses no entry" makes `ledger.jsonl` a folder, and asks that `read` gives the entry. A file that does not exist is an empty ledger and is not logged. Judged against *Scope* item 8 and the scenario.
- `read` builds each entry it gives from the protocol's fields alone, so a field a line holds beyond them does not cross the protocol. The entries held since a failed append come after the file's lines, because they were added after them. `unread` counts every line of the file that is no entry, whatever work item it was written for, the empty text after the last line break apart. Judged against *Data & interfaces* and `docs/architecture.md` *Rules that keep it portable*, rule 1.

**`ledger.jsonl` is readable by the user alone because the daemon creates it so.** The append gives the mode `0600` only to a file it creates. A file that already stands keeps its mode: the first version of the case "outlives the daemon" planted a line before the daemon started, and the file read `0644` (executed). The case now plants its line after the first daemon's close. The ledger changes no mode of a file it did not create.
