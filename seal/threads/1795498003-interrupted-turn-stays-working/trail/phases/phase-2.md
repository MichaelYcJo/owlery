# Phase 2: 1795498003-interrupted-turn-stays-working

## What this phase found

**Q2 is answered: `fs.watch` reports each append to a file once and at once under Electron 45's Node, so the watch is built as framed.** Executed, the probe `test_tmp_watch_electron.cjs` under this phase's scratch directory, run once with `ELECTRON_RUN_AS_NODE=1` and the repository's Electron 45.3.3, whose Node is 24.22.3. Another process appended to a file five times, 200 ms apart. `fs.watch` reported each append once, as `change`, within 2 ms of the moment a stat taken every 1 ms saw the file grow. A second probe, `test_tmp_watch_unlink.cjs`, saw the file's removal reported as `rename`. Executed, the first case of this phase, scenario 1's in `apps/desktop/test/daemon.test.ts`, runs under the same Node through the repository's runner and reads the interruption through the watch. Judged against `frame/questions.md` Q2's options.

**Departure from the frame: the watch waits for a session log that does not stand yet, because at a session's first prompt it does not.** `frame/design.md` *Scope* item 6 says the watch "starts at an event that leaves the pane `working` and names a log file that exists". Executed, the birth times of the session log the second recording wrote, read with `os.stat` against the recording's start: its folder was made at 4713 ms and the log at 4756 ms. The `UserPromptSubmit` of the session's first prompt began at 4702 ms. Claude Code waits for that hook before it writes the prompt, so the event reaches the daemon before the log stands. Built to the wording of item 6, the watch would never start in the first turn of a session. A reply interrupted there sends no later event, so it would stay `working`, and that is the recording's first interruption and scenario 2. So where the log does not stand, the watch looks for it every 100 ms for 10 seconds (`SESSION_LOG_WAIT_MS` in `apps/desktop/src/daemon/session-log.ts`). Once the log stands, the watch reads it from its first byte, since every byte in it was appended after the watch began. The look stops when the pane leaves `working`. Executed, `seal mutate` with a watch that gives up at once where the log does not stand: scenario 2's case went red. The wait costs one `stat` every 100 ms, at most 10 seconds after an event, and only while a working pane's log does not stand. That is not the tail read `frame/plan.md` *Alternatives considered* rejects, which wakes the daemon every second for the whole turn. Judged against `frame/design.md` *Scope* items 2 and 6 and scenario 2, and `frame/plan.md` *Alternatives considered*, the row on reading the tail every second. *Scope* item 6's sentence is the orchestrator's to fold.

**Q3 is decided by the work: the watch holds and hands on 16 KB of a line at most** (`LINE_BYTES`, 16,384 bytes). The recording's two entries are 773 and 786 characters as written (`trail/phases/phase-1.md`), so the bound is over twenty times the longest. A longer line is skipped to its end and never parsed. Judged against `frame/questions.md` Q3, whose default this is.

**The watch stands in a module of its own, which the frame does not name.** `frame/design.md` *Data & interfaces* says `Session` holds the watch, and it does. The reading of the file, the held start of a line and the skip of a long one stand in `apps/desktop/src/daemon/session-log.ts`, with their cases in `apps/desktop/test/session-log.test.ts`. That is a fourth test file beside the three `frame/plan.md` *Phases* names for this phase. The cases of a split line and of a long line need no daemon, and in `daemon.test.ts` each would also start a pane.

**What the build settled that the frame leaves open.**

- A working event that names the log the watch reads keeps that watch, and one that names another log starts a new watch. A later event of the same log restarting the watch would skip what was appended and not yet read. Scenario 3's case sends a `PostToolUseFailure` after the interruption's entry is written and before it is read, and `seal mutate` of the kept watch turns that case red. A watch that gave up is started again by the next working event, so a first prompt whose log stands only after the 10 seconds is read from the next tool call on.
- The daemon reads `transcript_path` as any text. A path that is not a whole path from `/` is not refused, because Claude Code sends whole paths and nothing in the frame asks for a refusal.
- The watch does not end in `Daemon#dropWorkItems`, where the silent start is also cleared, so it departs from `frame/plan.md` *Technical context*, which says the watch is "held and ended the same way". A delete and a removal drop a work item's panes only after `Daemon#endSessions` saw every pane's process exit, and they refuse otherwise. The exit ends the watch, so no watch is live there to end. The watch does end at a pane's exit, its close, its state's leaving `working` and the daemon's close, and a case pins each.
- `fs.watch` arms its watch at the next turn of the event loop. A write in the same turn as the start of the watch is therefore reported only with the next write, and the read then takes both. The interruption's entry comes after an Esc, so in practice it comes long after the watch starts. Two cases of this phase met the limit when they removed or wrote the log in the turn that started the watch, and each now waits before it does.
- The interruption is broadcast as an `agent` message with `event: "interrupted"` and no tool. The state's text is "The turn was interrupted, and the agent waits for what to do next.", as `frame/design.md` *Scope* item 4 gives it, and scenario 1's case pins it.
