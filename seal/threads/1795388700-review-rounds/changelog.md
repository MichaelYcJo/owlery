# Changelog: "Get a seal" runs a branch's review rounds and fix passes

Issue #41. The daemon could launch one role session at a client's request, and nothing ran a review on a branch: no control started one, nothing ordered the rounds and the fix passes, and no record of a round reached the repository.

- **A work item's view offers "Get a seal" at its foot, by the seal's place.** A press starts the review rounds on the work item's branch, and the sentence above the button says where they stand, for example "Review round 2 is running." The button is off while they run. Where the rounds cannot start, the reason stands under the button, for example "The worktree holds a change no commit holds, at notes.txt. A round reads a committed tree: commit the change or remove it first." They start on a branch that holds a commit after its base, in a repository that holds the place for work records, while no agent of the work item is working and none of its questions is open.
- **Owlery runs the rounds one stage at a time, in the work item's worktree.** A round is a fresh proofer session that reads files and changes none. A round that leaves a finding is followed by a fix pass, in which a crafter session commits its fixes, and a later round reads every commit of the pass. When a round leaves nothing open and no commit after it is unread, the sentence reads, for example, "The review rounds settled at 1a2b3c4, after round 2." Each stage's session is listed under "Ask" with "Stop", and its process has ended before the next stage starts.
- **The rounds go on with the window closed.** The daemon runs them and keeps itself running between two stages. Where the Mac is kept awake "While an agent works", it stays awake from the first stage to the last.
- **Each stage's record is committed on the branch.** The first start makes the work item's directory under the place for work records, with a `routing.md` that names the branch. After that Owlery commits each round's record, the record each fix pass closed findings in, and the work item's decisions, with your git identity and the repository's hooks. Each commit holds files of the work item's directory alone, and nothing is pushed. The records are in the form the pull request check reads. A round's record is the proofer's answer, unchanged, and Owlery writes none that the check would refuse.
- **From the second round on, Owlery asks before each fix pass whether the rounds are converging.** An orchestrator session reads the round records and answers, and the answer is listed among the decisions made without asking. At a no the rounds stop, and "Get a seal" runs the fix pass all the same. From round 6 on, a round that leaves a finding open stops the rounds without that question, and each press of "Get a seal" runs one more fix pass and one more round.
- **A question a stage raises is first decided from the code and the repository's documents.** The decision is listed among those made without asking. What they cannot answer parks the work item with the question, and the rounds go on by themselves once you have answered every open question in the view. A decision you reversed is handed to the next fix pass, and reads as applied once that pass has run.
- **A stage that fails, or that you stop, stops the rounds of its work item alone.** The work item's line then stands under "Needs you", its second row says the stage and why, for example "Review round 2 failed: the session reached its time limit and was stopped.", and a notification is raised as for any work item that begins to wait. While the rounds run the line stands under "Working", unless an agent in one of its panes waits for you. Where the daemon ended during a stage, the rounds are stopped when it starts again. "Get a seal" goes on from the committed records, so nothing has to be repaired first.
- **Each call a role's rule refused is counted.** A proofer that asks to write a file or to run a command is refused, and the commit of its stage adds a row to `trail/refusals.md` of the work item's directory, with the stage, the role, the tool and the rule, and with no text of the call.
- **A rename of a work item's branch keeps its records found.** The rename rewrites the branch's name in the work item's `routing.md` and commits that file. A branch is not renamed while its rounds run.
- **The rounds end at the review, and no stage of them has run with a real agent yet.** The broad run of the tests, the sealer and the pull request are later stages, so the seal's place still reads "No seal yet" after the rounds settle. Every stage of the tests is played by a stand-in. Whether a real proofer, crafter and orchestrator answer in the forms Owlery reads is measured by the first run on a branch of Owlery's own.
- **After an update, the view shows no "Get a seal" until the daemon restarts.** A daemon started by the build before this one starts no rounds, and the status line already names a daemon of another build.
- **For a client of the daemon:** `getSeal`, with `requestId` and `workItemId`, starts a work item's rounds and is answered with `done` or with an `error` whose message says why not. Wherever the daemon sends a work item, and in the last look, the work item carries `chain`: `null` where no rounds ran for it, and otherwise `state` (`running`, `parked`, `stopped` or `reviewed`), `says`, `reviewedAt` and `stages`, each stage with its `kind` (`round`, `fix-pass`, `judgment` for the question whether the rounds are converging, or `ruling` for the decision of a stage's question), `round`, `state`, `failure`, `startedAt`, `endedAt`, `headlessId` and `refusals`. A session can be launched as the pair `orchestrator` at `judgment`. A `renameWorkItem` that renames the branch is refused while the work item's rounds run. A client of an earlier build reads the absence of `chain` as no rounds, and a look written before this build is still read.
