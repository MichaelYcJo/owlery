**Decisions made while building, each with its grounds.**

- **The daemon reaches the module through `RoleAdapter.logins?: AccountLogins`.** It has four methods: `furnish`, `signIn`, `status` and `signOut`. `frame/design.md` *Data & interfaces*, *The adapter*, asks for "an interface that names no vendor" and names no method. The member is optional, so the adapters the cases build by hand stay valid, and an adapter without it signs nothing in. The daemon then refuses to add an account with no folder, to sign one in, and to remove a made one.
- **`CONFIG_DIR_VARIABLE` moved into `adapters/claude-accounts.ts`.** `claude.ts` and `hooks.ts` import it from there. The module also holds the list of linked names, `linkOwn`, and the three `auth` commands (*The adapter*, its first bullet).
- **Links are made only once the lookup has answered.** The module's `furnish` asks `ownFolder`, which is the Claude adapter's `defaultLoginFolder`. Before the lookup answers, that is null and nothing is linked. The daemon calls `furnish` at the add, before each pane's launch and before each headless session's launch (*Scope* item 4, "again before each launch under the account").
- **A link is never made over a name that stands.** `linkOwn` relies on `symlink` refusing a path that exists, and keeps what stands in the account's folder. A first draft also checked before linking. `seal mutate` could not break that check, since the refusal answers the same, so it was removed before the commit.
- **`claude auth status` is read by its exit code, and `loginExpiresAt` only as a date string.** Exit 0 says a login stands and 1 says none does. Any other exit, a kill or a timeout is an error with the command's last line of stderr. The CLI reference names `loginExpiresAt` without its format (`frame/design.md` *Sources*, the CLI reference). A string `Date.parse` reads is kept as the login's end, and anything else is kept as null. Q3 measures the real format.
- **The sign-in pane is a shell pane of no work item.** It runs the lookup's CLI with `auth login`, in `claudeEnv`'s cleared environment with `CLAUDE_CONFIG_DIR` set to the account's folder. Its working folder is the account's folder, and `SessionInfo.signsIn` names the account. No inbox line and no work item's view lists it, since both list panes by `workItemId`. At the pane's end the daemon reads `auth status` again and sends the accounts where the reading changed anything (*Scope* item 5).
- **The daemon reads no status at the add.** *Scope* item 5 names two times to read it: the pane's end and the person's request. A new account's row says "Sign-in not read yet" until one of them happens.
- **A failed `auth logout` refuses the removal, and the folder stays.** *Scope* item 11 says the daemon "runs `claude auth logout` with that folder and then removes the folder", and does not say what happens where the logout fails. Removing the folder anyway would leave a login the CLI may still hold outside the folder, such as a Keychain entry. The refusal carries the CLI's sentence.
- **The removal is refused while something runs under the account, and the check runs again after the logout.** A pane or a session can start while the logout runs. The refusal names each pane and each working session (*Scope* item 11).
- **A removal reads again the chain of each repository whose setting it cleared.** Where the default changed, it also reads each repository set to none. This is phase 2's rule for a change of a repository's account (`trail/phases/phase-2.md`, the decision on the re-reads at `setRepository` and `setDefaultAccount`).
- **A login read for an account removed meanwhile is refused with the store's sentence (`1f8f8cc`).** The first build answered "nothing changed" for such an account. `seal mutate` showed that no case could tell that answer from a reading that changed nothing, and the answer hid the removal from the request that asked. The guard was removed, so `setLogin`'s "No account N is kept." reaches the request, and a pane's end logs it.
- **`addMade` passes over an id whose folder stands already.** An `accounts/<id>` left by a run folder copied or edited by hand is never taken over by a new account. Both `accounts/` and `accounts/<id>` are made with mode 0700 (*Scope* item 3, "readable by the person alone").
- **The dialog's words.** The design names "Add an account", "Use an existing folder…", "Sign in", "Make the default" and "Remove the account" (`frame/design.md` *Data & interfaces*, *The window*). The row adds "Check sign-in" for the person's request of *Scope* item 5, and "Remove…" opens an in-row confirmation whose button is "Remove the account". Before the person confirms, the confirmation says what becomes of the folder and names each repository and work item, archived ones among them, whose setting the removal clears (*Scope* item 11; `docs/design.md`, the window names what will be lost before it is lost). A sign-in's row says "Signed in, the login ends in <age>", "Signed in, the login may have ended", "Not signed in" or "Sign-in not read yet". System default's row says nothing of a sign-in.
- **`Account.signedIn` and `Account.loginEndsAt` are required fields.** `frame/design.md` *The protocol* makes optional only a field of a type that existed before this work, and `Account` is this work's own.
