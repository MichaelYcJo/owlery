# Changelog: accounts per repository, work item and session

Issue #160. Every session Owlery started ran under the one Claude Code login the person's own config folder held, so a person with a work login and a personal one could not keep a repository on the login it belongs to.

- **Owlery keeps accounts, each one a Claude Code config folder.** "System default" is always an account. It has no folder, and a session under it runs as before this release. The Accounts dialog adds an account in one of two ways. You can hand over an existing config folder by its path, and Owlery then makes, reads and removes nothing in it. Or Owlery makes the folder in its own run folder and links into it what belongs to you in your own config folder, such as your settings, skills and conversations. The login and the CLI's own state stay the account's. The dialog renames an account, names the default and removes one. The dialog is reached from the sidebar's foot and from the app menu's "Accounts…".
- **Sign-in is Claude Code's own.** "Sign in" runs `claude auth login` under the account's folder in a terminal pane drawn in the dialog. "Check sign-in" asks `claude auth status`, and the row says whether a login stands and when it ends. Owlery reads no credential file, no Keychain entry and no token.
- **A repository, a work item and a session each take an account, and the nearest setting wins.** The order is the session's own, then the work item's, then the repository's, then the default. The repository's settings, the work item's menu and the menus of a new pane and a new headless session set it. The inbox and a work item's view name the account where it differs from the one the repository gives, and so does a pane's tab where it differs from the work item's. With System default alone, the window shows none of this.
- **Every session starts under its account's folder.** A role session and a headless session get `CLAUDE_CONFIG_DIR`. A Claude Code pane gets it in its command, after your login profile ran, so a profile's own export does not take its place. A shell pane gets it in its environment. Each ledger entry names the account its stage ran under.
- **A running Claude Code pane changes account and goes on with its conversation.** "Change Account…" in the pane's menu first says that a turn under way is cut. Owlery then ends the pane's process and starts `claude --resume` in the same pane under the other account, with the pane's tab and what it printed kept. The change is refused, with its reason, for a shell, a sign-in pane, a session asked in a work item, and two accounts that do not share one conversations folder.
- **An account removal signs Owlery's folder out first.** The removal is refused while anything runs under the account. For a folder Owlery made, it runs `claude auth logout` and then removes the folder. Every setting that named the account goes back to the setting above it.
- **"Refresh usage" reads an idle account's usage limit from Claude Code itself.** Each row shows the last limit values a session of the account handed over, with when they arrived, and shows no number where none arrived. "Refresh usage" stands where nothing runs under the account. Beside it, the dialog says that a refresh starts one short Claude Code session and uses a little of the account's limit. The session has no tool, takes one turn, writes no transcript and runs in an empty folder of Owlery's. It ends at its result or after one minute. The row shows what it handed over and what the turn reported it cost, and a refresh is no ledger entry. Nothing else starts one: no timer, no opening of the dialog, no start of Owlery. Owlery reads no token and calls no address of Anthropic's.
- **If your login profile exports `CLAUDE_CONFIG_DIR`, two things change for you.** Under System default, role sessions now run under that folder's login, where they ran under the default folder before. The reading of which plugins a pane enables, which decides whether Owlery asks which chain a repository's panes run, now reads that folder too, where it read the folder Owlery's own environment named. For anyone else nothing moves: both readings name the same folder.
- **What this release does not cover.** No agent has run a real `claude` under two logins. Three things are the owner's walk of this release (#184): a login found through `CLAUDE_CONFIG_DIR`, the links of a folder Owlery made, and a conversation resumed under another account. What a real turn far from a limit hands over, and which windows it names, is read from one recorded run's shape, whose values were placeholders. Reading usage outside the Accounts dialog and holding work back near a limit come in release 0.1.0 (#73, #74).
- **For a client of the daemon:** `ready` and the message `accounts` carry `accounts`, `defaultAccountId` and `refreshesUsage`. `Repository`, `WorkItem`, `SessionInfo` and `HeadlessInfo` carry `accountId`, a sign-in pane carries `signsIn`, and a ledger entry carries `account`. The new requests are `addAccount`, `renameAccount`, `setDefaultAccount`, `removeAccount`, `signIn`, `readSignIn`, `changeAccount` and `refreshUsage`. `setRepository`, `setWorkItem`, `start` and `ask` take `accountId`. A daemon of an earlier build sends none of these, and the window then shows no account.
- **For an adapter:** `RoleFeature` gains `accounts` and `limit-refresh`, `RoleAdapter.start` takes `accountDir` and `refresh`, and `RoleEvent` gains `limit`.
