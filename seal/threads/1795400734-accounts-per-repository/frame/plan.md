# Implementation Plan: accounts per repository, work item and session (#160)

## Technical context

The tree as read at `919bb6a`, the branch with `release/v0.0.3` merged into it. Phase 1 is built on it. Phases 2 to 5 are built on a tree that also holds #181, as *Overlap with the release* states. Each phase's crafter opens each coordinate below at its own HEAD before it builds on it.

- **One seam for role sessions.** `apps/desktop/src/daemon/daemon.ts#startHeadless` is the one caller of `RoleAdapter.start` (`apps/desktop/src/daemon/adapters/adapter.ts`). The Claude adapter builds the session's environment in `apps/desktop/src/daemon/adapters/claude.ts#claudeEnv` and spawns the CLI with it. An account's folder enters at `start` and leaves as one variable of `claudeEnv`.
- **One seam for panes.** `apps/desktop/src/daemon/daemon.ts#startSession` asks `DaemonOptions.commandFor` for a pane's command and merges its `env` over the daemon's. `apps/desktop/src/daemon/hooks.ts#paneCommands` is the `commandFor` the daemon runs with, and `#claudePaneCommand` writes the one line the login shell executes. #181 builds on the same seam on its branch (`5d37758`, read): a start also names the pane's folder and its work item's base, and `paneCommands` takes a function that says what a pane of a folder carries.
- **The stores.** `apps/desktop/src/daemon/repositories.ts` reads and writes `repositories.json` whole, and reads a field a later build added as absent. The accounts store follows it.
- **Hook events.** `apps/desktop/src/daemon/daemon.ts#agentEvent` receives each hook's whole payload from `apps/desktop/src/daemon/main.ts`. It keeps the event's name, its tool and what it says and asks, and it starts the watch of the session log at the payload's `transcript_path` while the pane works (#182). `docs/architecture.md` *The phone: the terminal session as a chat* says every event carries `session_id` and `transcript_path`.
- **The lookup of the CLI.** `apps/desktop/src/daemon/adapters/claude.ts#lookupCommand` runs the person's interactive login shell once per daemon and reads marked lines from what it prints. The person's own config folder is read the same way.
- **Cases.** The fake adapter (`apps/desktop/src/daemon/adapters/fake.ts`) stands for role sessions. A stand-in for `claude` on the case's `PATH`, as `apps/desktop/test/fixtures/claude-stand-in/claude` is for the terminal cases, stands for the pane's CLI and for `claude auth`. The built app is started only through `BuiltApp.start` with `OWLERY_BACKGROUND=1`, in as few starts as the window's cases need. A case that needs a stage of a chain starts the chain through the helper of `apps/desktop/test/chain-run.ts` and sends no message of its own for it: that helper sends `getSeal` at `919bb6a` and calls `Daemon#startChain` once #181 is merged.

Constraints the build keeps: no real `claude` runs in any case, nothing under the person's own config folder is written, and no case reads or writes the app's real data folder.

**What breaks in six months.** Claude Code's layout of its config folder is the CLI's to change. The ways it fails here, and what each costs:

- A later version adds a file of the person's that the list of linked names does not hold. That file then stays with each account, so one tool of the person's is missing under a second account until the list names it. The list is an allow-list for this reason: the other failure, a file of the account's that gets linked, would merge two logins without a sign.
- A later version stops following a linked `projects`, or keeps conversations elsewhere. A conversation is then not found under a second account. The change of a running pane's account fails visibly, at a `--resume` that finds nothing, and `frame/questions.md` Q3 holds the run that would show it first.
- A turn far from a limit emits no `rate_limit_event`, or a later version changes the event's fields. A refresh then spends its turn and shows no number, and the row says that the CLI handed over none. The fixture line of the adapter's case is the reference's type until `frame/questions.md` Q5's run replaces it with a recorded one.
- An account's folder is removed outside Owlery. Its Keychain entry stays, and the account's row names a folder that is gone. The daemon then says the account is not signed in, because `claude auth status` exits 1 for it.

## Operational impact

- **New state in the daemon's run folder.** `accounts.json`, and `accounts/` with one folder for each account Owlery made and one empty folder that a refresh runs in. Neither is committed anywhere. A build before this work ignores both.
- **`repositories.json` gains a field.** `accountId` on a repository and on a work item. A file without it reads as nothing set, and an older build that rewrites the file drops the field, which sets every repository back to the default.
- **A variable reaches role sessions.** `CLAUDE_CONFIG_DIR`, and under System default only where the person's login shell holds one. A person whose profile sets it gets role sessions under that login from this release on, where they ran under the default folder before. The changelog fragment says so.
- **A Claude Code pane's command grows.** Under an account with a folder it holds `env CLAUDE_CONFIG_DIR=<folder>` in front of `claude`. What #181 adds to the command and to the pane's environment is unchanged.
- **No new dependency, and no change of the oldest supported CLI.** `MIN_CLAUDE_VERSION` stays 2.1.326. `claude auth status` carries `loginExpiresAt` from 2.1.318 by the CLI reference. The version that first had `claude auth login` is not named there, and Q3's run shows it on the installed CLI.
- **The protocol only gains.** Every new field and message is absent from an earlier daemon, and the window reads its absence as the feature being off.
- **This pull request does not move the version.** `apps/desktop/package.json` names 0.0.3 at `919bb6a`: an earlier pull request of the release moved it (`docs/roadmap.md` *Releases and the tracker*).
- **Issues whose text this frame makes stale, for the orchestrator.** Issue #73 says the row "How to read usage limits" stays open, and issues #73 and #74 say nothing of an account. Phase 5 builds the line of issue #73's *Done when* on a role session's limit events, so that line names this work once it merges. Issue #160 names the sign-in command `claude login`. #181's `frame/plan.md` says that this work reads the plugin's settings from the account's folder, which is `frame/design.md` *Scope* item 14.
