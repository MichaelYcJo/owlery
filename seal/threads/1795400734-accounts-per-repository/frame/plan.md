# Implementation Plan: accounts per repository, work item and session (#160)

## Technical context

The tree as read at `41e2cc6`, and again at `8c97b8e` and `86659a8` for what phases 2 and 3 built (`frame/design.md` *Grounding*). It holds phase 1, which was built on `919bb6a`, and #181, which reached this branch in the merge `f0b7e36` of `release/v0.0.3`. Phases 2 and 3 were built on it. Phases 4 and 5 are built after `release/v0.0.3` is merged again, with #146 (*Overlap with the release*). Each phase's crafter opens each coordinate below at its own HEAD before it builds on it.

- **One seam for role sessions.** `apps/desktop/src/daemon/daemon.ts#startHeadless` is the one caller of `RoleAdapter.start` (`apps/desktop/src/daemon/adapters/adapter.ts`). The Claude adapter builds the session's environment in `apps/desktop/src/daemon/adapters/claude.ts#claudeEnv` and spawns the CLI with it. An account's folder enters at `start` and leaves as one variable of `claudeEnv`.
- **One seam for panes.** `apps/desktop/src/daemon/daemon.ts#startSession` asks `DaemonOptions.commandFor` for a pane's command and merges its `env` over the daemon's. `apps/desktop/src/daemon/hooks.ts#paneCommands` is the `commandFor` the daemon runs with, and `#claudePaneCommand` writes the one line the login shell executes. #181 built on the same seam: `daemon.ts#startSession` builds a start, `PaneStart`, of `continueLatest`, `folder`, `base`, `checkout` and `chosen`, and `paneCommands` takes a function of that whole start, `apps/desktop/src/daemon/pane-chain.ts#carriedIn`, which says what the pane carries of the owl chain and which settings file it is given.
- **A second seam reads the person's Claude Code folder.** `DaemonOptions.pluginEnabled` answers whether the AgenticSeal plugin is enabled for a folder, and `daemon.ts#readRecords` asks it once for each repository, for the `chain` the window asks by. It and `carriedIn` both call `apps/desktop/src/daemon/claude-plugins.ts#readPlugins`, which takes the config folder as an argument. Neither gives one at `41e2cc6`, so both read the folder of the daemon's environment (`frame/design.md` *Grounding*).
- **The stores.** `apps/desktop/src/daemon/repositories.ts` reads and writes `repositories.json` whole, and reads a field a later build added as absent. The accounts store follows it.
- **Hook events.** `apps/desktop/src/daemon/daemon.ts#agentEvent` receives each hook's whole payload from `apps/desktop/src/daemon/main.ts`. It keeps the event's name, its tool and what it says and asks, and it starts the watch of the session log at the payload's `transcript_path` while the pane works (#182). `docs/architecture.md` *The phone: the terminal session as a chat* says every event carries `session_id` and `transcript_path`.
- **The lookup of the CLI.** `apps/desktop/src/daemon/adapters/claude.ts#lookupCommand` runs the person's interactive login shell once per daemon and reads marked lines from what it prints. The person's own config folder is read the same way, on the lookup's third marked line, and the daemon asks the lookup at its start for the adapter's notice (`daemon.ts#readAgentNotice`).
- **Cases.** The fake adapter (`apps/desktop/src/daemon/adapters/fake.ts`) stands for role sessions. A stand-in for `claude` on the case's `PATH`, as `apps/desktop/test/fixtures/claude-stand-in/claude` is for the terminal cases, stands for the pane's CLI and for `claude auth`. The built app is started only through `BuiltApp.start` with `OWLERY_BACKGROUND=1`, in as few starts as the window's cases need. A case that needs a stage of a chain starts the chain through the helper of `apps/desktop/test/chain-run.ts`, which calls `Daemon#startChain`, and sends no message of its own for it.
- **The stand-ins for the login shell.** A case's stand-in that answers the lookup prints two marked lines at `41e2cc6`, so the lookup reads no config folder from it. Once the reader of plugins takes the lookup's answer (`frame/design.md` *Scope* item 14), a built app whose stand-in prints no third line would read `.claude` of the home of whoever runs the case. So phase 2 has each such stand-in print the third line from its own environment, in the files phase 2's *Verified by* names for it, and `apps/desktop/test/built-app.ts#BuiltApp.start` keeps giving the app a `CLAUDE_CONFIG_DIR` of its own. A case that starts the built app with the person's real login shell then reads the folder that shell names, which is the app's own unless the person's profile exports another.
- **This machine's pseudo-terminals.** `kern.tty.ptmx_max` is 511 on the machine the phases run on. `apps/desktop/test/daemon.test.ts` and the files that start the built app each open many pseudo-terminals, and where two worktrees' runs of them overlap, a pane's start fails with `posix_spawnp failed.` and the cases fail for no reason of the code (`trail/phases/merge-release.md`). So a phase's run of `daemon.test.ts`, and of any file that starts the built app, never overlaps another worktree's test run: the crafter runs them one command after another and never beside each other, and where the orchestrator has other worktrees building, it gives the phase a time when none of them runs such a file. A run that fails with `posix_spawnp failed.` is run again alone before any of its failures is read as the code's.

Constraints the build keeps: no real `claude` runs in any case, nothing under the person's own config folder is written, and no case reads or writes the app's real data folder.

**What breaks in six months.** Claude Code's layout of its config folder is the CLI's to change. The ways it fails here, and what each costs:

- A later version adds a file of the person's that the list of linked names does not hold. That file then stays with each account, so one tool of the person's is missing under a second account until the list names it. The list is an allow-list for this reason: the other failure, a file of the account's that gets linked, would merge two logins without a sign.
- A later version stops following a linked `projects`, or keeps conversations elsewhere. A conversation is then not found under a second account. The change of a running pane's account fails visibly, at a `--resume` that finds nothing, and `frame/questions.md` Q3 holds the run that would show it first.
- A turn far from a limit emits no `rate_limit_event`, or a later version changes the event's fields. A refresh then spends its turn and shows no number, and the row says that the CLI handed over none. The fixture line of the adapter's case is the reference's type until `frame/questions.md` Q5's run replaces it with a recorded one.
- An account's folder is removed outside Owlery. Its Keychain entry stays, and the account's row names a folder that is gone. The daemon then says the account is not signed in, because `claude auth status` exits 1 for it.
