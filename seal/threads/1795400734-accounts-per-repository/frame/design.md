## Scope

The subject of this work is the code, so the rules it changes are stated in *Rule changes* for the settle. In scope:

1. **The daemon keeps accounts.** An account has an id, the name the person gave it, the adapter it belongs to, its config folder, and whether Owlery made that folder. "System default" is an account that is always there, has no folder and is never removed: a session under it is launched as today. One account is the default, and it is System default until the person chooses another.
2. **A person hands over an account by its folder.** The person names an existing config folder by its absolute path. Owlery makes no link in such a folder and never deletes it. This is the one way an account that Orca, another tool or the person's own alias made comes in, and Owlery reads no other product's files.
3. **Owlery makes an account's folder.** For an account added with no folder, the daemon makes `accounts/<id>/` in its run folder, readable by the person alone.
4. **In a folder Owlery made, what belongs to the person is a link, and what belongs to the account is the folder's own.** *Data & interfaces* holds the list of names that are linked. A name of the list is linked only where the person's own config folder holds it and the account's folder holds nothing by that name, and the daemon makes the missing links again before each launch under the account. Every other name stays the account's own: its sign-in, the CLI's state file `.claude.json`, and the policy and remote settings the CLI caches for the account's organization.
5. **Sign-in is the CLI's own.** The daemon runs `claude auth login` in a terminal pane with the account's folder as `CLAUDE_CONFIG_DIR`, and the window shows that pane in the Accounts dialog. When the pane's process ends, and whenever the person asks by "Check sign-in", the daemon runs `claude auth status` with the same folder and keeps whether a login stands and when it ends. It reads no status at the add, so a new account's row says that its sign-in has not been read until one of the two happens. The command's exit code says whether a login stands, and the login's end is kept only where the command prints one the daemon can read as a date. Owlery reads no credential file and no Keychain entry, passes no token in any variable, and asks for no password or code in a field of its own.
6. **A repository, a work item and one session can each be set to an account, and the nearest setting wins.** A session's own setting is first, then its work item's, then its repository's, then the default. The daemon resolves it when the session is launched. A request that names an account the daemon does not keep is refused, and nothing of it is set. At its start the daemon clears a repository's or a work item's setting that names an account it does not keep, as where `accounts.json` was lost or edited, so an account added later never takes a setting it was not given.
7. **Every session is launched with its account's folder.** A role session and a headless session with no role get `CLAUDE_CONFIG_DIR` among the named variables of their environment. A Claude Code pane gets it in its command, after the login profile ran, because a profile's own export replaces a value of the pane's environment (probed, *Grounding*). A shell pane gets it in its environment, so a `claude` the person types there takes it unless their profile sets its own. Under System default a pane gets nothing, and a role session gets the `CLAUDE_CONFIG_DIR` the person's login shell holds, where it holds one, so a pane and a role session of one work item run under one login. That folder is the person's own config folder, and *Data & interfaces* says which folder each part of the daemon reads for it. The daemon gives a pane's launch the folder of the pane's account in the start `daemon.ts#startSession` builds (`PaneStart`), since the command and what the pane carries of the owl chain are both made from that start. Where a pane carries the owl chain (issue #181), the folder stands in the same command, in front of `claude`, and the bundle, the head and the pane's one settings file follow as that work gives them. Nothing of the bundle is written into an account's folder. The roles of a pane's chain are subagents of the pane's session, so they run under the pane's account, and no setting of this work reaches them apart from it.
8. **Each session says which account it runs under, and each ledger entry names it.** A pane and a headless session carry the id of the account they were launched with. A ledger entry carries the account's id and its name as they stood when the stage started. An entry of the broad gate, which runs a command and no agent, names no account. Through an adapter that does not declare `accounts`, a headless session is given no folder and runs under the agent's default login whatever setting is nearest. Such a session is launched under none, as a pane of a kind that takes no account is: it carries no account's id, its ledger entry names none, and the limit values it hands over are kept as System default's, whose login they are.
9. **A person changes the account of a Claude Code pane that runs.** The daemon keeps the latest conversation id the pane's hook events carry. On the person's word it ends the pane's process, waits for its exit, and starts `claude --resume <id>` under the new account in the same work item, in the same pane: the pane keeps its id, its tab, what it printed and the clients that receive it, and its record takes a second process (phase 4's decision of `frame/questions.md` Q4, `trail/phases/phase-4.md`). The new process starts at the size the window last gave the pane. A pane that has sent no event has no conversation and starts anew. The new process is launched as a new pane of that work item would be at that moment, but for the account and the conversation, so it carries the owl chain where its folder is then on it, its settings file is the one a launch under the new account gives (scope item 14), and its command never holds `--continue` beside `--resume`. Before it starts, the daemon ends the watch of the old process's session log and drops what the old process's events left on the pane: its state, an interruption, and a log that went unread. The new process's events name the log that is watched next. The window says before the change that a turn under way is cut. The change is refused, with its reason, where the two accounts' folders do not hold the same `projects` folder, for a shell pane, a sign-in pane among them, and for a headless session. Two folders hold the same `projects` where the real paths of the two are one, and a folder that holds none matches no other. Under System default the folder is the person's own config folder, and while the lookup has given none the change is refused. The window offers the change only where it can succeed. For that the daemon sends with each account where it keeps its conversations (*Data & interfaces*, *The protocol*, `Account.conversations`), and the change's dialog lists an account only where that place is the pane's account's own and is not null. "Change Account…" stands in a pane's menu only where the dialog would list an account. So a handed folder that keeps its own conversations is never offered for a pane of another account, and neither is System default while the lookup has given no folder. The daemon sent the place when it last sent the accounts, so it can be old, and the daemon's own comparison at the request decides. A request can still arrive for a pane whose process has ended, for the account the pane already runs under, for an account the daemon does not keep, or for a pane that is closed while its process ends, and the daemon refuses each with its reason. Where the new process cannot start, the pane stays as an ended pane under the new account, prints the reason in its own output, and the request is answered with the error. Before the new process starts, the daemon makes the new account's missing links, as before any launch under it (scope item 4). A role session's stage ends under the account it began with, and the next stage launched for the work item takes the nearest setting as it then stands.
10. **The window sets and shows accounts.** An Accounts dialog lists the accounts with the default and each one's sign-in, adds one by either way, renames one, signs in, names the default and removes one. Phase 2 built the list with each account's name, its folder and the default, the adding of a handed folder, the rename and the default. Phase 3 adds each row's sign-in, the adding with no folder, "Sign in" and the removal, because an account carries whether a login stands only once phase 3 builds sign-in. System default keeps its name, and an empty name is refused. The window offers a choice of account only where the daemon keeps an account besides System default: with System default alone there is nothing to choose, so the repository's settings, the work item's menu and view, the menus of a new session and the names on a line and a tab show nothing of accounts. The Accounts dialog is reached in both states. Its button in the sidebar's foot shows whenever the daemon sends accounts, and the app menu's "Accounts…" stands always, because that menu is built once at the app's start, and it opens nothing against a daemon that sends no accounts. A repository's settings and a work item's menu set that repository's and that work item's account. A new pane and a new headless session can be started under an account of their own. A line of the inbox names the account where the work item's account, or a running session's, differs from the one its repository gives. A work item's view names the work item's account, and a pane's tab names the pane's account where it differs from the work item's.
11. **A person removes an account.** The removal is refused while a live pane, a working headless session or a refresh of its usage runs under it, and for System default. For a folder Owlery made, the daemon runs `claude auth logout` with that folder and then removes the folder. Where the logout fails, the removal is refused with the CLI's sentence and the folder stays, because a folder removed then would leave a login the CLI may still hold outside it, such as a Keychain entry. The daemon looks again for a session under the account after the logout, since one can start while it runs. A handed folder is left as it is. Every setting that named the account is cleared, so its nearest setting above takes over, and the dialog names each repository and work item whose setting is cleared before the person confirms.
12. **Accounts are a feature an adapter declares.** The daemon passes a folder only to an adapter whose feature list names `accounts`, and a pane's kind says whether its panes take one. The window shows an account's controls by those two facts and never by a vendor's name. The fake adapter declares the feature and reports the folder each session was given.
13. **A person refreshes the usage of an account that runs no session, by a press.** Each account's row in the Accounts dialog shows the usage-limit values the CLI last handed over for that account, with the time they arrived, and no number where none arrived. Where no pane of the account is alive and no headless session of it works, the row has a control "Refresh usage". On the press the daemon starts one headless session under that account through the adapter: the account's folder, the cleared environment, no tool, no role, one turn, no transcript, a prompt that asks for nothing, in an empty folder of the daemon's own so that no repository's file is read. The daemon keeps what the session's stream says of the account's limits, stops the session at its result or after one minute, and the row shows the values or says that the CLI handed over none. The control says before the press that a refresh starts one short Claude Code session under the account and uses a little of its limit. Nothing starts a refresh but the press: no timer, no opening of the dialog, no start of the daemon. Owlery reads no token and calls no address of Anthropic's itself. The same reading keeps the values every other headless session of the account hands over, so an account that runs role sessions shows them with no refresh. The refresh's own reported cost is shown with its result and is no ledger entry, because an entry names a work item. A refresh is no headless session of a work item either, so the daemon keeps its state beside the account: running since a time, or how the last one ended. System default has a row too and is refreshed as any account is, in a session that is given no folder, and its values are kept beside the accounts. The session holds no tool, so a call it asks for is refused and not left to wait out the minute. A request is refused, with its reason, where a refresh of the account runs already, where the daemon keeps no such account, and through an adapter that does not declare the feature, beside the refusal while something runs under the account. The daemon's close stops a refresh that runs. Through an adapter that declares `limit-refresh` and not `accounts`, a refresh of any account but System default is refused with its reason, because its session would run under the default login and its values would be kept as another account's.
14. **What the daemon reads of a person's Claude Code folder for a pane, it reads in the folder of the pane's account.** `claude-plugins.ts#readPlugins` reads which plugins a pane's session enables from `settings.json` and `plugins/installed_plugins.json` of the config folder it is given. Its two callers in the app give it none at `41e2cc6`, so both read the folder the daemon's own environment names (*Grounding*). This work has each caller name the folder:
    - **At a pane's launch**, `pane-chain.ts#carriedIn` reads the folder of the pane's account, which the pane's start names.
    - **For the `chain` a repository sends the window**, `DaemonOptions.pluginEnabled` reads the folder of the repository's account: the account a new pane of the repository takes where neither the pane nor its work item is set to one. The daemon reads a repository's `chain` again where that account changes.
    - **Under System default** both read the person's own config folder, as *Data & interfaces* gives it, and no longer the daemon's environment. In a folder Owlery made, both names are links, so the reading is the person's own. In a handed folder it is that folder's.
    - **The pane's own settings file** follows the same reading. Under the choice of the owl chain, a pane whose account's folder enables the AgenticSeal plugin is launched with `claude-pane-<pane id>.json` in place of the shared settings file, written from that folder's `enabledPlugins`. A pane whose account's folder enables no such plugin takes the shared file. The file's name follows the pane's id and not the account. So where phase 4 starts a pane again under another account with the same id, that launch writes the file over from the new account's reading, or names the shared file, and the command never names a file written from the old account's reading.
    - **The window asks by the repository's `chain`, and the daemon launches by the pane's account.** A pane whose account is another than its repository's is therefore asked nothing. It is launched by its own account's reading and the answer the repository keeps, and where that reading finds the plugin and no answer is kept, it carries nothing of the bundle. #181 has the same for a worktree whose folder reads otherwise than the main checkout (`docs/architecture.md` *What each session loads*).
    - The repository's kept choice between the two chains is one for every account. The item changes the two callers and what gives them a folder, and adds no reader of its own.
