**Q4 is settled by the work, as its default reads.** `planRecords` now keeps two lists. `written` holds every file the commit writes, the moved workflow included. `created` holds only the files the setup creates where nothing stands. The arms `occupied`, `notFolders` and `otherLetters` read `created`. The moved workflow stays among `keptFiles`, so git's status and the hash of its text are both compared with the commit's. The arm that refuses a plan with no checked-out branch reads `written`, so a move with no branch is blocked as a setup is. Grounds: `frame/design.md` *Scope* item 4, "every arm that blocks a plan today still blocks it, and the workflow is compared there as a kept file", and `frame/plan.md` *Technical context*. **`readRecordsPlace(folder, version?)` always returns `olderCheck`, null where no version is given.** The daemon passes `this.options.version`. `chain-command.ts` and `stage-records.ts` read only the broad gate, so they pass none and read no workflow. Because the key is always present, the exact-shape expectations already in the tree gained `olderCheck: null`. In `records-place.test.ts` those are the `toEqual` cases on `readRecordsPlace`. Grounds: `frame/design.md` *Data & interfaces*, where the field is optional only for a daemon of an earlier build.

**The daemon's plan always carries `unread`.** It is the list where the plan moves the check, and `[]` otherwise, as the protocol comment states. Each sentence is cut at `STATE_TEXT_CHARS` by `cutText`, the way `Daemon#sealAt` cuts a broken seal's sentence, because a reader's refusal quotes the refused line. A work item whose reading throws anything other than a `ChainStop` is left out and logged, the way `Daemon#sealAt` handles one. The frame names neither the cut nor the log. Both follow the seal reading that *Scope* item 6 says this reading copies.

**A failed move writes back the bytes the checkout held, not git's blob.** The plan has just found the checkout's file equal to the commit's, so those bytes are the commit's text as the checkout holds it. Writing them back leaves `git status` empty even where a filter or a line-end setting makes the checkout's bytes differ from the blob. Scenario F's case holds this.

**The stamp's formula did not change.** It hashes the head, the branch and the files. The head fixes the version the commit pins. The moved workflow's text fixes the version the move goes to. A plan for another version therefore gets another stamp, which scenario D's case asserts.
