# Design: 1795339001-worktree-setup, a new worktree gets its ignored files and runs a setup command (#97)

The ticket is issue #97, split from #59 on 2026-11-20. A new work item's worktree holds only what git tracks, so a person or the agent installs the dependencies and copies `.env` by hand for each one. The issue asks that a repository name the ignored files a new worktree gets from its main checkout and the command a new worktree runs, that the command runs in a pane the person can see with its result on the inbox line, that a failed command leaves the work item created and usable, and that a repository that names nothing gets its worktree as today. #59 keeps the ports of each worktree and the setup again at a restore.

This frame decides the place: `.worktreeinclude` and `.worktreesetup` at the top of the repository's main checkout. The first is the file Claude Code, Codex, Conductor, Orca and Paseo already read for the same purpose. The second is a file of its own beside it, outside any place where Owlery keeps its records or its configuration, so #40's choice of that place moves neither (`frame/plan.md` *Overlap with the release*).

## Scope

**In.** Items 1 to 6 are the daemon's, items 7 to 10 the window's, item 11 Owlery's own repository, and item 12 the policy documents' text. The exact shapes are in *Data & interfaces*.

1. **Two files at the top of the repository's main checkout name the setup.** `.worktreeinclude` holds patterns in the syntax of `.gitignore`. `.worktreesetup` holds the command, as shell text. The daemon reads both from the repository's folder, `Repository.folder`, whether git tracks them or not, at each creation, each plan and each run again. A `.worktreesetup` that holds only white space names no command. A repository that holds neither file gets its worktree as today: nothing is copied, no setup pane starts, and the work item's setup record is null.
2. **The daemon copies the ignored paths the patterns match from the main checkout into the new worktree, after `git worktree add` and before any pane starts.** The paths are those that `git ls-files --others --ignored --exclude-from=<main checkout>/.worktreeinclude --directory -z`, run in the main checkout, lists and `git check-ignore --stdin -z`, run there, prints. A folder is one path and is copied whole. A link is copied as a link. The folders the worktree lacks above a path are made first. A path is written beside its place, in a folder of its own that git does not list, under `.owlery-copy-…/copy/<name>`, and moved into its place whole, so nothing stands at the place until the copy is whole, and a command in the person's pane neither lists nor adds the copy before then. A staging folder a stopped daemon left is removed by a later setup where the list names a path in that folder, once nothing writes in it: its `copy/` goes first and its `.gitignore` after, so while a copy the stopped daemon started still writes there, the folder stays with its `.gitignore` and git lists none of it. A path that already stands in the worktree is not written over and is not listed, and one that came to stand there during the copy, as by a command in the person's pane, is left as it is and listed as not copied. A path whose folder a link of the worktree leads out of the worktree is not written: it is listed as not copied. A path that fails to copy is recorded with its error, nothing of it is left in the worktree, the folders made for it among them, so a run again finds it missing, and the other paths and the command go on. The one exception is its staging folder. Where the copy in it holds a folder the source kept read-only, Owlery gives the copy's folders their owner's write bit and removes it. Where it still cannot be removed, as where a file of it carries the system flag `uchg`, the folder stays beside the path with its `.gitignore`, git ignores it, and the path's reason names it. A link at the staging name is left as it is and never followed. A failure of either git command is recorded as the copy's failure and refuses nothing.
3. **The setup record is the daemon's state, kept with its work item.** `WorkItem.setup` holds what was copied, what was not and why, the command, the pane it runs in, the state, the exit code, why it failed, and the times. The store keeps it in `repositories.json`. A stored work item without the field is read with `setup: null`, and every stored setup is read naming no pane, since the next daemon counts its pane ids from 1 again and the old id would name another pane.
4. **The command runs in a pane of the work item, through the person's login shell.** Where `.worktreesetup` names a command and it is the command the creation carries (item 7), the daemon starts a pane in the worktree whose process is `$SHELL -l -i -c <command>`, with the environment a terminal pane gets. The pane is of the kind `shell`, the record names its id, and the creating client receives its output as it receives the pane it asked for. It starts before the pane the creation names, and the creation's answer still carries the pane the creation names.
5. **The record's state follows the pane's process and the daemon's own acts.** It is `running` from the pane's start. At the process's exit it is `succeeded` where the code is 0, no copy failed, no signal ended the process and the daemon did not end the pane, and `failed` otherwise. Where `.worktreesetup` holds another command than the one the creation or the run again carries, or one where it carries none, or none where it carries one, no pane starts and the setup is `failed` at once, by its copy, with the sentence ".worktreesetup changed after the setup was shown, so no command ran."; it records the command the file holds. A process a signal ended is `failed` with the sentence "The setup command was ended by <signal>.", and a pane the daemon ended keeps its own sentence below, which comes first. A pane the daemon ended, at a `close`, an archive, a repository's removal or a delete, makes the setup `failed` with the sentence "The setup pane ended before its command did." A record that reads `running` when the store is read at the daemon's start is `failed` with "The daemon stopped before the setup command ended.", and every record is read with `paneId` null, so a pane the next daemon starts under the same id is no setup pane. Where only `.worktreeinclude` stands, the state is `succeeded` or `failed` at once, by the copy. A failed setup changes nothing else of the work item: its panes, its archive, its delete and its headless sessions are served as before.
6. **A person runs the setup again.** The client message `runSetup` names the work item, the pane's size and the command the window showed, `setupCommand`. The daemon refuses it for a work item it does not list, an archived one, one being deleted, one whose setup runs, and one whose repository holds neither file now. Otherwise it copies what is missing, takes the earlier setup pane off the lists, starts a new setup pane where a command stands and it is `setupCommand`, whole, records the new setup in place of the old, and answers `started` with the new pane, or `done` where no pane started. Where the file holds another command than `setupCommand`, no command runs, the record holds the command the file holds and the sentence of item 5, and the section then names that command for the next press.
7. **The "New work item" form names the command before the person creates the work item, and the creation runs that command and no other.** The `workItemPlan` answer carries the command `.worktreesetup` holds and whether `.worktreeinclude` stands, and the form says both under the folder. The form creates nothing while it holds no plan's answer for the folder's text, as after a key in the field, and says so. The creation carries the command the form showed, `setupCommand`, null where the plan was refused, and the daemon runs the command only where the file still holds it (item 5).
8. **The inbox line says "Setting up" while the setup runs and "Setup failed" where it failed.** The words stand in the line's second row. They change neither the line's state nor its group, and they raise no notification.
9. **The preview and the work item's view hold a "Setup" section.** It says how the command ended, or that it runs and for how long, names the command, lists the copied paths and each path that was not copied with why, and in the view offers "Run setup again" while the setup does not run. The button runs the command the section names: it carries that command, and its tooltip says that where the file holds another now, none runs and the section names the new one.
10. **The tab of the pane the setup record names reads "Setup".**
11. **Owlery's own repository gets `.worktreesetup` holding `pnpm install`.** It installs the dependencies and rebuilds node-pty for Electron in a new worktree of Owlery's (*Grounding*, the install's four seconds). Owlery's repository needs no ignored file but `node_modules/`, which the install makes, so it gets no `.worktreeinclude`.
12. **The rules of *Rule changes* are written into the policy documents at the settle, and `docs/design.md` with its Korean edition changes in this pull request.** This work's subject is the code, so it states the rules of *Rule changes* for the settle. `docs/design.md` *Principles* asks that a change to the window change that document in the same pull request, so Register's cell "Edges and rules" in *The themes* and the row "A row of a list of records" of *Components and their states* name the paths the setup copied or could not copy and the form of a path not copied, and Night watch light and Desk light raise `--state-failed` to the floor on a selected line, in both editions (`frame/plan.md` *Judgments of the run*, the row of the merge; review round 6).

**Out.**

- Ports of each worktree, the setup again when a work item is restored, and the variables a command receives, such as its ports: #59.
- Reading another tool's schema, such as `orca.yaml`, `conductor.json` or `.conductor/settings.toml`. `.worktreeinclude` is the one file another tool reads for the same purpose, and another product's schema changes on that product's schedule (`etcs/research/competitors/conductor.md` line 157: Conductor moved its setup three times).
- An archive or teardown script. The issue asks for none.
- A copy through anything but `cp -c` and Node's copy, such as a copy-on-write clone by another means or a link (`frame/plan.md` *Alternatives considered*, the row on linking). The clone through `cp -c` is in *Scope* item 2's copy, with Node's copy where it fails.
- Holding the pane the creation names until the setup ends (`frame/plan.md` *Alternatives considered*, the row "Hold the person's pane").
- A confirmation before a repository's command runs, beyond the form's naming it and the creation's running only that command. Q1's answer is that naming it at the form is the consent (`frame/plan.md` *Judgments of the run*).
- A notification when a setup fails, a mark on the sidebar's line, and a count of setups in the summary of what changed. The issue names the inbox line alone.
- The README's sentence on where the files are kept. #59's done criteria name it with the ports.

## Data & interfaces

**The two files.** Both stand at the top of the main checkout, `Repository.folder`. `.worktreeinclude` is read by git alone, through `--exclude-from`, so its syntax is `.gitignore`'s, negation and `**` among it. `.worktreesetup` is read whole as UTF-8 text. Its text, where it holds more than white space, is the command. It is passed whole as one argument after `-c`, so the person's shell reads it as it reads a line typed in a pane, several lines and comments among it.

**A new module, `apps/desktop/src/daemon/worktree-setup.ts`.**

- `readSetup(repo: string): Promise<{ include: boolean; command: string | null }>`: whether `.worktreeinclude` stands as a file, and the command `.worktreesetup` names.
- `copyIncluded(repo: string, worktree: string, clone = "/bin/cp"): Promise<{ copied: string[]; copiedCount: number; failed: { path: string; why: string }[]; failure: string | null }>`: the copy of *Scope* item 2. For each path it first checks that the nearest folder of the path's place in the worktree that stands lies inside the worktree once each link is read, and lists the path as not copied with `LEADS_OUT` where it does not. A path that stands in the worktree is skipped. It makes the folders the path lacks, then runs `clone` as `cp -c -R -P <source> <stage>`, one process per path, a folder's source given without its trailing slash, where `<stage>` is `<staging>/copy/<name>`, with `<staging>` a folder `.owlery-copy-<six letters or digits>` it makes beside the place and writes a `.gitignore` of `*` in, so git lists nothing in it. `cp -c` clones each file on APFS and copies the bytes itself where it cannot clone, as on a volume that is not APFS or across volumes, where it exits 0; Node's copy runs only where that process exits with a code other than 0 or cannot start, as where a file of the path cannot be read. Then it removes what the process left at the stage and copies the path there with `fs.promises.cp(source, stage, { recursive: true, verbatimSymlinks: true, force: false, errorOnExist: false })`. It then moves the stage into the place with no write over what stands there: a folder by `rename`, a link by making it again, any other file by a hard link or, on a volume without hard links, such as exFAT, where the link is refused with `ENOTSUP`, `EXDEV` or `EPERM`, by `copyFile` with `COPYFILE_EXCL`, and where something stands at the place it throws `APPEARED`. After each copy, failed or not, `removeStaging` removes the staging folder: its `copy/` first, through `removeCopy`, and the folder after, through `rm`. Where `rm` refuses the removal of the copy with `EACCES` or `EPERM`, `removeCopy` gives the copy's folders their owner's read, write and search bits, never following a link, and removes it again. Where the `copy/` still cannot be removed, the folder stays with its `.gitignore`. The error of a path that failed names it, and nothing names it after a copy that succeeded. Before it checks whether a path stands, it runs `removeLeftCopies` once in each folder a listed path lies in, which picks real folders only, by `readdir` with `withFileTypes`, so a link of the staging folder's name is left as it is, and removes, with all it holds, a folder of that name that is empty or holds a `.gitignore` reading `*` as the copy writes it, through `removeStaging`. Where a path fails, the folders made for it are removed too, each where nothing else came to stand in it. `failure` is the failure of either git command, and null otherwise. `copied` and `failed` hold 500 entries at most, as a loss's lists do (`worktrees.ts#LOSS_LISTED`), and `copiedCount` says how many paths were copied in all.
- `beginSetup(repo: string, worktree: string, now: () => number, shown: string | null): Promise<WorktreeSetup | null>`: reads the two files, copies where `.worktreeinclude` stands, and gives the setup, null where neither file stands. `shown` is the command the client showed the person, whole. Where the command the file holds is `shown`, the setup is `running` and names no pane yet where a command stands, and has ended by the copy where none does. Where it is another, the setup has ended by the copy, `failed` with `COMMAND_CHANGED`, and holds the command the file holds. A `.worktreesetup` that cannot be read is a setup that failed, with nothing copied.

**The protocol, `apps/desktop/src/shared/protocol.ts`.**

```ts
/** What the daemon did to set up a work item's worktree, as the repository's two files named it when the setup began. */
export interface WorktreeSetup {
  /** The ignored paths copied from the main checkout, a folder as one path, 500 at most. */
  copied: string[];
  copiedCount: number;
  /** The paths that could not be copied, each with the error, 500 at most. */
  failedCopies: { path: string; why: string }[];
  /** The command `.worktreesetup` held, or null where it named none. */
  command: string | null;
  /** The pane the command runs in, a pane of the kind `shell`, or null where no command stands, where its pane could not start, where `.worktreesetup` changed after it was shown, and once the daemon that started the pane has stopped, since the next daemon gives its id to another pane. */
  paneId: number | null;
  state: "running" | "succeeded" | "failed";
  /** The code the command's process exited with, or null while it runs and where no process exited. A process a signal ended reports 0, and `failure` names the signal. */
  exitCode: number | null;
  /** Why the setup failed where the exit code does not say it, as a sentence the window shows as it is: the pane ended before its command did, a signal ended the command, the daemon stopped, `.worktreesetup` changed after the setup was shown so no command ran, a git command failed, or the file or the shell could not be read or started. Null otherwise. */
  failure: string | null;
  startedAt: number;
  endedAt: number | null;
}
```
