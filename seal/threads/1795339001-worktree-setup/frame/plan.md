# Implementation Plan: 1795339001-worktree-setup, a new worktree gets its ignored files and runs a setup command (#97)

## Technical context

The tree as read at `6c63736`.

- **The creation.** `apps/desktop/src/daemon/worktrees.ts#createWorktree` (lines 521 to 536) cuts the branch and runs `git worktree add`, and returns the place. The `createWorkItem` case of `apps/desktop/src/daemon/daemon.ts` (lines 352 to 374) stores the work item, seeds its counts, starts the one pane the message names with `startSession` and answers `workItemCreated`, inside the `changing` chain that serialises creations, removals and deletes. The copy of *Scope* item 2 and the setup pane of item 4 go between `createWorktree` and `startSession`, in that chain, so a creation's answer waits for the copy and not for the command.
- **The panes.** `Daemon#startSession` (lines 1003 to 1049) spawns a pane through `DaemonOptions.commandFor`, keeps its output, and at its exit writes the exit line and broadcasts, but only while the pane is still listed. The `close` case (lines 686 to 696) takes the pane off the lists before it kills the process. So the setup's end is read in the exit listener itself, by the record's `paneId`, before the check of whether the pane is listed, and an end the daemon caused is marked before the kill. The archive, the repository's removal and the delete end panes through `Daemon#endSessions`, which the record treats as the `close`.
- **The commands.** `apps/desktop/src/daemon/hooks.ts#paneCommands` and `#claudePaneCommand` (lines 87 to 104) give each pane kind its command. `setupPaneCommand` joins them and has the same form as the Claude Code pane's, `$SHELL -l -i -c`, so the setup sees the PATH the person's profile sets. The probe of `frame/design.md` *Grounding* ran that form through node-pty and read the exit codes 0, 3, 127, and 1 for a kill.
- **The store and the look.** `apps/desktop/src/daemon/repositories.ts#StoredWorkItem` and `#isStoredWorkItem` (lines 12 to 27 and 61 to 76) refuse a work item whose fields are not their own, so the new field is optional on read. `apps/desktop/src/daemon/last-look.ts#isWorkItem` and `#lookOf` (lines 41 to 104) list the fields a look may lack, and #119 renames that list `CameLater` and adds two fields to it.
- **The window.** The inbox line is drawn in `apps/desktop/src/renderer/list.ts` lines 136 to 140 from `apps/desktop/src/renderer/view.ts#inboxLine`, `#lineMarks`, `#lineText` and `#lineBadge`. The preview and the view's right column draw `apps/desktop/src/renderer/shared.ts#detail` (lines 275 on; called at `list.ts` line 114 and `work-item-view.ts` line 731). A tab's label is `view.ts#tabLabel` (line 15). The form's plan is `view.ts#planLine` (line 1492), asked by `renderer.ts#askPlan` (line 1164).
- **The cases.** `apps/desktop/test/daemon.test.ts` creates work items in temporary repositories with a `commandFor` that runs `/bin/sh -c`, and pins a work item's fields in `WORK_ITEM_FIELDS` (line 25). Its repositories hold neither setup file, so its creation cases pin the "names nothing" path as they stand.

**Failure scenario of the chosen approach, six months on.** A repository whose `node_modules/` is a few gigabytes names it in `.worktreeinclude`. Node's copy writes the bytes, since cloning on write is not reached through Node on this Mac (*Grounding*), so each creation waits on the copy and each worktree holds a full copy on disk. The person sees a slow "New work item" and a disk that fills with worktrees. Q4 measures it, and the answer is a clone through `/bin/cp -c` or a command in `.worktreesetup` in place of the pattern. A second scenario: Claude Code reads `.worktreeinclude` by another rule than git's ignored-and-matched one, so a repository's file copies other paths in Owlery than in Claude Code (Q3).

## Operational impact

- No new dependency, no environment variable and no migration. `repositories.json` gains an optional field, and a file written by an earlier build is read with it null. A daemon of this build sends `setup` and the plan's two fields, and a window of an earlier build ignores them.
- A creation in a repository with a `.worktreeinclude` waits for the copy, about a second for 177 MB, and each copied path takes its own disk (Q4).
- A repository's `.worktreesetup` runs in the person's login shell when a work item is created, with the person's environment and rights. The form names the command before the creation (Q1).
- Owlery's own repository gains `.worktreesetup`, so a work item of Owlery's created by Owlery runs `pnpm install`, about four seconds with a warm store.
- This pull request moves no version: `apps/desktop/package.json` is at 0.0.2 already.
