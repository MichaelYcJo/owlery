# Changelog: a new worktree gets its ignored files and runs a setup command

Issue #97. A new work item's worktree held only what git tracks. It had no `node_modules`, no `.env` and no other ignored file its repository needs to run, so a person or the agent installed the dependencies and copied the secrets by hand for each one.

- **A repository names its setup in two files at the top of its main checkout.** `.worktreeinclude` holds patterns in the syntax of `.gitignore`, the file Claude Code, Codex, Conductor and Orca read for the same purpose. `.worktreesetup` holds a command, as shell text. Owlery reads both from the main checkout, whether git tracks them or not, and writes neither.
- **A new worktree gets a copy of each ignored path the patterns match.** Git decides what matches: a path is copied where a pattern matches it and git ignores it, so a tracked file, and an untracked file git does not ignore, are never copied. A folder is copied whole, a link stays a link, and a path that already stands in the worktree is not written over. Each path is copied beside its place, in a folder `.owlery-copy-…` that git lists nothing of, and moved into its place whole, so a path that comes to stand in the worktree meanwhile, as by a command in one of your panes, is left as it is, and a `git add -A` in a pane adds nothing of the copy. Such a folder that Owlery's background process left when it stopped during a copy is removed at a setup of that worktree that names a path in the same folder, once nothing writes in it. A path whose folder a link in the worktree leads out of it, such as a link the worktree's branch tracks, is not copied, and nothing is written through the link. A path that cannot be copied is listed with why, nothing of it is left in the worktree, and the others go on. Where the folder its copy was written in cannot be removed, even once Owlery has given back the write bit that a read-only folder of the source took from the copy, that folder stays, git lists nothing of it, and the path's why names it.
- **The copy clones each path on APFS.** Owlery copies with `/bin/cp -c`, which on APFS makes each file share its blocks with the main checkout's until one of them changes. On a 1 GB folder of 32,000 files it took 5.2 seconds and 12 MB of disk, against 14.3 seconds and 918 MB for a copy of the bytes. Where no clone can be made, as on a volume that is not APFS or across volumes, the bytes are copied.
- **The command runs in a pane of the work item, through your login shell.** The pane starts before the pane you asked for, in the new worktree, with your environment, so the command finds what your profile puts on the PATH. Its tab reads "Setup". It runs with your rights and asks nothing first: the "New work item" form names the command under the folder before you press Create, creates nothing until it names it, and the pane shows it run. The command runs only where `.worktreesetup` still holds the text the form named. Where the file changed in the meantime, no command runs, and the work item's line says "Setup failed".
- **The work item's line says "Setting up" while the command runs, and "Setup failed" where it failed.** A setup fails where a path could not be copied, where `.worktreesetup` changed after the command was shown, where the command ended with a code other than 0 or by a signal, and where its pane ended before the command did, as when you closed it or Owlery's background process stopped. A setup that succeeded leaves the line as it is. The words change neither the line's state nor its group, and raise no notification.
- **A failed setup leaves the work item created and usable.** Its panes, its archive and its delete work as before.
- **The preview and the work item's view hold a "Setup" section.** It says how the command ended, or how long it has run, names the command, lists the copied paths, and lists each path that was not copied with why. In the view it offers "Run setup again" once the command has ended, which copies what is missing and runs the command the section names in a new pane. Where `.worktreesetup` holds another command by then, none runs, and the section names the new one, which the next press runs.
- **A repository that names neither file gets its worktree as before.** Nothing is copied and no setup pane starts.
- **Owlery's own repository names `pnpm install` in its `.worktreesetup`,** so a new worktree of Owlery's installs its dependencies and rebuilds node-pty for Electron.
- **For a client of the daemon:** each work item carries `setup`, the record of what its setup copied, which pane runs its command, its state, its exit code, why it failed and when, or null where its repository named none. Its pane is null once the daemon that started the pane has stopped. A new message `runSetup`, with the work item and the pane's size, runs the setup again and is answered with `started`, `done` or `error`. `workItemPlan` carries `setupCommand` and `includes`. `createWorkItem` and `runSetup` carry `setupCommand`, the command the client showed the person, and the daemon runs no command that is not that text.
