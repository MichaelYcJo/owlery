## Not done

The exit line a pane prints at its end, `[process exited with code 0]`, does not name the signal that ended its process. The setup's record and its "Setup" section name it, and the line is every pane's, which this work item does not change.

A copy moves into its place by `rename` where it is a folder, and `rename` takes the place of an empty folder. A folder that a command in the person's pane makes between the copy's check of the place and the move, and leaves empty, is replaced by the copied one. Nothing the person wrote is lost there, and Node offers no move that refuses an empty folder. A link is moved by making it again. A file is moved by a hard link, or, where the worktree's volume makes no hard link, by `copyFile` with `COPYFILE_EXCL`. Each of these refuses whatever stands.

A staging folder that a stopped daemon left, `.owlery-copy-` and six letters or digits, is removed at a copy into that worktree only in the folder of a path the copy lists, only where it is empty or holds the `.gitignore` of `*` the copy writes, and only once nothing writes in it. Nothing ends a `cp` that the stopped daemon started, so it goes on writing in the folder's `copy/` until its copy is whole. The removal takes `copy/` before the `.gitignore`, so a removal that such a `cp` defeats leaves the folder with its `.gitignore`, and a copy after the `cp` has ended removes it. One left in a folder no listed path stands in, as after the repository's `.worktreeinclude` changed, stays and holds its disk. Git still lists nothing of it, by its `.gitignore`. Finding it anywhere would mean reading every folder of the worktree, `node_modules` among them, at each setup, and removing by name in folders the copy does not write.

Where the removal of a failed copy's staging folder is refused for permissions, the copy's folders get their owner's write bit and the removal runs again. Where it is refused again, as for a file that the system flag `uchg` holds, the folder stays with its `.gitignore` and the path's why names it. A later copy that lists a path in that folder tries again and drops the error. Where the path fails again, its own staging folder stays too, so each "Run setup again" of that path adds one. A copy that succeeded, whose staging folder holds such a file, leaves that folder as well, and no record names it. Git lists none of them. Carried to #144.
