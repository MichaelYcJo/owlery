## Not done

The exit line a pane prints at its end, `[process exited with code 0]`, does not name the signal that ended its process. The setup's record and its "Setup" section name it, and the line is every pane's, which this work item does not change.

A copy moves into its place by `rename` where it is a folder, and `rename` takes the place of an empty folder. A folder that a command in the person's pane makes between the copy's check of the place and the move, and leaves empty, is replaced by the copied one. Nothing the person wrote is lost there, and Node offers no move that refuses an empty folder. A link is moved by making it again. A file is moved by a hard link, or, where the worktree's volume makes no hard link, by `copyFile` with `COPYFILE_EXCL`. Each of these refuses whatever stands.

A staging folder that a stopped daemon left, `.owlery-copy-` and six letters or digits, is removed at the next copy into that worktree only in the folder of a path the copy lists, and only where it is empty or holds the `.gitignore` of `*` the copy writes. One left in a folder no listed path stands in, as after the repository's `.worktreeinclude` changed, stays and holds its disk. Git still lists nothing of it, by its `.gitignore`. Finding it anywhere would mean reading every folder of the worktree, `node_modules` among them, at each setup, and removing by name in folders the copy does not write.

The window does not hold a second press of "Run setup again" before the daemon answers the first. Where the first press started a pane, the second `runSetup` is refused with "The setup of work item <id> is still running.", which the status line says. Where the first ran no command, because `.worktreesetup` had changed, the second carries the same command, copies what is missing and runs nothing again, and the inbox that follows the first answer hides the button. A guard would need the window to keep the request until its answer, as the "Ask" field does, for a case only a double press reaches.
