# Changelog: a work item starts at the remote's commit

Issue #96. A work item that started from a remote's branch, such as `origin/main`, started from wherever your clone last fetched that branch. In a clone that had not fetched for days, the new branch was days behind before its first commit.

- **Owlery now fetches the one branch before it creates the work item.** A work item that starts from `origin/main` starts at the commit `origin` holds for `main` at that moment. This replaces the bullet "Owlery does not fetch" of issue #85's entry in this release.
- **One fetch asks one remote for one branch.** It moves your clone's copy of that branch, `refs/remotes/origin/main`, and nothing else: no local branch, no other branch of the remote, no tag, and no file of your checkout. A branch pushed to the remote since your last fetch is still not in the menu, because Owlery fetches only a branch the clone already lists.
- **A work item that starts from a local branch fetches nothing.** One that starts from your local `main` starts where `main` stands.
- **The form says what the work item starts from.** Under the menu "Starts from" it reads "Fetching origin/main…" while it asks, and then "Fetched: origin/main is at 1a2b3c4." The form asks once for each remote's branch the menu holds, each time it opens. Typing a name asks nothing.
- **Where the fetch fails, the form says so and you can still create.** The line then reads "origin/main could not be fetched (…). It starts as last fetched, at 1a2b3c4, which the clone has held for 3 days." The brackets hold git's own first line, or that the remote did not answer. The age is how long your clone has held that commit, which git records. It is not the time of your last fetch, which git does not record in a place every worktree shares.
- **A remote gets ten seconds.** A fetch that has not ended by then is given up, and the work item starts as last fetched. Owlery's background process, the daemon, has no terminal, so a remote that needs you to type a password or a passphrase fails in the same way.
- **You do not have to wait for the fetch.** "Create" stays on while the form fetches, and the work item is made once that fetch ends. Where it failed and the form could say so only after you pressed "Create", the status line at the foot of the sidebar says the same sentence.
- **A work item created shortly after the form's fetch starts where the form said.** The daemon uses a fetch that ended less than a minute ago and asks the remote again otherwise.
- **After an update, the form shows no line under "Starts from" until Owlery's daemon restarts.** A daemon started by the build before this one answers no fetch. A work item created against it starts as last fetched, as before.
- **For a client of the daemon:** a new message `fetchBase`, with `repo` and `base`, is answered with `baseFetched`, which carries `base`, `commit`, `fetch` (`none`, `fetched` or `kept`), `failure` and `since`. A request the daemon refuses is answered with `error` under the request's `requestId`. `createWorkItem` now fetches a remote's branch before it cuts the work item.
