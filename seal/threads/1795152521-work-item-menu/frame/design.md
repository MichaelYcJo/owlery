## Scope

In scope, as numbered items. A **running session** of a work item is a pane of it whose process is alive, or a headless session of it in the state `working`.

**The repository as a unit**

1. **The store.** The daemon keeps repositories, and each work item inside one, in a new file `repositories.json` in the run directory, written whole at each change as `work-items.json` is at `95decb6`. A stored repository holds its id, its folder (the top-level folder of the repository's main checkout, as item 3 reads it), `name` (the name a person gave it, or null), `icon` (or null), `defaultBase` (or null), `hidden`, `addedAt`, its groups, each an id and a name, and its work items. A stored work item holds the fields of `95decb6` without `repo`, and `pinned`, `muted`, `groupId` (or null) and `archivedAt` (or null). A work item's id is unique over the whole store, and so is a repository's and a group's. No id is given twice, to a work item, a repository or a group, though the one that bore it was removed: the file holds, beside the repositories, the next id of each of the three kinds, and each count only rises. The file is therefore an object that holds the three counts and the list of repositories. A file that holds the list alone, the shape phase 1's build wrote and no release shipped, is read with each count one past the highest id of its kind in the list, and the start from `work-items.json` sets the counts the same way. Where `repositories.json` does not exist and `work-items.json` holds work items, the store starts from those work items. Each work item's `repo` is read as item 3 reads a folder's repository, so a `repo` that is a linked worktree's folder gives the main checkout it belongs to, and where git cannot read the `repo`, as where the folder is gone, the `repo` stands as the file holds it. The store then holds one repository for each distinct folder that reading gives, in the order of each one's first work item, with every work item under its own and every new field at its empty value. Two `repo` values that name one main checkout therefore start as one repository. `work-items.json` is read for that start alone and is never written again. A daemon of an earlier build writes an array over a file it cannot read as one (`work-items.ts`, the constructor and `add`), so the new shape takes a new file's name.
2. **The protocol.** `ready` and `inbox` carry `repositories`, every stored repository, the hidden among them. They carry `workItems`, the work items that are not archived, and `archived`, the archived ones. A `WorkItem` gains `repoId`, `pinned`, `muted`, `groupId` and `archivedAt`, and its `repoName` is the repository's `name` where one is set and the last part of its folder otherwise. Where a `ready` carries no `repositories`, the daemon is of an earlier build: the window's status line says "Owlery's background process is from an earlier build. End its sessions and start Owlery again.", the sidebar lists no repository, and the inbox lists the work items as before.
3. **Adding a repository.** A new client message adds the repository a folder is inside, with no work item. The repository of a folder is the top-level folder of its main checkout. Where the folder is inside the main checkout, a submodule's checkout and a checkout whose git directory stands apart among them, it is the folder `git rev-parse --show-toplevel` gives. Elsewhere it is the first worktree `git worktree list --porcelain` prints when it is run in the folder, and where that worktree holds no `.git` at its top, as for a linked worktree of a submodule, the folder is refused with "<folder> is a worktree of a repository whose main checkout git does not name". A folder inside a linked worktree, one of Owlery's own among them, therefore names the repository the worktree belongs to, the same one the main checkout's folder names, and never a repository of its own. An add, a creation and a plan all read a folder's repository this way. A folder outside any git repository is refused with the sentence a creation there gets, and a folder whose repository has a bare main checkout is refused with "<folder> belongs to a bare repository, which has no checkout to keep". The start from `work-items.json` reads each old `repo` the same way (item 1). A repository already stored is not added twice, and where it was hidden it is shown again. A creation in a folder whose repository is not stored adds it first, and a creation in a hidden repository shows it again. The sidebar holds no button that adds a repository: the `add-repository` button phase 1 built goes (`## Removes` row 8). A person adds a repository with no work item in the "New work item" form, through the checkbox "Register the repository only", with the id `work-item-register-only`, unchecked at each opening. While it is checked, the name, the menu "Starts from" and the kind of pane are disabled, the form shows no branch and no folder of a plan, and the form's button reads "Register". A press then sends the client message that adds a repository, with the folder of the form's field, and creates no work item, no branch and no worktree. At the daemon's answer the form closes and the repository stands in the sidebar, and a refusal's sentence is shown in the form, as a creation's is.
4. **The sidebar.** The sidebar lists every repository that is not hidden, in the order the store holds them, with its work items under it. A repository with no work item is listed. While a search is typed or a state is chosen in the filter, a repository none of whose work items is left is not listed, as at `95decb6`. Beside the button that folds it, a repository's row holds a "+" button, which opens the "New work item" form with that repository's folder in its field, and a "…" button, which opens the repository's menu (item 12). The "+" button at the sidebar's top, `new-work-item`, opens the form with the folder it last held, and is the one place a repository that is not listed is added from, with a work item or, by item 3's checkbox, without one.

**The menu, and a work item's**

5. **How a menu opens and closes.** A menu is drawn in the window, as an element with the role `menu` whose items have the role `menuitem`. It opens:
   - on `contextmenu` on a work item's line in the sidebar, on the inbox screen, on the history screen and on the screen of archived work items (item 18), and on a repository's row, which a press of the right button and a press with the Control key both raise;
   - on the key M alone, read by its place on the keyboard, or F10 with Shift: for the line or the row the keyboard is on, and otherwise, on the inbox screen, the history screen and the screen of archived work items, for the selected line. The key is not read in a field, in a terminal, while a dialog is open or while a menu is open;
   - on a click of a repository's "…" button.

   The keyboard goes to the menu's first item. The Down and Up arrows move through the items, Enter and Space press one, and Escape closes the menu and returns the keyboard to where it was. A press outside the menu closes it. A press inside the menu but on no item, such as its separator or its edge, leaves the menu open with the keyboard on the menu itself, so Escape and the arrows still work. While a menu is open the window reads none of its other keys (`view.ts#inboxKey`, `view.ts#commandKey`). The hints under a list's preview name the key.
6. **A work item's menu** holds, in this order: Rename; Open in Finder, then one item for each installed editor and each installed terminal (item 7); Copy path and Copy branch name; Pin or Unpin; Mute notifications or Unmute notifications; one item for each group it can move to and one to leave its group (item 22); Archive; Delete. The menu of an archived work item holds Restore, the items of item 7, the two copies and Delete.
7. **Open in.** The desktop app's main process holds a list of known apps, each with its name, its kind, editor or terminal, and the name of its bundle. An app is installed where its bundle stands in `/Applications`, `/Applications/Utilities`, `/System/Applications`, `/System/Applications/Utilities` or `Applications` under the person's home folder. The window asks the main process for the installed ones once at load. Open in Finder opens the folder with Electron's `shell.openPath`. Open in an app runs `open -a <the bundle's path> <the folder>` through `execFile`, with no shell. The main process opens only an app of its list, and a failure's sentence is shown in the window's status line. The folder is a work item's worktree or a repository's folder. The main process tells them by a `.git` at the folder's top and refuses any other path; a path where nothing stands is answered "<folder> is gone.".
8. **Copy.** The main process writes the text to the system's clipboard: a work item's worktree folder, its branch's name, or a repository's folder.
9. **Pin.** A pinned work item stands before the unpinned ones of its list, and the pinned keep their order among themselves. Its list is: in the sidebar, its group or the ungrouped work items of its repository; on the inbox screen, its state's group; on the history screen, the whole list. A pinned line carries a mark with the words "Pinned".
10. **Mute.** The window raises no notification for a session of a muted work item, nor for a session of an archived work item (`view.ts#notificationFor`). Its line shows its state as any line does, and carries a mark with the words "Notifications muted".
11. **Rename.** A dialog takes the new name. The daemon stores it as the work item's `title`, with the white space at its ends removed, and refuses an empty one with "Give the work item a name.". The dialog asks the daemon what a rename of the branch would give, as the name is typed, and shows the answer. The branch a rename gives is `owlery/<slug of the name>`, with `-2`, `-3` and so on appended while another local branch bears the name. The dialog's choice "Rename the branch too" is enabled only where all of these hold: the name leaves a slug; the work item's branch still exists; the branch the name gives is not the one the work item has; the branch has no upstream; and no remote of the clone holds a branch of its name. Otherwise the dialog says the first of them, in that order, that does not hold. A rename with the choice taken runs `git branch -m` in the repository, after the daemon read the same conditions again, and stores the new branch. Where a condition no longer holds or git refuses, nothing is changed, the name neither. The worktree's folder keeps its name.

**A repository's menu**

12. **A repository's menu** holds, in this order: Settings; Change icon; Show archived work items; New group; Open in Finder and the installed apps (item 7); Copy path; Hide from sidebar; Remove.
13. **Settings.** A dialog holds the name the sidebar shows and the base a new work item starts from. An empty name gives the repository the last part of its folder as its name. The base is chosen in a menu of the repository's bases, as the form's menu lists them, with a first choice "The repository's default branch" that stores null. A creation without a `base`, and a plan's `defaultBase`, use the stored base where the repository still lists it, and the default base `worktrees.ts#basesOf` reads otherwise.
14. **Icon.** A dialog takes one character, an emoji among them, or nothing. The sidebar shows it before the repository's name. More than one character is refused. `frame/questions.md` Q1 asks what an icon is, and this item is its default.
15. **Hide.** A hidden repository is not listed in the sidebar. Its work items stay on the inbox screen and the history screen, and their notifications arrive. While at least one repository is hidden, the sidebar shows a button under the repositories that says how many are, and opens a dialog that lists them, each with a "Show" button.
16. **Remove.** Removing a repository takes it and its work items, the archived among them, out of the store. A dialog names each work item the repository holds and each running session, and holds two checkboxes, both unchecked when it opens.
   - With neither checked, the removal runs no git and removes no file: the repository, each worktree's folder and each branch stay on disk, and the dialog says that Owlery will no longer list them.
   - "Also delete the work items' worktrees and local branches" is shown where the repository holds a work item. Checked, the dialog reads the loss of each work item (item 19) and names it under that work item, with the "Force delete" checkbox of item 19 where any of them would lose something. Before the first delete, the removal refuses where a work item's stamp is missing, where a session runs that the message does not name, and where an archive is ending the sessions of one of the work items, and then deletes nothing. The removal then deletes each work item as item 20 states, one after another, each delete ending that work item's sessions, and takes the repository out of the store only after every one is deleted. Where one delete is refused or fails, the removal stops there: the work items deleted before it are gone, the repository and the others stay, and the refusal sentence starts with the title of the work item whose delete was refused.
   - "Also move the repository's folder to the Trash" is enabled where the repository holds no work item or the first checkbox is checked: a linked worktree of a repository that moved to the Trash no longer works. Checked, the window asks the main process to move the folder to the macOS Trash with Electron's `shell.trashItem`, after the daemon answered that the repository is removed. The folder is moved whole and nothing in it is erased.

   The removal ends the running sessions as item 21 states. Where the repository holds a work item the message does not name, the daemon refuses with "A work item was added since you looked. Read it again." and removes nothing.

**Archive**

17. **Archive.** An archive sets `archivedAt` and changes nothing on disk. Where the work item has a running session, a dialog names each first, and the archive ends them (item 21). Where it has none, the archive runs at the menu's press. A pane the archive ended stays listed as an exited pane with its kept output, and a headless session it stopped is `failed` with the error "ended when the work item was archived". The daemon stops reading git for an archived work item, and refuses to start a pane or a headless session in one, with "work item <id> is archived, restore it first". It refuses the same, with the same sentence, while an archive waits for the work item's sessions to end, so no session starts after the archive ended the ones it named and the error above stays true. While a delete of the work item is in progress it refuses to start a pane or a headless session, with "work item <id> is being deleted".
18. **The archived list and restore.** "Show archived work items" opens a third copy of the `list-screen` template, which lists that repository's archived work items, the one archived last first, under a head that names the repository. A line there opens no view. Its menu is the archived one of item 6, and the preview's button reads "Restore". A restore sets `archivedAt` to null, and the daemon reads the work item's branch again at once. The work item is then listed where it was, with its exited panes and their output and its headless sessions' answers, for as long as the daemon that held them lives. That is what the daemon holds of a session's history at `95decb6`, and it is lost when the daemon exits, with or without an archive.

**Delete**

19. **What a delete would lose.** A new client message asks. The daemon answers with:
   - the local branch, where it exists;
   - the worktree's folder, where git lists a linked worktree there;
   - the commits that the branch or the worktree's `HEAD` holds and that no other local branch, no remote's branch as the clone holds it and no tag holds, the newest first, each by its short hash and its subject;
   - in the worktree, the paths of the tracked files with a change that is not committed, the paths of the untracked files, each file by its own path, and the ignored files and folders, a folder as one name, such as `node_modules/`;
   - `blocked`, the sentence why the delete cannot run, where another worktree has the branch checked out or the worktree is locked, and null otherwise;
   - `unreachable`, true where git reads nothing in the repository's folder;
   - a stamp, a string that differs wherever any of the above differs.

   Each list carries at most 500 entries and the count of all of them. **Something would be lost** where the loss names a commit, a tracked file with a change or an untracked file. The delete dialog shows all of the answer, and the running sessions, and says "Nothing on a remote is removed.". Where a list is cut it says how many more there are. Where something would be lost, the dialog holds the checkbox "Force delete", unchecked. Its "Delete" button is disabled until the answer has arrived, while `blocked` is a sentence, and while something would be lost and "Force delete" is not checked. The keyboard starts on "Cancel". The ignored files and folders are named, because a removal of the worktree removes them (the probes) and `docs/product.md` *File explorer and editor* says a person fills in a worktree's `.env` by hand. They do not make a delete a forced one: the issue's rule names uncommitted files, untracked files and commits, and a worktree with installed dependencies would otherwise always need the force.
20. **The delete.** A delete carries the stamp of the loss the person read, and `force`, true where the person checked "Force delete". The daemon, in this order: refuses while an archive of the work item is ending its sessions, with "An archive of work item <id> is ending its sessions. Try again."; reads the loss again and refuses where its stamp differs, with "What the delete would remove has changed. Read it again.", refuses where `blocked` is a sentence, with that sentence, and refuses where something would be lost and `force` is not true, with "The work item holds work a delete would lose. Check Force delete to delete it anyway."; ends the running sessions (item 21); reads the loss once more and refuses in the same three ways; runs `git worktree remove` on the folder where git lists a worktree there, with `--force` only where `force` is true, so a plain delete also meets git's own refusal of a changed worktree; runs `git branch -D` on the branch where it exists; takes the work item, its panes and its headless sessions off the daemon's lists. Where a step fails, the steps after it do not run, the work item stays listed and the error is the daemon's answer. Owlery removes a worktree and a branch through those two git commands alone: it removes no file by itself, runs no `git push`, and passes git no ref under `refs/remotes`. Where the loss is `unreachable`, the delete takes the work item off the list and removes nothing on disk, and the dialog says that the folder stays.
21. **Ending sessions.** An archive, a delete and a repository's removal each carry the ids of the running sessions the person was told of. Where a session runs that the message does not name, the daemon refuses with "A session started since you looked. Read it again." and ends none. Otherwise it kills each pane's process, stops each headless run, and waits until each pane's process has exited. Where one has not exited within the wait `frame/questions.md` Q2 leaves to the work, a delete is refused and removes nothing, and a repository's removal is refused and removes nothing more: the work items a removal that deletes deleted before it stay deleted (item 16). An archive is not refused for a pane that outlives the wait: it goes on, and the pane stays listed as running under the archived work item until its process exits. An archive is refused while a delete of the work item is in progress, with "work item <id> is being deleted".

**Groups, and order**

22. **Groups.** "New group" on a repository's menu opens a dialog that takes a name, kept without the spaces at its ends, and an empty one is refused. Two groups of one repository may share a name. A group belongs to one repository, and a move into a group of another repository is refused with "Group <id> is no group of the work item's repository.". In the sidebar a repository lists its ungrouped work items first, then each group under a heading of its name, in the order the groups were made, a group with no work item among them, except while a search or a filter is applied, when a group none of whose work items is left is not listed. A group's heading carries the count of its work items, and a repository's count counts the grouped ones too. A work item whose group its repository does not hold is listed among the ungrouped. A work item's menu holds "Move to <group>" for each group of its repository but its own, and "Move out of <group>" where it is in one. The inbox screen and the history screen do not show groups.
23. **One change at a time.** A rename that renames a branch, a delete, a repository's removal and a creation run one after another, on the chain `Daemon#creating` is at `95decb6`, so no two of them pick or remove the same branch.
24. **A description on hover.** Every `button` of the window whose content is an icon or a mark alone, a repository's "+" and "…" among them, and every item of a work item's menu and of a repository's menu, carries a `title`, which the system shows on hover: one short sentence of what a press does, in other words than the control's name. A menu's entry holds its description beside its label, so an item added to a menu without one fails scenario 21's case. The descriptions tell registering a repository from creating a work item. `new-work-item` says "Create a work item: a new branch and worktree in a repository. The form can also register a repository alone.". A repository's "+" says "Create a work item in <the repository's name>: a new branch and worktree.". The checkbox of item 3 says "Add the repository to the sidebar without creating a work item, a branch or a worktree.". Phase 3 writes the other sentences, and each later phase writes those of the items it adds.

Out of scope.

- Moving an archived work item's files away, keeping its uncommitted and ignored files while the folder is gone, and running a setup script on restore. Issue #60 keeps them.
- Renaming or moving a worktree's folder at a rename. A running session's process stands in that folder.
- Renaming, removing or reordering a group, and reordering repositories. The issue names a new group and a move between groups, and nothing else of them.
- Finding again the work items of a repository that was removed from Owlery and added again. Their folders and branches are on disk, and Owlery lists none of them.
- A "…" button on a work item's line. The issue gives one to a repository's row alone.
- A menu on the summary screen's lines and in a work item's view. The issue names the sidebar and the inbox.
- An image file or a colour as a repository's icon, unless `frame/questions.md` Q1 is answered that way.
- Recovering a deleted branch. The dialog shows each commit's hash before the delete.
- Naming what a repository's folder holds before it moves to the Trash, such as a branch that was never pushed. The folder is moved whole and a person can put it back.
- Apps installed outside the folders item 7 names, and an app that is not in the main process's list.
- A session's history kept across the daemon's exit. `docs/roadmap.md` *Milestones* row 4 holds bringing sessions back.

## Data & interfaces

`apps/desktop/src/shared/protocol.ts`:

- New types. `Group { id: number; name: string }`. `Repository { id: number; folder: string; name: string; customName: string | null; icon: string | null; defaultBase: string | null; hidden: boolean; groups: Group[] }`, where `name` is the name the sidebar shows and `customName` the one a person gave. `WorkItemLoss { branch: string | null; worktree: string | null; commits: { hash: string; subject: string }[]; commitCount: number; uncommitted: string[]; uncommittedCount: number; untracked: string[]; untrackedCount: number; ignored: string[]; ignoredCount: number; blocked: string | null; unreachable: boolean; stamp: string }`. `Running { panes: number[]; headless: number[] }`, the running sessions a person was told of.
- `WorkItem` gains `repoId: number`, `pinned: boolean`, `muted: boolean`, `groupId: number | null` and `archivedAt: number | null`.
- `ready` and `inbox` gain `repositories: Repository[]` and `archived: WorkItem[]`.
- New client messages, each with a `requestId`:
  - `addRepository { folder: string }`
  - `setRepository { id: number; name?: string | null; icon?: string | null; defaultBase?: string | null; hidden?: boolean }`
  - `removeRepository { id: number; workItems: number[]; running: Running; delete?: { stamps: Record<number, string>; force: boolean } }`, where `workItems` names the work items the person was told of, and `delete` is present where the person chose to delete them from disk, with the stamp of each one's loss
  - `addGroup { repoId: number; name: string }`
  - `setWorkItem { id: number; pinned?: boolean; muted?: boolean; groupId?: number | null }`, where `groupId` moves the work item into a group of its repository, or out of its group where it is null (*Scope* item 22)
  - `planRename { id: number; title: string }`
  - `renameWorkItem { id: number; title: string; branch: boolean }`
  - `archiveWorkItem { id: number; running: Running }`
  - `restoreWorkItem { id: number }`
  - `readLoss { id: number }`
  - `deleteWorkItem { id: number; stamp: string; force: boolean; running: Running }`
- New server messages. `done { requestId: number }` answers each of them that has no answer of its own, which is every one but `planRename` and `readLoss`, before the `inbox` that carries a change; a request that changed nothing, such as an `addRepository` of a repository already stored and shown, gets `done` and no `inbox`. `renamePlan { requestId: number; branch: string | null; blocked: string | null }` answers a `planRename`. `workItemLoss { requestId: number; id: number; loss: WorkItemLoss }` answers a `readLoss`. A request that fails is answered with the `error` message of `95decb6`.
