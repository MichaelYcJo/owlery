Constraints the tree and the owner set.

- **How the window is driven.** Every start of the Owlery app by an agent sets `OWLERY_BACKGROUND=1`, and an agent makes as few starts as its verification needs. `BuiltApp.start` sets the variable and gives the app a user data folder of its own under the system's temporary folder. The crafter and the proofer of a phase run the file `test/work-item-menu.test.ts` by itself, which is one start, and start the app in no other way.
- **The owner's running app.** The owner runs the app for the hand run of issue #24 from the main clone, `/Users/michael/Documents/GitHub/owlery`, which stands on `release/v0.0.1`: an Electron app that reads that clone's `apps/desktop/dist`, and a daemon (pid 95337) that uses `~/Library/Application Support/@owlery/desktop/`. This work item is built in the worktree `/Users/michael/Documents/GitHub/owlery-93` (since 2026-11-20, after phase 1), and no party builds, tests or runs the broad gate in the main clone, because `test/built-app.ts#buildApp` rewrites the `dist` of the tree it runs in. No party stops that daemon, reads or writes that folder, or creates a work item in a repository of the owner's. Cases and drives use the temporary repositories of `test/repositories.ts` and the suite's own app data. No case and no drive presses an "Open in" item or a "Copy" item, or moves a folder to the Trash: each acts on the owner's desktop, clipboard and Trash.
- The branch is never rebased, and no git hook is skipped.
- Git runs in the daemon alone, through `execFile` with arguments and never a shell (`src/daemon/worktrees.ts:1-3`). A branch's name and a folder reach git as arguments, and a branch only inside a full ref or as the argument of `git branch`.
- The window is sandboxed and has no access to git, to the file system or to other apps (`src/main/main.ts:33-38`). What git knows reaches it through the daemon, and what the Mac holds through the main process.
- The daemon outlives the app, so a window of this build can meet a daemon of an earlier one, which ignores every new message and sends no `repositories` (`frame/design.md` *Scope* item 2). The reverse does not happen without a downgrade.
- The debugging port does not reach a menu the system draws (`test/work-item-form.test.ts:89`), and on macOS no key raises `contextmenu` (`frame/design.md` *Grounding*, the probe `test_tmp_menu_probe.js`).

**The failure scenario of the chosen approach.** The store becomes a new file, and the old one is left as it was. A person who goes back to an earlier build then sees the work items of the day of the update, without what was renamed, archived, deleted or added since, and a work item deleted since is listed there with its folder gone. The whole store is one file written whole at each change, so a store of thousands of work items rewrites all of them at each pin. A delete reads the loss, ends the sessions and reads it again, so a process the daemon did not start, such as an editor that saves a file between the second read and the removal, can still put a file into the folder that the person was not told of; a plain delete then meets git's own refusal, and a forced one removes the file. The loss counts as held a commit that a remote's branch holds in the clone, so a commit that was pushed and then deleted on the remote without a fetch is not named. The commits a tag holds are not named either. The installed apps are found by their bundles' names in the folders `frame/design.md` *Scope* item 7 names, so an app that was renamed or installed elsewhere is not offered, and an app of the list that does not take a folder from `open -a` opens without it. Removing a repository with its work items deleted stops at the first delete that fails, and leaves the repository listed with the rest. The start from `work-items.json` reads each old `repo` through git, so a repository whose folder git cannot read at that one start, as on a disk that is not mounted, is stored under the folder the old file holds, and where that folder was a linked worktree's it stays one after the disk is back: nothing reads it again. The menu's key M is read by the window, so a future screen that takes typed letters outside a field has to be named to the function that reads it.

## Operational impact

The daemon's list moves from `work-items.json` to a new file, `repositories.json`, in the same run directory. The first start of this build's daemon reads `work-items.json` and writes the new file at its first change. `work-items.json` stays as it was and is never written again, so an earlier build that is started later lists the work items of the day of the update.

A daemon that an earlier build started and that is still alive sends no repositories and answers none of the new messages. The window then says so in its status line and lists no repository until that daemon exits, which it does a minute after its last session ended and its last window closed.

The protocol gains the messages and the fields `frame/design.md` *Data & interfaces* lists. A client that reads `workItems` alone no longer sees an archived work item.

A delete runs `git worktree remove` and `git branch -D` in a person's repository, and with the force it removes files no commit holds. Removing a repository can move its folder to the macOS Trash. Nothing runs against a remote.

No environment variable and no dependency is added. The version does not move: the release's version has already moved. Phase 6's commit adds `changelog.md`.
