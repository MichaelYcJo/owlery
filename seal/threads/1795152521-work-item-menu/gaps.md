## Not done

`apps/desktop/test/daemon.test.ts#runFolderWithWorkItem` still writes `work-items.json`. Writing `repositories.json` there was within reach and was not taken: the helper's cases now also hold the daemon's start from the old file.

The daemon pins, mutes and renames an archived work item where a message asks it to. Refusing those for an archived work item was within reach and was not taken: the window's menu of an archived work item offers none of them, and `frame/design.md` *Scope* item 17 names a pane and a headless session as what the daemon refuses there.

Enter does nothing on the screen of a repository's archived work items. Having it restore the selected one, as it opens the selected one on the inbox, was within reach and was not taken: `frame/design.md` *Scope* item 18 names the preview's button and the menu as what restores, and a key pressed by mistake would change what the lists hold.

The screen of the archived work items lists one repository's. Reaching it for a hidden repository, whose row and menu the sidebar does not draw, was within reach and was not taken: `frame/design.md` *Scope* item 12 puts "Show archived work items" on a repository's menu, and the dialog of the hidden repositories shows one again.

The keyboard's place on a line is lost when the sidebar or a list draws its lines anew, which each does at every list the daemon sends (`apps/desktop/src/renderer/sidebar.ts#showSidebar` and `apps/desktop/src/renderer/list.ts`, `read`). So after a press of Pin or of Mute notifications from the keyboard, the keyboard returns to the line and leaves it when the daemon's list arrives. Keeping the keyboard on its line across such a drawing was within reach and was not taken: it is how every list of the window is drawn since before this work, and `frame/design.md` *Scope* item 5 names the keyboard's return at Escape alone. A menu that closes at Escape returns the keyboard to the line as it is then drawn, which a case holds.

The "New work item" form ends its plan's timer when its dialog's `close` event arrives (`apps/desktop/src/renderer/renderer.ts`, the listener of `workItemDialog`). Phase 2 found that the event of a close can arrive after the same dialog opened again (`trail/phases/phase-2.md`), and gave the rename dialog's listener a guard for it. Giving the form's listener the same guard was within reach and was not taken: no case shows the form losing a plan, and the form was not phase 2's. Phase 3 changed the form and left the listener as it is: the dialogs it added rest no state on a `close` event (`trail/phases/phase-3.md`).

A removal's dialog, a repository's settings and its icon's dialog return the keyboard to the page when they close, and not to the repository's row: the menu's item the keyboard was on is gone by then. The dialog before an archive and the delete dialog do the same for a work item's line. Returning it to the row was within reach and was not taken: `frame/design.md` *Scope* item 5 names the keyboard's return at a menu's Escape alone, and the rename dialog of phase 2 does the same.

The daemon sends a pane's process one signal when it ends it for a removal, for a delete or for an archive. It refuses the removal and the delete where the process outlives the 3 seconds, and archives the work item with the pane still running. A second, harder signal after the wait was within reach and was not taken: `frame/design.md` *Scope* item 21 names a kill, a wait and a refusal, and a process that is ended harder loses what it had not written.

A read of the branches that began before a removal or a delete can end after it, and then keeps what it read of a removed work item under that work item's id (`apps/desktop/src/daemon/daemon.ts#readCommits`). Dropping such a read was within reach and was not taken: no id is given twice, so no list shows what is kept, and no case could see the guard fail. It costs one `inbox` that carries nothing new.

The daemon stores the base a `setRepository` names without asking git whether the repository lists it. Refusing a base the repository does not list was within reach and was not taken: `frame/design.md` *Scope* item 13 already passes over a stored base the repository no longer lists, at each plan and each creation.

The sidebar's filter and the theme's control carry no sentence of what they do. Each is a `label` over a `select`, and `frame/design.md` *Scope* item 24 names every `button`. The filter's `title` says what it shows, and the theme's control has none.

A linked worktree of a submodule, or of a repository whose git directory stands apart from its checkout, is refused with a sentence at an add, a plan and a creation, and stands as `work-items.json` holds it at the start (`apps/desktop/src/daemon/worktrees.ts`, `mainOf`). Git lists a git directory first for such a worktree and names no checkout. Reading the checkout from that git directory's configuration was within reach and was not taken: review round 3 asks for the refusal, how each kind of git directory records its checkout was not measured, and nothing shows a person working in such a worktree.

A delete leaves on disk a folder that stands where the work item's worktree was and that git no longer lists as a worktree, as after a `git worktree prune`. The loss names no folder then, the delete removes the branch and takes the work item off the lists, and nothing in the window says that the folder stays. Removing such a folder was within reach and was not taken: `frame/design.md` *Scope* item 20 has Owlery remove a worktree through `git worktree remove` alone and no file by itself, and git removes only a folder it lists.

A delete leaves the folder `<worktrees' root>/<repository's name>` where it removed the last worktree under it, empty. Removing the empty folder was within reach and was not taken, on the same sentence of item 20.

The delete dialog reads the loss when it opens and after a refusal, and not while it stands open. Reading it again at each list the daemon sends was within reach and was not taken: a loss that changed meanwhile has another stamp, so the daemon refuses the delete and the dialog then reads and names the new one.

The main process moves to the Trash any folder that holds `.git` at its top, a linked worktree's among them (`apps/desktop/src/main/openers.ts#trashFolder`). Telling a repository's folder from a worktree's there was within reach and was not taken: it takes a read of what `.git` is, which a checkout whose git directory stands apart shares with a linked worktree, and the window names the folder of a repository the daemon keeps, which *Scope* item 3 holds to a main checkout.

A removal that deletes waits for each work item's sessions in turn, up to 3 seconds for each. Ending every session first and waiting once was within reach and was not taken: `frame/design.md` *Scope* item 16 deletes each work item as item 20 states, and item 20 ends a work item's sessions only after its loss was read and not refused, so a work item whose delete is refused keeps its sessions.

Two groups of one repository may bear one name. Refusing a name a group of the repository already bears was within reach and was not taken: `frame/design.md` *Scope* item 22 names an empty name as the one a new group is refused for, and each group has an id of its own, so a move names the right one. A person who makes the same name twice sees two headings alike, and this work can remove neither (`frame/design.md` *Scope*, out of scope).

A group's heading in the sidebar is no control: it folds nothing, opens no menu, and takes no keyboard focus. Folding a group, or a menu on its heading, was within reach and was not taken: item 22 names a heading of the group's name, and the issue names a new group and a move between groups, and nothing else of them.

The daemon sets the group of an archived work item where a message asks it to, and an archived work item keeps the group it stood in, so a restore lists it under that heading again. Taking a work item out of its group at its archive was within reach and was not taken: item 18 has a restored work item "listed where it was", and the window's menu of an archived work item offers no move.

The dialog of a new group, a repository's settings and its icon's dialog stay open where the daemon no longer keeps their repository, and their press is then answered "no repository <id>" in the dialog. Closing them at the list that drops the repository, as the removal's dialog closes, was within reach and was not taken: phase 3 built the two earlier ones that way, and only a second client of the daemon can remove a repository while a dialog of this window is open on it.
