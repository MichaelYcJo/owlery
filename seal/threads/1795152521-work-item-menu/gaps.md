## Not done

The items "Show archived work items" and "New group" of a repository's menu are drawn, and their press closes the menu and opens nothing, as `frame/plan.md` *Phases* row 3 states. Leaving them out until they do something was within reach and was not taken: the row asks for them drawn, and rows 4 and 6 build what they open.

`apps/desktop/test/daemon.test.ts#runFolderWithWorkItem` still writes `work-items.json`. Writing `repositories.json` there was within reach and was not taken: the helper's cases now also hold the daemon's start from the old file.

A work item's menu holds no item for a group, for an archive or for a delete after phases 2 and 3. Drawing them as items that do nothing was within reach and was not taken: `frame/plan.md` *Phases* rows 4, 5 and 6 build each with what it does, and an item that does nothing reads as one that failed.

The keyboard's place on a line is lost when the sidebar or a list draws its lines anew, which each does at every list the daemon sends (`apps/desktop/src/renderer/sidebar.ts#showSidebar` and `apps/desktop/src/renderer/list.ts`, `read`). So after a press of Pin or of Mute notifications from the keyboard, the keyboard returns to the line and leaves it when the daemon's list arrives. Keeping the keyboard on its line across such a drawing was within reach and was not taken: it is how every list of the window is drawn since before this work, and `frame/design.md` *Scope* item 5 names the keyboard's return at Escape alone. A menu that closes at Escape returns the keyboard to the line as it is then drawn, which a case holds.

The "New work item" form ends its plan's timer when its dialog's `close` event arrives (`apps/desktop/src/renderer/renderer.ts`, the listener of `workItemDialog`). Phase 2 found that the event of a close can arrive after the same dialog opened again (`trail/phases/phase-2.md`), and gave the rename dialog's listener a guard for it. Giving the form's listener the same guard was within reach and was not taken: no case shows the form losing a plan, and the form was not phase 2's. Phase 3 changed the form and left the listener as it is: the dialogs it added rest no state on a `close` event (`trail/phases/phase-3.md`).

A removal's dialog, a repository's settings and its icon's dialog return the keyboard to the page when they close, and not to the repository's row: the menu's item the keyboard was on is gone by then. Returning it to the row was within reach and was not taken: `frame/design.md` *Scope* item 5 names the keyboard's return at a menu's Escape alone, and the rename dialog of phase 2 does the same.

The daemon sends a pane's process one signal when it ends it for a removal, and refuses the removal where the process outlives the 3 seconds. A second, harder signal after the wait was within reach and was not taken: `frame/design.md` *Scope* item 21 names a kill, a wait and a refusal, and a process that is ended harder loses what it had not written.

A read of the branches that began before a removal can end after it, and then keeps what it read of a removed work item under that work item's id (`apps/desktop/src/daemon/daemon.ts#readCommits`). Dropping such a read was within reach and was not taken: no id is given twice, so no list shows what is kept, and no case could see the guard fail. It costs one `inbox` that carries nothing new.

The daemon stores the base a `setRepository` names without asking git whether the repository lists it. Refusing a base the repository does not list was within reach and was not taken: `frame/design.md` *Scope* item 13 already passes over a stored base the repository no longer lists, at each plan and each creation.

The sidebar's filter and the theme's control carry no sentence of what they do. Each is a `label` over a `select`, and `frame/design.md` *Scope* item 24 names every `button`. The filter's `title` says what it shows, and the theme's control has none.

A linked worktree of a submodule, or of a repository whose git directory stands apart from its checkout, is refused with a sentence at an add, a plan and a creation, and stands as `work-items.json` holds it at the start (`apps/desktop/src/daemon/worktrees.ts`, `mainOf`). Git lists a git directory first for such a worktree and names no checkout. Reading the checkout from that git directory's configuration was within reach and was not taken: review round 3 asks for the refusal, how each kind of git directory records its checkout was not measured, and nothing shows a person working in such a worktree.
