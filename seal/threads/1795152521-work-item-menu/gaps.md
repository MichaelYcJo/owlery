## Not done

A repository's "…" button is drawn and has no listener, as `frame/plan.md` *Phases* row 1 states. Disabling it was within reach in phases 1 and 2 and was not taken: phase 3 gives it its menu (`frame/plan.md` *Phases* row 3). A press of the right button on a repository's row, and the menu's key with the keyboard on it, open nothing until then either.

The store gives a new work item one more than the highest id it holds, and a new repository one more than the highest repository's id. Keeping counts that never go back was within reach in phase 1, in `apps/desktop/src/daemon/repositories.ts`. It was not taken then: no entry can be removed before phase 3, whose removal of a repository is the first to take entries out of the store (`frame/design.md` *Scope* item 16). `frame/plan.md` *Phases* row 3 now holds the counts, as work phase 3 builds before that removal, and `trail/phases/phase-1.md` hands the point to phase 3.

`apps/desktop/test/daemon.test.ts#runFolderWithWorkItem` still writes `work-items.json`. Writing `repositories.json` there was within reach and was not taken: the helper's cases now also hold the daemon's start from the old file.

A work item's menu holds no item for a group, for an archive or for a delete after phase 2. Drawing them as items that do nothing was within reach and was not taken: `frame/plan.md` *Phases* rows 4, 5 and 6 build each with what it does, and an item that does nothing reads as one that failed.

`frame/design.md` scenario 7 names a press of a repository's "+" button, which opens the form on the repository's folder. A case for it in `apps/desktop/test/work-item-menu.test.ts` was within reach and was not added: `frame/plan.md` *Phases* row 2 names the work item's menu, its pin and its rename for that file, the button's code is phase 1's and passes as it stands, so its red needs one more start of the app with the button's listener taken out, and row 3 gives the file the cases of a repository's row. Phase 1's probe is the one run that pressed the button (`trail/phases/phase-1.md`).

The keyboard's place on a line is lost when the sidebar or a list draws its lines anew, which each does at every list the daemon sends (`apps/desktop/src/renderer/sidebar.ts#showSidebar` and `apps/desktop/src/renderer/list.ts`, `read`). So after a press of Pin or of Mute notifications from the keyboard, the keyboard returns to the line and leaves it when the daemon's list arrives. Keeping the keyboard on its line across such a drawing was within reach and was not taken: it is how every list of the window is drawn since before this work, and `frame/design.md` *Scope* item 5 names the keyboard's return at Escape alone. A menu that closes at Escape returns the keyboard to the line as it is then drawn, which a case holds.

The "New work item" form ends its plan's timer when its dialog's `close` event arrives (`apps/desktop/src/renderer/renderer.ts`, the listener of `workItemDialog`). Phase 2 found that the event of a close can arrive after the same dialog opened again (`trail/phases/phase-2.md`), and gave the rename dialog's listener a guard for it. Giving the form's listener the same guard was within reach and was not taken: no case shows the form losing a plan, and the form is not this phase's.
