# Changelog: the daemon caps the agents, the worktrees and the panes by what this Mac holds

Issue #32. Nothing capped how many agents ran at once or how many worktrees stood, and nothing told a person how many this Mac holds. An agent is bound by memory, a worktree by disk, and the panes a view showed side by side were fixed at four on every Mac.

- **A "Machine…" button at the sidebar's foot opens the Machine dialog.** The dialog's first line says what Owlery's background process, the daemon, read of this Mac, for example "36 GB of memory, 12 cores of which 6 are performance cores, a load of 0, and 25.1 GB free of 494.4 GB on the worktrees' disk." A row for each cap follows: "Agents at once", "Worktrees" and "Panes side by side", each with its field, "Use the default" and the sentence that gives its default with the numbers it came from. The daemon reads the load and the free disk again each time the dialog opens.
- **The cap on agents defaults to the smaller of the performance cores and what half the memory holds.** An agent is counted at 679 MB until the daemon has measured 5 agents on this Mac, and then at the highest of the last twenty it measured. The row says which, for example "The default is 6: the 6 performance cores, fewer than the 27 that half of 36 GB holds at 679 MB an agent (not measured on this Mac yet)." A Mac whose `sysctl` gives no performance cores counts all its cores.
- **The daemon measures each agent's memory once a minute while an agent lives.** It reads the resident memory of each Claude Code pane's process and of each working headless session's process in one `ps` call. It reads nothing while no agent lives, and keeps the last twenty measures in its run folder, so a restart keeps them.
- **The cap on worktrees defaults to the worktrees that stand and the ones more the free disk holds, with 10 GB kept free.** Until a worktree is measured on this Mac its row says "Nothing is proposed until a worktree is measured on this Mac." The daemon measures a work item's worktree once with `du`: when its setup's pane exits, at once where the repository names no setup, and at the daemon's start for each worktree that stands with no measure, one at a time. It does not measure a worktree again as it grows.
- **The cap on panes side by side defaults to 4 under 16 GB of memory, 6 from 16 GB and 8 from 32 GB.** A person sets it from 1 to 16.
- **A person sets each cap, or gives it back to its default.** "Save" keeps what the fields hold, and "Use the default" lets a cap follow its default again. The daemon refuses a value that is no whole number, one under 1 and a pane cap over 16 with a sentence, for example "The cap on panes side by side is a whole number from 1 to 16." The caps a person set are kept in the daemon's run folder, and every window is told of a change. A field a person has typed in keeps what they typed while another window changes a cap.
- **A headless session over the cap on agents waits for the machine.** That is a session a person asks for in a work item's view, and a stage of a chain. A pane always opens. A Claude Code pane counts as an agent while it lives, and a shell pane is no agent. A waiting session starts as soon as a place frees under the cap, or when a person raises the cap. The queue starts a session a person asked for first, then a stage of a chain that has already run a stage, then a chain's first stage, and within each the one that waited longest. A waiting session gets its time limit and its start time when it starts, so the time it waited counts toward no stage's time or cost.
- **The inbox says which work item waits, and how many go before it.** The line keeps its state, and its second row reads "Waiting for the machine (2 ahead)", or "Waiting for the machine" where none goes before it. A question, a call to allow and a stopped chain still say more. A chain whose stage waits is still drawn as working, and its foot says the same words. The session's own line under "Ask" says "Queued" with the mark of no agent, and offers "Stop". The status line counts the agents against the cap and the sessions that wait, for example "Daemon running, 4 agents of 4, 1 waiting". It now stands on a row of its own, the sidebar foot's whole width, above the foot's buttons. The Machine dialog lists the sessions that wait under the agent row, below the label "Waiting for the machine", in the order they start: each work item's name, and on the line under it what it waits to run.
- **The "New work item" form warns where the disk may not hold the worktree, or where the worktrees are at their cap.** Under the plan stands, for example, "The disk may not hold this worktree: 10.2 GB free, 10 GB kept free, and a worktree of this repository takes 440 MB." and "This is worktree 2 of a cap of 1." The first counts a worktree of the repository at the largest one measured. The second reads the cap a person set, or else the default. On a disk that cannot hold one more worktree the default is the worktrees that stand, so the form then says both. "Create" stays enabled, since a person may know what they are about to remove.
- **"Side by side" shows as many of a work item's panes as the cap on panes.** The stage lays its tiles out row by row in the tabs' order: two columns for 2 to 4 tiles, three for 5 to 9 and four for 10 to 16, with the last tile spanning what is left of its row. A rule stands between the tiles. The button's title names the cap, for example "Show up to 8 of this work item's panes at once".
- **The screenshot run shows a line that waits for the machine and the Machine dialog.** In `pnpm run screenshots`, the run sets the cap on agents to the agents that run, as a person does, and asks a prompt in one more work item, whose session waits. Its line in the inbox says "Waiting for the machine", and a new shot opens the Machine dialog, which lists the session.
- **No real Claude Code process has been measured, and no real worktree.** Every test gave the daemon its own `ps`, `du` and `sysctl`, or the machine `OWLERY_MACHINE` names, under which nothing is measured. The rules between the tiles of three and four columns were read in no screenshot.
- **After an update, the caps hold once the daemon restarts.** A daemon started by the build before this one sends no machine: the window hides the "Machine…" button, queues nothing and shows four panes side by side at most. The first start of the new daemon runs one `du` for each worktree that stands, one at a time.
- **For a client of the daemon:** `ready` carries `machine`, and a new server message `machine` carries it again each time it changes. It holds `reading` (`memoryBytes`, `cores`, `performanceCores`, `load` and `disk` with `freeBytes` and `totalBytes`, or null), `agents` (`proposed`, `byCores`, `byMemory`, `set`, `running`, `perAgentBytes`, `measured` and `queue`, the ids of the waiting sessions in the order they start), `worktrees` (`proposed`, `set`, `standing`, `perWorktreeBytes` and `keepFreeBytes`) and `panes` (`proposed` and `set`). A client reads a missing `machine` as a daemon that keeps no cap. The client message `readMachine` has the daemon read the load and the disk anew and send `machine`. The client message `setCaps`, with `requestId` and any of `agents`, `worktrees` and `panes`, sets a cap, and `null` gives it back to its default; the daemon answers `done`, or `error` with the sentence of a refusal. `HeadlessState` gains `queued`, and a session that waited carries `queuedAt`, the time it joined the queue. A session that never waited carries no `queuedAt`. `workItemPlan` carries `disk` (`freeBytes`, `keepFreeBytes`, `needsBytes`, `standing` and `cap`) where the daemon read a disk. `OWLERY_MACHINE` holds a JSON object with `memoryBytes`, `cores`, `performanceCores`, `freeBytes` and `totalBytes`, and an optional `load`, which the daemon reads in place of the machine.
