# Changelog: the window reads the lists again

Issue #216. Owlery's background process, the daemon, outlives the window for days, and between its timers what it holds can stand behind git and GitHub. An open pull request whose checks have ended was read again only every 5 minutes. Nothing in the window asked the daemon to read again, so a person who saw a stale branch or stale checks had to restart the app or the daemon, and lost what they had in front.

- **The sidebar's head holds a refresh button, after the bell.** The row now reads: the bell, the refresh, the filter and "+". The refresh is two arrows round a circle, and pointing at it says "Read the work items again from git and GitHub."
- **A press has the daemon read again what a window's connection has it read.** That is each work item's branch from git, or the commit its worktree stands at where it has no branch yet, and its record, with whether a commit holds each word of the person's its record holds, each repository's records place, every open pull request it watches through `gh`, and the notice of its agent where one stands. A read of git under way ends first, so a commit made just before the press is in the answer. A pull request whose read was under way at the press is read once more at once.
- **The window draws the lists the daemon sends back, and keeps what the person had in front.** The screen in front, the pane in front of a work item's view and the filter stay. The daemon answers once git has been read and the pull requests have been read, or after 5 seconds. A pull request read after that reaches every window as before.
- **The button shows that it works until the answer.** Its arrows turn, it says "Reading the work items again…", and a second press sends nothing. Under the system's setting for less motion the arrows stand.
- **A refusal and a missing answer are said in the status line.** A read that fails is said as "The work items were not read again: <why>." Where no answer comes within 15 seconds, the status line says "The daemon did not answer in 15 seconds, so the lists stand as they were." Against a daemon of an earlier build, which does not know the request, the window's own wait of 10 seconds on each request ends the press first, with a sentence that names "Restart Daemon…" (#133). Where the window already says that the daemon is of another build, that notice follows the sentence, so "Restart Daemon…" stays in the status line; choose it to update the daemon.
- **A window that connects shares the press's list of reads.** One list in the daemon's code holds what both read again, so a read added later reaches both. Where a window connects while the daemon asks `gh` for a pull request, that pull request is now read once more after the ask ends.
- **For a contributor:** the client message `readLists` asks for the four lists, and the daemon answers the asking client with an `inbox` and then a `done`, or with an `error`. The daemon option `listsWaitMs` bounds the answer's wait for the pull requests, 5 seconds by default. The stand-in for `gh` in `apps/desktop/test/chain-run.ts` takes `seconds`, a wait before it answers.
