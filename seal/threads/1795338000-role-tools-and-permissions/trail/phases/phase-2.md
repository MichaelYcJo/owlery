**Decisions made while building, each with its grounds.**

- **A path's real location is read with the system's `realpath`, not Node's own.** `realpathSync` settles each `..` before it follows a link, so `link/../b.txt`, where `link` points outside the worktree, read as a path inside it while a write there lands outside. `realpathSync.native` follows the link first, as the write does. For the same reason the rule joins a relative path to the worktree as text and never through `path.join`. Found by the case, which failed on that path until the change. Judged against `frame/design.md` *Scope* item 9.
- **A link whose target is not there is outside.** A write through it creates the target wherever the link points, and nothing read where that is. The rule refuses it. *Scope* item 9 names only links on the part of the path that exists.
- **A write that names no file is refused with the sentence of "a read, or another call".** The sentence for a write outside the worktree quotes the path, and such a request has none. *Data & interfaces* gives no sentence for it.
- **The worktree's own folder counts as inside it.** No file is written at a folder's path, and no case could hold a clause that told the two apart (`seal mutate`, survived), so the clause went.
- **`answerPermission` with an `allow` that is no boolean is an `error`**, "an answer to a permission request says whether it allows the call", and nothing changes. *Data & interfaces* names one `error` for the message. Read as false, a client's malformed message would refuse a person's call in the person's name. Judged against the `ask` case, which refuses a malformed message the same way.
- **The fake adapter raises all its requests first, then waits for every answer.** *Scope* item 14 says it "reports each as a `permission` event before its text, waits for `answer`". Raised one at a time, no session would ever wait on two requests, and the daemon's list of a work item's requests, "the oldest first", could not be held by a case. The lines of the answers stand in the text in the requests' order, whatever order they were answered in. Its ids are `ask-1`, `ask-2`, counted in each session, so two sessions give the daemon the same ids, as two CLIs can.
- **The Claude adapter's event for a request is built by `eventsForLine`, and a second function, `controlRequestOf`, reads the same line for the id and the input the answer needs.** The neutral event carries no input, and an allowance has to give the call's input back unchanged.
- **An answer given after the result is written nowhere, and no code says so.** The result ends the session's input, and the ended stream takes no write. A line that emptied the adapter's list at the result survived its mutation, so it went, and the case "writes no answer once the result has ended the session's input" holds the behaviour.
- **A request with no `tool_name` is reported with an empty name and the action `other`.** The CLI waits for an answer to every request that has an id, so the adapter drops none of them.
- **`WorkItem.permissions` is required in the type**, as *Data & interfaces* writes it, and `lookOf` reads its absence in a file as none. The window's read of an absent field is phase 3's (scenario 22). One fixture of `test/view.test.ts` gained `permissions: []` so that the file typechecks, and no case of that file changed.
- **`claudeArgs`' comment no longer says a role launch "adds to them and takes none away".** A launch with no role now passes `--disallowedTools`, which a role launch does not.
