# Changelog: each role session holds its role's tools, and a call that asks for permission reaches the daemon

Issue #39. Every headless session was launched with the same tools, and a call that needed permission was answered by nobody: Claude Code refused it inside the session, and the window said nothing of it.

- **A role session holds its role's tools and no other.** A crafter at a fix pass holds `Read`, `Glob`, `Grep`, `Bash`, `Edit` and `Write`. A proofer at a round and a sealer at the seal hold `Read`, `Glob`, `Grep` and `Bash`, so neither holds a tool that writes a file. No `Task`, `NotebookEdit`, `Skill` or tool of the web reaches a role session. The head of a role's rules file names the tools the session holds. A session with no role keeps Claude Code's default tools, less `AskUserQuestion`, `EnterPlanMode` and `ExitPlanMode`, which ask a person something no stream of the session carries.
- **Every call Claude Code would ask a person about reaches Owlery's background process, the daemon.** Every headless session runs in the permission mode `default` and passes `--permission-prompt-tool stdio`, so Claude Code asks its question on the session's own streams, and the daemon answers there. No launch turns a permission check off.
- **The daemon answers a role session's request by the role's rule, and never asks you.** It allows a crafter's write inside the work item's worktree, refuses its write anywhere else, the role bundle's folder among them, and allows its commands. It refuses each command of a proofer and of a sealer that asks for permission, and every other request of a role session. The agent is told why, and is told to name the step that needed the call in its report. A real proofer session on Claude Code 2.1.330 was asked to run `printf x >> README.md`: the daemon refused the call, and the file kept its bytes. No stage launches a role session yet: the review rounds and the gate do (#41, #42).
- **A crafter's write is inside the worktree only where every reading of its path is.** A path that leaves the worktree through `..` or through a symbolic link is refused, and so is one that starts with `~`, holds a NUL, has a `..` in the part that does not exist yet, or has a part the system cannot read. A few paths that would land inside are refused too, each failing closed: a file whose name starts with `~` is allowed only as `./~name`, and a path written longer than the system reads is refused.
- **A question you ask in a work item's view waits for you when its session asks to make a call.** The work item's line stands under "Needs you" and says the call, as in "Asks to use Bash: pnpm test", followed by "(and 1 more)" where more wait. A work item held by a question says its question first. The line's age counts from the earliest of its waits. A notification titled with the work item says "Needs you", one for each new call, and none for a muted work item or for the work item whose view is in front of you.
- **You allow or refuse the call in the work item's view.** The session's line under "Ask" says "Needs you" with the waiting mark, and each call it waits on stands in a card: the tool, the whole call in the fixed-width face, which you can select, and "Allow" and "Refuse". An allowance covers that one call, and the same call asks again. A refusal tells the agent "The person refused this call." Both buttons are reached with the Tab key, and the keyboard stays on its button while the window draws the lists the daemon sends.
- **A call nobody answers ends with its session.** Where the session finishes, fails, is stopped, reaches its limit of 60 minutes or its work item is archived or deleted, its calls leave the line and the view. The limit counts from the session's start, whether or not it waits. The daemon keeps no request across its own restart, since the session that asked is gone by then.
- **A session with no role no longer has its calls refused in silence.** It waits for your answer, and ends at its limit where nobody answers.
- **After an update, a session asked of a daemon started by the build before this one has its calls refused as before, until the daemon restarts.** A window of the build before this one beside a daemon of this one shows a waiting session as working and cannot answer it. The status line already names a daemon of another build.
- **For a client of the daemon:** a work item carries `permissions` in `ready`, in `inbox` and in the last look: the calls its headless sessions wait for the person to allow or refuse, the oldest first, each with `id`, `headlessId`, `tool`, `action` (`read`, `write`, `run` or `other`), `text` (2,000 characters at most, a cut one ending with a mark that says so) and `at`. A client of an earlier build reads its absence as none, and a look written before it is still read. A new message `answerPermission`, with `requestId`, `workItemId`, `id` and `allow`, is answered with `done` before the `inbox` that carries the change, with `error` `no permission request <id> waits in this work item` for a request that does not wait in that work item, and with `error` `an answer to a permission request says whether it allows the call` where `allow` is not a boolean. An `ask` with a `role` is answered with `error`, and starts nothing, where the adapter does not declare both `role-tools` and `permission-requests`: `the <adapter's name> adapter cannot launch a role: it does not declare <the missing features>`. Both adapters declare the two.
