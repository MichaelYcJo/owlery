## Technical context

The tree as read at `98f10be`.

`apps/desktop`. The connector is `src/daemon/adapters/adapter.ts`: `RoleEvent` (8-14), `RoleRun` (16-22) and `RoleAdapter` (24-43), whose `features` no adapter fills. The cases are `test/claude-adapter.test.ts`, which puts a script in the CLI's place through a script `SHELL`, `test/fake-adapter.test.ts`, `test/daemon.test.ts`, which builds a `Daemon` with the fake adapter and reads what a client receives, `test/last-look.test.ts`, `test/view.test.ts`, and the files that start the built app, which run one at a time in the `app` project of `vitest.config.ts`. `test/role-session.test.ts` holds the one case that launches the person's own `claude`, and runs only through the script `role:run`.

**The constraints.** The session's input is one pipe, so the handshake, the prompt and every answer go through it in order, and it must stay open until the result (`frame/design.md` *Grounding*, the row of the held input). A request is answered by the daemon's code and by nothing that reads a command's text: `skills/core/SKILL.md` *The first value* keeps a judgment of meaning out of a script, and whether a shell command changes source is such a judgment. The option `--permission-prompt-tool` is hidden from the CLI's help, and its `stdio` value was read in the executable and probed without a model.

**The failure scenario of the chosen approach.** In six months Claude Code changes what crosses the hidden option: the request's shape, the handshake, or whether the option is read. A role session then waits at its first call that asks, until its limit ends it, or the CLI refuses every such call itself and each stage's report says it could do nothing. No case of the suite sees it, because every case stands a script in the CLI's place. The bound is the run of `role:refusal` at each move of `MIN_CLAUDE_VERSION` and the limit that ends a waiting session. The second failure: the grants and the roles' definitions drift apart. A proofer whose every command is refused stops running the narrow tests its definition asks for, each round's evidence becomes `read` where it was `executed`, and nothing in the inbox says so. `frame/questions.md` Q1 puts that cost to the owner, and `frame/design.md` *Scope* item 19 names the work that removes it. The third: a crafter's command writes outside the worktree, and the daemon's rule, which allowed the command by the role alone, saw nothing.

## Overlap with the release

The spawn names #119, #41, #42 and the worktree of #40. `gh issue list --milestone "release: 0.0.2"` lists further open issues, #43 to #47, #22, #36, #97, #110, #48 and #49, which the spawn does not name and this frame did not read as overlaps, except #110, which has no code.

**A permission request passed to the person sits beside #119's park and does not use it.** A park belongs to a work item: `Daemon#park` refuses a work item that is already parked, keeps its record in `asked.json` across a restart of the daemon, and gives the person's answer as text for the next stage to read. A permission request belongs to one live session: a session can wait on several at once, each has to be answered to a process that is waiting, and each is gone when that process ends. Carried by a park, a second request would be refused, and a restart would leave a parked work item whose answer nothing can take. What the two share is the line: each makes its work item's line say `waiting`, and the text of the line says which. Under this design no stage the daemon runs ever waits for the person on a request (`frame/design.md` *Scope* item 8), so a park stays the one way a run stops for a person.

## Operational impact

No dependency is added. One variable is read by the suite alone, `OWLERY_ROLE_REFUSAL`, and `package.json` gains the script `role:refusal`. No migration: the daemon writes no new file, and a request is kept in memory with its session.

The launch of every headless session changes: each passes `--permission-prompt-tool stdio`, a role launch passes `--tools`, and a launch with no role passes `--disallowedTools`. `MIN_CLAUDE_VERSION` stays 2.1.326. The options were probed on 2.1.330 alone, and `frame/questions.md` Q5 names what is not known of the versions between.

A compatibility break a person meets: a session with no role, asked from the work item's view, no longer has its calls refused in silence. It waits, its work item's line says so, and it ends at its limit where nobody answers.

The protocol gains `permissions` on a work item, in `ready`, `inbox` and the look, and the client message `answerPermission`. A window of this build reads a work item without the field as one with no request. A window of an earlier build beside a daemon of this one shows a waiting session as working and cannot answer it, and its status line already names a daemon of another build. A `last-look.json` written before this build is still read.

The version does not move: `apps/desktop/package.json` reads `0.0.2`. `docs/` is not edited in this pull request: the rules are in `frame/design.md` *Rule changes*, for the settle of release 0.0.2.
