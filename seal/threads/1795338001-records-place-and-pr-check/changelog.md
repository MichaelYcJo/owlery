# Changelog: connecting a repository creates the place for work records and the pull request check

Issue #40. A person pointed Owlery at a folder and got work items, and nothing was created in the repository: no place for work records, and no check that reads them outside the app. A later seal would have had no committed grounds, and a colleague without the app no verdict.

- **Connecting a repository now offers one commit that creates both, and you read it first.** When you register a repository that lacks a part of the place, a dialog opens. It lists each file Owlery would write with its whole text, the commit's subject and the branch the commit lands on. Nothing is written until you press "Set up and commit". "Not now" writes nothing, and the entry "Records and check…" of the repository's menu opens the dialog again at any time.
- **The commit holds three files and nothing else.** They are `seal/README.md`, `seal/config.json` and `.github/workflows/owlery-seal.yml`. The commit is made with your git identity and your repository's hooks, on the branch your checkout stands on. Other work you had staged stays staged. Nothing is pushed.
- **What stands in the repository is kept.** A repository that already holds an AgenticSeal records root and its `hygiene.yml` gets no file, and the dialog says what it holds. Where the repository keeps a `seal/` folder of its own, Owlery's root is `agentic-seal/`.
- **The broad gate command is set in the same step.** It is the command that must pass on a commit before it is sealed. The dialog holds a field for it and writes it as the `Broad gate` key of the root's `config.json`. Owlery proposes a command from your `package.json`, its `check` script or else its `test` script, and you can change it before the commit. For a repository that already has the place, the dialog shows the command and the file that keeps it.
- **The dialog says up front what is out of scope.** Its first sentences are: "Owlery commits work records to this repository. A repository that cannot keep work records in its tree is out of scope for Owlery." The setup is refused, with the reason shown, where no branch is checked out, where both `seal/` and `agentic-seal/` hold something of the project's own, and where git ignores a path the setup would write.
- **A commit that fails leaves nothing behind.** Where a hook refuses the commit, Owlery unstages its files, removes them and the folders it made, and shows what git printed.
- **The check runs on GitHub without the app.** The workflow is named `seal`. On each pull request it fetches the check's scripts from Owlery's repository, at the tag of the release that wrote the workflow, and runs them on Python 3.12 or newer. A pull request whose branch no work item's records name is not judged and passes.
- **The setup's commit is local until you push it.** A work item cut from the remote's base before that push holds no place for records. Nothing in the app says so yet.
- **Owlery owns what it took from AgenticSeal.** The check's 19 scripts stand in `pr-check/` at the top of Owlery's repository. They started from AgenticSeal 0.38.4 under its MIT License, whose text is beside them, and they are Owlery's to change. `docs/architecture.md` now says that Owlery follows no release of AgenticSeal, and names this choice for the check in place of "not decided". The role bundle's notice no longer binds its files to AgenticSeal's tag.
- **A work item's records now have a place for its decisions and its questions.** They live in `decisions.md` of the work item's directory. Each decision made for the work item without asking you, and each question it was parked with, is one fenced block of fixed fields. A decision is `decided`, `reversed`, `applied` or `carried`, and a question is `open` or `answered`. `docs/architecture.md` states the fields and the states.
- **Nothing in the app writes or shows a decision or a question yet.** This release gives the daemon, Owlery's background process, the code that reads the file and writes each change of it. The inbox line, the reversal and the answer come with issue #119, which builds on that code.
- **For a client of the daemon:** each repository carries `records`, with `root`, `check` and `broadGate`, each null where the checkout holds none. `planRecords` is answered with `recordsPlan`, which says what a setup would write and carries a stamp. `setUpRecords` takes that stamp, and is answered with `error` where the repository changed since the plan was made.
- **For a contributor:** the desktop suite now runs `python3`, version 3.12 or newer, and `.github/workflows/check.yml` sets it up. One case hands the same fixtures to the daemon's reader of a record block and to the check's reader, and fails where they answer differently.
