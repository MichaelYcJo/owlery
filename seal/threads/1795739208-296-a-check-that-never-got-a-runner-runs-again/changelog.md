# Changelog: a check that never got a runner runs again

Issue #296. When GitHub could not place a macOS job on a hosted runner, it gave up after about 15 minutes and cancelled the job with no runner and no step. The pull request's `check` then read as cancelled, `seal pr-wait` ended at exit 1, and a person reran the job by hand before the pull request could merge. The same could happen to the `package` job at a release's tag.

- **A job that no hosted runner took is run again without a person.** The new workflow `rerun-unstarted` starts when a run of `check` or of `package` completes with a conclusion other than success. It asks GitHub to rerun a job only where GitHub cancelled it with no runner, no step and the annotation `The job was not acquired by Runner of type hosted even after multiple attempts`. The run's summary says what it decided.
- **No other job is rerun.** A job that ran and failed, one that a newer push or a person cancelled, one of a pull request whose branch has moved to another commit or that comes from another repository, and one of an attempt numbered 5 or more each stay as they ended. The summary of the workflow's run names which of these it met.
- **It serves runs only once `release/v0.1.0` merges into `main`.** GitHub starts the workflow from the copy of its file on the default branch, so the pull requests into the release branch before that merge still need a never-started `check` rerun by hand.
- **For a contributor:** the decision is `.github/scripts/rerun-unstarted.mjs`, which takes the run's values from its environment, calls `gh api`, and imports only Node's own modules. Its cases, in `apps/desktop/test/rerun-unstarted.test.ts`, run it against a stand-in `gh` answering with the responses GitHub gave for the runs of #296. The workflow holds `actions: write`, `checks: read` and `contents: read`, and pins its two actions to a commit.
