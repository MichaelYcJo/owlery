# Changelog: the role refusal hand check reaches the daemon

Issue #191. `pnpm run role:refusal` and `pnpm run role:refusal:sealer` asked a real proofer or sealer to run a shell command that changes a file. Each role's definition tells it to run no such command, so a role that held to its definition declined, no permission request reached the daemon, and the check failed while the daemon's refusal went untested.

- **The two scripts now run the real `claude` against a stand-in for the model.** The stand-in is a server on the loopback that the check starts. It answers the session's first turn with the shell command itself, so the request reaches the daemon whatever a model would choose. The CLI is still launched by the daemon with a role's arguments and the built bundle, and the daemon still answers the request by its rule.
- **The check spends none of your usage and needs no login.** It gives the CLI a placeholder key and a home folder of its own. The daemon takes a Claude Code config folder of the check's own as its default and gives it to the session, as it gives an account's folder. In every run the session wrote its conversation into the check's config folder, and in the runs whose folders were listed afterwards the check's home stayed empty and the config folder held what the CLI writes there. In the daemon's code, every read of a Claude Code folder that this check reaches names the check's own folder. No run traced the daemon's reads of files, or the CLI's writes outside the two folders, so those parts rest on reading the code. The check still needs `pnpm install` and a `claude` your login shell finds.
- **A failure says where it stopped.** The check reads, in order, that the session holds its four tools and runs on the placeholder key, that the session wrote its conversation into the check's config folder, that the CLI asked the stand-in for a turn, that the request for the command reached the daemon, that the stand-in was told the daemon's reason as a failed call, that the file kept its bytes, and that no request waited for a person.
- **The two scripts print what the check prints, in a terminal and in an agent's shell alike.** They name Vitest's default reporter, so the CLI's version, the check's kept folder and every request the stand-in received are printed even where Vitest would otherwise hide a passing case's output.
- **`pnpm run role:run` is unchanged.** It is still a real session on your login and costs your usage.
- **Nothing changes in the app.** The daemon, the adapter and the role bundle are as they were.
