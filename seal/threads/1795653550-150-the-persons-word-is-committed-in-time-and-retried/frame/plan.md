# Implementation Plan: the person's word is committed in time and retried

## Technical context

The tree as read at `82a55e8f`.

**One function makes every commit of a worktree.** `apps/desktop/src/daemon/worktrees.ts#commitPaths` (`:892`) asks `whyNoCommit`, runs `git add`, asks `git diff --cached --quiet`, runs `git commit`, and unstages its paths where either command fails. Each git runs through `gitIn` (`:848`), an `execFile` with no limit, which resolves when git's output pipe closes. The limit goes under `git add` and `git commit`, the commands that run a program of the repository's: a clean filter, a hook, a signer. The commands that only read, and the `git reset` that unstages, stay on `gitIn`.

**The pattern for a bounded git stands in the same file.** `worktrees.ts#askRemote` (`:293`) starts git with `spawn`, `detached: true`, so git leads a process group, and ends the group at its limit. Its comments state why a fetch settles at git's exit and not at the pipe's close. The commit's runner follows it, with two differences the probe of `frame/design.md` *Grounding* gives. The first signal is SIGTERM and never SIGKILL, because a killed `git commit` leaves `index.lock`. A SIGKILL follows the grace, because a hook that ignores SIGTERM outlives git and holds the pipe.

**The daemon's commits of one worktree run one after another.** `Daemon#wordCommits` (`daemon.ts:478`) holds, for each worktree, the promise of the last commit asked for there. `commitWord` (`:2907`) and `inWorktree` (`:2921`) append to it, and a chain's stage commits through `inWorktree` (`:3164`, `:3179`). So one commit that does not end holds each later one, `beginChain` (`:2971`) and `close` (`:810`). The limit bounds each link of that chain, and the unit of *Scope* item 7 appends to the same map.

**What says a session works.** `Daemon#works` (`daemon.ts:2911`) reads the live panes and the headless sessions of a work item, and `this.chains` holds a running chain. The states change at an agent's event, at a pane's exit, at a headless run's end, at a chain's end and where the session log names an interruption. The timer of *Scope* item 8 reads `works` and `chains` at each turn and hooks none of those places.

**What reads the records.** `Daemon#readCommits` (`daemon.ts:4131`) calls `readRecord` for each open work item and `readBranch`, which holds the branch's head. The derivation of *Scope* item 6 runs there, for a work item whose record holds a `reversed` decision or an `answered` question, keyed by the record's text and the branch's head. `worktrees.ts#fileAt` (`:1038`) gives a file's text at a commit, or null.

**Constraints.**

- A case that leaves a `reversed` or an `answered` block in a worktree's record without a commit now sees the daemon commit it once the records are read. The builder finds each such case of `apps/desktop/test/daemon.test.ts` and the built-app files by running the files it changes, and adjusts the case or makes its commit expected. `apps/desktop/test/screenshots.test.ts:663` writes the parked work item's record with open questions alone, which is no person's word.
- The existing cases of `describe("the commit of a person's word")` pin the subjects of a reversal and of the answers, the trailer, the order of two words, the close's wait and the log's line. Each stays green without an edit, except where it reads a second log line that the retry now adds inside the case's own wait.
- The cases wait on what happens, with short limits given through the options, and never on a fixed sleep of the default limits.
- A case that starts a hook which never ends removes its processes in its cleanup by the process ids it recorded.

**The failure scenario of this approach.** The derivation reads the states `reversed` and `answered` as the person's. A later writer of either state that is not the person, such as a stage that answers a question from the tree, would have its block committed by the daemon under a subject that names the person, between that stage's write and its own commit. The guard that exists is the hold while a chain runs or a session works. A writer outside both would need the derivation to read who wrote the block. The second risk is the limit itself: a repository whose `pre-commit` hook takes longer than five minutes on a records-only commit has every stage's commit ended, and its chain stops each time with the sentence of the limit. The remedy then is the constant, and `frame/questions.md` Q1 holds it for the owner.

## Alternatives considered

| Approach | Failure scenario | Verdict |
|---|---|---|
| Bound the commit with `execFile`'s `timeout` option | The option signals git alone. The probe's sixth case shows the hook running on and git's pipe open six seconds later, and `execFile` calls back at the pipe's close, so the commit still holds the worktree. | Rejected. |
| End the commit with SIGKILL at the limit | The probe's fifth case: `index.lock` stays, and every later git that writes the index fails until a person removes the file. | Rejected. SIGTERM first, SIGKILL after the grace for what ignored it. |
| Skip the hooks and the signature in the daemon's commit (`--no-verify`, `--no-gpg-sign`) | The commit would never hang. `docs/architecture.md` *Records are committed to the repository* says the setup's commit "runs the repository's hooks", and `commitPaths`' docstring holds every commit to it: a repository that requires signed commits would get unsigned ones from Owlery. | Rejected, against the policy. |
| A limit of 30 seconds or 2 minutes | A hook that lints or typechecks the tree on each commit can take longer, and the limit then ends a commit that would have landed, at every try and at every stage of a chain. | Rejected. |
| A limit of 5 minutes, with the close ending a commit after 3 seconds | A hook that hangs holds the worktree's later commits for five minutes at each try. The close is not held by it. | Chosen. The cost of a long limit falls on a hung hook alone, and the cost of a short one on every slow hook. Q1 of `frame/questions.md` leaves the value open to the owner. |
| The close waits for the whole limit | "Restart Daemon…" and "Quit Owlery Completely…" would take up to five minutes. | Rejected. |
| The close ends every commit under way at once | A commit that would have landed within the second is ended, and its word waits for the next daemon. The existing cases pin that the close waits for it. | Rejected. |
| Keep `commitWord` as it is, and keep in the daemon's memory which words it left or failed to commit | `Daemon#checkIdle` (`daemon.ts:4248`) ends the daemon 60 seconds after the last window closed where nothing runs, and the app's update and "Restart Daemon…" end it too. The list goes with the process, the next daemon knows of no owed word, and the word stays out of every commit with nothing said, which is the defect of the issue. The premise that would keep the structure is that the daemon outlives the wait. `checkIdle`, read at `82a55e8f`, says it does not. | Rejected. |
| Store the owed words in the daemon's run folder | A stored list has to be kept in step with the tree: a session's own commit, a reset or a deleted branch each change what is owed with no write to the list. | Rejected. `docs/architecture.md` *Code runs the order, the orchestrator judges* has the daemon read where a work item stands from its records. |
| Read what is owed from the tree: the record in the worktree against the record at HEAD | The failure scenario of *Technical context*: a writer of `reversed` or `answered` that is not the person. | Chosen. It replaces the record's arm of `commitWord`. It outlives the daemon, and it turns false by itself when any commit carries the word. |
| Carry the commit's subject from the handler, as today | A try the handler never saw, after a restart, has no subject, so a second way to make one would stand beside the first. | Rejected. The subject is made from what is owed. |
| Commit a word left for a session at each place a session stops working | Those places are an agent's event, a pane's exit, a headless run's end, a chain's end and an interruption read from the session log. A place that is missed, or one added later, leaves the word with nothing said. | Rejected. |
| Retry inside `Daemon#readCommits` | Its timer runs only while a client is connected (`scheduleCommitRead`, `daemon.ts:4025`). A person who reverses a decision and closes the window while an agent works would have the word committed only when a window next opens. | Rejected. |
| A timer of the daemon's own, armed only while a word is owed | A daemon with a word whose commit keeps failing wakes every three seconds to compare a time. It runs no git in that turn. | Chosen. |
| Retry a failed commit at every turn, or every minute without end | Each try runs the repository's hooks, and in a repository that signs with a passphrase each try opens the passphrase's prompt. | Rejected. The wait doubles from one minute to one hour, and a change of the record or of the branch's head ends it. |
| Say it on the line alone, or in the view alone | The line has no room for git's reason, and a view is read only once it is opened: a person back at the inbox would not learn that a commit failed. | Rejected. The view says both cases with the reason, and the line says the failure alone. |
| A "Try again" button in the view | It adds a control and a message of the protocol for what the timer and the next word already do. `docs/design.md` *Principles*, 2. | Rejected. |
| Leave the setup of the records place without a limit | Its commit runs the same hooks (`records-place.ts:514`), and a hook that does not end holds the request and each creation, rename and delete behind it on `Daemon#changing` (`daemon.ts:1195`). | Rejected. It is the same defect in the second place that makes a commit, and it takes the runner of *Scope* item 1. |
| Build the refusal of a stage's block during a git operation here, as the issue's comments describe | It changes `Daemon#decided`, `Daemon#park` and each stage that calls them, which no line of *Done when* asks for, and the comments name #51, #41 and #42 as its owners. | Rejected. ## Operational impact

No migration, no environment variable and no dependency. The protocol gains one optional field of `WorkItem`, `wordOwed`: a window of an earlier build ignores it, and a daemon of an earlier build sends none, which a client reads as null. A deployer should know of two changes in what git meets. The git that makes a commit of Owlery's now runs with no input and in a process group of its own. Its hooks had no input from git before either, so a hook that reads its input sees what it saw. A commit that takes longer than five minutes is ended, where it used to run to its end. This pull request does not move the version: `routing.md` says the version already stands at 0.0.5.
