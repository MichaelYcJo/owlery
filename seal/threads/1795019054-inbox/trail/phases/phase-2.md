## What this phase found

**The frame holds, with one row that leaves a part out.** Every path `frame/design.md` *Data & interfaces* and *Removes* name for the window was opened at `5be3d88` and is where the frame says: `apps/desktop/src/renderer/renderer.ts`, `view.ts` with `tabLabel`, `index.html` with the two kind buttons and the form's two options, and the protocol in `src/shared/protocol.ts` as phase 1's record describes it. `routing.md` answers Planning `the session` and `frame/design.md` carries that mark. `frame/plan.md` *Phases* row 2 names *Scope* items 3, 6, 7 and 8 and leaves out the window's half of item 5, the close control on each tab. That is the first departure below.

**What the window does now.**

- The top bar has one "+" button per kind of pane the daemon offers, in the daemon's order, then "+ Work item". The form's choice lists the same kinds. Both are built once per connection, from `ready.paneKinds`.
- The side panel's first list is headed "Inbox". Each work item is one line, a button: the title and the state on the first row, the branch and the new commits on the second. The line's tooltip is the worktree's folder.
- A click on a line shows the work item's most recent live pane. Where it has none, the window sends `start` with the work item's id and the first kind that reports state.
- Each tab is a label and a close control. The close control sends `close` and does nothing else. The tab and its terminal go when an `inbox` no longer lists the session, whoever closed it. Where the closed pane was in front, the last remaining tab comes in front.
- At each `inbox` the window replaces both of its lists, raises a notification for each session whose state became `waiting` or `finished`, drops the panes the lists no longer hold, and redraws the lines.

**Departures from the frame and decisions made while building, each with its grounds.**

- *The close control on each tab was built in this phase.* `frame/plan.md` *Phases* row 2 does not name it, and row 1 delivers item 5 "in the daemon and the protocol". `frame/design.md` *Scope* item 5 says "The window puts a close control on each tab", this is the last phase, and the window had to drop a tab at an `inbox` that no longer lists it in any case. Judged against `frame/design.md` *Scope* item 5.
- *A line's state is that of the work item's most recent live pane of a kind that reports state.* Item 6 says "the state of its most recent pane that reports state". Item 1 says a session that has exited is `alive: false` "whatever its last state", and an exited session keeps that last state in the lists. A line that read it would say `working` for a process that ended, with nothing left to correct it. So `inboxLine` passes over a pane that is not alive and reads the next most recent one. A work item whose only agent pane exited shows no state. Judged against `frame/design.md` *Scope* items 1 and 6.
- *"Most recent" is the highest session id.* The daemon numbers sessions in the order it starts them, and `SessionInfo` carries no time.
- *The form preselects the first kind that reports state, and lists the kinds in the daemon's order.* The form listed Claude Code first before this phase and Shell second. The daemon's order is Shell first. Preselecting the kind a line opens keeps the form's default what it was, and `agentKind` in `view.ts` is the one place that picks that kind for both. Judged against `frame/design.md` *Scope* items 3 and 7.
- *A window that finds no live session opens a pane of the first kind the daemon offers.* The window used to open a shell there by name. The first kind in the daemon's list is the shell, so a person sees what they saw. Judged against item 3, "names no kind itself".
- *A pane of a kind the list does not hold is labelled with the kind as the daemon spells it.* The sessions and the kinds come from one daemon, so this is reached only if the daemon lists a session of a kind it does not offer.
- *The notification's text.* The title is the work item's title, or the tab's label for a pane without a work item. The body is "Waiting for you" or "Finished". Judged against item 8, "saying which".
- *No notification at `ready`.* The window takes the states it finds at connection as they are and notifies only of a change an `inbox` brings. A reload would otherwise notify again of every session that waits.
- *A session an `inbox` lists for the first time counts as having had no state.* The daemon starts every session without one, so this only names the case.
- *"In front" is the pane whose tab is shown, while `document.hasFocus()` is true.* Judged against item 8.
- *A pane another client opened gets its terminal here when its work item's line is clicked.* The window attaches to it then, as it attaches to the sessions of `ready`. It is not given a tab before that; `gaps.md` *Not done* says so.
- *The window does not remove a tab at its own `close`.* Phase 1's record allows either moment. One path, the `inbox`, removes a tab whoever closed the pane.
- *`workItemLine` is gone and `inboxLine` stands in its place.* It returns the line's four parts, and the page puts each in an element of its own, so the state can carry a colour.
- *The side panel's "Hook events" list stays.* `frame/design.md` *Removes* names the work-item list alone.
