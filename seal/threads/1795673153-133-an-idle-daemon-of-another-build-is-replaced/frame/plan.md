# Implementation Plan: an idle daemon of another build is replaced

## Technical context

The tree as read at `f2b74826`.

The work stands on four places of `apps/desktop`, and `frame/design.md` *Grounding* holds what each does today:

- **The main process finds the daemon.** `src/main/daemon-client.ts#ensureDaemon` (`:42-72`) returns a daemon that answers, or starts one. `#answers` (`:8-22`) says hello and reads the type of `ready`. `#stopDaemon` (`:106-119`) signals the process `daemon.json` names after a daemon answered there, and waits until it is gone. `src/main/daemon-control.ts#daemonControl` runs each start and each stop in turn, so a replacement placed inside the `start` act cannot meet a stop or a second start half way.
- **The daemon's process.** `src/daemon/main.ts` holds the one `stop` (`:55-65`), which SIGTERM, SIGINT and the idle exit call, and writes `daemon.json` after it listens (`:102-103`). Its standard output is `daemon.log` of the run folder (`src/main/daemon-client.ts:46-54`).
- **The daemon's handler.** `src/daemon/daemon.ts#handle` (`:965`) is one `switch` on the message's type, whose `default` returns (`:1763-1764`).
- **The window.** Every message leaves through `src/renderer/shared.ts#send` (`:62-64`), and every refusal arrives at `case "error"` of `src/renderer/renderer.ts#onMessage` (`:2010-2050`).

Constraints:

- A daemon of a build before this work knows none of what this work adds. So the replacement reads only what such a daemon already sends, its `ready`, and stops it only by the signal it already takes. The answer of *Scope* item 5 exists in a daemon from this build on, so it serves a window of a later build, and item 8 is what a window does until then.
- The daemon outlives the app, so each part of this work that lives in the daemon reaches a person one update late. That is the ground for building the daemon's parts in release 0.0.5, before the first public release, 0.1.0, and not after it.
- `docs/architecture.md` *What a session survives*: an update ends no agent. The judgment of *Scope* item 2 falls toward keeping on every doubt.

The failure scenario of the chosen approach, in six months:

- **A kind of work the lists do not show.** Someone gives the daemon a job that is no pane, no headless session and no chain, and adds it to `Daemon#checkIdle`. The lists still read as idle while it runs, and a load replaces the daemon under it. Scenario D of `frame/design.md` is where that shows, once the job's case is added there, and the docstring of the unit of *Scope* item 1 names `Daemon#checkIdle` as the fact it mirrors.
- **A second client.** The load judges the daemon idle, and before the signal lands another client starts a pane, which the stop ends. The interval runs from the hello the judgment reads to the signal `stopDaemon` sends after a hello of its own. Where one app runs on a run folder, its window is the one client and waits for the load's answer. Where a second app of another build shares the run folder (`frame/design.md` *Grounding*), which only a developer's Mac does, its window is a second client today. Its pane can end in that interval, and the replacement can end the daemon that app just started (`trail/phases/phase-1.md`, the paragraph on that interval). *Scope* item 3 bounds the replacements to one per build, and this release accepts the interval for that case. The phone (v0.2) is the first second client every person has, and its work weighs this interval.
- **The memory of replaced builds hides a replacement a developer wanted.** A developer who rebuilds to an earlier build's exact script while the app runs keeps the daemon of the build between, with the notice. "Restart Daemon…" replaces it.
- **The wait of item 8 cuts a slow request.** It only arms against a daemon that sends no `answersUnknown`, which is a build from before the first public release, so it ages out with those daemons. A person who meets it sees a sentence that says the daemon has not answered, which is true at that moment. A creation arms no wait, since a refusal before its answer would turn the Create button back on and a second press would make a second work item (round 2, finding 1).

## Operational impact

- No migration, no new environment variable and no new dependency.
- **The protocol gains two optional fields**, `answersUnknown` of `ready` and `unknown` of `error`. A client of an earlier build ignores both.
- **`daemon.log` gains two kinds of line** (`frame/design.md` *Data & interfaces*). The app reads back only the last line of a start that failed, which neither is.
- **An app started from a checkout now replaces an idle daemon of another build on the run folder it shares**, where it only said so before. An agent that starts the app with a user data folder of its own, as the suite does with `--user-data-dir`, meets no daemon but its own.
- **The first load after an update can take longer**: a comment of `apps/desktop/test/daemon-restart.test.ts` says a daemon's stop took 7 ms where it was measured (`read`), and the start of a daemon follows it.
- This pull request does not move the version. `routing.md` *Why this way* gives the move to the release's own work item.
