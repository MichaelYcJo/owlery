- **The command's input is the null device.** *Scope* item 6 reads "Its input is closed". A process started with no descriptor 0 gives that number to the first file it opens, and its reads then land in that file. A read of the null device ends at once, which is what the item asks of the run: a command that waits for a key gets none. Judged against item 6's own grounds, "as a check on another machine runs it".
- **What an earlier run printed is removed when the next command starts, and three ends keep nothing.** *Scope* item 9 has the daemon write the output "when the run ends, whatever its result", "in place of the file an earlier run left". `GateRun.output` says whether a `readGateOutput` has text to answer with, and it is false while a command runs. A file left by the run before would answer for a run that is still going, or for one the daemon's end cut. So the file goes before the command starts. A command that printed nothing leaves no file, and a daemon that closes writes none, since it stores nothing of the chain there either.
- **`cut` says that the kept text is as long as the bound.** *Data & interfaces* has `cut` say "the run printed more than is kept". The file of the run folder is the command's text and nothing else, so a daemon started later has the text's length alone to answer from. The runner keeps the last `GATE_OUTPUT_CHARS` characters, and `gate.ts#outputCut` reads a text of that length as cut. A command that printed exactly that many characters is answered as cut with nothing lost.
- **`Standing` holds the gate's commit and the paths that differ, not the runs.** *Scope* item 1 gives `Standing` "the runs of `trail/gate.md`". The gate's row reads two values: `gateCommit`, the commit the newest run block names, and `sinceGate`, the paths at which that commit's tree and the head's differ. `chain.ts#gateHolds` reads both, and phase 3's row reads `gateCommit` as the seal's target.
- **A gate record the reader refuses stops the chain at every step.** *Scope* item 3 has the daemon start "no stage that reads it". `chain.ts#standingOf` reads every record before it says the step, as it does for the round records, so a refused line of `trail/gate.md` at the head also stops a chain that owes a round.
- **The run's block is appended to the record as the head holds it.** *Scope* item 7 appends "below what stands there". The worktree may hold a change of `trail/gate.md` that no commit holds, since the start's check passes a change inside the work item's directory. The daemon builds the text on the file the head commit holds and writes it over the worktree's, so no run block a person wrote by hand is committed with the daemon's. Judged against *Scope* item 11, "Only the daemon's own run counts".

**Constraints found by trying.**

- macOS's `/bin/sh` gives itself the variable `TERM=dumb` where it inherits none, and does not export it. So a command's own `$TERM` reads `dumb`, and a program it starts gets none. The case reads `env`.
- A process the command leaves behind can hold the two pipes after the shell has exited. The run ends 300 ms after the shell's exit all the same, and nothing printed after that is kept.
- A stop signals the shell's process group while the shell lives. A process that ignores the signal and outlives the shell is not killed: after the leader's exit the group's id may name another's processes, which is `adapters/claude.ts`'s reason too.
