# Design: 1795393338-broad-gate-and-sealer

Issue #42: nothing runs the broad gate on the head commit or asks a sealer for a verdict.

This frame keeps three words of `seal/threads/1795388700-review-rounds/frame/design.md` in the sense that frame gives them: the **chain**, a **stage** and the **step owed**. It adds five, each used in one sense. The **gate** is the stage in which the daemon runs the repository's broad gate command. The **gate's commit** is the commit that the newest run block of `trail/gate.md` names. The **closing records** are the files of the work item's directory that *Data & interfaces* lists under that name. The gate **holds at the head** where no path but a closing record differs between the gate's commit and the branch's head. A **seal** is a verdict block of `guarantee.md` that reads `sealed`. Two names of #41's code hold the word "gate" in another sense: `chain.ts#Gate` and `chain.ts#gateBefore` say what comes before a fix pass, and neither is this frame's gate.

## Scope

### The order

1. **The order's function gains the gate and the seal, and the resting state `reviewed` goes.** The rows below follow the row of the verifying round in the table of `seal/threads/1795388700-review-rounds/frame/design.md` *Scope* item 4, and they replace that table's last row. The first row that holds decides, as there. In the merged code the table is `chain.ts#stepOwed`. Its `Step` gains `{ is: "gate", round, head }`, `{ is: "seal", round, commit, run }` and `{ is: "sealed", round, at }`, where `commit` and `at` are the gate's commit and not the head, and loses `reviewed`. `Standing` gains what the rows read, each from the file as the head commit holds it, which is how `chain.ts#standingOf` reads the round records. `gateCommit` is the gate's commit, resolved whole, and `sinceGate` is the paths of item 2; `chain.ts#gateHolds` reads the two. `verdicts` is every verdict block of `guarantee.md`, and `sealCommit` is the commit the newest of them names where it reads `sealed`, resolved whole. A newest run block or a sealed verdict that names a commit the repository does not hold resolves to null, so the gate, or the seal, is owed again, and the next block is appended below it.

   | What the records and git say | The step owed |
   |---|---|
   | The gate does not hold at the head: `trail/gate.md` holds no run block, or a path that is no closing record differs between the gate's commit and the branch's head | The gate, on the branch's head |
   | `guarantee.md` holds no verdict block, or its newest verdict block is no seal whose `target:` names the gate's commit | The seal, on the gate's commit |
   | None of the above | The chain is `sealed` |

   The rows above them are #41's. So a change outside the work item's directory owes a verifying round before a gate, and a decision that stands `reversed` owes its fix pass before a gate. No seal is given while a decision stands `reversed`.
2. **Whether the gate holds is read from two trees, not from a walk of commits.** The daemon lists the paths that differ between the gate's commit and the branch's head, with `git diff --name-only` (`worktrees.ts#pathsBetween`). The gate holds where each listed path is a closing record. So a merge commit, a decision's commit and an answer's commit after the gate's commit each owe the gate again. `worktrees.ts#pathsOfCommits`, which #41 reads the commits after a round's target with, walks commits and leaves a merge's own changes out, so it is not this read.
3. **A record the daemon cannot read stops the chain.** Where the reader refuses a line of `trail/gate.md` or of `guarantee.md`, the daemon appends nothing to that file and starts no stage. `chain.ts#standingOf` reads every record before the order gives a step, so such a line stops the chain whatever step it owes, a round among them. The chain stops with a sentence that names the file and the line. `standingOf` throws it as a `ChainStop`, as it does for a round record the reader refuses, from the refusals `seal-records.ts#readGate` and `seal-records.ts#readGuarantee` give.

### The gate

4. **The gate's command is the `Broad gate` key of the records root's `config.json` in the work item's worktree.** The daemon reads it with `records-place.ts#readRecordsPlace` when the gate starts, after the check of item 5, so the text it reads is the text the head commit holds. A `getSeal` is refused, among the refusals of #41's *Scope* item 1 (`Daemon#whyNoChain`), where that key holds no command, so no round is spent on a branch that no gate can pass. A gate that finds no command stops the chain. What stops a gate before its command starts lists no stage, since a stage holds the command and its exit: the chain stops with the sentence of `chain.ts#gateNotRunSays`, "The broad gate did not run: …".
5. **The gate runs on a clean worktree at the branch's head.** Before the run the daemon reads the head and holds the worktree to the rule of #41's *Scope* item 6 (`Daemon#noChangeOutside`): no tracked file with a change no commit holds, and no untracked file, outside the work item's directory. After the run it reads both again. Where the head moved, or such a change stands, no record is written, and the chain stops with a sentence that names the path or the two commits. Before the run that sentence is `gateNotRunSays`'s and no stage is listed (item 4). After the run the gate's stage is `failed`.
6. **The daemon runs the command with no terminal, as a check on another machine runs it.** The command is passed whole to `/bin/sh -c`, in the worktree, as the leader of a process group of its own. Its input is the null device, so a read of it ends at once, and its two output streams are pipes. Its environment is a pane's (`pty.ts#terminalEnv`) without `TERM` and `COLORTERM`, and with the `PATH` that the person's interactive login shell prints. `gate.ts#loginPath` asks that shell at the first gate of the daemon's life and never again, in the way `adapters/claude.ts#lookupCommand` asks it, with a script and a wait of its own: `gate.ts` imports nothing of `adapters/claude.ts`. Where the shell prints no `PATH`, the command runs with a pane's own. No stage of the work item starts before the command's process has exited.
7. **A run that exits with 0 is recorded and committed.** The daemon appends one run block, `run: <head> against <base commit>`, to `trail/gate.md` of the work item's directory, below what the head commit holds of the file, and writes that text over the worktree's file. So no line that the worktree alone holds, such as a run block a person wrote by hand, is committed with the daemon's run. The file's text is `seal-records.ts#gateText`'s, and the write goes through `record-writer.ts`. `<base commit>` is the work item's `baseCommit`. It commits the file through `Daemon#chainCommit`, with the subject *Data & interfaces* gives and the trailer `Seal-Routing: <directory's name>`.
8. **Any other end stops the chain and commits nothing.** The other ends are an exit with another code, a signal, the gate's time limit, a client's `stopGate`, and an archive, a delete or a removal of the work item. The stage is `failed`, and its sentence says the exit code or what ended the run. A daemon that closes ends the process group as well and stores nothing, as it does of a stage's session: `Daemon#close` waits for every chain's run, and a command left running would hold the close. The work item's line then waits, with that sentence in its second row, by #41's *Scope* item 27. A later `getSeal` runs the step owed, which is the gate again unless the branch changed.
9. **What the command printed stays within reach after the daemon ends.** The daemon keeps the last `GATE_OUTPUT_CHARS` characters of the two streams, in the order they arrived. Before the command starts, it removes what an earlier run of the work item left. When the run ends, whatever its result, it writes the kept characters to one file of its run folder for the work item. A command that printed nothing leaves no file, and a daemon that closes during the run writes none. A daemon given no run folder keeps them in memory. A client reads them with `readGateOutput`. A delete of the work item removes the file.
10. **The gate has a time limit and a stop.** The daemon ends the process group at `GATE_LIMIT_MS` from the start, and at a client's `stopGate`, with the signal and the wait that a role session's stop has. `frame/questions.md` Q2 holds the limit's value.
11. **Only the daemon's own run counts.** No message of a client records a run, and the daemon reads no result but the exit of the process it started under item 6.
12. **The gate has a ledger entry.** When the run ends the daemon calls `Ledger#add` with the stage `{ role: null, stage: "gate" }`, the run's two times, its state, what stopped it, and `usage` null. `Daemon#enter` makes a session's entry and takes a session, so the gate's call is its own, with the repository's folder and the branch as the store holds them at the gate's start.

### The seal

13. **The seal stage is a fresh sealer session that reads files only, in the work item's worktree.** The daemon launches a sealer at `seal` through `Daemon#runStage`, the method every stage that is a session starts through, and resumes no conversation. The prompt holds the run's number and the work item's directory. The run's number is one more than the count of the verdict blocks that `guarantee.md` holds at the head. ## Data & interfaces

**The closing records** of a work item's directory: `trail/gate.md`, `guarantee.md` and `trail/refusals.md`.

**Where each field of `docs/product.md` *The seal* is read.** The verdict block gains only what no other committed record holds.

| Field | Where it is read |
|---|---|
| tree | The commit of the newest verdict block's `target:`, and the `Branch` row of `routing.md` |
| base | The base of the same `target:` line |
| item | The work item's directory, which the guarantee's first heading names |
| gate | The newest run block of `trail/gate.md`. A seal's target is that commit (*Scope* item 1) |
| rounds | The round records of `trail/rounds/` at the sealed commit |
| who built, who judged, the model, the rules | The daemon's lines of the verdict block, below |

**The verdict block**, in `record-blocks.ts` and in `pr-check/lib/fields.py`. The keys `target:`, `original:` and `Verdict:` stand at `14ee70e`. The daemon's lines are the keys the daemon writes, and each reader holds each of them at most once.

| Key | Value | Written by |
|---|---|---|
| `target:` | `<sha> against <base>` | the sealer, as the prompt gave it |
| `original:` | as it stands | nobody in Owlery's chain. A sealer's block that holds one is taken as it stands, since both grammars take the line |
| `Verdict:` | `sealed`, `withheld reason: <reason>` or `undecided question: <question>` | the sealer |
| `built-by:` | One name or more, joined by a comma and a space. A name is `the session` or a session's id, which holds no white space and no comma | the daemon |
| `judged-by:` | One session's id | the daemon |
| `model:` | The judging model's name, as its adapter reports it. It opens and ends with a character that is no white space, so a name of two words reads | the daemon |
| `rules:` | `owlery <version>`, with the version the daemon was given, which is one word | the daemon |
