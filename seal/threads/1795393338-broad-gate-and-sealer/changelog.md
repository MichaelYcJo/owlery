# Changelog: "Get a seal" runs the repository's broad gate and asks a sealer for a verdict

Issue #42. "Get a seal" ran a branch's review rounds and stopped there. Nothing ran the repository's own check on the commit the rounds had read, and nothing asked a party that built none of the work whether that commit holds, so no branch could be sealed.

- **Once the review rounds settle, Owlery runs the repository's broad gate on the branch's newest commit.** The broad gate is the command that `config.json` of the place for work records names under `Broad gate`, as that commit holds it. Owlery runs it in the work item's worktree through `/bin/sh`, with no terminal, as a check on another machine runs it, and with the `PATH` your login shell prints. Only this run counts, so tests you ran yourself are no gate. It runs only on a worktree that holds no change outside the work item's records. "Get a seal" is refused before any round where the repository names no command, with a sentence such as "seal/config.json of the worktree names no command under "Broad gate", so no broad gate can run on this branch and no seal can be given. Name the repository's check there, and commit it."
- **A gate that passes is committed as a record.** `trail/gate.md` of the work item's directory gains one block that names the commit the command ran on and the commit the branch was cut at. The commit holds that file alone, runs the repository's hooks, and is not pushed.
- **A gate that does not pass stops "Get a seal" and commits nothing.** That is a command that exits with another code than 0, one a signal ends, one that runs past 60 minutes, one you stop, and one under which the branch gained a commit or the worktree gained a change. The work item's line then stands under "Needs you", and its second row says why, for example "The broad gate failed: the command exited with code 3." The next press of "Get a seal" runs the gate again, and no round, unless the branch changed.
- **The work item's view lists the gate first under "Ask".** The line holds the mark and the word of the gate's state, the words "Broad gate" and the command. While the command runs it offers "Stop", which ends the command. Once the run has ended it offers "Show output", which draws what the command printed under the line, as a failed session's error output is drawn. A gate that failed says why under its line, for example "The command exited with code 3."
- **What the command printed stays readable after the daemon restarts.** Owlery keeps the last 262,144 characters of the command's two output streams in a file of its own folder, and says under the line where it kept the end alone. The file goes when the work item's next gate starts and when the work item is deleted. It is never committed, since a check's output can hold what your environment holds.
- **After a gate that passed, Owlery asks a sealer for a verdict on that commit.** The sealer is a fresh session that reads files and holds no tool that writes one, and each of its commands that asks for permission is refused. Its answer is its run's section of `guarantee.md`, which Owlery appends to that file and commits, below the sections of earlier runs.
- **The verdict decides what follows.** At `sealed` "Get a seal" has ended, and the sentence above the button reads, for example, "The sealer sealed 1a2b3c4, after round 2." At `withheld` it stops, the work item's line stands under "Needs you" with the reason, for example "The sealer withheld its verdict: round 2 closed a finding the tree still holds.", and the next press asks a sealer again. At `undecided` the sealer's question is first decided from the code and the repository's documents by an orchestrator session, and the decision is listed among those made without asking. The gate and the sealer then run again. A question they cannot answer parks the work item, and so does the question of the third `undecided` verdict of one work item and of every later one, with no decision asked.
- **A seal names no commit but the one the gate passed on.** After that commit only `trail/gate.md`, `guarantee.md` and `trail/refusals.md` of the work item's directory may change. Any other commit, a decision's, an answer's or a merge's among them, has the gate run again before a sealer is asked, and a commit that changes a file outside the work item's records has a review round run first.
- **The seal record names who built the work and who judged it.** Owlery adds four lines to the sealer's verdict block: `built-by:`, `judged-by:`, `model:` and `rules:`, which reads `owlery` and the app's version. A session you drove yourself is named `the session`. A fix pass's session is named by its own id, which the commit that records the pass carries in the trailer `Seal-Built-By:`. Owlery reads that trailer from the commits of the branch's own line, so a merge of the base branch into the work item's branch names no session of another work item. Where the session that judged is one of the sessions that built, Owlery writes no verdict and stops, and the pull request check refuses a block that names one session on both lines.
- **The approval line and the inbox name the two stages.** While the gate runs, the sealer's place reads "Broad gate" with the mark of work, and the line's second row in the inbox reads "Broad gate". While the sealer's session runs, the place reads "Judging" and the row reads "Sealer, verdict". A gate that failed is no failure of the sealer: the place then waits, reads "Gate failed", and says why under the places. A sealer's session that failed marks the place "Failed".
- **The pull request check reads the records Owlery writes.** The copy of the check under `pr-check/` takes the four new lines of a verdict block, lets `trail/refusals.md` follow the sealed commit beside the gate's record and the guarantee, and refuses a verdict whose judge is one of its builders. Its sentences for a missing gate record, a missing guarantee and a verdict that is not `sealed` say what Owlery does. A connected repository's check reads the new lines from the release that ships this work.
- **The role bundle's texts for the sealer say what Owlery's sealer does.** The sealer runs no command and writes no file, checks each claim by reading, and answers with its run's section. The steps that ran a command, read a pull request's body or wrote `guarantee.md` are gone from its definition, its form and its template.
- **The gate has an entry in the ledger.** It holds the gate's two times and how it ended, and no usage, since no agent's turn is spent on it.
- **No real sealer and no gate of a repository's own check has run under Owlery yet.** Every stage of the tests is played by a stand-in, and every gate of the tests is a command the test names. Whether a real sealer answers in the form Owlery reads, and how long a real check runs against the limit of 60 minutes, is measured by the first run on a branch of Owlery's own. `pnpm run role:refusal:sealer` asks a real sealer to write a file, to show the refusal, and spends your usage.
- **A sealed branch does not light the seal's place yet, and no pull request is opened.** The sentence above "Get a seal" says that the sealer sealed, and the seal's place still reads "No seal yet". A `withheld` verdict starts no fix pass by itself: you read the reason and fix what it names.
- **After an update, no gate and no sealer runs until the daemon restarts.** A daemon started by the build before this one stops at the review rounds, and the status line already names a daemon of another build. A work item whose rounds an earlier build of this release left settled shows no sentence above "Get a seal", and the next press goes on from the committed records.
- **For a client of the daemon:** a chain's `state` is `running`, `parked`, `stopped` or `sealed`, and `reviewed` and `reviewedAt` are gone. A stage's `kind` may be `gate` or `seal`, and each stage carries `gate`: `null`, or for a broad gate `command`, `exitCode` (`null` while it runs and where no process exited) and `output` (whether its output can be read). `stopGate`, with `requestId` and `workItemId`, ends the running gate's command and is answered with `done`, or with an `error` where none runs. `readGateOutput`, with the same fields, is answered with `gateOutput`, which carries `text` and `cut`, or with an `error` where no output is kept. `getSeal` is answered with an `error` where the worktree's `config.json` names no broad gate command. `readLedger` lists a gate's entry with the stage `{ role: null, stage: "gate" }`. A window of an earlier build sends none of the new messages.
