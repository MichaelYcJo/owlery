## Data & interfaces

**The pane's command** (`hooks.ts#claudePaneCommand`): `exec claude --settings <file> [--plugin-dir <bundle> --append-system-prompt-file <head>] [--continue]`. The bracketed part is given where the pane carries the chain. `paneCommands` takes one more argument, a function from a pane's folder to what the pane carries, so `hooks.ts` reads no repository itself. The daemon's `commandFor` takes a `PaneStart` as its third argument (`daemon.ts`), which holds whether the pane continues, the folder it opens in and the work item's base.

**The pane's environment** where it carries the chain: `OWLERY_CHAIN`, the launcher's absolute path, and `OWLERY_BASE`, the work item's base branch where a round's target line takes its name and otherwise the commit the branch was cut at, as `chain.ts#roundBase` chooses between the two. A pane of a work item that records neither gets no `OWLERY_BASE`, and the command then asks for `--base`.

**The pane's settings file**: `claude-hooks.json` as today, and a second file of the run folder for a pane under the choice "the owl chain", which holds the same hooks and `enabledPlugins`. The daemon writes the second file before each such launch, from the person's files as they then stand.

**The chain command**, run in a worktree. Each subcommand but `ask` prints one JSON object on its first line and exits with 0, or prints a sentence on its error output, exits with 1 and commits nothing.

| Subcommand | Does |
|---|---|
| `owed [--base <base>]` | Reads the records at the head and prints the step `chain.ts#stepOwed` owes: `start`, `round`, `fix-pass`, `gate`, `seal`, `sealed` or `parked`. For `round`, `fix-pass` and `seal` it writes the stage's prompt and the role's rules file (`claude-roles.ts#rulesText`, with the head of scope item 8 for a pane's subagent) under `chain/<work item>/` of the run folder and prints their paths with the bundle agent's name |
| `start [--base <base>] [--automation <yes or no>]` | Makes the work item's directory and commits its `routing.md`, which names the planner and the implementer as `the session`, where no directory names the branch. With `--automation` the routing holds the `Automation` row with that answer. Where a routing stands, an answer it does not hold is refused, naming the file to change |
| `round <answer-file> [--base <base>]` | Reads a proofer's answer, writes the round record the order owes and commits it |
| `fix-pass --by <session>` | After a fix pass's commits: reads the close blocks, checks each `fixed` commit, and commits the record with the pass's session in the `Seal-Built-By` trailer. `--by` is a subagent's id, or `the session` where the session fixed it itself. It reads the round record at the head, and refuses with the step the records owe where the close blocks are already committed |
| `gate` | Runs the `Broad gate` command of the records root's `config.json` at the head, with no terminal. A pass commits a run block of `trail/gate.md`. A failure prints what the command printed |
| `seal <answer-file> --judged-by <id> --model <name>` | Reads a sealer's section, completes its verdict block and commits `guarantee.md` |
| `body` | Writes the pull request body's seal section and the back's section, between their marker lines, into a file under `chain/<work item>/` of the run folder, and prints that file's path and the head it was composed at, for the session to pass to `gh pr create --body-file` |
| `ask` | The hook's subcommand, and the one that prints no JSON. It reads the `PreToolUse` event's JSON on its input and the routing of the directory that names the worktree's branch. It exits with 0 to let the call through. It exits with 2 and writes the reason to its error output to refuse it, which is how a hook's command refuses a tool call. It exits with 1, naming the input as not read, where the routing reads `yes` and the input is no such event, which the CLI reads as a hook's error that refuses nothing |

**The bundle's hook** (`apps/desktop/role-bundle/hooks/hooks.json`): one `PreToolUse` entry whose matcher is `AskUserQuestion` and whose command is `[ -z "$OWLERY_CHAIN" ] || "$OWLERY_CHAIN" ask`. A role session of the daemon runs with every hook off and with no `OWLERY_CHAIN`, so the hook acts in a pane alone.

**The protocol** (`apps/desktop/src/shared/protocol.ts`): the client message `getSeal` goes. A repository gains `chain`, what the daemon read for it: whether its folder is on the owl chain, whether the AgenticSeal plugin is enabled there, and the person's answer, `owlery`, `plugin` or null. `setRepository` gains the field `paneChain`. A daemon of an earlier build sends no `chain`, and the window then asks nothing.

**The store** (`repositories.ts`): a stored repository gains `paneChain`, absent in a file an earlier build wrote and read as null.

**The daemon**: `Daemon#startChain(workItemId, byPerson)`, public, in place of the `getSeal` case.
