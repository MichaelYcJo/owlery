# Phase 5: 1795497826-pane-carries-the-chain

## What this phase found

### Where the tree contradicted the frame

**A pane under the choice gets a settings file of its own, and not one second file.** `frame/design.md` *Data & interfaces* names "a second file of the run folder" for every pane under the choice "the owl chain". What the file holds differs by repository: `enabledPlugins` is merged from the user's settings, the folder's `.claude/settings.json` and the main checkout's `.claude/settings.local.json`. `claude` reads the file a moment after the daemon starts the person's login shell, so two panes of two repositories launched in that moment would share the later launch's plugins. Decision: the file is `claude-pane-<pane id>.json` in the run folder (`hooks.ts#writePaneSettings`), written before each such launch and written over at the next such launch of a pane of that id. A daemon numbers its panes from 1, so a later daemon writes over the files of an earlier one as its panes take their ids. Nothing removes a file whose id no later pane under the choice takes. Judged against scope item 10, "so both chains never run in one session".

**What a pane carries is read from its start, and not from its folder alone.** *Data & interfaces* says `paneCommands` takes "a function from a pane's folder to what the pane carries". The choice needs the repository's main checkout, where the local settings file stands, and the person's answer. `daemon.ts#PaneStart` gained `checkout` and `chosen`, and `carries` takes the start whole and answers a `hooks.ts#Carried`: the chain, and the `enabledPlugins` of the pane's own settings file or null. `hooks.ts` still reads no repository and no settings of the person's.

**The window asks by the main checkout, and the daemon launches by the pane's folder.** *Data & interfaces* gives a repository a `chain`, "whether its folder is on the owl chain", and scope item 1 reads the chain from the folder a pane opens in. The two differ on a branch that adds or removes Owlery's workflow. Where a worktree holds the workflow, the main checkout does not, and the plugin is enabled, the window asks nothing, no answer is kept, and the pane carries nothing of the bundle, by scope item 10's last sentence. The branch of issue #146 is such a worktree in this repository until its pull request merges, which is the order `frame/plan.md` *Overlap with the release* states. The phase built the frame as written and changed nothing for that worktree.

**Scope item 10 does not say what the answer means where the plugin is not enabled.** Decision: the answer is read only where the folder is on the owl chain and the person's Claude Code enables the plugin there. Where the plugin is off, the pane carries the chain with the settings file every pane shares, whatever answer is kept. Grounds: the owner's decision that the owl chain is on by default, and the choice exists to keep two chains out of one session. A person who answered "the AgenticSeal plugin" and later turns the plugin off gets the owl chain. The repository's settings still show the answer that is kept.

**Scope item 9 does not say what a value of `enabledPlugins` other than `true` and `false` is.** Decision: a key is read as enabled unless its value is `false`, and each value is kept as the person's file states it. Grounds: a key read as off that Claude Code loads puts two chains in one session, which is the defect the choice prevents, and a key read as on that Claude Code does not load costs the person one question.

**Scenario 5 names two files, and the window's wiring needed a third.** `apps/desktop/test/view.test.ts` holds the window's functions and `apps/desktop/test/daemon.test.ts` the store and the launch. Neither runs the dialog. `apps/desktop/test/chain-choice.test.ts` starts the built app with a Claude Code config folder of its own and holds the dialog over the "New work item" form, the answer, the next pane, the settings, and the config folder's bytes. Scenario 6 names `hooks.test.ts` and `daemon.test.ts`, and the cases of `pane-chain.ts#carriedIn` stand in `apps/desktop/test/pane-chain.test.ts`.

**A new work item of a folder the window holds no repository of is asked nothing.** The form takes any folder. Where the daemon has not listed the repository yet, the window holds no `chain` for it, so the first pane opens with no question, and the daemon launches it with nothing of the bundle where the plugin is enabled. The next Claude Code pane of the repository asks.

**`pane:run` takes on the agents and the skills of scenario 16's last part, and not the hooks.** `frame/design.md` scenario 16 says `pane:run` takes the last part on in phase 5. The second case of `apps/desktop/test/pane-session.test.ts` starts a pane under the choice, with the person's own settings read for the plugin, and asserts on the settings file, on the bundle's agents and on the absence of any agent or skill under the plugin's name. It does not read which hooks ran: phase 4's probe read that from the conversation file by hand, and this phase started no real `claude` to learn the form of that record. No agent ran either case of the file after this phase changed it.

### Decisions made while building

**The reader is `apps/desktop/src/daemon/claude-plugins.ts#readPlugins`, and it takes the config folder as its last argument.** It takes the pane's folder, the main checkout and the config folder, and answers the merged `enabledPlugins` with the enabled keys that are AgenticSeal's. The default of the config folder is `claudeConfigDir()`: the folder `CLAUDE_CONFIG_DIR` names in the daemon's environment, and otherwise `.claude` of the person's home. A pane inherits the daemon's environment, so that is the folder its `claude` reads, unless the person's login shell names another. Issue #160 passes the pane's own folder there. A plugin is told by the script its check runs, `records-place.ts#PLUGIN_CHECK`, in the install folder `plugins/installed_plugins.json` names for the key, and not by its name.

**The daemon is given the reader, and reads nothing of the person's without it.** `DaemonOptions.pluginEnabled` is what fills a repository's `chain.plugin`. `main.ts` gives it `readPlugins`. A daemon built without it, as most cases build one, tells its clients that no repository has the plugin enabled, so no case reads the person's own settings by default. `BuiltApp.start` gives the app a `CLAUDE_CONFIG_DIR` under its own user data folder for the same reason. No case pins that line: it can fail only on a machine whose owner enables the plugin.

**A repository's `chain` is read where its records place is read.** `Daemon#readRecords` reads both at an addition, at a setup and at each scheduled read, and a change of either sends the lists. The person's answer is the store's `paneChain`, and the lists carry it as `chain.chosen`.

**The window asks through one function, `renderer.ts#beforePane`.** The pane bar's buttons and the form's "Create" both go through it. Over the form the dialog opens as a second modal dialog, so the form keeps what was typed, and the creation is sent once the daemon answered `done` to the answer. The owl chain is the choice the dialog opens on. A dialog closed with no answer opens no pane and keeps none.

**Nothing of the dialog listens to its `close` event.** The first build cleared what waited on the dialog at that event. In the built app, started in the background, the event of a cancelled dialog arrived after the dialog had opened again, and dropped the creation that waited on the second answer. `chainAsked` is read at the daemon's answer to what the dialog sent, and nowhere else.

**The repository's settings show the field where the choice is read, and where an answer is kept.** Its menu holds "Ask at the next Claude Code pane", "The owl chain" and "The AgenticSeal plugin". The first takes the answer away.

### What was seen red

- The cases of `apps/desktop/test/claude-plugins.test.ts` failed before the reader stood, on the import of a module that was not there. Every other new case first ran against code that was already written, so each unit was shown red by `seal mutate`, one break at a time.
- `claude-plugins.ts`, nine mutants red: `CLAUDE_CONFIG_DIR` not read, the local file read before the project's, the project's read before the user's, the local file read from the worktree, a key read as enabled only where it is `true`, an install folder that stands taken for the plugin's, every enabled key taken for the plugin's, every entry asked to hold the script, and an `enabledPlugins` that is a list taken as stated.
- `hooks.ts`, six mutants red: the own file given where the launch names no plugins, the file without the hooks, the file without `enabledPlugins`, one file name for every pane, the file written under the shared file's path, and a shell asked what it carries.
- `pane-chain.ts`, six mutants red: the answer read where no plugin is enabled, no answer and the answer "plugin" both carrying, no answer carrying, the plugin's keys left as stated, the folder given as the main checkout, and every folder read as on the owl chain.
- `repositories.ts`, four mutants red: a changed answer read as no change, the answer not assigned, the answer of a file not read, and a file whose answer names neither chain taken.
- `view.ts`, ten mutants red: a shell asked, each of the three conditions of `asksChain` dropped in turn, each half of what shows the settings field dropped, the field's value, an unchanged answer sent, the answer "plugin" read as none, and the default of `settingsFields` set to no answer.
- `daemon.ts`, against the cases of `daemon.test.ts` under "a Claude Code pane and the owl chain", seven mutants red: the refusal of an answer that names neither chain, the answer not stored, the answer not passed to the launch, the worktree passed as the main checkout, the plugin read as off, the checkout read as on no chain, and the lists' `chosen` set to null.
- One mutant of `daemon.ts` SURVIVED: a change of what was read of the chain no longer counted as a change. The case then got its last step, which removes the main checkout's local settings file while no pane and no request is under way and waits for the lists that say the plugin is on again.
  The mutant is red against the case as it now stands.

The file's fourth case then came, which hides the field once the plugin is off, so each direction of the line that sets it is watched.
