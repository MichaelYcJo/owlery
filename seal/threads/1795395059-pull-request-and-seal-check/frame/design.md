## Scope

### The pull request stage

1. **After a seal the chain owes the pull request, where the work item's routing sends it to one.** When the order's function gives the step `sealed` (`chain.ts#stepOwed`, `seal/threads/1795393338-broad-gate-and-sealer/frame/design.md` *Scope* item 1), the chain's run, `daemon.ts#runChain`, reads two more things before it rests the chain in the state `sealed`. The first is the `Destination` row of the work item's `routing.md` at the branch's head, read with `worktrees.ts#fileAt` and `decision-record.ts#routingAnswer` as the seal stage reads the `Implementation` row. The second is the pull request the daemon stores for the work item (item 12). The pull request stage is owed where the row reads `open the pull request` and one of these holds: no pull request is stored, the stored one is `closed`, or the stored one is `open` and the commit it was last pushed at is not the branch's head. Where the row reads `stop before the pull request`, or the stored pull request is `merged`, no stage is owed and the chain rests. The order's function is not changed: `stepOwed` and its `Standing` gain nothing, it stays a function of the records and git, and what GitHub holds is read by the chain's run. Once the stage has ended well, the run rests the chain `sealed`, with the stage's sentence of *Data & interfaces* in place of the one `chain.ts#sealedSays` gives. Where a later start owes no stage, the chain keeps the stored pull request's sentence, "Pull request #N is open.", in place of `sealedSays`.
2. **A chain that is not `sealed` reaches no code of the stage.** The stage has one caller, the branch of the chain's run that item 1 names. No message of a client pushes a branch or opens a pull request.
3. **The stage commits nothing and writes no file in the worktree.** A commit after the gate's commit that is no closing record owes the gate again (`chain.ts#gateHolds`), so the stage would break the seal it carries. So no `pr.md` is written, which #42's frame left to this work to commit before the gate or to change the rule for (*Out of scope*, its first item). The body's file is written in the daemon's run folder, and in the system's temporary folder for a daemon given no run folder, and removed when the stage ends.
4. **The branch is pushed to one remote, with the person's git.** The remote is the first of these that names one: the remote of the work item's `baseBranch`, where that names a remote's branch; the clone's one remote, where it has one; `origin`, where the clone has it. Where none names one, the stage fails with a sentence that says the clone names several remotes and no base on one of them, or, where the clone has no remote, with a sentence that says so. The daemon runs `git push --set-upstream <remote> <branch>` in the worktree, with no `--force` and with `GIT_TERMINAL_PROMPT=0`, so a push that would ask for a credential fails. The repository's own push hooks run. A push the remote refuses fails the stage with git's first line.
5. **Every call to GitHub goes through the person's `gh`, and Owlery reads and stores no token.** The daemon starts `gh` with no shell and no terminal, in the worktree, as the leader of a process group of its own. Its environment is the broad gate's (`gate.ts#gateEnvironment`): a pane's, without the two variables that say a terminal stands, with the `PATH` the person's interactive login shell prints, which the daemon asks once for the gate and for this stage (`gate.ts#loginPath`). To it the stage adds `GH_PROMPT_DISABLED=1` and `NO_COLOR=1`. Where no `gh` stands on that `PATH`, the stage fails with a sentence that says so and names `https://cli.github.com`. One module, `github.ts`, holds every call, and the calls are of four kinds: `gh pr list`, `gh pr create`, `gh pr edit` and `gh pr view`. Each call and the push end at `GITHUB_LIMIT_MS`, and the process group is ended as a broad gate's command is (`gate.ts#startGate`): a signal, and a kill after the wait.
6. **An open pull request of the branch is updated, and a second one is never opened.** After the push of item 4, the stage runs `gh pr list --head <branch> --state open --json number,url,headRefOid,body`. Where it lists one pull request, the stage replaces the seal section of that body (item 10) and sends the body with `gh pr edit <url> --body-file <file>`. Where it lists none, the stage runs `gh pr create --head <branch> --title <title> --body-file <file>`, with `--base <branch>` where item 8 gives one, and reads the address `gh` prints. Where it lists more than one, the stage fails with a sentence that names their numbers. The pull request is opened ready and never as a draft.
7. **The title is the work item's own.** It is the work item's `title`, and where that is empty, the subject of the oldest commit the branch holds after `baseCommit`. A title is cut at 256 characters. An edit of an open pull request leaves its title as it is.
8. **The base is the work item's base branch, named as GitHub names it.** Where `baseBranch` names a remote's branch, the base is that name without the remote. Where it names a local branch, the base is that branch's name. Where it is null, the daemon names no base, and `gh` takes the repository's default branch.
9. **The body is composed from the records the head commit holds, and opens with the seal section.** The seal section holds the newest verdict block of `guarantee.md`, copied line for line, under a heading and one fixed sentence that names the record's path. The block is the lines from `line` to `end` of the last `Verdict` that `seal-records.ts#readGuarantee` gives, so it holds the sealer's lines and the four the daemon wrote, `built-by:`, `judged-by:`, `model:` and `rules:`, as the record holds them. *Data & interfaces* gives the section whole. Below it the daemon writes, each under its own heading and each only where its record stands: `changelog.md` whole; for each round record its path and one line for each finding, with the finding's heading and its close's verdict; the newest run block of `trail/gate.md`; and each decision of `decisions.md` with what was decided and its grounds. Every record is read with `worktrees.ts#fileAt` and `#filesAt` at the branch's head and through the daemon's own readers: `seal-records.ts#readGuarantee` and `#readGate`, `round-record.ts#readRoundRecord` and `decision-record.ts#readDecisionRecord`. Where the body would pass 65,536 UTF-16 code units, the parts below the seal section are replaced, the last first, each by its heading and one line under it that names the part's record, until the body fits. The seal section is never cut.
10. **Only the seal section is Owlery's in an open pull request's body.** At an edit the daemon reads the body `gh pr list` gave, replaces the lines from the opening marker to the closing marker with the new section, and changes no other line. Where the body holds no marker line, the section is put before the body's first line. Where it holds more than one opening marker or more than one closing marker, an opening marker with no closing one, a closing marker with no opening one, or a closing marker above the opening one, the stage fails with a sentence that says so, and changes nothing.
11. **A stage that fails stops its one chain, and nothing parks.** The stage throws a `StageStopped`, as a failed broad gate does (`daemon.ts#runGate`), and the chain is `stopped` with a sentence that names the stage and says why (`chain.ts#stoppedSays`), as #41's *Scope* item 14 has it: no `gh`, a `gh` that is not logged in, a push the remote refused, a pull request `gh` could not create or edit, a call that reached its limit. The seal stands, since nothing was committed. A later `getSeal` reads the records, finds the chain `sealed`, and runs the stage again by item 1. A question's block would be a commit after the seal, so no failure of the stage is written as a question (`frame/plan.md` *Alternatives considered*).

### The watch

12. **A work item carries its pull request, as GitHub last answered.** `WorkItem` gains `pullRequest`, a `PullRequest` or null. *Data & interfaces* gives the type. The daemon stores it with the work item, in `StoredWorkItem`, as it stores `setup` and `chain`. The stage writes it from a `gh pr view` of the address `gh pr create` printed or `gh pr list` gave. No record of the repository holds it.
13. **The daemon reads an open pull request again on a timer, with one call and no agent.** The read is `gh pr view <url> --json number,url,state,isDraft,headRefOid,mergedAt,statusCheckRollup`. It runs for each work item that is not archived and whose stored pull request is `open`: once at each client's hello and `PR_POLL_MS` after the stage has opened or edited the pull request, then every `PR_POLL_MS` while the pull request's checks are `pending` or its `head` is not the commit the stage pushed, and every `PR_REST_POLL_MS` otherwise. The timer runs only while a client is connected, as the read of the branches does. The watch holds neither the daemon nor the Mac: it keeps no process between two reads, and `checkIdle` and `wantsAwake` do not read it.
14. **The checks are read into three states, and the pull request into four.** A check of the kind `CheckRun` is `pending` until its `status` is `COMPLETED`, then `passed` for the conclusions `SUCCESS`, `NEUTRAL` and `SKIPPED`, and `failed` for every other. A check of the kind `StatusContext` is `pending` for the state `PENDING` or `EXPECTED`, `passed` for `SUCCESS`, and `failed` for every other. The pull request's `checks` is `none` where GitHub lists no check, `failed` where one check failed, `pending` where none failed and one is pending, and `passed` otherwise. An entry the daemon cannot read is kept as a check named by its position with the state `failed`, and decides nothing more.
15. **The work item's line shows the result.** Where no pane and no chain says more, a pull request whose checks are `pending` makes the line's state `working`, one whose checks `failed` makes it `waiting`, and one whose checks `passed` makes it `finished`. The line's second row says the result in the words of *Data & interfaces*, and names the first failed check. The window raises the notification of a work item that begins to wait or finishes when the line's state changes so, as it does for a session.
16. **A read that fails changes nothing but its own sentence.** Where `gh` fails or its answer does not read, the stored pull request keeps what the last read gave, and its `failure` holds one sentence with `gh`'s first line. The next read runs at `PR_REST_POLL_MS`. A read that succeeds clears the sentence.
17. **A work item whose pull request merged shows no decision on its line, in the summary or under the filter.** Where the stored pull request is `merged`, the line's mark of decisions is empty, `changesSince` counts no decision of the work item, and the filter of the decisions does not list it. The work item's view and its preview go on listing every decision with its grounds, and the record keeps them. The watch reads a `merged` or a `closed` pull request no more.
18. **An archive, a delete and a removal change nothing on GitHub.** The watch reads no archived work item. A delete removes the stored pull request with its work item, and names no ref of a remote to git, as today.

## Data & interfaces

**The seal section of a pull request's body.** The two marker lines are `<!-- owlery:seal -->` and `<!-- /owlery:seal -->`, each alone on its line. `<path>` is the path of `guarantee.md` from the repository's top.
