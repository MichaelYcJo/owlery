**Constraints.**

- Nothing may be committed after the seal but a closing record (`seal/threads/1795393338-broad-gate-and-sealer/frame/design.md` *Scope* item 2). So the stage writes no record, and the pull request is the daemon's state.
- The daemon runs no Python (`docs/architecture.md` *What we take from AgenticSeal*). So whatever the check compares the body with is composed twice, once in the daemon's code and once in the check's.
- The person's `gh` cannot post a check, and a job cannot end as neutral (`frame/design.md` *Grounding*, GitHub's documents).
- No case and no probe reaches GitHub or a real remote, and none starts a real `claude`, by the owner's rules of this run. A start of the built app goes through `apps/desktop/test/built-app.ts` `BuiltApp.start` with `OWLERY_BACKGROUND=1`.
- `README.md` and `README.ko.md` are held to equal counts of headings and of table rows by the repository's broad gate (`seal/config.json`, `Broad gate`).

**The failure scenario of the chosen approach.** In six months the first failure is the posted check. The workflow of a connected repository posts `Owlery seal` with the run's token, and an administrator required that name. A pull request from a fork gets no posted check, so it waits on a check that never comes until an administrator lets it through. The same happens to every pull request where the organisation's settings hand workflows a token that cannot write a check, and there no pull request passes until someone changes the setting or stops requiring the check. The second failure: `gh` changes the shape of `statusCheckRollup` or the words it prints after `pr create`, the daemon reads no address or no check, and every stage fails after the push has already landed, so the branch is on the remote with no pull request until the person opens one by hand. The third: a person's `gh` resolves another repository in the worktree than the one the daemon pushed to, as in a clone with a fork and an upstream, and the stage fails with `gh`'s words at each start. The fourth: the seal section's two composers drift, the daemon writes a section the check refuses, and every pull request Owlery opens is red until a release fixes one of them. Scenario 2 runs the check's Python over the daemon's body in every run of the suite, which catches the drift for the shapes that case writes. The fifth: the watch reads GitHub every 30 seconds for each open pull request with a pending check, and a person with many such work items meets `gh`'s rate limit, after which each read fails with its sentence until the limit lifts.

## Operational impact

- **No migration.** A work item an earlier build stored holds no pull request, and is read with none.
- **No new dependency of the app.** The stage needs the person's `gh` on the `PATH` of their login shell, logged in to the host of the repository, and a git that can push to the remote with no question asked. Where one is missing the stage stops with a sentence that says which, and the seal stands.
- **The daemon pushes a branch to the person's remote and opens a pull request there, with nobody asked at that moment.** It does so only after a seal, only where the work item's `routing.md` reads `open the pull request`, never by force, and it sets the branch's upstream. The repository's push hooks run.
- **The daemon calls GitHub through `gh` while a client is connected**: once at a hello and then every 30 seconds for each open pull request with a pending check, and every 5 minutes for each other open one.
- **The workflow Owlery writes at a connection asks for the right to write checks**, and its step is handed the run's token. A repository connected by a build of the release branch before this work keeps the file it has, whose job posts nothing, since a committed file is kept. No release has shipped such a build.
- **A connected repository's check comes from the release that wrote its workflow.** A workflow that passes `--post` to a `pr-check/` without the option fails, so the option and the workflow's text ship in one release.
- **An administrator who requires `Owlery seal` blocks every pull request that gets no posted check**: one from a fork, and every one where the organisation gives workflows a token that cannot write a check. The dialog and the README say so.
- **`pr-check/` loses three files.** Nothing outside the folder loads them.
- **The protocol changes as `frame/design.md` *Data & interfaces* lists.** A window of an earlier build ignores the new field, and a window of this build reads its absence as no pull request.
- **The version does not move.** The first pull request of `release/v0.0.2` moved it. This work's `changelog.md` is written in phase 4.
