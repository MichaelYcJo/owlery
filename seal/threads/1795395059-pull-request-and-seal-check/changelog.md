# Changelog: a sealed branch opens its pull request, and GitHub shows the seal as a check

Issue #43. "Get a seal" ended at the sealer's verdict. Nothing pushed the sealed branch or opened its pull request, the pull request check refused the body of every pull request a "Get a seal" work item could have, and GitHub showed the verdict only as the result of a job, which cannot end as neutral.

- **After a seal, Owlery pushes the branch and opens the pull request.** This happens where the work item's `routing.md` reads `open the pull request`. Owlery pushes the commit the seal and its own check of the head speak of, named by its id, so a commit you make on the branch while the stage runs is not pushed. It pushes with your git, to one remote, never by force, and sets the branch's upstream. The remote is the one your base branch is on, or your clone's one remote, or `origin`. A push that would ask for a credential fails rather than waits, and your repository's push hooks run. Owlery then opens the pull request through your `gh`, found on the `PATH` your login shell prints. It calls `gh` to list, open, edit and read a pull request and for nothing else, and reads and stores no token.
- **A branch gets one pull request.** Where the branch already has an open pull request, Owlery replaces the seal section of its body and opens no second one. Every other line of that body is yours, and its title is left as it is. A new pull request takes the work item's title, or the subject of the branch's first commit where the title is empty, and is opened ready, against your base branch.
- **The body opens with the seal.** Its seal section, between the lines `<!-- owlery:seal -->` and `<!-- /owlery:seal -->`, copies the newest verdict block of the work item's `guarantee.md` as the commit holds it. Below it stand the changelog, each review round's findings with how each closed, the newest run of the broad gate and the decisions made without asking. Where the body would pass GitHub's limit of 65,536 characters, those parts give way to a line that names their record, the last first, and the seal section is never cut. A part that quotes one of the two marker lines on a line of its own, with nothing but spaces or tabs around it, gives way to that line whatever the body's length, so the body holds one seal section.
- **Opening the pull request commits nothing.** A commit after the seal would break it, so the pull request is kept by Owlery and in no record. Where the push or `gh` fails, "Get a seal" stops, the work item's line stands under "Needs you" with why, for example "The pull request stage failed: no gh stands on the PATH of the login shell, so Owlery cannot open the pull request; GitHub's CLI is at https://cli.github.com", and the seal stands. A push the remote refuses says why, for example "git push to origin failed: ! [rejected] … (fetch first)" for a branch that moved on the remote. The next press opens the pull request and runs no round, gate or sealer again. While the stage runs, the line's second row reads "Pull request".
- **The sentence above "Get a seal" names the pull request**, for example "Pull request #12 is open." or, after an update, "Pull request #12 carries the seal at 1a2b3c4."
- **Owlery reads an open pull request's checks while the window is open.** It reads each open pull request once when a window connects, every 30 seconds while a check runs or GitHub has not seen the pushed commit, and every 5 minutes otherwise, with one call of `gh` and no agent. Nothing is kept running between two reads, and the reads do not keep the Mac awake. A merged or closed pull request is read no more, and neither is an archived work item's.
- **The work item's line shows the result.** Its second row reads "Checks running", "Check failed: build", "Checks passed", "Pull request open" for one with no checks, "Merged" or "Closed". A failed check makes the line need you, and the line raises a notification where it begins to need you or finishes, as for a session. A pane that works or waits, a running or stopped chain, a park and a call waiting for you each still say more.
- **The work item's view lists the pull request under the seal's place.** It shows the pull request's number and its state, the result of its checks, and one row for each check with its state. The number opens the pull request in your browser, and a check's row opens the check. Where the last read failed, the view keeps the earlier answer and says why under the rows, for example "The last read failed, so the facts above are from the read before it: gh pr view exited with code 1: HTTP 502." The approval line and "Ask" list no step for the pull request.
- **A merged pull request takes the work item's decisions off the inbox.** As an archive does, the merge takes them off the line's mark, the summary and the filter of the decisions. The work item's view still lists each decision with its grounds, and the record keeps them.
- **The pull request check posts its verdict as a GitHub check named `Owlery seal`, on the pull request's head commit.** A ready pull request whose head commit carries a seal gets a passed check titled "Sealed at" and the sealed commit. One with no seal there gets a failed check titled "No seal at the head commit", and one whose records the check refuses otherwise, "The records are refused". A draft that would be refused gets a neutral check, "Draft: judged when it is ready", and a pull request that declares no work item a passed one, "Not judged: no work item is declared". The check's summary holds the verdict block and each refused line. The workflow's own job ends as before, and a check GitHub refuses to take changes no result.
- **The workflow Owlery commits at a connection lets its job post the check.** It asks for the right to write checks, hands the job the run's token and runs the check with `--post`. A pull request from a fork gets the job's result and no `Owlery seal` check, because GitHub gives its run a token that cannot write one.
- **An administrator makes `Owlery seal` required on GitHub, and Owlery changes no setting there.** The dialog "Records and check" says how, and says that a required check holds a fork's pull request until an administrator lets it through. For a repository that keeps AgenticSeal's `hygiene.yml`, it says that this workflow posts no such check. Its buttons now stay at its foot while a long plan scrolls. The README has a section on the check: what posts it, on which commit, what each result means and how to require it.
- **The check reads the body's seal section alone.** It refuses a section whose verdict block differs from the newest verdict block of the work item's `guarantee.md` at the head commit, and reads no other line of the body, which is yours to edit. A body with no seal section is not read. The check's copy of AgenticSeal's body composer, `pr_body.py`, and the two files only it loaded are gone from `pr-check/`, so a pull request no longer needs a `pr.md`.
- **Owlery writes no review and merges nothing.** The verdict is a check, and you merge.
- **No pull request has been opened on GitHub by Owlery yet, and no `Owlery seal` check posted.** Every test pushed to a repository on the same Mac and called a stand-in for `gh`, and every posted check went to a server on the same Mac. Whether your `gh` opens the pull request with the login it holds, and whether GitHub offers `Owlery seal` as a required check, is measured by the first pull request of Owlery's own that Owlery opens.
- **After an update, no pull request is opened until the daemon restarts.** A daemon started by the build before this one stops at the seal. A repository connected by an earlier build of this release keeps its workflow, whose job posts no check, until that file is rewritten.
- **For a client of the daemon:** a stage's `kind` may be `pull-request`. Wherever the daemon sends a work item, it carries `pullRequest`: `null`, or `number`, `url`, `state` (`open`, `merged` or `closed`), `head` (the commit GitHub last named as the head), `pushed` (the commit Owlery pushed), `checks` (`none`, `pending`, `passed` or `failed`), `list` (up to 50 checks, the failed ones first, each with `name`, `state` and `link`), `listCount`, `readAt` and `failure`. A daemon of an earlier build sends no such field, and a window reads its absence as no pull request.
