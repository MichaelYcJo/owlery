**The frame holds on its coordinates, and one of its claims does not.** The work item has no `frame/`. `routing.md` names issue #117 as the frame (Planning: the session). `apps/desktop/test/terminal-basics.test.ts` is unchanged since #111, so the issue's line numbers at #30's head (608, 760, 787) are this tree's (read: `git log` of the file). `SUBMENU_LEAVE_MS` is 300 in `src/renderer/menu.ts`, and the submenu case's failing check is the one after the move back onto Finder (read: run 44915064055, `work-item-menu.test.ts:369:35`). What this phase measured points to another cause, below.

**The spawn prompt's push and draft pull request were declined, so nothing was measured on GitHub's runner.** The prompt allowed pushing the branch and opening a draft pull request to read the `check` run. Contract rule 6 withholds both from every agent, and rule 3 ranks a spawn prompt below it. The causes below were measured on the owner's Mac by probes that recreate each failure. The runner's logs were read instead: runs 44915064055 and 44919934535 for the failing lines, and 44993092666, at #118's head, where the submenu case passed only at its retry `(retry x1)` as the first file of the `app` project. #118's one-at-a-time split did not remove that failure.

**The submenu case raced the 300 ms pause through the debugging port's round trips, and the page's speed is not the cause.** Between the move onto "Copy path", which starts the pause, and the move back onto Finder, which stops it, the case made three round trips: a read of the submenu, a read of Finder's place, and the move. The probe `test/test_tmp_menu.test.ts` (removed) ran the case with the page's processor slowed eightfold (`Emulation.setCPUThrottlingRate`), and it passed (executed). So the time on the runner is spent outside the window's page, between the case's process and the window. What the runner's first start does in that time is not measured (`gaps.md`). The case now hands the page the two arrivals, the `pointerenter` on "Copy path" and on the submenu and its Finder item, in one task of the page, so no turn of the pause's timer can fall between them. The close after the pause is timed by the page's own clock, at least `SUBMENU_LEAVE_MS` less a millisecond for the clock's rounding; the constant is exported from `menu.ts` for that. Judged against issue #117 *Done when* ("a case that does not race the timer and still fails where the pause is removed").

**The worktree link case pointed before the pane's text was drawn, and the terminal does not look again under a pointer that stays.** xterm's `Linkifier` (`node_modules/@xterm/xterm/src/browser/Linkifier.ts`, read) asks its link providers when the pointer comes onto a row, and a row drawn later is looked at again only where a link was already under the pointer. After `viewOf`, the view is in front at once, and the pane's replay comes from the daemon later. The probe `test/test_tmp_card.test.ts` (removed) stopped the daemon for two seconds across `viewOf("Korean input")`, with SIGSTOP and SIGCONT on the daemon of the app the probe started. It failed as run 44919934535 failed: "the window never showed a link under the pointer on row 3" in `clickLink`, and then the same three cases after it, `ArrowLeft with the Command key: expected '' to be '01'`, `expected 'Shell 3' to be 'Shell 2'` and "the window never showed one tab" (executed). Run 44915064055's failure, "the card of the link on row 3" at `:760` right after `openPane`, is the same cause with a new pane's output in place of the replay (read).

**The class is every place a case of the file points at a pane's row after a pane comes onto the stage.** It was listed from the helpers that point (`pointAt`, `restOn`, `clickLink`, `linkAt`) and each of their calls after `openPane`, `viewOf`, or a click that puts another view in front. `restOn` and `clickLink` now go through `comeOnto`, which brings the pointer onto the cell again from the row with no link every two seconds until the link or its card shows, fifteen seconds at most. `linkAt` is called only in the path case, right after `openPane`, and that case now waits for the link of its pane's last line first. The window draws the output in order, so every row read after it is drawn, and a `false` there is no longer read off an empty row.
