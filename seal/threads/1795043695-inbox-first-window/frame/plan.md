# Implementation Plan: the app opens on the inbox, not on a pane of terminals

## Technical context

The tree as read at `12cd34f`, and the window's code of issue #8 at `d3bc681`. The fold of direction B and of the summary screen read it at `1d5b49f`, and the fold of the polish at `b061855`, after phases 1 to 4 (`frame/design.md` *Grounding*).

`apps/desktop`: the window is three files in `src/renderer/`. `index.html` holds the page and its styles: a top bar, the terminal's stage and a side panel. `renderer.ts` holds the connection to the daemon, the terminals, and every element the page gains after load, built by hand with `document.createElement`. `view.ts` holds what the window says and decides as pure functions, and `test/view.test.ts` holds their cases. No case loads the page: the tests run with vitest in Electron's Node (`pnpm run test`), and `renderer.ts` is shown by a drive of the built app. `build.mjs` bundles `renderer.ts` and copies `index.html` and xterm's stylesheet into `dist/`. `src/main/main.ts` opens the one window. The daemon is `src/daemon/`, with its cases in `test/daemon.test.ts`, and `src/shared/protocol.ts` is what it and the window exchange.

These facts of the present window and daemon shape the build.

- **Every pane is made at `ready`.** `renderer.ts#onMessage` attaches each live session, and starts a pane of the first kind where none is alive. The inbox screen needs neither, and the daemon sends a session's output only to a client that started or attached it, so a window that attaches nothing receives no output.
- **A terminal is sized where it is displayed.** `renderer.ts#newTerminal` fits the terminal before the window sends `start` or `createWorkItem` with its columns and rows. `@xterm/addon-fit` 0.11.0 resizes nothing while the terminal's parent is not displayed. A creation sent from the inbox screen therefore carries xterm's default size, and the window makes the terminal once the view is shown, fits it and sends the real size, from `renderer.ts#terminalFor`.
- **The "Ask" section of issue #8 reads the pane in front.** At `d3bc681`, `view.ts#workItemInFront` gives the work item "Ask" asks in, and the list shows every headless session of every work item. The daemon's `ask` needs a work item and no pane.
- **The window reads no key and keeps no selection.** A line of the inbox is a button, and the page listens for no key outside a field and a terminal. Direction B's J, K and Enter and its preview need a selected line, which this work keeps by the work item's id, so that the redraw of the list at every `inbox` does not move it.
- **The protocol carries less than direction B draws.** It gives a count of new commits, a state without its time, and no text of what an agent asks, so the preview and the view's right column hold fewer parts than artboards B1 and B2 (`frame/design.md` *Scope* item 16).
- **Nothing records when a person last looked.** The daemon writes one file into its run folder, the list of work items, and a session's state lives in its memory alone. `docs/architecture.md` *The phone: the terminal session as a chat* keeps state off the UI's side, so the look the summary screen is worked out from is the daemon's to keep, and the protocol and the daemon change for it (`frame/design.md` *Scope* item 18).
- **A `ready` is sent before the counts of new commits are read.** At a hello the daemon sends the counts it holds and then reads git, and it reads nothing while no client is connected. A daemon started again therefore sends `null` for every count, and a daemon that had no client sends the counts of the last window's time, while the look holds the counts of that time too. The summary is worked out from `ready`, so the daemon reads before it answers (`frame/design.md` *Scope* item 18).
- **The page can load no typeface from the network.** Its content security policy is `default-src 'self'`, and artboards B1 and B2 load their three families from Google Fonts.

These facts of the window and the daemon as phases 1 to 4 left them shape phases 5 to 9.

- **The page's look is one `:root` block in `index.html`.** Direction B's colours and three typefaces are its properties, and the rules under it read them. Nothing is a theme, and the main process opens the window on one ground it names itself.
- **`renderer.ts` is one file of 740 lines that builds elements in 17 places.** The sidebar, a fourth screen, the search and the fuller preview each add to it.
- **The daemon reads one number per work item from git, and one word per session from a hook.** It keeps neither the time of a state nor anything else the event carried, and neither a commit's hash nor a file's name.
- **A work item's branch is cut at `HEAD`, and the branch `HEAD` was on is not kept.** A work item made before phase 5 has no base branch to say.
- **The tree's code holds none of the seal's reds,** and the one drawing it copies into `dist/` is the icon.

The drive needs a run folder with a short path: with a long one the daemon exits at once (issue #19), and Electron's `--user-data-dir` chooses the folder (`trail/phases/phase-2.md` of `1795042041-headless-session` at `d3bc681`).

**The failure scenario of the chosen approach.** The window stays hand-built DOM that redraws a whole list at every `inbox`, now in three screens, a preview and a list inside the view. Milestone 2 adds the approval line and the back of the seal, milestone 3 the question screen and milestone 4 a diff view, and each new screen adds a branch to `renderer.ts` that no case reads. A redraw of the inbox while a person tabs through it drops the focus's place; the line J and K select is kept by id and survives it. These smaller costs stand from the first day.

- Which view is open lives in the page, so the reload after the daemon went away returns the person to the inbox or to the summary.
- A headless answer that arrives while the inbox is in front shows nowhere until its work item is opened.
- A terminal made for a view stays in memory, hidden, for the window's life, until issue #9 decides otherwise.
- A work item's view is a sidebar, a terminal and a column of facts side by side, the arrangement the study reads as closest to the products the owner wants to move away from. The terminal is 764 pixels of a window 1440 wide, and narrower in a smaller window, where the sidebar and the right column keep their widths.
- The system's typefaces are macOS's. On another system the same names give other letters, and the screens differ from the mockups there.
- The look is one record for the daemon. Losing focus counts as having looked, so a person who glances at the window and leaves loses the marks of what they did not read, and a phone that sends `looked` later clears the desktop's. The window that is left open and focused all day sends none, and a change in those hours is told by the notification alone.
- A daemon that lost its sessions, because it was started again, shows every work item that had a state as changed, with "No agent is running.", which is what happened.
- The page grows to a sidebar, four screens, two lists that are narrowed together and a preview of commits and files, all drawn again whole at every `inbox`. A list longer than its column scrolls, and a redraw that does not hold the scroll's place by hand loses it, as it loses the focus's place today.
- Two themes double what a person must look at: every screen is read in both, and a rule that reads a colour by its value in place of a property looks right in one theme and wrong in the other. The cases over `themes.css` catch a colour written as a hexadecimal number or with `rgb()`, `rgba()`, `hsl()` or `hsla()` outside it, and a name one block lacks; nothing but an eye catches a colour written another way, or a property used for the wrong role.
- The view's right column is one layout in both themes, so Letter's view is not the letter the owner saw in variant 4: it is the same facts on ruled paper under a serif title, with the seal at the foot.
- Each timed read asks git for every branch's head and its count ahead of the base, two `git rev-list` and one `git rev-parse` per work item, and for a log and a diff where a head moved. With many work items a read takes longer than the 500 milliseconds a hello waits, and that load's `ready` carries the commits of the read before.
- A session's text is whatever the agent's event carried, 2000 characters of it, sent to every client at every change of state and written into the look's file. A last message that quotes a secret is on the disk in `last-look.json`, readable by the user alone.
- The theme is kept on the UI's side, under a sentence this work adds to the policy. A phone that wants the desktop's theme has no way to learn it.
- Every hello waits for one read of the counts per work item, two `git rev-list` and one `git rev-parse`, the hello of the app's check that a daemon runs among them, so the window's first screen comes that much later, by up to the wait of 500 milliseconds. Where git is slower than the wait, the load's summary names no new commit, and the commits show as the lines' counts once the `inbox` arrives.

## Operational impact

No dependency is added. The protocol gains the message `looked` and the field `lastLook` of `ready`, and the daemon writes a second file into its run folder, `last-look.json`, readable by the user alone (`frame/design.md` *Scope* item 18). A hello is answered after the daemon read each work item's new commits from git, or after 500 milliseconds where git takes longer. A session gains three fields and a work item five (`frame/design.md` *Scope* item 23): the time, the text and the tool of a state, and a repository's name, a base branch, how far it is ahead of that base, the newest commits and the changed files. `work-items.json` gains the base branch, and a `last-look.json` an earlier build wrote reads as no look once. A window of this build reads a `ready` without the field as no look, so a daemon left running by an earlier build shows no summary and ignores `looked` as it ignores any message it does not know. The version does not move: `0.0.1` was moved by the first pull request into `release/v0.0.1`.

The window opens 1440 pixels wide and 900 high, where it opened 1100 by 720, with its title bar hidden and its traffic lights inside the sidebar on macOS. It fetches nothing from the network and draws in the system's typefaces. The app writes one more file, `appearance.json` in its user data folder, which holds the theme a person chose.

The app no longer opens a shell in the user's home at start, and no longer offers a pane outside a work item. A daemon left running by an earlier build can still hold such a pane. The new window gives it no tab, and it ends when its process is ended from outside the app.

The tree gains two drawings that are not under the repository's licence, `apps/desktop/assets/seals/owl.svg` and `owl-icon-cream.svg`, and a `TRADEMARKS.md` that says so (`frame/design.md` *Scope* item 15). A person who redistributes the app reads that file beside `LICENSE`.
