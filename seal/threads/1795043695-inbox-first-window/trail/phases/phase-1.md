**Departures from the frame and decisions made while building, each with its grounds.**

- *The window makes no terminal while the view is hidden.* *Scope* item 7 says "a terminal prepared while the view is hidden is fitted when it is shown, and the fit sends `resize`". `@xterm/addon-fit` measures nothing in an element that is not displayed (`frame/design.md` *Grounding*), and a terminal opened there has no cell size until the page lays it out again. `createWorkItem` now sends xterm's default size, 80 columns by 24 rows, without a terminal. When `workItemCreated` arrives, the window opens the view, makes the terminal in the displayed stage, fits it, and sends `resize` with the fitted size. The result is the one item 7 asks for: the process has the size of the pane as shown. The process starts at 80 by 24 and is resized a moment later. Judged against *Scope* item 6, "A terminal is made when its pane is first in front", and item 7's last sentence.
- *One function makes every terminal, and every terminal attaches.* `terminalFor` runs the first time a pane is in front. It sends `resize` and then `attach`, for a pane this window started as well. The window drops the `output` of a pane until that pane's `replay` arrives, because the replay holds everything printed before it. Without that guard a pane this window started would draw its first output twice: the daemon already sends the starter its output. The `pending` map and `adopt` are gone with the prepared terminals.
- *A `start` from a view carries the size of the terminal in front,* or 80 by 24 where the view has none. The pane's own terminal sends its fitted size once it is made.
- *A pane started from a view comes in front when the daemon answers `started`.* The window adds the session to its list at that answer, because the `inbox` that lists it comes after. Where the person returned to the inbox before the answer, the pane is in front the next time that view opens.
- *The pane last in front stays in front while it is a tab, an exited pane included.* *Scope* item 5 says "where it is still a tab". An exited pane the window holds is still a tab.
- *`askButton` has no new case.* `frame/plan.md` *Phases* row 1 asks for scenario 9 "as cases, each seen red before its code". The function lost its branch for a missing work item and gained nothing, so no case can be red against the old code. Its two remaining cases are the old ones, and the two cases of the removed branch went with it (`frame/design.md` *Removes*, last row). `headlessLines` has the new case.
- *`tabLabel` has three cases where it had five.* The two that named a pane without a work item and a work item the window does not hold tested the removed parameter. `notificationFor` keeps its case for a pane without a work item, titled "Claude Code 3".
- *The "Ask" field is emptied when the view of another work item opens, and kept when the same view opens again.* *Scope* item 9 says "when the view of another work item opens". When the daemon answers `asked`, the field is emptied only where it still belongs to the work item that was asked in, so a prompt typed meanwhile for another work item is not lost.
- *A `headless` message redraws the "Ask" section alone.* It arrives once per piece of an answer, and a redraw of the tabs at each would drop the pointer's and the keyboard's place there.
- *The keyboard goes to the line of the work item the person left* when "← Inbox" is pressed, and to the terminal in front when a view opens.
- *`[hidden] { display: none !important; }`.* The two screens are a flex box and a grid, and an author's `display` otherwise wins over the `hidden` attribute.
- *The unsealed emblem is dimmed by opacity and drawn without colour* (`filter: grayscale(1)`), so the red wax does not read as a seal that was given. How dim is phase 2's, with the mockup.
- *`TRADEMARKS.md` follows the shape of the plugin's own file,* and names the one drawing by its path. The README sentence is the same in both editions.
- *The package's whole `tsc --noEmit` ran before the build's commit.* `apps/desktop/tsconfig.json` has no narrower form, and the package is the workspace's only one. The broad run stays the orchestrator's.
