# Implementation Plan: the Korean input regression test runs and passes

## Technical context

The tree was first read at `ed91bb6`, with this work item's `routing.md` alone added, and issue #18's `frame/design.md`, `frame/plan.md` and `trail/phases/phase-2.md` at `edb2a28`, before that work merged. It merged into `release/v0.0.1` on 2026-11-19 as `c128acb`, and this branch, then frame commits alone, was rebased onto that commit. The window was read again at `c128acb`, whose tree the frame commits left as it was outside this work item's directory: `renderer.ts`, `work-item-view.ts`, `view.ts` and `index.html` under `apps/desktop/src/renderer/`, for the way to a pane, the focus, the form and the keys. Probe 4 of `frame/design.md` *Grounding* drove that window. The owner's decision of 2026-11-19 was folded at `bdaf5b0`, where phase 1's case stands committed and its phase open, and probe 5 started the app once under the switch that decision adds. The branch was rebased onto `7159499` after phase 2 closed, and then took `f42ab46` by a merge; every commit of this branch that a record names is the commit that rebase made, as *Judgments of the run* states.

What this work builds on, in `apps/desktop`:

- **The suite runs inside Electron's Node.** `scripts/test-in-electron.mjs` starts vitest with the Electron binary and `ELECTRON_RUN_AS_NODE=1`, because `node-pty` is built for Electron. The same binary starts as the app once that variable is removed, and that Node holds `WebSocket` and `fetch` (`frame/design.md` *Grounding*, probe 3). The case therefore needs no new dependency to start the app and to speak to its debugging port.
- **No case loaded the window before this work.** `test/view.test.ts` reads the window's decisions as pure functions of `src/renderer/view.ts`, and the modules that draw the window had been shown only by drives of the built app from a builder's scratch. Phase 1 committed the first helper that starts the app, `test/built-app.ts`.
- **The app is steered from outside its code, but for one switch.** `--remote-debugging-port` and `--user-data-dir` are Electron's own switches. `src/daemon/pty.ts#loginShell` runs `$SHELL -l` in a shell pane, and `src/daemon/worktrees.ts` reads `OWLERY_WORKTREES`. The case uses these four. Nothing outside the app's code keeps its window from taking the system's focus when the app is started as a child process, so the work adds `OWLERY_BACKGROUND` to `src/main/` (`frame/design.md` *Scope* item 14).
- **A window that never held the system's focus composes.** Under the switch the app was at no reading the front app, its page reported no focus until focus emulation was set, its zero-delay timers took 0 ms, and two lines replayed through the debugging port reached the pane's process as typed (`frame/design.md` *Grounding*, probe 5).
- **The terminal sends composed text from timers.** `@xterm/xterm` 6.0.0 reads its hidden textarea in zero-delay timers after `compositionupdate` and `compositionend`, and a keydown that is no composition key cancels a pending send. A drive faster than those timers loses the text, and one paced by them delivers it (`frame/design.md` *Grounding*, probes 1 and 2).
- **A pane is inside a work item's view, and the app starts none.** The app opens on the inbox screen with no terminal. The "New work item" form creates a work item with one pane of the kind chosen in it, and the window opens the work item's view with that pane in front, focused by `src/renderer/work-item-view.ts#showView`. The form preselects the Claude Code kind, so the case chooses the shell kind. The view's `#pane-buttons` opens further panes, one button per kind, and the case uses none of them.
- **The window's own keys do not reach a pane's typing.** J, K and Enter are read by `KeyboardEvent.code` only while the summary, the inbox or the history screen is in front and the focus is in no field, and K and N with the Command key on every screen. The lines press J, K and Enter in a pane, and what guards them is the bytes of scenario 1.
- **The run folder's length constrains nothing.** Issue #19's fix is in the tree at `d2df840`. The case's user data folder sits under the system's temporary folder so that the case owns and removes it.

**The failure scenario of the chosen approach.** The case drives a real window at every broad gate and depends on a pace. On a loaded machine a timer of the page can run late against a step, a line arrives short, and the gate fails for no change in the tree. A case that fails that way more than once gets retried without being read, and then it guards nothing. These costs stand beside it.

- The recorded steps age. A new macOS or a new Electron can change what an input source produces, and the case keeps passing on the old record. Only the typed run at the next release shows it, and nothing forces a person to make that run.
- `Input.imeSetComposition` is marked experimental in the debugging protocol. An Electron upgrade that renames it fails the case in that upgrade's pull request, where it is seen and fixed.
- The debugging port sends one call at a time, so what an input source does inside one keydown reaches the page as separate tasks. A sequence that depends on that cannot be replayed, and the fixture then names its line under `replayDiffers`.
- The receiver is chosen through `SHELL`. A daemon that stops reading `SHELL` for a shell pane breaks the case, and the case has to find another way in.
- The case reaches its pane through the form's element ids and the kind `shell`. A change of the form, of its ids or of the kinds the daemon offers fails the case at its first step, in that change's pull request, and the change then rewrites that step.
- The gate opens the app's window over the person's windows for the length of the case. Under the switch it takes neither the keyboard nor a place in the Dock. A person who clicks it gives it the keyboard, and a key typed then reaches the pane and fails the case.
- The switch is code of the shipped app that only a test and an agent use. A person who sets `OWLERY_BACKGROUND=1` gets an app with no Dock icon and no menu bar, whose window they have to click.
- The case no longer reads a window that holds the system's focus, which is the window a person types in. Only the typed run reads that one.
- Whether a change of the front app, or a second gate's app, ends a composition in a window that never held the focus was not measured (`frame/questions.md` Q2). Where it does, the case fails on a line and its failing line says that a composition was ended from outside.
- Until the owner's first typed run, every line's steps are the order this frame assumed, and the case shows only that the pane handles that order.

## Operational impact

No dependency is added. The app reads one new variable of its environment, `OWLERY_BACKGROUND`: with the value `1` it starts with no Dock icon and a window that does not take the keyboard, and without it the app starts as before. `apps/desktop/package.json` gains one script, `korean:typed`. The version does not move: `0.0.1` was moved by the first pull request into `release/v0.0.1`.

`pnpm run test`, and so the broad gate, now builds the app and opens its window for the length of the case, on a machine with a display. The window opens over the person's windows and takes neither the keyboard nor a place in the Dock. It starts a daemon of its own in a folder under the system's temporary folder and stops it.

A release gains one step for a person: `pnpm --filter @owlery/desktop run korean:typed`, typed with a Korean input source, whose change of `apps/desktop/test/fixtures/korean-input.json` is committed with the release.
